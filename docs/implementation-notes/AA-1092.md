# AA-1092 — pre-PII review of the public CRM routes added since the AA-969 review (AA-Partner part)

S278 system audit M24. Scope: every `/crm/public/v1` route added or changed after the AA-969 review (root
`docs/audits/2026-11-04-S268-crm-security-review/`, 04/11/2026): Book now (AA-1072), the VNPay IPN and the stub gateway
(AA-1072), the sales partner pages (AA-1071: intake link, partner view, sign-in code, session), the traveller travel
routes (AA-1070: travel, rooming, visa checklist) and the client page's "Pay online" (AA-1072). Method: read each route,
its service function, its tenancy context and its tests, against the AA-969 checklist (rate limits, input validation,
signature and replay, errors, enumeration). Other parts of AA-1092: AA-TripPlanner-Web, AA-Booking, AA-CIS-Infra.

## Threat note

- **Assets:** the agency's clients (name, e-mail, phone typed into Book now and the partner intake), the client link a
  booking mails, money records (payments recorded from the gateway's notice), the partner's commission view.
- **Threats:** a forged or replayed gateway notice marks an invoice paid; a flood of forged notices keeps the webhook
  slot busy for every agency; many addresses together make an agency create clients and mail links without bound;
  an anonymous caller guesses links, codes or references; an error answer tells a caller something about a client.
- **Controls checked or added:** see the table. **Residual items** are tracked in Linear AA-1092 (not in this public
  repo).

## Decisions

- **Per (address, reference) for forged signatures** (R5): not per address alone, the same reasoning as the AA-969
  round-3 Twilio fix (shared sender addresses); and not per reference alone (review round 2): a forger who knows a
  live reference and repeats the flood every minute would lock it for every address, VNPay included, and the payment
  would never be marked paid. Keyed on both, a forger locks only their own address for that reference; the bound on
  database and secret work per known reference holds per address, like the misses. Test
  `test_a_forger_cannot_lock_a_reference_for_another_address` and `test_the_genuine_notice_is_confirmed_after_a_forged_flood`.
  Rejected alternative: caching the agency secret per reference (as `HookCache` does for Twilio) would refuse forged
  notices in memory with no lockout at all, but it keeps a payment secret in process memory per open session; the
  pair key gives the same safety for the genuine notice with no secret cached.
- **Unsigned = not VNPay** (R4): counting those per address cannot hurt VNPay's shared addresses, because VNPay signs
  every notice. `fullmatch` on the hash (a trailing newline does not pass).
- **Book now gets its own bucket** (R8) in the existing per-form limiter, so bookings never use up the inquiry form's
  quota and the other way round.

### Decisions

- **The ceiling is the agency's setting, not an environment variable** (tech lead rule S278: policy values are data
  with a page to change them). `tenant_settings.public_price_per_minute` (crm-066), default 60, bounds 10..600 in the
  column CHECK and in the API (422 `invalid_price_checks_per_minute` before the CHECK). The owner changes it on
  Settings > Payments "Online booking" (the existing `PAYMENT_SETTINGS` action, owner only, audited by field). The
  bounds keep an owner from switching the guard off (no 0) or setting it past what Booking should take from one agency.
- **Per task, in memory.** The CRM API has no shared limiter store (every limiter is `FixedWindowLimiter`, one small
  task on Dev). With N tasks an agency gets up to N x its value; the default 60 (three addresses at their own ceiling of
  20) is sized for one or two tasks. A shared store (Redis or the database) is a follow-up only if the API runs many
  tasks.
- **Charged after the agency is read, before Booking.** The ceiling is read in the same `intake_tx` query that already
  reads the Book now switch (`SETTINGS_SQL`), so the check costs no extra query; nothing goes to Booking past it. The
  key is `price:<tenant id>` in its own limiter (`booking_agency_price_limiter`), the limit per call
  (`FixedWindowLimiter.allow(key, limit)`).
- **One form = one bucket** keyed on the form id, not the public key: the partner path knows only the form id (it
  reaches the form through the link), and a public key can change without the form changing. Book now keeps its own
  bucket `book:<key>` (bookings never use up the inquiry form's quota, R8).
