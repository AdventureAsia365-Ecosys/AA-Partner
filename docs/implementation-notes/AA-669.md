# AA-669 — My Content as a DataTable (portal)

`/portal/content` (My Content, was `/portal/t10-review`) already used the kit DataTable for title, channel, goal,
status and created (CIS #556). This change builds the rest of the issue: place / topic, angle, words, published at,
the actions column, the published status, the date-range and place filters, the two named views and the bulk rules.
Session S251, agent Claude Code. CIS side: AA-CIS-App branch `feat/aa-669-content-list-params` (the piece's live post
on `GET /v1/content-writing/reviews`).

## Decisions

- **Rules in `portal/lib/myContent.ts`** (no React, no imports), tested with `node --test` (`lib/myContent.test.ts`,
  the AA-761 pattern). `ReviewList.tsx` only wires them to the kit.
- **Status** = `published` (the request has a live post: `published_at` from CIS, read over every piece of the
  request) > `ready` > `writing` > `not ready`.
  "Writing" stays a status of its own (the list already polls while a piece is being written); the issue's three
  are the settled ones. A held piece reads `ready` (AA-614: the tenant never sees why its publish is refused).
- **Title** = the piece's own first markdown heading (blog, landing page), else the angle's name. **Angle** = the
  angle's name with its formula (`formula_fit`) under it. For a social post both read the angle's name: the post has
  no headline of its own.
- **Place / topic** = the tour ("name · country"), else the route hub ("Hanoi route · 3 stops"), else the moment's
  activity type. The place filter searches the same text.
- **Words** count the written text without markdown marks or links; null (—) while there is no text.
- **Date range** applies to Created or Published (a select next to the two dates). A range on Published leaves out
  what is not published.
- **Views**: built-in "All content", "Ready to publish" (status ready, newest first) and "Published this month"
  (status published, published from the 1st of the current month, newest published first); the tenant saves its own
  (filters + sort) with the save button. Stored with the kit's `savedViews` store (localStorage, key per tenant name,
  table id `my-content-views`) and sanitized when read back. The kit DataTable's own Views menu is off: it stores only
  the table's internal state, not these page filters, and two Views menus would confuse. `?view=ready-to-publish` /
  `?view=published-this-month` open a view (for links from the dashboard or a notification later).
- **Actions** (icon buttons, each stops the row click): View (the drawer), Export (blog: HTML page, HTML fragment,
  plain text; other channels: plain text), Publish (blog with WordPress connected, Facebook with the Page connected;
  disabled with the reason as its tooltip otherwise, hidden once published), Write again (disabled with its reason
  while writing, when the tour is closed, and on a published row).
- **Duplicate / regenerate = "Write again"**: `POST /v1/content-writing/requests/{request_id}/write` with no CTA (the
  request's or the brand's is used, as for the first write). The new piece becomes the request's latest, so it
  replaces the row (Writing, then Ready); the old piece stays in history. A copy as a
  second, separate request would need a new CIS endpoint (a request clone) and doubles rows for the same angle; the
  issue's goal (another take on the same piece) is met by writing again. Confirm dialog first (it runs a paid write).
- **No Write again on a published row (independent review, S251).** The first version allowed it. CIS read the
  live post of the latest piece only, so after a rewrite the row turned Ready, lost its post link, left "Published
  this month" and offered Publish again: a second live WordPress / Facebook post for the same request, with the old
  post no longer visible from My Content. Fixed on both sides: `regenerateBlock()` refuses a published row with the
  tooltip "Unpublish the live post first to write a new version" (the tenant unpublishes from Publish > Published),
  and CIS now reads the request's live post over all of its pieces and returns `published_piece_id`, so a rewrite
  made anyway (before this rule, or through the API) keeps the row Published: Publish, bulk publish and Write again
  stay refused, and the post link's tooltip says the live post shows an earlier version (`liveIsEarlierVersion()`).
  The CIS publish endpoint itself still allows new text as a new post (AA-726 design); "one live post per request"
  in the API is an open choice for a later issue (CIS notes).
- **Bulk**: Export selected = each piece in its row format (blog HTML page, others text). Publish selected = blog
  pieces that are ready and not published, only with WordPress connected (the issue's rule); a confirm dialog says how
  many go out and how many are left out. Single-row publish also asks first (it posts publicly).

## Changed (vs. the issue)

- "duplicate / regenerate" is one action, Write again (above).
- Status has a fourth value, Writing (in-flight write), next to ready / published / not ready.

## Tradeoffs

- Client-side filtering, sorting and paging over the one reviews call (no server params): one row per request is
  small per tenant, the payload already carries everything the columns need, and every other portal table works the
  same way. The CIS notes (AA-CIS-App `docs/implementation-notes/AA-669.md`) say when to revisit.
- Saved views live in the browser (the kit store), not on the server: no new CIS table for a convenience.
