# AA-952 — CRM-23 slice 1: AA lines from the accepted hold set + confirm after the deposit (C-M3 "confirmed")

Card: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 CRM-23 (Module 7, deps 18, 21b, B2b) and
milestone W4 = M3 "AA products quoted, held, **confirmed** from the interactive proposal". Gap from the S258 live proof
(root `.tmp-session/S258/crm-proofs/RUNBOOK.md` §2): no shipped code turned an accepted proposal's hold set into AA lines
or a Booking confirm; `crm.proposal.accepted_hold_id` was written and never read (AA-950 notes, "Not built"). The rest of
CRM-23 (Stripe, schedules, reminders, refunds, bank-transfer `payment_claimed` + extend) is later slices.

Sources read: CONTEXT.md; AA-946 / AA-947 / AA-949 / AA-950 notes; `app/proposals/{public,holds,client_page,builder,
service}.py`, `app/booking/{aa_lines,sync,client,contract,views}.py`, crm-014 (the AA line guard), crm-017
(`crm.aa_request`, `crm.booking_line_aa_money`), crm-021; AA-Booking `app/b2b/holds.py` (`confirm_hold` idempotent on
the hold, one booking for the whole set) and `app/routers/b2b.py`; schema reference (verified 2026-10-30, crm-023);
schema-ownership; lessons (CRM, Booking CI). Session S259, agent Claude Code.

Branches: AA-Partner `feat/aa952-confirm-after-deposit`, AA-Booking `feat/aa952-hold-confirm` (contract 1.2).

## Decisions

- **The lines are written by the Booking sync job, not by accept.** Accept runs in the client link's context
  (`client_link:<id>`), and crm-014 lets only a `job:` / `platform:` actor write an AA line (CRM24), and
  `crm.booking_line_aa_money` only a `job:` actor. Accept and a paid deposit only **nudge** `crm_booking_sync` (one job
  row per event, ids only); the minute run would pick them up anyway (pull, idempotent: a proposal with any line of its
  options is never written again; a set with any confirm request is never confirmed again by itself).
- **Line id = option id.** The proposal hold's Booking `line_ref` is the option id (AA-950 `holds._lines`), and the
  existing sync matches Booking's answers (confirm per `line_ref`, feed events by `line_ref` or hold id) to
  `booking_line_id`. Writing the AA line with the option's UUID as its id makes every existing path work without a
  mapping column, so **no crm migration**.
- **Net from Booking via contract 1.2, no crm migration.** The CRM never stored the held quote's per-line prices or its
  `price_hash` (the confirm presents it; `hold_pending_price_hash` is cleared once Booking answers). AA-Booking now
  answers every `Hold` with the quote it holds (`price_hash`, `currency`, `fx`, `lines[].b2b_price`; additive minor
  1.2, Booking `feat/aa952-hold-confirm`). The line's cost = that `b2b_price` with the quote's FX lock; the sell = the
  option's `sell_amount` (the agency's price, set by owner / agent under the builder's rules). A 1.1 answer is a
  `ContractError`: nothing written, retried next run.
- **One confirm per set, fanned out.** Booking's confirm books the whole hold. One `confirm` request on the set's first
  line (lowest id); `apply` writes the answer on every line sharing the hold in the trip (`SET_LINES_SQL`). The same
  fan-out for a refused confirm and for a release (a release lets the whole set go: a Lost before the deposit releases
  every line, not just one).
- **"Deposit paid" = the accepted proposal's deposit schedule row `paid`** and the trip at booked / pre-departure /
  travelling (`CONFIRM_DUE_SQL`), not the stage alone (a stage can be moved by hand). Only lines of an accepted
  proposal set are auto-confirmed; a hand-asked AA line (AA-947) keeps its Confirm button.
- **Not confirmed when the hold is no longer live** (`hold_expires_at > now()` in the due query; Booking's 410 when it
  ran out meanwhile). Lines Booking reports expired / released at write time read `expired` (`hold_expired` /
  `hold_released`) + urgent task `aa_hold_expired`; the line's actions offer `requote` (the agency's way on). Booking's
  own `hold.expired` event already moves held lines to `expired` (AA-947 feed).
- **A refused confirm reads `failed` with Booking's code** (or `expired` / `sold_out` / `not_served` by the existing
  `REFUSED_SUB`), opens urgent task `aa_confirm_failed` and is not re-sent by itself (the agent decides: re-quote).
  This also applies to an AA-947 hand-asked confirm: before, an unmapped refusal left the line `held` with the code,
  offering Confirm again with the same refused hash.
- **Unknown hold at Booking** (`GET /holds/{id}` 404): lines `failed` (`hold_not_found`) + task `aa_lines_failed`;
  other refusals (`unknown_partner`, `forbidden`) and outages are retried next run (an outage stops the run's Booking
  calls, as for requests).

- **Review fixes (S259, verdict ship-with-fixes).** (1) The confirm fan-out loop in `apply` reused the name
  `status`, which holds the request's own status: a set confirm left its `crm.aa_request` `pending` (leased), so the
  sync re-sent the confirm every lease (120 s); with an `on_request` answer it never ended. Renamed to `line_status`.
  (2) `proposal_sets` now isolates each proposal: an error while writing one proposal's lines (missing FX rate CRM25,
  a CHECK, a builder KeyError) is counted `proposal_lines_error`, logged with tenant id + error class only, and the run
  goes on; the same around `queue_confirms` (`confirms_error`). `Forbidden` / `NotFound` (agency locked / gone) still
  propagate so the run counts the agency `skipped` as before.

## Tradeoffs

- **Contract change vs crm migration.** Storing the held quote (hash, per-line prices, FX) on `crm.proposal` would have
  needed crm-024 (+ Infra copy, DB Migrate, ordering) and still left holds made before it without data. Reading it from
  Booking keeps Booking the owner of prices (ADR 0005) and needs only an additive Booking change; cost: Booking must be
  deployed first.
- **Option id as line id** instead of a `proposal_option_id` column: no migration and no mapping code; the one rule to
  know is that an accepted option and its AA line share a UUID (both are random v4: no clash in practice; the insert is
  `ON CONFLICT DO NOTHING`).
- **Pull in the minute sync + nudge** instead of a new job kind: no kinds / gate / DB Migrate idle list change, and a
  deposit taken before the lines exist still confirms on the next run.
- **Fan-out writes on every set line**, so a manual Confirm on any line of the set also books the set once (Booking is
  idempotent on the hold); a release of one line of a set releases all of them (Booking cannot release part of a hold).

- **A proposal whose lines keep failing to write** is retried every minute (it stays in `DUE_SQL`) and logged
  `crm_proposal_lines_failed` each time, rather than blocking its agency. No task is opened for it: the transaction
  that would write one is the one that failed. Watch the log / `proposal_lines_error_count` in the job result.

## Should know

  quote); (2) root contract `docs/contracts/booking.b2b.v1.openapi.yaml` to 1.2 (patch prepared at root

- An accepted proposal whose trip is Lost before the first sync run gets no lines; its hold runs out at Booking (48 h).

- A hand-pressed "hold" on an `expired` set line uses the set's old quote under `crm-line:<id>`; Booking refuses it and
  the line reads the code; "requote" is the path (as the task text says). Not changed here.

# AA-952 — CRM-23 slices 2 and 3: agency invoices, payments against them, refunds, the agency's own payment methods

Session S260 (Claude Code, lane L4). Sources read: Linear AA-952 (card + S259 comment); design v3 §2.7–§2.9, §3.3
group F, §3.5 (C31, delete block), §3.6 (retention), §4.6 (matrix); `lanes/data-privacy-integrations.md` §2.7
(invoice / payment / refund_request / payment_provider_account columns), §3.4 (cancel), §3.5 (C31), §6.3 (Stripe
Connect Standard); design ERD `docs/architecture/erd/design/crm.md`; CONTEXT.md (CRM-18, F4, lifecycle); crm-010,
crm-016, crm-023; `app/proposals/service.py`, `app/permissions.py`, `app/ledger/fx.py`; lessons (migrations, RLS,
Partner CI). Schema reference verified 2026-10-30 06:24 UTC (crm-023).

Branches (AA-Partner): `feat/crm-invoices-payments-schema` (crm-024 only, MIG-4), `feat/crm-invoices` (slice 2 code),
`feat/crm-payments` (slice 3 code).

## Decisions

- **One migration for both slices (crm-024), shipped alone first.** It is contract class (constraints on
  `crm.payment` / `crm.tenant_settings`, `crm.status_transition` rows, a replaced `crm.erase_subject`), so MIG-4:
  migration-only PR → Infra copy → manual DB Migrate apply → code PRs. One apply instead of two; slice 3's schema is
  small and was designed with slice 2's.
- **Invoices sit on top of the existing schedule rows, they do not replace them.** A deposit / balance invoice names
  one `crm.payment_schedule` row of the accepted proposal and bills exactly its amount, currency and due date. The
  schedule stays the source of the computable gates (deposit paid → booked, portal unlock, Booking confirm); an
  invoice paid in full marks its schedule row paid through the same side effects as the CRM-18 "Mark paid".
  Service-fee and adjustment invoices have no schedule row.
- **Schedule invoices are always tax-inclusive** (DB CHECK): they bill what the client accepted; the tax is shown
  inside the total. Service-fee / adjustment invoices follow the agency's setting (inclusive by default).
- **Numbering:** `<prefix>-<6+ digits>`, a per-agency gapless counter (`crm.invoice_sequence`, +1 under the row lock
  inside the issuing transaction; CRM40 refuses any other move). The number is given at issue, never to a draft; a
  void invoice keeps its number. The prefix applies to invoices issued after a change.
- **No traveller column on an invoice.** The bill-to is the trip's lead, read through the vault when the document is
  rendered. So no name is copied into an accounting record, `crm.erase_held` needs no change, and the traveller erase
  is untouched. Trade-off below.
- **"Included" lines** list what the invoice covers (the trip's live agency and AA booking lines: a title snapshot,
  no amount). Design §2.9 rule 3 never shows per-line prices or the B2B price to a client, and the margin serializer
  has nothing to strip: invoice responses carry sell amounts only.
- **Payments:** `crm.payment` (append-only, crm-016) gains `invoice_id`, `provider`, `provider_ref`, `entry_kind`
  (payment / refund) and `refund_of`. Partial payments are allowed against an invoice; the crm-016 rule "one payment
  per schedule row" stays for payments without an invoice (partial unique index). The balance is derived (payments −
  refunds), never stored.
- **Refunds** only from an approved `crm.refund_request` (design §6.3): proposed (owner / agent) → approved / rejected
  (`REFUND_APPROVE`: owner any amount, agent up to `refund_owner_threshold_base`, judged on the amount converted to the
  base currency with the FX resolution the ledger uses; no rate = fail closed, only the owner) → executed (the refund
  entry in `crm.payment`).
- **BYO provider abstraction:** `crm.payment_provider_account` + `app/payments/providers.py`. `manual` is the only
  provider with code: its instructions (the agency's own bank details, its office for cash) print on its invoices,
  and members record what arrived. `stripe` / `vn_gateway` are reserved values; asking for them is 409
  `provider_not_available`. The agency is always the merchant: no Adventure Asia account holds or moves client money.
- **Permissions (no new matrix rows):** view = `TRIP_VIEW` (every role; sell amounts only); create / issue / void an
  invoice, record a payment, request and execute a refund = `PAYMENT_MARK_RECEIVED` (owner, agent); approve / reject =
  `REFUND_APPROVE`; invoice settings and payment methods = `PAYMENT_SETTINGS` (owner).
- **SQLSTATEs:** CRM39 (invoice_issued / invoice_empty / invoice_totals), CRM40 (sequence_step); next CRM41.

## Changed (vs the card)

- Stripe Connect Standard, schedules / reminders, idempotent webhooks, the bank-transfer `payment_claimed` → one
  extend → verify task, `paid_unfulfillable`, pay-on-arrival, the client-side pay page: **not in these slices** (the
  lane scope is invoices + payments with a manual provider; Stripe needs Nghiệp's test-mode platform account, B4 a).
  The statuses and columns they need exist in crm-024 so that card adds code, not schema.

## Tradeoffs

- Bill-to read at render time: an invoice re-rendered after the lead's name changed shows the new name. The
  alternative (a vault-encrypted name snapshot) needs a traveller column, an erase step and a hold-rule change; left
  for when an agency asks for a frozen bill-to.
- An open (issued, unpaid) invoice does not block a trip delete (design §3.5: paid / claimed only), so a purged trip
  takes its issued invoices and leaves a gap in the numbers. The trip delete already needs the owner / own-trip rule
  and the trash window.
- Payments carry no frozen FX block yet (design R17 "amounts received convert at the receipt date"): receivables are
  in the invoice currency; base-currency reporting is the reports card.

## Should know

- The refund-entry ↔ request link (`refund_request.refund_payment_id`) is written by the API in one transaction; the
  database does not refuse a stray refund entry (append-only table, no back reference). The schema test shows it.
- `crm.payment.schedule_id` is nullable now: code that reads payments by schedule (`trip_overview`) keeps working.

## Slice 2 (invoices) — what shipped

- API: `app/invoices/service.py` (drafts from a schedule row or typed lines, edit, issue, void, the trip list, A-10
  receivables, settings, the document), `app/invoices/render.py` (escaped HTML with a CSP `<meta>`),
  `app/routers/invoices.py`; readiness needs crm-024 (`app/db.py`).
- The document is a JSON envelope (`{html, filename}`), not `text/html`: the BFF forwards JSON only, and the web
  opens the HTML in a new tab from a Blob (print or save as PDF). The CSP `<meta>` blocks script in that tab.
- A schedule invoice's charge line reads "Deposit (proposal version N)" / "Balance (…)", never the trip title (a title
  can name the client).
- Web: the trip's Invoices card (under the Proposal tab), A-10 `/payments` (receivables; it replaces the empty state of
  that section), Settings > Payments "Invoices". The kit form controls (`Field`, `Input`, `Select`, `Textarea`,
  `Checkbox`, `Radio`) were not in the CRM barrel; `app/_kit/index.ts` exports `./core/FormControls` now so the new
  forms pass `aa-kit/no-raw-form-control` without new suppressions (the core file itself is unchanged).
- Rows on `/payments` are a CSS grid, not a `<table>` (`aa-kit/no-raw-table`; the kit `DataTable` needs client column
  functions, and this page is a server component).

## Slice 3 (payments, refunds, payment methods) — what shipped

- API: `app/payments/service.py` (record a payment, refund requests: request / approve / reject / execute, the A-10
  list, payment methods), `app/payments/providers.py` (the BYO provider interface, `manual` only),
  `app/routers/payments.py`. `app/invoices/service.py` views now carry the payments, refund requests and the
  paid / refunded / balance amounts; the document prints them and the agency's pay-by instructions (unpaid invoices
  only).
- `app.proposals.service.mark_paid` is split: `settle_schedule` holds the CRM-18 effects (row paid, Booked, portal,
  Booking confirm) and runs for a "Mark paid" or for the last payment of a schedule invoice. "Mark paid" is refused
  (409 `invoice_issued_for_row`) while an issued invoice bills the row, so one row is never paid twice by two paths.
- Decision: a rejection is held to the same §4.6 rule as an approval (an agent cannot reject a refund above the
  threshold either): both are the decision the matrix gives the owner.
- Decision: the threshold is judged on the refund converted to the base currency at today's rate
  (`fx.resolve`); with no rate the agent's check fails closed and the owner decides. The decision stores
  `base_currency` / `base_amount` with it.
- Decision: no refund task / bell yet: A-10 Payments lists the requests to act on (`GET /refund-requests`, default
  proposed + approved). Reminders and the bell are the reminders card.
- Not built (later cards): Stripe Connect (needs the agency's own test-mode account, B4 a), webhooks,
  `payment_claimed` -> Booking hold extend -> verify task (C31, Fix A8), card-race `paid_unfulfillable`, the client's
  C-10 payments page, reminders, FX block on payments.

## Review fixes (S260) — slice 3

- Void after a full refund: `invoices.void` refuses only while the invoice holds money (payments - refund entries > 0,
  409 `invoice_has_payments`) or a refund request is still proposed / approved (409 `refund_pending`; defensive: with
  the API's own refunds, nothing held already means no open request). `actions()` takes that net amount, so the Void
  button comes back once every payment was refunded. A voided invoice frees its schedule row (a new invoice, or Mark
  paid). Before: one payment, even refunded, kept the invoice open for good (listed, overdue, blocking the row).
- One row, one path: `proposals.void` (the balance row) refuses while an issued invoice (open / payment_claimed /
  expired) bills the row (409 `invoice_issued_for_row`) and voids a draft one with the row (reason "The schedule row
  it billed was voided", audit `invoice_void` reason `schedule_void`; the response lists `invoices_voided`). Decision:
  auto-void the draft rather than refuse: a draft bills nothing yet and could never be issued against a void row.
  `record_payment` on a schedule invoice locks the row and refuses when it is not due (409 `schedule_not_due`) instead
  of recording money and skipping the settlement.
- Lock order: invoice rows before the schedule row everywhere (`issue`, `record_payment`, and now `proposals.void`,
  which locks the row's live invoices first and reads them again under the schedule lock to catch one raised
  meanwhile). `mark_paid` locks only the schedule row and reads the invoice without a lock.
- §4.6 approval matrix: an agent's approval is judged on the refunds already approved / executed on the same invoice
  (their stored `base_amount`) plus this one (a split 900 + 900 reaches the owner at a 1,000 threshold). An approved
  refund without a base amount in today's base currency makes the total unknown: the owner decides. A rejection moves
  no money and is still judged on the request alone. `decide_refund` takes the invoice row lock (two agents deciding
  two requests at once see each other's approval). An agent never approves a request they asked for (403
  `refund_self_approval`, audited as a denied `refund_approve`); they may reject it (a withdrawal); the owner may
  approve their own (the top of the matrix; a one-owner agency must be able to refund).
- Tradeoff: the running total is per invoice, not per trip: two invoices refunded by the same agent in parts can still
  each sit under the threshold. With the self-approval rule a second member is involved every time.
- Web: refusal copy for `refund_self_approval` / `refund_pending`; `invoice_issued_for_row` now also says "or void the
  invoice first" (the row's void returns it too). The Approve button is still shown to the requester (the web has no
  member id on the refund view); the API refuses with the copy above.

# AA-952 — CRM-23 slice 4: "I have paid" claim, one hold extension, re-hold after a late payment, reminders

Session S261 (Claude Code, lane l1-crm-invoices). Sources read: Linear AA-952 (card + S259 / S260 comments); design v3
§3.3 group F (`invoice.claimed_at`, `hold_extended_at`), §3.5 "Deposit link (C31, Fix A3, Fix A8)", F6 step 5, WF-9,
card CRM-23 (R / E); errata S247 (BYO: the agency is the merchant); triage S260 §4 lane 2 item 5; contract
booking.b2b.v1 `POST /holds/{id}/extend` (`ExtendRequest.reason` payment_claimed | client_recheck) and AA-Booking
`app/b2b/holds.py` (extend once, +72 h capped by the departure; a hold's quote is honoured only within its
`valid_until`; re-hold limit 3 a UTC day); crm-024 (invoice statuses and `crm.status_transition` rows); ADR 0017 (expand
lint and runtime classes); lessons (migrations, RLS, Partner CI). Schema reference verified 2026-10-30 15:16 UTC
(crm-027): `invoice.status` already allows `payment_claimed`, `paid_unfulfillable`, `expired`; `claimed_at` and
`hold_extended_at` were missing.

Branch (AA-Partner): `feat/aa-952-invoice-claims-holds` (one PR: crm-028 expand + code + web).

## Decisions

- **crm-028 is expand, in its own first commit of the same PR** (ADR 0017 d1): nine nullable / defaulted columns on
  `crm.invoice` only (`claimed_at`, `hold_extended_at`, `hold_extend_code`, `rehold_requested_at`, `rehold_quote_id`,
  `rehold_price_hash`, `rehold_code`, `last_reminded_at`, `reminder_count`). No CHECK on them (a CHECK on an existing
  table is contract): the code keeps the value lists. Infra `run_migration.py --inspect` (main 6d7470e): expand, no
  errors.
- **No new `crm.status_transition` row** (an INSERT into an existing table is contract). Every move this slice makes is
  already allowed by crm-024: open -> payment_claimed (claim), payment_claimed -> open (the agent: "not received"),
  open / payment_claimed -> paid, open / payment_claimed -> paid_unfulfillable.
- **The invoice status `expired` stays unused; the pay window is derived.** A deposit invoice of an accepted builder
  version with an AA hold can be paid by transfer while that hold lives (`crm.proposal.hold_expires_at`, moved by the
  extension and the re-hold). Persisting `expired` would need expired -> paid / paid_unfulfillable transitions
  (contract) for the money that still arrives after it. The client page and the agency views read
  `pay_window = {state, until}`.
- **The pay link is the client's own proposal link** (C-04 "Accept and deposit"), not a new link purpose: a new
  `client_link.purpose` would widen a CHECK (contract) and give the client a second link to keep. The accepted page
  carries `payments` (issued deposit / balance invoices of that version only: never another version's, never a
  service fee or adjustment of the trip). Bank details only while the window is open.
- **One extension per invoice, asked by the claim.** Idempotency-Key `crm-invoice:<id>:extend` (a retry of a lost
  answer gets the extended hold back); `hold_extended_at` set once; a later claim (after "Not received") never asks
  again. Booking's refusal code is kept in `hold_extend_code`; `booking_unavailable` is retried by the Booking sync
  (`claims.extend_due`, while the hold lives), so a Booking outage during the client's click is not lost.
- **The claim is committed before Booking is asked** (two transactions, the AA-947 rule): the verify task exists even
  if the extension never answers; its due time moves to the new expiry when it does.
- **Re-hold rule (card E):** in the Booking sync, not in the member's request: AA lines are written by a job actor only
  (crm-014 CRM24), and the decision paid vs paid_unfulfillable must be taken once, from Booking's answer (crm-024 has
  no paid -> paid_unfulfillable). So `record_payment` leaves the invoice open / claimed with `rehold_requested_at` and
  the sync decides within the minute (nudged). Order: `GET /holds/{current}` (still active -> `hold_live`, the CRM's
  expiry was stale) -> one quote of the accepted AA choice (`holds._lines`, the same body the client's hold sent) ->
  the quote written on the invoice -> `POST /holds` with `crm-invoice:<id>:rehold`. Accepted only when no line is sold
  out and the new net total is **not above** the expired hold's (`price_higher` otherwise): the agency's cost never
  rises behind its back; the agent decides (reject the refund request and re-quote, or refund).
- **Not re-held -> one refund request per payment** for what is left to ask back, proposed by `job:crm_booking_sync`
  (so an agent may approve it within the threshold: the self-approval rule names members only), urgent task
  `payment_unfulfillable`, bell. The schedule row stays due, the trip does not move to Booked.
- **`rehold_limit`** (Booking's 3 re-holds a UTC day): the invoice waits for the next UTC day (`rehold.due` takes the
  sync's `now`), at most 26 h after the money, then ends as `rehold_limit`.
- **Confirm after a re-hold:** `CONFIRM_DUE_SQL` takes the proposal's current hold (`p.hold_id`) as well as the
  accepted one, and a hold is live by the line's expiry or the proposal's (the extension moves the proposal's at once,
  the lines' with the feed's `hold.extended` refresh). A late `hold.expired` of a hold the line left only writes that
  hold's commitment.
- **Reminders = agent first** (U8, E3 `reminders_mode='agent_first'`): bell + one open `invoice_overdue` task, never a
  message to the client. Cadence: the day after the due date, then every 3 days, at most 5. Run in the hourly
  `crm_stage_date_rule` (no new job kind: no gate / DB Migrate idle list change).
- **Card button** exists only as the guard the card asks for ("pay link after hold expiry -> expired page, no
  session"): 410 before any provider; otherwise 409 `card_not_offered` / `provider_not_available`. The Stripe session
  is the follow-up card.
- **Deposit invoice due date = the schedule row's date** (slice 2 behaviour, confirmed in
  `test_claim_without_a_hold_verify_task_not_received_and_void`: `due_on = max(row due, issue day)`).

## Tradeoffs (slice 4)

- **Derived window vs the `expired` status:** the agency's receivables filter cannot ask for `expired` invoices; the
  row shows the note "AA places released" instead. Writing the status would need a contract key (transitions).
- **No CHECK on the new columns** (expand only). The codes are closed lists in code; a later contract key can pin them.
- **Re-hold price rule is strict** (`price_higher` even by a cent): the safe default; the agent can re-quote by hand.
- **A paid_unfulfillable deposit keeps its schedule row's one live invoice** (it is never void), so that row takes no
  new invoice: the agency re-quotes on a new version (new rows).
- **Extension retries ride the minute sync** (no backoff of their own); one call per claimed invoice per run while
  Booking is down stops the run like any outage.
