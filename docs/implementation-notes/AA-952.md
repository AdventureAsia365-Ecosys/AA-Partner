## Decisions

- **The lines are written by the Booking sync job, not by accept.** Accept runs in the client link's context
  (`client_link:<id>`), and crm-014 lets only a `job:` / `platform:` actor write an AA line (CRM24), and
  `crm.booking_line_aa_money` only a `job:` actor. Accept and a paid deposit only **nudge** `crm_booking_sync` (one job
  row per event, ids only); the minute run would pick them up anyway (pull, idempotent: a proposal with any line of its
  options is never written again; a set with any confirm request is never confirmed again by itself).
- **Line id = option id.** The proposal hold's Booking `line_ref` is the option id (AA-950 `holds._lines`), and the
  existing sync matches Booking's answers (confirm per `line_ref`, feed events by `line_ref` or hold id) to
  `booking_line_id`. Writing the AA line with the option's UUID as its id makes every existing path work without a
  mapping column, so **no crm migration**.
- **Net from Booking via contract 1.2, no crm migration.** The CRM never stored the held quote's per-line prices or its
  `price_hash` (the confirm presents it; `hold_pending_price_hash` is cleared once Booking answers). AA-Booking now
  answers every `Hold` with the quote it holds (`price_hash`, `currency`, `fx`, `lines[].b2b_price`; additive minor
  1.2, Booking `feat/aa952-hold-confirm`). The line's cost = that `b2b_price` with the quote's FX lock; the sell = the
  option's `sell_amount` (the agency's price, set by owner / agent under the builder's rules). A 1.1 answer is a
  `ContractError`: nothing written, retried next run.
- **One confirm per set, fanned out.** Booking's confirm books the whole hold. One `confirm` request on the set's first
  line (lowest id); `apply` writes the answer on every line sharing the hold in the trip (`SET_LINES_SQL`). The same
  fan-out for a refused confirm and for a release (a release lets the whole set go: a Lost before the deposit releases
  every line, not just one).
- **"Deposit paid" = the accepted proposal's deposit schedule row `paid`** and the trip at booked / pre-departure /
  travelling (`CONFIRM_DUE_SQL`), not the stage alone (a stage can be moved by hand). Only lines of an accepted
  proposal set are auto-confirmed; a hand-asked AA line (AA-947) keeps its Confirm button.
- **Not confirmed when the hold is no longer live** (`hold_expires_at > now()` in the due query; Booking's 410 when it
  ran out meanwhile). Lines Booking reports expired / released at write time read `expired` (`hold_expired` /
  `hold_released`) + urgent task `aa_hold_expired`; the line's actions offer `requote` (the agency's way on). Booking's
  own `hold.expired` event already moves held lines to `expired` (AA-947 feed).
- **A refused confirm reads `failed` with Booking's code** (or `expired` / `sold_out` / `not_served` by the existing
  `REFUSED_SUB`), opens urgent task `aa_confirm_failed` and is not re-sent by itself (the agent decides: re-quote).
  This also applies to an AA-947 hand-asked confirm: before, an unmapped refusal left the line `held` with the code,
  offering Confirm again with the same refused hash.
- **Unknown hold at Booking** (`GET /holds/{id}` 404): lines `failed` (`hold_not_found`) + task `aa_lines_failed`;
  other refusals (`unknown_partner`, `forbidden`) and outages are retried next run (an outage stops the run's Booking
  calls, as for requests).

- **Review fixes (S259, verdict ship-with-fixes).** (1) The confirm fan-out loop in `apply` reused the name
  `status`, which holds the request's own status: a set confirm left its `crm.aa_request` `pending` (leased), so the
  sync re-sent the confirm every lease (120 s); with an `on_request` answer it never ended. Renamed to `line_status`.
  (2) `proposal_sets` now isolates each proposal: an error while writing one proposal's lines (missing FX rate CRM25,
  a CHECK, a builder KeyError) is counted `proposal_lines_error`, logged with tenant id + error class only, and the run
  goes on; the same around `queue_confirms` (`confirms_error`). `Forbidden` / `NotFound` (agency locked / gone) still
  propagate so the run counts the agency `skipped` as before.

## Tradeoffs

- **Contract change vs crm migration.** Storing the held quote (hash, per-line prices, FX) on `crm.proposal` would have
  needed crm-024 (+ Infra copy, DB Migrate, ordering) and still left holds made before it without data. Reading it from
  Booking keeps Booking the owner of prices (ADR 0005) and needs only an additive Booking change; cost: Booking must be
  deployed first.
- **Option id as line id** instead of a `proposal_option_id` column: no migration and no mapping code; the one rule to
  know is that an accepted option and its AA line share a UUID (both are random v4: no clash in practice; the insert is
  `ON CONFLICT DO NOTHING`).
- **Pull in the minute sync + nudge** instead of a new job kind: no kinds / gate / DB Migrate idle list change, and a
  deposit taken before the lines exist still confirms on the next run.
- **Fan-out writes on every set line**, so a manual Confirm on any line of the set also books the set once (Booking is
  idempotent on the hold); a release of one line of a set releases all of them (Booking cannot release part of a hold).

- **A proposal whose lines keep failing to write** is retried every minute (it stays in `DUE_SQL`) and logged
  `crm_proposal_lines_failed` each time, rather than blocking its agency. No task is opened for it: the transaction
  that would write one is the one that failed. Watch the log / `proposal_lines_error_count` in the job result.
