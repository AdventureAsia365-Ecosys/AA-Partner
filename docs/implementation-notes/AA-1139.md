# AA-1139 — TripPlanner module of the agency app (AA-Partner side)

Lane l19 of S285. Settings › Add-ons › Trip planner in the CRM web, backed by the CRM API, relaying to CIS (site
settings) and TripPlanner (leads, usage, webhook key). Companion PRs: CIS (`tenant.addons.v1` 1.1 routes),
TripPlanner (tp-035 + `lead.submitted.v1` 1.1 planner routes), AA-CIS-Infra (scope `tripplanner.leads/manage`), root
(contracts, retention row, ERD).

## Decisions

- **The module lives in the CRM web** (Settings › Add-ons › Trip planner) **and in the Content studio** (Account ›
  Trip planner). Fix pass (review finding): the lead route by e-mail / webhook, the signing key and the delivery status
  only matter for an agency WITHOUT the CRM add-on, and such an agency has no CRM agency (CIS creates one only for a
  live `crm` subscription), so a CRM-only page could not serve them. The studio page reuses the CRM's view with its own
  sender; its route handler (`web/app/api/studio/trip-planner`) reads and writes the site settings at CIS
  `/v1/account/tripplanner` with the studio token, and TripPlanner's half through `/crm/v1/studio/trip-planner*`.
- **Who may use the studio routes of the CRM API**: not `crm.member` (there may be no agency), CIS's directory: the
  API asks `tenant.membership.v1` for the caller's `(iss, sub)` memberships (the membership feed's client and scope
  `cis.tenant/read`, no new grant) and keeps the ACTIVE one of the requested tenant. Owner and editor read, owner
  rotates; viewer and strangers get 403 before TripPlanner is asked. No cache (a removal takes effect at once; the page
  makes three calls at most). The role is never taken from the request or from the studio token's claims (the web
  checks the claim first only to spare the calls).
- **Roles**: `TRIPPLANNER_VIEW` (owner, agent: agents work the planner's leads) and `TRIPPLANNER_MANAGE` (owner, like
  the other Settings that bind the agency). The assistant is refused before CIS or TripPlanner hear of it.
- **CRM channel**: shown, not chosen. CIS sends leads to the CRM whenever the agency holds `crm.core` (the CIS 390
  view); the owner still sets the e-mail / webhook route used if the CRM add-on ends. Changing that resolution would
  change TripPlanner's routing and the CRM pull entitlement; not in this slice.
- **Theme**: the page edits the brand colour (`accent`) and the text / link colour (`accent-deep`); other brand tokens
  an agency already has are kept; the planner's brand layer picks contrast for the rest. "Use the default colours"
  sends an empty theme.
- **Key shown once**: only the rotate answer carries the key; the BFF has no GET for it; the page shows it in place
  with Copy and forgets it on reload. A rotation asks for confirmation (kit ConfirmModal) because the old key stops at
  once.
- **Usage**: AI sessions used against the plan quota (danger tone when used up), leads this month and in the last 24
  hours. No warning share of our own (a threshold would have to be a setting).
- **Leads**: ids, times, channel, delivery status, tries, last error code. The agency opens a lead where it was
  delivered (CRM Inbox, its mailbox or its webhook); TripPlanner never sends the traveller here.

## Tradeoffs

- The studio routes of the CRM API write no agency audit row (there may be no agency): the key rotation is recorded by
  TripPlanner (`rotated_by` `studio-member:<id>`) and in the API log; the route and look changes by CIS's audit
  (`membership:<id>`).

- The module page makes up to four remote calls (CIS module, TripPlanner usage, key info, leads). Each is short
  (5 s timeout) and TripPlanner's parts fail soft, so a TripPlanner outage leaves the CIS part usable.
- Custom domains stay a staff action (DNS + certificate job in CIS); the page shows their state only.

## Should know

- Before the Infra scope is applied TripPlanner answers 403 and the page shows usage, key and leads as "not available";
  before the CIS deploy the whole page is 503 `tripplanner_unavailable`.
- The M2M secret's informational `scopes` list should gain `tripplanner.leads/manage` with the next credential write
  (the CRM asks each scope by name; nothing breaks without it).
- Studio key rotation needs TripPlanner's code PR and tp-035 as fixed in this wave (both accept `studio-member:<uuid>`);
  before them TripPlanner answers 400 `invalid_actor` and the studio page shows "not available". The studio site
  settings need the CIS PR (`/v1/account/tripplanner`); before it the studio page is 503 / "cannot be read".
