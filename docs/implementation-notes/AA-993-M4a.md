# AA-993 Phase E, slice M4a (Partner / CRM) — `registered_keys` on `/crm/health/ready`

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §2 M4a; critic point 23; root ADR 0017
decision 7 (Proposed). Same change as AA-Booking's M4a.

## Decisions

- `registered_keys` = every `crm-NNN` row of `crm.v_schema_versions` (the view filters `crm-%`), sorted: the list
  `READY_SQL` already reads to compute `missing_schema_versions`. No extra query.
- In the body whenever the schema read succeeded (200 and the "schema behind" 503); not on `db: error` /
  `not_configured`.
- `REQUIRED_SCHEMA_VERSIONS` unchanged.

## Changed

- Nothing against the design. `/crm/health/ready` has no response model, so the OpenAPI export does not change.

## Tradeoffs

- One key per migration in a public, rate-limited, cached body (23 keys today). The keys are migration numbers only.

## Should know

- Ships before M4b so the first `schema-gate` reads a task with the field (`missing_schema_versions` is the fallback).
- Integration test `test_readiness_as_crm_app` pins the full body (ran green on a local PostgreSQL, S256).
- Live proof (orchestrator, after deploy): `/crm/health/ready` lists `registered_keys` ending in `crm-023`.
- Rollback: revert; nothing reads the field until M4b.
