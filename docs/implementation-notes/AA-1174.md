# AA-1174 — crm.ops.v1 1.18 `GET /privacy-evidence` (AA-Partner part)

The CIS Platform › Compliance page (Obligations tab) needs live evidence that campaigns go only to opted-in contacts and
that consent capture works. CIS never reads the `crm` schema, so the CRM serves counts on its ops contract.

## Decisions

- **Counts only, no agency audit event.** Same pattern as `/data-coverage`: one `platform_tx` per agency (RLS FORCE: a
  bare `crm_app` count reads 0 rows), platform-wide sums, one log line. No agency id or name, no contact, no address.
- **What a violation is.** A dispatch row with purpose `marketing`, status and gate_result `sent`, decided in the window,
  whose contact's latest `crm.consent` row of purpose `marketing` at or before `decided_at` is not `true`, or whose
  address was on `crm.campaign_suppression` at send time (`created_at <= decided_at` and not deleted before it).
- **Erased contacts are left out.** Erasure removes the traveller and its consent rows, so a past send would read as a
  violation; such sends are counted apart (`excluded_erased`). In practice it stays 0: `crm.erase_subject` (scope
  traveler) deletes the contact's dispatch rows together with its consent, so the send leaves the counts entirely. The
  branch only guards a future erase path that would keep dispatch rows.
- **No CRM setting, no migration.** The window is the CIS setting `cis.compliance.campaign_consent_window_days`, passed
  as `days`; the route caps it at 365 (a technical constant bounding one call's scan).

## Changed

- The plan put the window in a CRM setting (would need crm-086); it is a bounded query parameter instead (critique of the
  plan).

## Tradeoffs

- Suppression history is approximate: lifting a suppression deletes its row (`app/campaigns/unsubscribe.py`), so a send
  made while a since-lifted suppression was in force cannot be seen. The consent rows are append-only, so the consent
  half is exact.
- `app/ops/privacy_evidence.py` opens `platform_tx` read-only (added to the code rules' PLATFORM_MODULES). One call opens one transaction per agency; fine at today's agency count, and CIS calls it only on Refresh evidence
  (at most every 10 minutes).

## Should know

- `api/tests/integration/test_aa1174_privacy_evidence_db.py` runs the SQL on PostgreSQL with the RDS role shape through
  `platform_tx`: two invented agencies (a send with a yes, a send after a no, a yes withdrawn after the send, a
  suppressed address, an erased contact, plus a transactional mail, a dropped mail and a send outside the window), and
  asserts the change in every count, so RLS FORCE returning 0 rows or a lost "consent at send time" fails it.
