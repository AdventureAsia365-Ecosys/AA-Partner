## Decisions

- **One small migration, crm-011, no new table.** The insights opt-out and the AA-raised data requests are the only
  data the console needs that has no column. A new tenant table would also have to join `crm.erase_subject`'s keep
  list or delete steps (else the agency erase fails with CRM16), so both live on existing tables.
- **`insights_opt_out` on `crm.tenant_entitlement`, not on `tenant_settings` (deviation from design §3.3).** Q2 3.12
  makes the opt-out an AA action on the owner's written request. `tenant_settings` is owner-writable and would need a
  new column guard; `tenant_entitlement` is already platform-only through the crm-008 trigger (every column, CRM04),
  so a member can never flip it and no new guard is needed.
- **AA-raised requests reuse `crm.erasure_request`** (`purpose` = `offboard` | `export_only`, `owner_accepted_at`).
  "Awaiting the owner" = `requested_by LIKE 'platform:%' AND owner_accepted_at IS NULL` (no backfill needed). A new
  trigger (CRM18) makes the rules hold whatever the API does: AA inserts only an unconfirmed agency request; only the
  owner sets `owner_accepted_at`, once, on a still-requested AA row, without moving its status; an unconfirmed AA row
  only moves to cancelled (the owner declines); `export_only` never moves to erasing; a platform actor never sets
  `confirmed_by` nor moves a row to erasing / erased (the AA-942 documented recovery, erasing -> failed with actor
  `platform:l1`, stays allowed); nobody forges `requested_by platform:*`. Unscoped sessions (migrations, the master's
  run-script) are not restricted, like the crm-008 guards.
- **The rejected alternative:** an export-only marker inside the receipt JSON, with no migration. A hack: the receipt
  is the erase's output, and nothing in the database would stop AA from confirming.
- **`platform_tx(..., statuses=...)`, default active only.** Reads name every status; lock / unlock, allowed features
  and the opt-out accept active + locked; a job retry accepts active + offboarding (an offboarding agency's erase
  job); invites, data requests and owner recovery stay active-only (the owner or the members must be able to answer
  in the CRM, which a locked agency cannot). Inside `platform_tx` a missing agency is **404 `tenant_not_found`** (the
  L1 console knows the agency list; there is nothing to hide) and a refused status **409** `tenant_locked` /
  `tenant_status` (was 403 `not_a_member` / `tenant_locked` for the AA-939 recovery routes). `system_tx` (jobs) keeps
  its 403 answers.
- **Second `platform_tx` opener `app/ops/console.py`**, with the same code-rules fence as `app/members/recovery.py`:
  only `app/routers/ops.py` calls the console's platform functions; `offboarding.raise_request`,
  `team.create_invitation` and `queue.retry_failed` are called only from their module and the console.
- **Ticket references in the audit as `ticket:<REF>` object ids.** The audit takes codes and ids only (`reason` is a
  code), so the L1 ticket goes into `object_ids` with a strict pattern `^[A-Za-z][A-Za-z0-9]{0,15}-[0-9]{1,10}$`
  (e.g. `AA-941`, `SUP-1234`). Required on lock, unlock, owner invite, allowed features, insights opt-out
  (`owner_request_ref`), data requests, job retry, owner-recovery open and create agency (review fix); optional on
  member deactivation and recovery complete (bodies the CIS lane may send without one).
- **Reads are audited per agency (`ops_read`)**, one event per agency on each list page (≤ 50 by default, 200 max),
  as designed (§4.9 "AA ops reads"). The owner's access log shows them. Accepted volume; revisit if the list is
  polled (the S-01 page loads on open and on Refresh only).
- **The response allow-list is an explicit key list plus forbidden patterns** (`app/ops/serializer.py`,
  `OpsAllowListRoute` set by `class_router()` for OPS like `MarginFilteredRoute` for AGENCY). Strict (500
  `ops_key_not_allowed`) on test / local so CI fails; drop + log (names only) elsewhere. Every ops route also has a
  Pydantic response model with `extra='forbid'`. `cost_usd` / `ai_cost_usd_month` stay allowed: they are AA's own
  platform AI spend, not agency money.
- **Validation errors on ops routes answer `{detail: invalid_request, message, fields}`** (field names only). FastAPI's
  default 422 body echoes the submitted input, which on the first-owner invite would carry the owner's address back
  through the CIS relay.
- **First-owner rule:** refuse 409 `owner_exists` (an active owner, or a member with role owner in status invited /
  active), 409 `owner_invite_pending` (a pending / claimed unexpired owner invitation), 409 `has_travellers` (any
  `crm.traveler` row, trashed and archived included, or any `crm.form_submission` row), then the plan's
  `member_limit_reached`. The invitation itself is the shared `team.create_invitation(ctx: AnyContext, ...)` extracted
  from `team.invite` (vault-encrypted address + blind index, token hash, SES mail inside the transaction). The address
  is never stored in clear, logged or returned (not even masked).
- **Allowed features never touch `tenant_settings`**: AA allows, the owner switches on (unit test asserts no
  `tenant_settings` SQL in the console module).

- **The owner confirms with a new member route** `POST /crm/v1/lifecycle/offboarding/{id}/accept {export_waived}`
  (owner only, `agency_export` action); decline is the existing cancel (audit reason `declined`). A deletion's
  confirmation takes the dry-run counts (409 `legal_hold` under a hold) and queues the export job unless waived; an
  export-only request is never waived and never counted. `view()` adds `purpose`, `raised_by`, `awaiting_owner`;
  the owner's own `request()` answers 409 `data_request_awaiting` while an AA request waits; `confirm_erase()`
  answers 409 `export_only_request` for an export and 409 `data_request_awaiting` before the confirmation.
- **Locked agency in the web:** `/me` answering 403 `tenant_locked` sends the person to the chooser with "This agency
  is locked by AA" (EN default, VI by choice); the chooser also shows it when the session's agency is listed as
  locked.

## Changed

- Spec route list vs. shipped: all routes of the spec are served. Small differences:
  - `GET /tenants/{id}/data-requests` answers `{items: [DataRequest]}` (latest 10, newest first); `POST` answers
    the DataRequest plus `owners_notified`.
  - `DataRequest.status` adds `cancelled` and `failed` to the draft contract's four values (owner-made requests and
    a refused erase need them).
  - `GET /tenants/{id}/jobs` answers `{items: [FailedJob]}`.
  - `PUT /entitlements-allowed` answers the full Entitlements object; `PUT /insights-opt-out` answers `{opt_out}`.
  - `POST /tenants` requires `ticket_ref` (goes on the `agency_create` event) and is **create-only**: an existing id
    answers 409 `tenant_exists` and nothing is written (review fix, blocking: the converge path silently renamed any
    agency, locked / offboarding / offboarded included, with no audit event). `provision_agency(create_only=True)`;
    the Dev seeder keeps converging. Deactivate and recovery complete take an optional `{ticket_ref}` body; recovery
    open requires `ticket_ref` now.
  - `DataRequest.status` adds `export_downloaded` (review fix): an AA export the owner downloaded but has not closed
    still holds the single open-request slot (crm-010 unchanged: only the owner's "Close request" ends an
    `export_only` row), so it is no longer reported as `done`; `done` = erased, or downloaded and closed.
  - The AA-939 recovery routes on a locked agency answer 409 `tenant_locked` (was 403) and on an unknown agency 404
    `tenant_not_found` (was 403 `not_a_member`).
- `team.invite` is now `lock_seats` + `create_invitation(ctx: AnyContext, ...)` (behaviour unchanged for the owner);
  `team.plan_of(ctx: AnyContext)` is the plan read without the permission check.
- `app.agencies.provision_agency(..., audit_object_ids=())` and `ProvisioningContext.audit(..., object_ids=())`.
- `SystemContext.status` (the agency status the platform / job block opened with).
- `app/members/mail.py` adds `data_request_message` (EN then VI, link to Settings > Data and privacy).
- `crm.job`: `queue.failed_jobs`, `queue.failed_count_24h`, `queue.retry_failed` take the open platform context's
  connection, so the read / retry and its audit event commit together. A retry resets attempts, error, result, the
  lease and the release counter (`progress.releases`).
- Tests: `test_route_guard` probe bodies now pass the ops allow-list; the AA-939 ops route test returns real shapes.

## Tradeoffs

- **One transaction per agency on the list.** `crm.tenant` is FORCE RLS and the crm-007 registry function is the only
  cross-agency read; fine for Dev (a handful of agencies). At prod scale a SECURITY DEFINER directory function
  (crm-0xx) would answer one page in one query.
- **Audit volume of list reads** (one `ops_read` per agency per page) accepted as designed; see Decisions.
- **`has_travellers` is stricter than "no travellers":** trashed and archived travellers count, and so does any stored
  inquiry (an unprocessed form submission becomes a traveller soon). The intake job can still race the check (the seat
  lock does not block intake): an inquiry stored after the check and before the invitation is accepted ends up in an
  agency whose first owner AA invited. Closed by the review fix: `invitations.accept` re-runs the rule for an owner
  invitation sent by a platform actor (`invited_by platform:*`): an active owner -> 409 `owner_exists`, any traveller
  or stored inquiry -> 409 `has_travellers`, with a `denied` `invitation_accept` event; the invitation stays claimed
  (it expires with its TTL; L1 can then use the owner recovery). Owner invitations an agency's own owner sends are not
  re-checked (a co-owner is the owner's call).
- **Export-only requests reuse the offboarding export** and occupy the single open agency-request slot until the owner
  closes it (Cancel = "Close request" on the page); the file expires after 7 days. CRM-35 (AA-967) replaces this with
  the full export zip and a data-request log.
- **Locked agencies:** members cannot cancel a pending owner recovery or answer a data request while locked
  (`tenant_tx` refuses). So opening / completing a recovery, inviting and raising data requests need an active agency;
  the 14-day recovery window keeps running during a lock (a lock pauses completion only).
- **`error_class` of a failed job** is the job row's `error` column cut to 80 characters: the worker stores the error
  class, but the reaper / release write short fixed texts (no data); kept as is.

  e.g. `SUP-1234`), the opt-out needs `owner_request_ref` (same pattern). A 422 answers field names only.
  `inbound_mail_30d` is always 0 until CRM-17 ("not tracked yet" in the UI).

  `tenant_entitlement.insights_opt_out` in `v_insight_fact` or the aggregator. Likewise `allowed_features` is not a
  feature gate yet (the LLM gateway checks `tenant_settings.ai_enabled` only); each feature card must check it.
- **Retrying a `crm_offboard` erase job** continues an erase the owner confirmed (AA-942 recovery path); the S-01
  page warns. A locked agency's jobs cannot be retried (409 `tenant_locked`): they would fail again.
