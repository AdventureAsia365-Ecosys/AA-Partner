# AA-933 (CRM-05) — AA-Partner repo, API skeleton, `crm.job` runner

Card: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 CRM-05; root ADR 0010 (decisions 1–3),
ADR 0006b decision 6 (route classes), ADR 0003a (job table per owner). Lane S248 `aa933-partner-skeleton`.

## Decisions

- **Layout `api/` (not `backend/`)** as ADR 0010 decision 1 and the Infra owner registry (`owners.yaml` owner `crm`,
  `path: api/migrations`) say. `web/` and `portal/` arrive with CRM-07 (AA-935) and P2a (AA-979).
- **Health under `/crm/health` and `/crm/health/ready`**, not `/partner/health`: the card, ADR 0006b and the
  `crm.ops.v1` contract all use the `/crm` prefix, and the ALB / CloudFront rule forwards `/crm/*` only. The lane
  brief said `/partner/health`; the design wins (one prefix for every API path).
- **AWS names `aa-crm-<env>-*`** (ECR `aa-crm-dev-api`, service and task family `aa-crm-dev-api`, roles
  `aa-crm-dev-ecs-task-role` / `-ecs-execution-role` / `-app-deploy`). The lane brief said ECR `aa-partner-dev-api`,
  but the CI apply role may only create ECR repos `aa-crm-<env>-*` (Infra `cicd_crm.tf` CrmEcrRepoManage) and the KMS
  key policies already name `aa-crm-dev-ecs-task-role` (AA-932). Product name AA-Partner, resource prefix crm.
- **Route-class guard = one verifier, then an audience check.** One `MultiIssuerVerifier` (byte copy of the CIS
  module) holds every configured `(issuer, client)` pair; each route class (`/crm/v1`, `/crm/ops/v1`,
  `/crm/staff/v1`) lists the pairs it accepts. A token that verifies but belongs to another class gets **403**
  (`wrong_audience`), which is what the card's R test asks for ("a `cis-admin` or `breakglass` token on any
  `/crm/v1` route → 403"); a token that does not verify gets 401. The guard is a router-level dependency, so a route
  added to a class router cannot skip it; a unit test walks every app route and checks it.
- **Identity values come only from the environment** (Terraform task definition), no code constants: the repo is
  public and pool IDs are on the DM-6.10 list. An empty value means "this class accepts nothing" (fail closed).
- **`tenant_tx()`** (`app/tenancy.py`) is the only way a request reaches tenant data: one transaction, `SET LOCAL`
  of `app.tenant_id`, then the membership check against `crm.member` (already filtered by RLS), then
  `app.member_role` and `app.actor`, optionally `SET LOCAL ROLE` to one of the four NOLOGIN readers (allow-list).
  A static test (AST) fails when code outside the allowed modules calls the pool directly.
- **Base table template** (`api/db/templates/tenant_table.sql`) and a catalogue guard (integration test) that every
  table in schema `crm` except the platform tables has the base columns, the trash columns, ENABLE + FORCE RLS and a
  tenant policy. crm-002 is the first user: `crm.tenant`, `crm.member`, the status-transition table and trigger.
- **Readiness** reads `crm.v_schema_versions` (crm-002), a `security_barrier` view owned by `crm_owner` over
  `shared.schema_versions WHERE version LIKE 'crm-%'`; DML on it is revoked from `crm_app` (a simple view is
  auto-updatable through its owner's rights).
- **Heartbeat kind `crm_heartbeat`**, idle-exempt in DB Migrate (owners.yaml). crm-001 has no singleton index for a
  recurring kind, so the recurring scheduler uses an idempotency key per time slot (`crm_heartbeat:<slot>`): two
  workers in the same slot insert one row (`ON CONFLICT DO NOTHING`), and no schema change is needed.
- **Job payloads carry ids only** (DM-6.3, card E check): `app/jobs/payload_guard.py` refuses any key that is not an
  id (`*_id`, `*_ids`) or in a short list of non-personal control keys, at enqueue time; a unit test scans every
  `enqueue(...)` call in `app/` for literal payload keys.
- **Job errors keep the class name only** (crm-001 column comment: "error class and ids only, never personal data or a
  message echoing input"), unlike Booking which stores the message.

- **Retention kind `crm_job_retention`** (data standards §7 row `crm.job`, named in the crm-001 comment as "the crm_
  TTL kinds, AA-933"): succeeded 30 d, cancelled 90 d; failed rows are **kept** because §7 says "archive before delete:
  failed rows only" and there is no CRM archive bucket yet; DRY RUN by default (DM-7.2, `JOB_RETENTION_DRY_RUN`).
  **Scheduled by a due-now maintenance hook** (`DailyRetentionSchedule`, Booking `DailySchedule` pattern), not as a
  `Recurring` kind (review round): a Recurring kind keeps its next slot queued ahead, which the deploy gate and Infra
  DB Migrate (`JOB_BUSY_SQL`, "any queued (any run_after)") count as busy, so it would block every deploy and every
  DB Migrate apply of every owner. The hour is `JOB_RETENTION_UTC_HOUR` (default 19 UTC = 02:00 ICT, Booking's hour).
  Only exempt kinds may be Recurring (unit test `test_only_deploy_gate_exempt_kinds_queue_ahead`).
- **Rate limit** on the public routes (ADR 0010 decision 2 "from AA-933"): fixed one-minute window per client address,
  in process; the address is the `X-Forwarded-For` entry `RATE_LIMIT_XFF_HOPS` (default 2) from the right.
- **Deploy gate path `/crm/ci/deploy-gate`**, not under `/crm/ops/v1`: that prefix is the `crm.ops.v1` contract with
  the CIS admin (WORKFORCE tokens only).
- **ARM64**: Docker Build Check and the deploy build run on `ubuntu-24.04-arm` (free on a public repo), no QEMU.

## Changed (vs the card)

- `/crm/health` **plus** `/crm/health/ready` (the card names only the first; the ready probe is the deploy smoke and
  alarm contract shared with Booking).
- `/crm/v1/me` is the one real agency route (membership echo, ids and role only), so the guard and `tenant_tx()` have
  a live check; `/crm/ops/v1` and `/crm/staff/v1` routers exist with their guards but no route (the contract
  operations are CRM-13a / CRM-26 / CRM-13b). The unit test proves the class guards with probe routes mounted in the
  test app and walks every served path. Because FastAPI runs router dependencies only for a matched route, any path
  under the still-empty `/crm/ops/v1` and `/crm/staff/v1` answers **404** live, not 401 (review round): the live guard
  checks are 401 / 403 on `/crm/v1/me` only, and a unit test pins the 404s. No `whoami` probe was added, so the served
  surface stays exactly the `crm.ops.v1` contract (no extra operation outside it).
- crm-002 adds the readiness view `crm.v_schema_versions` (Booking's pattern): `crm_app` has no right on `shared`.
- "Shared conformance tests" for the runner = the CIS job-table template comparison (byte-copied comparator) plus the
  ported Booking queue / worker tests and the lease re-claim integration test.

## Tradeoffs

- **One verifier for all classes vs one per class**: one verifier gives the 403 the card wants for a misrouted token
  and one JWKS cache per pool; the cost is that the class check is ours (tested over every served path).
- **No identity defaults in code** (Booking has Dev constants with a `docs-lint: ignore`): this repo is public from the
  first commit, so the values come from Terraform. Consequence: a fresh Dev task refuses every token until Infra sets
  the env (which the Infra branch of this lane does).
- **Policy `TO` the six CRM roles (`crm_owner`, `crm_app`, the four readers), not `TO PUBLIC` and not only
  `crm_app`**: the ecosystem catalogue rules (AA-CIS-Infra `db/rls_catalogue_rules.py` rule b, run nightly on the
  Dev dump) flag any policy TO PUBLIC; naming only `crm_app` would leave a reader reached by `SET LOCAL ROLE` with no
  policy (zero rows). A reader granted SELECT later is tenant-scoped automatically; any other role matches no policy
  and sees nothing. With FORCE the policy binds `crm_owner` too, so a future owner-run data fix must set
  `app.tenant_id` (or a card adds an owner policy, as `crm.erase_subject()` will need). Guarded three ways: crm-002
  guard 1 raises on a crm policy TO PUBLIC, the base-template catalogue test checks the exact role set, and the
  template file carries the `TO` list (review round S248: the first draft used PUBLIC).
- **Recurring schedule by idempotency key per slot** instead of a singleton partial index: no schema change to
  crm-001 (already copied to Infra), at the price of one finished row per slot (pruned after `keep_days`).
- **Rate limit in memory**: per task, lost on restart; acceptable as a ceiling on Dev until WAF (first real agency).

## Should know

- crm-001 is a **byte copy** of AA-CIS-Infra commit `42e41c0` (lane AA-932); do not edit it here. crm-002 needs its
  own Infra copy PR after this repo's `main` has it.
- Integration tests run on PostgreSQL 15 with the RDS role shape (`aa_cis_admin` not superuser, `crm_app`
  NOINHERIT, readers granted to `crm_app` only), mirroring Infra rl-003 / rl-004. Mutation-checked: weakening
  `crm.member` (no trash check, no updated_at trigger, a `USING (true)` policy) fails 8 tests.
- The XFF hop count (2) assumes CloudFront appends the viewer and the ALB appends the NLB address; verify on the first
  live request (`/crm/health` log line `client` vs a known caller IP) and adjust `RATE_LIMIT_XFF_HOPS`.
- The membership feed (`tenant.membership.v1`, AA-978) and agency creation (CRM-13a) do not exist yet: on Dev a
  synthetic agency and member are inserted by the seeder of CRM-07 (AA-935) or by hand through `tenant_tx`-shaped SQL.
- The CI-only Postgres passwords (`ci.yml` service container and DSNs) and the fake DSN in `test_db_readiness.py`
  carry an inline `# gitleaks:allow`: the shared `.gitleaks.toml` rules (`uri-embedded-credentials`,
  `credential-key-literal`) flag them, and the Security Audit job scans the full history, so a later fix commit
  would not help. A real credential never gets this marker.
- AA-CIS-Infra's connection budget now reads this repo's pool size (`api/app/db.py`, first `max_size=` after
  `create_pool(`) from `main` (`--verify-sources`): the Infra PR of this card merges after this repo's first PR, and a
  pool change here must update Infra `db/connection_budget.json` in the same week (the nightly run fails otherwise).
