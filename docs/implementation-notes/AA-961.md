## Decisions

- **Two tables.** `crm.incident_flag` (the design ERD name, group I) holds what Booking reported for one departure:
  departure id, the contract's incident code, open / cleared with times and the two Booking event ids. Ids and codes
  only. The affected trips are **not** stored: they are read at view time (live trips with a booking line on the
  departure), so a line added after the flag is covered and an agency without a line sees nothing (card "Done when").
  `crm.calendar_feed` is new (not in the design ERD): one ICS subscription per member. The design's
  `calendar_connection` is the OAuth sync (Google / Graph through the agency's own account, errata S247) and stays for
  the BYO card; the ICS feed is its fallback the design names (§5.10 "fall back to an ICS link").
- **Writers in the database.** `crm.guard_incident_flag` (CRM41): only `job:` / `platform:` / `seed:` actors write an
  incident; a member never raises or clears one, and a raised row keeps its departure, code and event.
  `crm.guard_calendar_feed` (CRM42): a member creates only their own feed; only that member or an owner revokes it;
  token, member, scope and expiry are fixed (a new link is a new row); the public fetch (actor `calendar_feed:<id>`)
  changes only `last_fetched_at` / `fetch_count` of its own row.
- **Lookup policy** `calendar_feed_token_lookup` (SELECT only, keyed on `app.calendar_feed_hash`, live feeds only) is
  the `client_link_token_lookup` pattern; listed in `EXTRA_POLICIES` of the template test.
- **Erasure.** Neither table names a trip or a traveller, so only the agency scope of `crm.erase_subject` changes (the
  crm-026 text + `incident_flag` next to the Booking feed rows, `calendar_feed` before the members). Contract class
  (ADR 0017 §3: a replaced function), MIG-4 order.
- **Retention.** `crm.incident_flag` already has a DM-7 row ("until the agency deletes the trip or offboards"); the root
  PR moves it to its own row (ids and codes only, until offboarding: it is departure-scoped, not trip-scoped) and adds
  `crm.calendar_feed` to the agency configuration row.

- **Feed handling** (`app/booking/sync.py` `apply_incident`): `departure.incident` opens the flag and one urgent
  `aa_incident` task per affected booked / pre-departure / travelling trip (`task_open_kind_uq` keeps it to one); the
  clear closes the flag and leaves the tasks to the agent. `contract.Event` reads `incident_code` (the fixed list) and
  `occurred_at` tolerantly (a malformed time falls back to now; only the flag uses it). The "drafted WhatsApp" of the
  card waits for module 9 (CRM-28); nothing is sent.
- **Region** = a country code: the running AA line's tour country (`crm.aa_catalog_tour.country_code`), else the
  trip's first destination mapped to ISO (`vietnam` -> `VN`, ...), else `unknown`. The accepted proposal's day
  `place` is shown as the finer "where today". The design says "AA region"; the catalog cache has no region below the
  country today, so the country is the region until CIS publishes one.
- **Names hidden** (R37): the travelling view and the reach list carry traveller ids and which contact fields exist,
  never a name. `POST /duty/reveal` opens name / phone / e-mail / emergency contact for at most 50 travellers, one
  `reveal` event per traveller (the meter counts travellers). Card R: up to 5 travellers the reason defaults to
  `duty_of_care`; above 5 a reason from `BULK_REASONS` is required (`other` is not one); the member's reveals of the
  last hour (the existing reveal meter, so one-field reveals count too) plus the request may not pass 60 -> 429
  `reveal_rate_limited` with a denied audit event and nothing decrypted. Health codes are not in the bulk reveal: they
  stay one by one on the client page, where the consent check lives.
- **Emergency contacts and medical notes** already live encrypted in the F1 vault (`traveler.emergency_contact_enc`,
  `traveler_health.health_flags_enc` under its consent); no new PII column. The permission matrix gets three rows,
  every role allowed (`duty_of_care_view`, `calendar_view`, `calendar_feed_manage`); the reveal actions are the
  existing `reveal_contact` / `reveal_sensitive`.
- **Calendar sources**: departures / returns of live trips, `due` payment schedule rows (crm-016), `open` /
  `payment_claimed` invoices (crm-024), signing deadlines = start - 21 days while a signature is `pending` (R29's T-21;
  there is no deadline column in crm-025), open tasks with a due time, requested / confirmed calls (crm-012 slots).
- **ICS without personal data**: the feed leaves the CRM (it sits in the member's Google / Apple / Outlook account), so
  it carries a fixed English label, the trip's first 8 id characters and a link back to the trip, never the trip title
  (it may name the client), a name or an amount. `X-WR-CALNAME` is the agency name. URL on the partner host
  (`PARTNER_WEB_ORIGIN`, the existing `invitation_origin` setting), path `/crm/public/v1/calendar/<token>.ics` (the
  ALB already sends `/crm/*` of that host to the API; no Infra change).
- **Card E (revoked token)**: a stopped link answers 404, so the subscribed calendar stops updating and keeps what it
  had; the calendar page shows the banner (stopped by you / by an owner, trips and bookings unchanged, make a new
  link). Making a new link revokes the old one (one active per member).
- Web: two new CRM nav sections (Travelling now, Calendar) with Lucide `Plane` / `CalendarDays` in the CRM-local shell
  (not kit core); the reach list uses the kit `DataTable` selection (lint `no-raw-table`).

## Changed

- crm-027 is numbered after crm-026 (merged as #137 while this lane ran); it starts from the crm-026 `erase_subject`
  text (Guard 0 checks the crm-026 keep-list names are in the live text).

- The calendar is an agenda by day (one month, a kind filter, my trips / the agency), not a grid month view: it reads
  the same on a phone and needs no new kit component.
- `REQUIRED_SCHEMA_VERSIONS` gains crm-027 (after crm-026, which the AA-967 code PR #138 added).

- Review fix (S260): Travelling now treats a trip without an end date as open-ended (a `travelling` trip stays
  travelling, the stage job only raises `return_date_missing`), and keeps a trip the stage job moved to `completed`
  through its return day (`end_date` between the window start and today). The incident badge (`FLAG_TRIPS_SQL`) and
  the `aa_incident` task (`INCIDENT_TRIPS_SQL`, the agency's today) include that return-day trip. The calendar and the
  ICS feed read departures / returns of `completed` trips too, so the return of the day and past departures keep their
  UIDs in subscribed calendars; signing deadlines still read live trips only.

## Tradeoffs

- A trip completed early by hand (end date still ahead) is not in Travelling now (completed counts only up to today),
  but its planned departure / return stay in the calendar: the calendar shows the planned dates.

- The hourly reveal limit is per API process (the meter is in memory, one task on Dev): exact on Dev, a lower bound
  with several tasks. Moving the count to the database is a hardening item, not this card.

- No purge of cleared incident flags: a few rows per departure per agency, ids and codes only; a window can come with
  the lifecycle purge later without a schema change.
- No per-fetch audit event for the ICS feed (a subscribed calendar polls every few minutes to hours): the row's
  `last_fetched_at` / `fetch_count` show it is in use; creating and revoking a feed are audited by the API.
