## Decisions

- **Two tables.** `crm.incident_flag` (the design ERD name, group I) holds what Booking reported for one departure:
  departure id, the contract's incident code, open / cleared with times and the two Booking event ids. Ids and codes
  only. The affected trips are **not** stored: they are read at view time (live trips with a booking line on the
  departure), so a line added after the flag is covered and an agency without a line sees nothing (card "Done when").
  `crm.calendar_feed` is new (not in the design ERD): one ICS subscription per member. The design's
  `calendar_connection` is the OAuth sync (Google / Graph through the agency's own account, errata S247) and stays for
  the BYO card; the ICS feed is its fallback the design names (§5.10 "fall back to an ICS link").
- **Writers in the database.** `crm.guard_incident_flag` (CRM41): only `job:` / `platform:` / `seed:` actors write an
  incident; a member never raises or clears one, and a raised row keeps its departure, code and event.
  `crm.guard_calendar_feed` (CRM42): a member creates only their own feed; only that member or an owner revokes it;
  token, member, scope and expiry are fixed (a new link is a new row); the public fetch (actor `calendar_feed:<id>`)
  changes only `last_fetched_at` / `fetch_count` of its own row.
- **Lookup policy** `calendar_feed_token_lookup` (SELECT only, keyed on `app.calendar_feed_hash`, live feeds only) is
  the `client_link_token_lookup` pattern; listed in `EXTRA_POLICIES` of the template test.
- **Erasure.** Neither table names a trip or a traveller, so only the agency scope of `crm.erase_subject` changes (the
  crm-026 text + `incident_flag` next to the Booking feed rows, `calendar_feed` before the members). Contract class
  (ADR 0017 §3: a replaced function), MIG-4 order.
- **Retention.** `crm.incident_flag` already has a DM-7 row ("until the agency deletes the trip or offboards"); the root
  PR moves it to its own row (ids and codes only, until offboarding: it is departure-scoped, not trip-scoped) and adds
  `crm.calendar_feed` to the agency configuration row.

## Changed

- crm-027 is numbered after crm-026 (merged as #137 while this lane ran); it starts from the crm-026 `erase_subject`
  text (Guard 0 checks the crm-026 keep-list names are in the live text).

## Tradeoffs

- No purge of cleared incident flags: a few rows per departure per agency, ids and codes only; a window can come with
  the lifecycle purge later without a schema change.
- No per-fetch audit event for the ICS feed (a subscribed calendar polls every few minutes to hours): the row's
  `last_fetched_at` / `fetch_count` show it is in use; creating and revoking a feed are audited by the API.
