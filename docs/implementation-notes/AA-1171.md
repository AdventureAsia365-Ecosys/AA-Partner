# AA-1171 — Alerts catalogue P0 (AA-Partner part)

Lane l12 of S287 (tech lead decisions D1, D3; root `docs/audits/2026-11-21-S287-alerting-inventory/README.md` §8).

## Decisions

- crm-085 seeds six CRM settings, area `ops`, single approval (like the other operational CRM values), today's code
  constants as defaults: `crm.ops.jobs_stuck_after_s` (900), `crm.ops.jobs_overdue_factor` (2),
  `crm.ops.audit_export_lag_min` (180), `crm.ops.audit_verify_lag_h` (50), `crm.ops.audit_partition_months_ahead` (1),
  `crm.ops.membership_feed_stuck_failures` (10). Read at every evaluation (`ps.get`), never copied into a constant.
- Shipped with its readers in one PR, like crm-082 and crm-084: the readers fall back to the compiled defaults, so the
  code deploying before Migration Apply registers crm-085 changes nothing, and readiness does not wait for it.
- `GET /crm/ops/v1/ops-checks` (crm.ops.v1 1.17, any full OPS reader) is the check registry the CIS alerts catalogue
  reads (the "ops check registry v1" shape Booking serves too). The new response keys are on the ops allow-list; the
  root contract gets the path and version 1.17 in the root PR of this lane.
- The last alert per check comes from the `crm_ops_alert` ledger rows (`queue.last_alerts`, the query lives in the job
  queue module per the code rule).

## Changed

- `kinds.overdue_after_seconds(kind, factor)`; `metrics.backlog_sample(..., overdue_factor=None)` reads the setting
  when no factor is passed. `membership_feed.STUCK_FAILURES` is gone (the other feeds' constants are untouched).
- The settings-lint baseline lost the removed constants; `MAX_PENDING` is marked a technical constant.

## Tradeoffs / not done

- Still code values, shown as such in the registry (`editable_via: none`): the 80 % AI spend warning (the shared AI
  core's `budget.threshold`, a vendored module) and the bulk reveal 60 per hour (it is also the access rate limit of
  `app.duty.service.HOURLY_LIMIT`; changing it is an access decision). Follow-up.
- The catalog / booking / entitlement sync `STUCK_FAILURES` constants raise no ops check e-mail; not in scope.

## Should know

- The CIS catalogue reads this route with the CIS staff token through `crm_console` (path `/ops-checks` allowed there).
