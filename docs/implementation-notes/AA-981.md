# AA-981 follow-up — full-history secret scan for AA-Partner

Follow-up of AA-981 (secret scanning guard for public repos), which added the full-history gitleaks job to the root
repo and AA-CIS-Infra and left the public app repos for later. This repo is public, so every commit, branch and pull
request head is readable. Session S248, agent Claude Code, lane `apps-secret-scan`.

## Decisions

- **Same workflow as the root repo and AA-CIS-Infra.** `.github/workflows/secret-scan.yml` is the root repo's file
  with `master` -> `main` and its own nightly minute: job **gitleaks** (every PR to `main`, lines the PR adds,
  `.gitleaks.toml` and `.gitleaksignore` read from the PR's base commit; a PR that changes either file fails until the
  label `secret-scan-baseline-reviewed` is on it) and job **gitleaks full history** (nightly, push to `main`,
  dispatch; every branch, tag and `refs/pull/*/head`, closed PRs included).
- **Same rules.** `.gitleaks.toml` is the root rules block byte for byte (default rules + `uri-embedded-credentials`,
  `terraform-plaintext-secret`, `credential-key-literal`, AWS network-ID and lock-file allowlists); only the header
  and `title` differ. A rule change lands in every repo that carries the file.
- **Pinned image, not the release tarball.** `ghcr.io/gitleaks/gitleaks:v8.28.0` with its digest, the image the root
  repo and Infra use, so one version runs everywhere.
- **Baseline by commit fingerprint** (`<commit>:<file>:<rule>:<line>`), grouped under one neutral comment per class.
  No value and no credential status in the file: this repo is public; triage lives in the private record (Linear
  AA-981).
- **CODEOWNERS** lists `/.gitleaks.toml` and `/.gitleaksignore`.
- **One scanner, one rule set.** The "Security Audit" job of `ci.yml` used to run gitleaks over the full history
  (shared rules, release tarball 8.30.1) with the PR's own ignore file. That step is removed; "Security Audit" keeps
  its name and its other steps (the required check name does not change) and no longer needs `fetch-depth: 0`. The PR
  gate is now the check **gitleaks**, which must be added to the required checks of `main` after merge (orchestrator
  step).

## Changed

- New `.github/workflows/secret-scan.yml`, `.gitleaksignore` baseline, `.gitleaks.toml` header (rules unchanged),
  CODEOWNERS entries.
- Docs that described the scan (README / CONTEXT / workflow comments) now point to `secret-scan.yml`.
- Not changed: the required check names, the other CI jobs, the deploy workflows.

## Tradeoffs

- **Full history on every PR vs base..head + nightly.** Security Audit scanned the whole history on every PR, with the
  shared rules. The PR job now scans only the PR's commits, with rules the PR cannot loosen; the history job covers
  everything else (including heads of closed PRs) nightly and on every push to `main`. A finding already in history no
  longer blocks unrelated PRs.
- **Pins vs allowlist entries.** Every historical finding is pinned by commit rather than widening the shared rules
  (for example a global `tests/` path allowlist), so the rule file stays identical across repos and a new value in the
  same file is still reported.
- **Label guard.** Anyone with write access can add the label; it makes a baseline change explicit (plus CODEOWNERS),
  it does not stop a determined writer.

## Should know

  here, header only) but no `.gitleaksignore`.
- Local scan used for the baseline: gitleaks 8.28.0 (same version as the image) over a `git clone --mirror` (branches,
  tags, `refs/pull/*/head`): 9 commits scanned, 2 PR heads, 0 findings (CI-only values carry `# gitleaks:allow`). 0
  findings with the new `.gitleaksignore`.
- After merge: create the label (if not yet), add **gitleaks** as a required check of `main`, run the canary procedure

- A lane branch or PR head with a secret-like value turns the nightly red even after the branch is deleted
  (`refs/pull/N/head` stays public): rotate if real, then pin the commit.

## Review round (S248, independent review of the app-repo port)

Four should-fix findings, applied to the app repos and, as a follow-up PR, to the root repo and AA-CIS-Infra:

- **Inline allow comments need the label.** An added line with an inline `gitleaks:allow` comment was hidden from
  both jobs with no label. The PR job now lists the files where the PR's commits add such a line (each commit's
  patch, merge commits as a dense combined diff; file names only) and treats it like a baseline change. Existing
  inline allows on the base branch are not affected. Chosen over `--ignore-gitleaks-allow` on the PR job: an
  approved inline allow survives the squash merge, a commit fingerprint does not.
- **The label goes stale.** The label was read from the PR on every event, so a push after the review could add
  a new ignore line and still pass. Now, when the PR has a baseline change and the label: on `synchronize` the job
  compares the previous head with the new one (blob of each file + new inline allows outside the base); on a
  change, an unknown previous head (force push), or `opened` / `reopened` with the label already on, it removes
  the label (job permission `pull-requests: write`, used only for that call) and fails. The reviewer reads the
  new change and adds the label again. Removing it (rather than only failing) keeps later runs honest: a run
  started by another label event would otherwise trust the old label.
- **Fingerprint formats documented.** gitleaks 8.28 git mode honours the global `<file>:<rule>:<line>` format
  for every commit (verified locally: a global entry suppressed a base..head finding). The `.gitleaksignore`
  header now says so, recommends commit pins, and explains that a commit pin does not survive the squash merge:
  prefer a narrow `.gitleaks.toml` allowlist, otherwise pin the PR commit in the PR and the squash commit in a
  follow-up PR.
- **Required check pinned to GitHub Actions.** The post-merge step uses `PATCH .../required_status_checks` with
  the full `checks` array plus `{"context": "gitleaks", "app_id": 15368}` (not the legacy `contexts` POST, which
  any status source could satisfy), run after the PR's own `gitleaks` check is green and before the merge, so
  there is no window without a required secret gate.

Tradeoffs: an update-branch merge that brings a baseline change from the base branch also drops the label (the
blob differs); rare, and the cost is one more review. A fork PR cannot remove the label (read-only token): the
run fails with an error asking a maintainer to remove it.

Known gap, not changed here (also in the root repo and Infra): gitleaks does not scan the content of merge
commits in `base..head` (verified: an evil merge adding a secret passes the PR job). The squash commit on the
default branch is scanned by the full-history job. Closing it in the PR job (`--diff-merges=first-parent`)
would also rescan the base-branch lines an update-branch merge brings in, and those are pinned by other commits.
