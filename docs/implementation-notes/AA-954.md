# AA-954 (CRM-24b) — Offline PWA

Card: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 CRM-24b (implements R16; checklist:
installable; **itinerary-only cache**; documents online only (Fix A2); clear on sign-out / expiry. **R:** a cache
inspection test finds no document, Stage 3 or F1 field. **E:** offline shows the last synced itinerary with "last
updated"), §2.4 C-09, §2.9 rule 7, WF-8 ("ITINERARY (works offline)", "DOCUMENTS (online only, mine)",
"[Email Minh]"). Builds on the AA-953 portal per person (`/c/t`, `components/portal/`).

Branch: AA-Partner `feat/s262-aa954-crm-offline-pwa` (API + web, one PR, no migration).

## Decisions

- **The page writes the copy, the service worker keeps only the shell.** The worker never sees an API response: the
  page builds the itinerary copy itself (`lib/offlineItinerary.ts`) and stores it in Cache Storage. A worker that
  cached API answers would have to filter JSON in a second place and could keep a document or a Stage 3 answer by
  mistake; this way the worker's whole data surface is `/c/t` (server-rendered, no traveller data: everything personal
  is fetched by the browser) and hashed `/_next/static/*` files.
- **Allow-list by copying named fields** (`offlineCopy`), with type checks, length caps and a 120-row cap; nothing is
  deleted from the home. A field the API adds later never reaches the device. The copy holds: trip title and dates,
  days (number, Before you go flag, date, title, place, zone and UTC offset), services (title, dates, status,
  pay-on-arrival; the confirmation class is dropped), agency name, agency contact e-mail, `saved_at`,
  `link_expires_at`, `offline_ref`.
- **Flights are not kept offline.** The card lists "days, times, places and the agency contact"; flight numbers are
  vault-encrypted travel PII (`traveler_flight.flight_no_enc`) and the traveller has them in their own booking.
  Revisit only if the business owner asks.
- **Agency contact = the agency mailbox the portal mails come from** (trip owner's own, else the agency's; same order
  as the code mails). `crm.member` holds no name, e-mail or phone (identity is Cognito), and the WhatsApp channel has
  no number on file yet, so the e-mail is the only contact the CRM can give today. `null` without a mailbox.
- **`offline_ref`** (API): `sha256("aa-crm-portal-offline-ref:" + sha256(token))[:32]`, in both home answers. It lets
  the page tell whether a stored copy belongs to the link the browser now holds without exposing the token, the stored
  hash or an internal id. A signed-out answer for **another** link clears the copy (another traveller's or another
  agency's link on a shared device: one client host serves every agency).
- **Clear rules.** Card: "cleared at sign-out and when the link expires". Implemented: sign-out (the page deletes every
  `aa-portal-*` cache and tells the worker), 404 from the API (expired, revoked or re-issued link, closed trip), a copy
  past `link_expires_at` (checked offline too, so expiry works without a network), another link's signed-out answer,
  and "Remove from this device" on the offline view. A 12-hour portal session that simply ran out does **not** clear
  the copy (the card ties it to the link, and a traveller on a multi-day trek would otherwise lose it).
- **Sign-out clears the device whatever the server answers** (review fix pass). The page drops every `aa-portal-*`
  cache and tells the worker *before* the POST, and again after it, so offline, 429, 5xx and a 404 for a revoked link
  leave nothing either (the server session of a failed POST stays; the next signed-in answer stores a copy again,
  which matches what the person then sees). A counter bumped by every clear guards each load: an answer whose request
  started before a clear neither stores the copy nor asks for the shell, and a write that raced the clear is cleared
  again (the clear always wins).
- **The worker runs messages one at a time** (a promise chain): a `clear` that arrives while a `precache` is still
  fetching runs after it, so the shell cannot be written back after sign-out. The page side also drops a precache
  message that is still waiting for the worker when a clear comes.
- **Conflicts: server wins, no background sync.** The copy is read-only: nothing is written offline, so there is
  nothing to merge. Every signed-in answer replaces the copy (also after "Switch" to another person of the group); the
  `online` event reloads the home. Writes offline fail at once with "You are offline" (status 0).
- **Scope `/c/t`, script at `/c/sw.js`.** A worker's maximum scope is its own directory, and `/c/t/` would not cover
  `/c/t` itself; serving from `/c/` avoids a `Service-Worker-Allowed` header. Inside the scope the worker handles only
  a navigation to exactly `/c/t` (no query) and `/_next/static/*`; the link landing `/c/t/<token>` and everything else
  go to the network untouched.
- **Shell precache from the page, once per load.** On a signed-in load the page sends `/c/t` plus the static files it
  loaded (resource timing); the worker re-checks every URL (same origin, `/c/t` or `/_next/static/*`, no `..`), needs
  `/c/t` to be a `text/html` 200 basic response, and replaces the shell cache as a whole, so old deploys' chunks never
  pile up. `activate` drops older-version `aa-portal-*` caches.
- **Manifest**: generic name ("My trip" / "Chuyến đi của tôi" via `?lang=vi`, because a manifest is fetched without
  cookies), the CRM web's own mark as icons (the same mark as `app/icon.svg`; the client pages already show the
  "Adventure Asia Partner" header). Agency-branded install names would need a per-agency manifest URL; not in v1.
- **Icons are static PNGs** generated by `tools/pwa/pwa_icons.py` (pure Python, no image library; reproducible
  byte for byte) instead of an `ImageResponse` route.

## Changed

- API: `ClientLink.expires_at` (the `client_link_tx` lock query already selected it); `portal.home` adds
  `offline_ref` (both answers), `link_expires_at` and `agency_contact` (signed in). No new route, no migration.
- Web: `/c/sw.js`, `/c/portal.webmanifest` route handlers; `/c/t` metadata (manifest, theme colour, iOS meta,
  apple-touch icon); `PortalPage` gets `offline` (only `/c/t` sets it): registers the worker, keeps / clears the copy,
  shows `OfflineView` when the network fails, the offline banner, the install prompt, the "works offline" note; the
  `client.offline.*`, `client.install.*`, `client.manifest.*`, `client.error.offline` strings (EN + VI,
  `lib/i18nOffline.ts`).
- E2E: `lifecycle-thin.spec.ts` step 6b (manifest link, both caches, no Stage 3 value in the kept copy, offline reload
  shows the copy, back online, sign-out empties every portal cache).

## Tradeoffs

- Cache Storage over IndexedDB / localStorage: it is what a cache inspection (card R) looks at, the worker and the page
  share it, and one JSON entry is all that is needed.
- Keeping the copy through an expired session (until sign-out / link expiry) is weaker than clearing on every
  signed-out answer, but matches the card and the trek use case; another link's answer, a gone link and expiry still
  clear it.
- No push, no background sync (card: "No push notifications in v1"; nothing to sync).
- Google Fonts are not cached (another origin); offline pages fall back to system fonts.

## Should know

- Card R is `web/tests/offlinePwa.test.ts` "a cache inspection finds only the itinerary": a home with a sentinel in
  every non-itinerary field (Stage 3, waiver, envelope, document, flight, names, payments, a future F1 field), then
  every cache entry is read back as text. The worker is tested by running its source in a fake worker scope.
- A real Chromium run against a local `next start` (client host, API answers stubbed) showed: the worker active at
  `/c/sw.js`, the shell + data caches, the offline reload with "last updated", back online replacing the copy, sign-out
  leaving no cache, and the worker's offline page after sign-out. Screenshots were taken locally, not committed.
- `beforeinstallprompt` only fires in Chromium on a real HTTPS host with the manifest + worker; headless runs never
  show the button, so the install prompt is checked on Dev by hand (Chrome on Android or desktop, or DevTools >
  Application > Manifest "Installability").
- Sign-out races are covered in `web/tests/offlinePwa.test.ts`: a precache with slow fetches then a clear (worker),
  sign-out with no answer / 429 / 500 / 404, a load answered (signed in) only after sign-out, and `settle` with a clear
  landing mid-write.
- Service workers need a secure context: the Dev client host is HTTPS; on plain http the page works online only.
- Dev E2E fixes found by the live check (no product change): `client-proposal.spec.ts` step 9 now waits for the held AA
  line the accept's Booking sync writes, asserts the trash's 409 `has_aa_line` / `cancel_trip`, and marks the trip Lost
  (still at Proposal, so the cancel flow, booked onward, does not apply); `slice2-m1m2.spec.ts` proves a settings save
  by the PUT 200 and the values after a reload, the transient "Saved" marker being lost when a web deploy rolls.
