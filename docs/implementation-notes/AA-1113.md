# AA-1113 — CRM slice: every CRM AI call through the CRM gateway, its ledger and its caps

Lane l13 of S283 (Claude Code). Issue scope this slice covers: "CRM AI calls go through the gateway ledger and the
connection caps" (S282 audit R28, G12). The CIS half of the issue (the F3 scrub in the shared CIS gateway, the over-cap
flag in `catalog.v_llm_gateway_config_v1`, the acc3 budget) is other lanes; root ADR 0009 decision 10 was accepted by the
tech lead in S283.

## Decisions

- **The premise "direct CRM AI calls remain" does not hold.** A full read of `api/app` and `api/scripts` (17/11/2026)
  finds exactly three model call sites, `agency_ai.draft` (`crm_draft_reply`), `supplier_confirm.run`
  (`crm_supplier_confirm`) and `notes_options.run` (`crm_notes_options`), and all three call
  `app.state.llm_gateway.call(...)`: the CRM's own gateway (`app/llm/gateway.py`). That gateway already writes one
  `crm.llm_call` row per attempt (refused and failed included, 0 USD for a refusal), keeps the `crm.llm_usage_daily`
  rollup, applies the per-agency rate cap, the stage kill switch, the app profile (AI switch and the CRM's daily
  budget), the agency's monthly budget and its ceiling, and runs the F3 scrub before any call (fail closed). The only
  other Bedrock call, `ApplyGuardrail`, is the scrub's pass 3 and is written as its own guard row. Nothing calls the
  CIS gateway: the CIS clients in `app/cis/` read tenants, members and add-ons only. The raw-SDK guard
  `tests/unit/test_gateway_bypass.py` (AA-642 L6) already fails on any boto3 Bedrock runtime method, vendor SDK import
  or vendor host outside the two provider adapters.
- **So the slice is guards and proof, not rerouting.** What the raw-SDK guard did not catch is a bypass one level up:
  a module that builds or reaches the gateway's own provider or scrubber (`BedrockConverseProvider(...)`,
  `StubProvider(...)`, `app.state.llm_gateway.provider.complete(...)`, `build_scrubber(...)`, `scrubber.scrub(...)`,
  `stage_caps.complete(...)`) would call a model with no ledger row, no budget and no scrub, without touching boto3.
  `tests/unit/test_aa1113_gateway_wrapper.py` closes that: outside the wrapper modules, no import of
  `app.llm.providers` / `app.llm.stage_caps`, no construction of a provider, scrubber, detector or gateway, no
  `.scrub(` call, no read of a gateway's private parts (`.provider`, `.scrubber`, `._attempts`, ...), and no outbound
  client module (the ones that import an HTTP transport) names an AI path of another app (`/llm`, `/ai/`, `/gateway`,
  `/completions`, `/converse`, `/generate`, `/embed`). Same ratchet as the raw-SDK guard: an allow-list entry whose
  file no longer has a hit fails.
- **Proof per path with a fake provider.** `tests/unit/test_aa1113_ai_paths_ledger.py` runs each of the three services
  through the real `LlmGateway` with the real F3 `PiiScrubber` (a detector that finds nothing, so passes 1-2 do the
  work) and a fake provider that records what it is sent: a planted e-mail and phone never reach the provider; an ok
  call writes one ledger row and one rollup; a used-up agency budget, a reached CRM daily cap and a failed scrub each
  write one 0 USD refused row and never call the provider; a provider error writes one error row and the result falls
  back to "reply by hand".

## Changed

- `api/tests/unit/test_aa1113_gateway_wrapper.py` (new): the wrapper guard and its detector tests.
- `api/tests/unit/test_aa1113_ai_paths_ledger.py` (new): the three AI paths through the real gateway.
- No application code changed and no migration: every path already goes through the gateway.

## Tradeoffs

- **Connection caps are not enforced in the CRM by this slice.** A connection cap is a CIS value
  (`shared.llm_provider_connection.monthly_budget_usd` + `shared.llm_connection_cost_policy.hard_stop`), summed by the
  CIS gateway over `shared.llm_call_log` only. The CRM cannot read either (root ADR 0008a: the CRM reads no
  `shared.llm_*` table, and `crm_app` has no grant on them), and CIS cannot read `crm.llm_call` (it reads the CRM's
  usage over `GET /crm/ops/v1/llm/usage`). Making the CRM count and stop needs a cross-repo change; three ways, for the
  tech lead (none needs a paid call):
  1. **CIS adds, CRM obeys (preferred).** CIS adds the CRM's month-to-date spend (the `/llm/usage` read it already
     makes) to the connection the CRM uses, and relays a hard stop through the existing app-profile write
     (`PUT /crm/ops/v1/llm/app-profile`, `ai_enabled=false` with a reason): the CRM then refuses `app_disabled` with a
     0 USD row on every call, no CRM migration. A distinct CRM refusal code for it (e.g. `connection_budget_exhausted`)
     would need a new app-profile column (crm-076, contract) and is optional.
  2. **The over-cap flag through the view.** The CIS over-cap flag planned for `catalog.v_llm_gateway_config_v1` (for
     TripPlanner) is granted to `crm_app` as well, and the CRM gateway reads its connection's flag before a call (fail
     closed). Needs the CIS view migration plus a grant, and a CRM connection key that matches the CIS registry (today
     the CRM rows say `bedrock` / `bedrock_role`, the CIS registry says `acc2` / `acc1` / `acc3`).
  3. **A CRM-side cap of its own.** A setting `crm.ai.connection_monthly_cap_usd` (crm-076 seed, contract) checked
     against the CRM's month spend: counts only the CRM's own share, not the connection's total, so it does not meet
     the issue's "one cap for every caller".
- Today the gap is small: the CRM's only live route is Amazon Nova Lite on acc2 (root ADR 0009 amendment S265, Dev
  only), and the acc2 connection has no monthly cap in the CIS registry; the ADR already says the CRM's acc3 entries
  stay off until its spend counts toward the connection caps.
- **Follow-up owner (review of this slice, S283).** This PR is the CRM proof-and-guard part of AA-1113 only; it does
  not close the issue's connection-cap item ("CRM calls show in the ledger with caps applied"). Option 1 above is the
  recommended path and is handed to the CIS gateway / over-cap-flag lane of AA-1113 (AA-CIS-App: count the CRM's
  month-to-date spend from `GET /crm/ops/v1/llm/usage` toward the connection's monthly cap, and relay a hard stop
  through `PUT /crm/ops/v1/llm/app-profile` with `ai_enabled=false`; no CRM migration). If the tech lead picks option 2
  or 3 instead, that choice is recorded here and on the issue. AA-1113 stays open until that part ships and is verified
  live; this slice alone does not move it to Done.

## Should know

- The guard counts names, not types: a module that imports `LlmGateway` for a type hint is fine; calling
  `LlmGateway(...)` is not (only `app/llm/gateway.py` builds one, `app/main.py` calls `build_gateway`).
- Tests use invented names and addresses only; no AWS, no paid call (the provider is a fake, the scrubber's detector a
  stub).

## Lane l7 of S284 — the CRM under the connection caps (option 2 above, through a CIS contract view)

### Decisions

- **Option 2, not option 1.** Option 1 (CIS counts the CRM's month from `GET /crm/ops/v1/llm/usage` and relays a stop
  through the app profile) needs an M2M client: CIS reaches crm.ops.v1 only with the staff member's own token today, so
  a background count could not run (new Cognito client, Terraform, CRM scope). Option 2 needs one CIS migration (CIS
  450, `catalog.v_llm_connection_cap_v1`, SELECT to `crm_app`) and this code, no CRM migration.
- **The CRM adds its own spend.** The view sums the CIS ledger (CIS + TripPlanner rows); the CRM adds its month of
  `crm.llm_usage_daily` (no RLS, every agency, guardrail rows included) since the view's `month_start`. Every CRM call
  of a process runs on its one provider connection, so the whole rollup is that connection's CRM share.
- **Spend rules per environment** (`crm.spend.environment`, crm-076): dev refuses `connection_budget_exhausted` at the
  cap and `spend_unreadable` on a read error; prod never refuses for the cap (tech lead S283: a connection cap alerts
  and fails over, it never stops a customer call) and logs `crm_llm_connection_cap_reached`. A missing view or a
  missing grant (CIS 450 not applied) goes on with one warning: no cap is published yet.
- **Connection names.** `bedrock` (the ECS task role's own Bedrock) maps to CIS `acc2`; `bedrock_role` has no mapping
  (its account depends on the role ARN in the environment), so no cap is read for it and the process logs it once.
  Root ADR 0009 already keeps the CRM's acc1 / acc3 routes off until their spend counts toward the caps: naming that
  mapping (a setting, crm migration) comes with the route that needs it.
- **Gateway size.** `gateway.py` is at its code-health size and `LlmGateway.call` at its complexity baseline: the call
  site changed one line (`app_profile.then_connection_cap(await self._app_refusal(ctx), ctx.conn, first)`), the rule
  lives in its own module; `app_profile` hosts the one-line chaining so the gateway's imports stay as they are (the
  open AA-1126 Partner PR edits the gateway's import line and `_app_refusal`; this keeps the two PRs apart).

### Changed

- `api/app/llm/connection_cap.py` (new), `api/app/llm/app_profile.py` (`then_connection_cap`),
  `api/app/llm/gateway.py` (the call site), `api/tests/unit/test_code_rules.py` (the module is a DB module: platform
  reads on the call's connection, like `app_profile.py`).
- Tests: `api/tests/unit/test_aa1113_connection_cap.py` (the rule, both spend rules, read errors, unmapped providers,
  the three AI paths through the real gateway), `api/tests/integration/test_aa1113_connection_cap_db.py` (as
  `crm_app` in `tenant_tx`, a stand-in table of the contract's columns).
- `CONTEXT.md`: the "Connection cap" bullet.

### Tradeoffs

- CIS does not count the CRM's spend (it cannot read `crm.llm_call`): the CRM stops at the shared total, CIS may pass
  the cap by at most the CRM's share. Today the CRM's only route is acc2, which has no monthly budget row on Dev, so
  the check reads one row-less query per call.
- The web shows the generic "write it by hand" line for `connection_budget_exhausted` (`aiDraft.fallbackKey` falls
  back); a dedicated line belongs with the AA-1126 / plan-quota UI work, which edits the same file.

### Should know

- Order: CIS 450 applied first (migration-only PR), then this PR (it also works before: the view is missing, the call
  goes on).
- Live check: the CRM ledger rows of the three AI stages carry their caps (agency budget, app profile) as before; with
  a Dev connection budget set on `acc2` below its month spend, a draft is refused `connection_budget_exhausted` with a
