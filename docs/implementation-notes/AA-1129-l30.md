# AA-1129 lane l30: the portal smoke's Activity pager case after the studio words its own action labels

Hotfix for the post-deploy UI smoke of Deploy Web Dev, red since 19/11 01:14Z on one case:
`e2e/smoke-portal/aa761-account-pages.spec.ts` "Activity: the pager asks the server for the next page" (68 of 69 passed).
Deploy and the post-deploy verify were green; the web was live.

## Decisions

- **The page changed on purpose; the spec follows it.** Lane l2 PR 1 of this issue (P3, activity labels in the page
  language) made the Activity column show `activityLabel(action, label, lang)`: an action the studio words itself
  (`tenant.login` -> "Signed in") ignores the label the server sends. The mocked pager rows carried their page number
  in the label (`Signed in (page n)`), so the page showed "Signed in" on every row and the spec never found
  "Signed in (page 1)". The failure screenshot of run 44544289251 shows exactly that: mocked rows, "Signed in" over
  "Content studio".
- **The page marker moved to the detail line.** `activityDetail` passes a non-download detail through unchanged, so
  the mocked rows now read `Content studio (page n)`; the rows keep the real action (`tenant.login`) and the real label.
  The spec still asserts the same thing: page 1 is shown, the pager's next button asks the API for page 2, page 2 rows
  are shown, and `page=2` was requested.
- **The next button is found by its name.** The kit pager's icon buttons have had `aria-label` "Next page" /
  "Previous page"; the spec clicks `getByRole('button', { name: 'Next page' })` instead of the sibling XPath, and
  checks the "Page 1 / 3" -> "Page 2 / 3" label around it.

## Changed

- `e2e/smoke-portal/aa761-account-pages.spec.ts`: mocked rows, the pager click, two label assertions, header comment.
- `web/tests/studio/account.test.ts`: one unit test pinning the rule the smoke relies on (a known action ignores the
  server label; its detail is shown as sent).

## Tradeoffs

- Using an action the studio does not word (so the server label would show) would also have worked, but it would mock
  a row shape the API never sends. Keeping `tenant.login` and varying the detail stays close to real data.

## Should know

- The portal smoke runs only after Deploy Web Dev (it needs the deployed agency host and the e2e studio sign-in), so a
  web change to visible text is not caught before merge. Before changing a label or a formatter on a studio page, grep
  `e2e/smoke-portal/` for the old text.
- No local live run: the logged-in smoke needs the e2e studio user's partner sign-in (repository secrets). Checked:
  e2e `tsc --noEmit` (the workflow's Type check step), the unit tests near the page, the failure artifact.
