# AA-934 — CRM-06 KeyProvider and field encryption

Card: design v3 §6.3 CRM-06 (`AA-Ecosys/docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md`), the lane text
`lanes/data-privacy-integrations.md` §2.1–2.3 and §5.1–5.2, the S247 errata (BYO integrations) row CRM-06.
Checklist: DEK per tenant per purpose; AES-GCM with AAD; HKDF blind index; vault columns; rewrap contract test.
R: decrypting with another tenant's context fails and is audited `denied`. E: DEK cache expiry mid-request
re-unwraps transparently. Done when (delivery plan): a DB dump of the vault shows ciphertext only.

## Decisions

- **Migration key `crm-003`, not `crm-002`.** The card was written when the vault was planned as the second file;
  `crm-002` became the tenancy base (AA-933). The vault columns land in `crm-003`.
- **Tables in `crm-003`:** `crm.tenant_key` (DEK store on Dev), `crm.integration_credential` (errata S247: wider
  provider list + wizard health columns), `crm.traveler` (the F1 identity vault columns of lane §2.3, so CRM-08 only
  writes rows) and `crm.audit_event` (append-only; needed for the R test "audited `denied`").
  `traveler_health`, `traveler_flight`, `document`, `consent` stay with CRM-09 (AA-937).
- **`crm.audit_event` is not partitioned yet.** CRM-12 (AA-940) owns the F5 audit (monthly partitions, hourly Object
  Lock export, hash chain, audit page). Partitions need a maintenance job and per-partition RLS, which is CRM-12's
  design; on Dev (synthetic agencies only) converting the table later is a cheap copy. This card ships the columns
  of lane §2.11 plus `outcome allowed|denied`, INSERT/SELECT only for `crm_app`, a trigger refusing UPDATE, DELETE
  and TRUNCATE, codes only (no free text, no personal data).
- **Denials survive the request's rollback.** `tenant_tx()` now runs the route's work in a savepoint. Audit events
  are queued on the context (`ctx.audit(...)`) and written at the end: all of them when the block succeeds; only the
  `denied` ones when it raises (the work is rolled back to the savepoint, the denials are inserted, the transaction
  commits, the original exception is re-raised). So a decrypt denial is recorded even when it ends the request.
- **Ciphertext format** (design §3.2): `key_version (2 bytes, big endian) ‖ nonce (12) ‖ ciphertext ‖ tag (16)`,
  AES-256-GCM from `cryptography`. AAD = `crm.v1 ‖ tenant_id ‖ table ‖ column ‖ row_id ‖ key_version header`
  (components joined with U+001F after validation), so a value cannot move between tenants, tables, columns, rows or
  key versions, and the header cannot be edited.
- **KEK wrappers behind one interface.** `KmsKeyWrapper` (alias `alias/crm-<env>/data`, `GenerateDataKey` /
  `Decrypt` / `Encrypt` with the encryption context `{tenant_id, purpose}`, exactly what the AA-932 key policy
  allows) and `LocalKeyWrapper` (AES-GCM keyring, context as AAD) for tests and local runs only: settings refuse
  `KEY_PROVIDER=local` outside `test` / `local`.
- **The row stores the KEK it was wrapped under** (`kek_provider`, `kek_id` = the KMS key ARN KMS returns), so a
  rewrap can move DEKs between KEKs (BYOK later) and old rows still unwrap.
- **Rotation path.** Three layers: (1) the KMS key rotates automatically (AA-932, transparent to wrapped DEKs);
  (2) `KeyProvider.rewrap(ctx, target)` re-wraps every live DEK of the tenant under another KEK without touching
  any ciphertext (the contract test, BYOK path); (3) `KeyProvider.rotate(ctx, purpose)` retires the current DEK and
  creates version n+1: new values use n+1, older values still decrypt (the version is in the header).
- **Blind indexes stay valid across DEK rotation.** The index key derives from the tenant's *index root*: the oldest
  live `vault` DEK (lane §5.2 `HKDF-SHA256(DEK_vault, salt = tenant_id, info = "bidx:" ‖ column)`). Rotation keeps
  old versions (they decrypt old rows), so the root never changes and no re-index job is needed. Destroying a single
  old version is not offered (only `destroy(tenant)` at offboarding).
- **Index sizes:** email and phone 16 bytes, full normalised name 8 bytes (est.; exact dedupe but less linkable than
  16), name tokens 4 bytes (design: deliberately lossy).
- **Normalisation:** email trim + lowercase (must contain one `@`); phone to E.164 with `phonenumberslite`
  (libphonenumber metadata without geocoder/carrier data; default region optional, unknown region = must start
  with `+`); names NFKD, combining marks removed, `đ/Đ` mapped to `d` (no Unicode decomposition), casefold, split on
  anything that is not a letter or digit.
- **Process cache** of unwrapped DEKs, TTL `DEK_CACHE_TTL_SECONDS` (default 300, design "about 5 minutes"). A DEK
  provisioned or rotated inside a transaction is kept only in that transaction's memo, never in the process cache:
  if the transaction rolls back, no other request can encrypt under a key that was never stored.
- **Generic decrypt cannot open integration secrets.** `Vault.decrypt()` refuses purpose `integration`;
  `Vault.decrypt_secret()` is the only path, and a lint (`tests/unit/test_vault_rules.py`) allows its call sites only
  in `app/integrations/dispatch*`, `app/integrations/webhook*` and `app/integrations/health*` (errata S247). A second
  lint fails when a route response model has a field named `*_enc`, `*_bidx`, `secret*` or `wrapped_dek`.
- **Live self-test** without touching tenant data: `python -m app.vault.selftest` (KMS round trip under the nil
  tenant context, prints a JSON verdict) for the Dev live check through ECS Exec.
- **Readiness reports the key provider** (`keys: kms|local|not_configured`) but does not fail on it, so a missing
  env value shows in the smoke output without blocking liveness.

- **KMS `AccessDeniedException` and `InvalidKeyUsageException` are 503 `KeyUnavailable`, not denials** (review
  round 1). A wrong `tenant_id` context gives `InvalidCiphertextException`, and the purpose is checked in the app
  before KMS is called, so those two codes mean an IAM or key-policy misconfiguration. Classing them as denials would
  answer every decrypt with 403 and write a false `denied` audit row. Denials stay `InvalidCiphertextException`,
  `IncorrectKeyException` and a bad local tag.
- **`UnwrapDenied` leaves `KeyProvider` only through `get_dek`** (review round 1). `current_dek`, `index_root`,
  `rotate` and `rewrap` turn a refused unwrap of the tenant's own key row into `KeyUnavailable("key_unwrap_refused")`
  (503). Before, a tampered `wrapped_dek` row or a KMS refusal on the encrypt / blind-index path reached the
  unhandled-error handler as a 500. The read path keeps the audited `DecryptionDenied`.
- **The KMS client is built once per wrapper under a `threading.Lock`, from a dedicated `boto3.session.Session`.**
  The first calls after a deploy run in parallel `asyncio.to_thread` workers, and the default boto3 session is not
  thread-safe.
- **Table names in the field AAD are capped at 40 characters**, the same limit as the audit `object_kind` code
  (`app/audit.py`, CHECK `audit_event_object_kind_chk`), so `Vault._deny` can always record its row. Column names stay
  at 63.
- **After `destroy()`, a new value raises `KeyDestroyed`** instead of `KeyUnavailable("key_race")`: when the v1 insert
  conflicts and there is no current key, `_provision` looks at the stored v1 row and reports the shred.
- **`tenant_key_guard` also fixes `kek_provider` / `kek_id`**: the wrapping triple (`wrapped_dek`, `kek_provider`,
  `kek_id`) changes only together with `rewrapped_at`, and a destroyed row never gets a wrapped DEK back.

  the per-transaction DEK memo. The DB access lint allows `app/vault/store.py` (the DEK store) next to the existing
  DB modules.
- `REQUIRED_SCHEMA_VERSIONS` adds `crm-003`: readiness is 503 until DB Migrate applies it.
- New pinned dependency `phonenumberslite`.
- AA-CIS-Infra (separate PR): the task role gets `kms:GenerateDataKey`, `kms:Decrypt`, `kms:Encrypt` on the data
  key with the same context conditions as the key policy; the task definition gets `KEY_PROVIDER=kms` and
  `KMS_DATA_KEY_ID=alias/crm-<env>/data`; the byte copy `db/migrations/crm/003_crm_vault_keys.sql`.
- AA-Ecosys root (separate PR): the `crm` row of `docs/database/schema-ownership.md` names the crm-003 tables. The data
  standards §7 retention rows for all four tables already existed (v1.3, AA-929), so the Infra retention-row check
  passes without a registry change.

## Tradeoffs

- **Audit of allowed decrypts is not done here.** The vault audits denials only; field reveals and the single
  `list_view` event per page are CRM-09 / CRM-12 (design §4.4), so list views do not flood the audit.
- **No `ReEncrypt`.** Rewrap unwraps and wraps in the process (the DEK is in memory anyway when used), so the task
  role needs no `kms:ReEncrypt*` and one code path serves local → KMS and KMS → KMS.
- **Stale current-version cache across tasks.** After a rotation another task may encrypt with the previous version
  for up to the TTL; harmless (the old version stays valid until the tenant is destroyed).
- **Python cannot zero memory.** Unwrapped DEKs live in `bytes` until garbage-collected; repr never prints them and
  they never reach logs, jobs or Sentry.

- **Crypto-shred is immediate only in the process that runs `destroy()`.** It evicts the local cache; other API and
  worker tasks may keep serving the unwrapped DEK for up to `DEK_CACHE_TTL_SECONDS` (300 s). Acceptable on Dev with
  synthetic agencies. CRM-35 (offboarding) must wait out the TTL before it reports the tenant shredded, or make the
  processes re-check `destroyed_at` (for example a short-TTL "tenant destroyed" check before each cache hit).
- **No `(tenant_id, name_token_bidx)` GIN index yet.** `traveler_name_token_bidx_idx` is on `name_token_bidx` alone;
  RLS filters rows correctly, but at scale a 4-byte token lookup scans candidates of every tenant. CRM-08 (search)
  should switch to `btree_gin` on `(tenant_id, name_token_bidx)` when it adds the query (the extension needs a
  master-level `CREATE EXTENSION` in its migration).

## Should know

- **Apply order on Dev:** Infra PR (IAM + env) apply → DB Migrate `crm/003_crm_vault_keys.sql` (check → apply) →
  merge the `bot/db-schema-reference` PR → deploy AA-Partner (readiness needs `crm-003`). The Infra copy can only go
  green after this repo's PR is merged (Migration Copy Guard compares with `main`).
- Live check: `/crm/health/ready` 200 with `schema_version` `crm-003` and `keys` `kms`; ECS Exec
  `python -m app.vault.selftest` prints `"ok": true`.
- `crm.tenant_key` rows are never deleted while live: a DELETE is refused unless the row was destroyed first
  (`destroy(tenant)` nulls `wrapped_dek` and sets `destroyed_at`); offboarding (CRM-35) then deletes the rows.
- A request cancelled mid-flight (`asyncio.CancelledError`, not an `Exception`) rolls back everything, queued
  denials included; only exceptions take the "commit the denials" path.
- Verified locally on PostgreSQL 16 (initdb in a scratch dir, the RDS role shape from `bootstrap_roles`): unit 335
  passed after review round 1 (coverage 96.8 %), integration 38 passed; a mutation that drops the "commit the denials" branch fails three
  tests. CI runs PostgreSQL 15.
- The nil tenant id `00000000-0000-0000-0000-000000000000` is reserved for the self-test context; `crm.tenant` rows
  are random UUIDs.
- **Offboarding and audit retention need a path (CRM-12 / AA-940 and CRM-35 / AA-967 scope).** `crm.audit_event`
  references `crm.tenant` with no `ON DELETE` action, and its trigger refuses DELETE / TRUNCATE even for `crm_owner`.
  Data standards §7 says offboarding hard-deletes `crm.tenant` and audit partitions are dropped after export. CRM-12
  converts the table to monthly partitions (dropping a partition is the retention path) and must decide the FK: drop
  it, or keep it and let CRM-35 run after the tenant's partitions are exported and dropped.
- **Migration key collision with AA-935.** The AA-935 lane also drafted a `crm-003` file. This PR keeps `crm-003`
  (free on `origin/main` of AA-Partner and AA-CIS-Infra when written); whichever lane merges second moves to `crm-004`
  (Partner file, Infra copy and `REQUIRED_SCHEMA_VERSIONS`) and rebases onto the `tenant_tx()` savepoint and audit code.
- Rewrap contract coverage: the unit cases run local → local (new KEK), local → KMS and KMS → KMS (BYOK key) through
  `FakeKms`; the integration test runs local → local on the real `crm.tenant_key`. Card R also runs under the KMS
  wrapper (`test_under_kms_another_tenants_value_and_a_copied_key_row_are_denied_and_audited`).
