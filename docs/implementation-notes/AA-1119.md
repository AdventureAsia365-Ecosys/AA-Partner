# AA-1119 — Release safety (AA-Partner part)

Whole picture, decisions and merge order: root `docs/implementation-notes/AA-1119.md` (S291, lane e-release-safety;
S282 audit R31, R32, R40).

## Decisions

- **Rollback after a red post-deploy check** (`deploy-web-dev.yml`): the deploy job records the revision the service runs before
  `update-service` (`ecs_smoke_rollback.py previous`); when `verify` or `smoke` fails on main after a successful deploy, job
  `rollback` moves the service back to it (`ecs_smoke_rollback.py rollback --apply`), refusing and changing nothing when
  the target is unknown or unsafe; job `report` opens or comments on the `deploy-smoke-red` issue and closes it on the
  next verified deploy. `result` is unchanged: the run stays red.
- `.github/scripts/ecs_smoke_rollback.py` and its test are byte copies of the same files in AA-CIS-App, AA-Booking,
  AA-Partner and AA-TripPlanner-Web: change them in all four in one wave.
- The web workflow names no container (one per family), so the script runs without `--container` and
  requires exactly one container definition. `test_post_deploy_verify_web_portal.py` now expects the two new jobs and
  allows exactly two `$GITHUB_OUTPUT` writes (the rollback target and the outcome; AA-993's rule against skip outputs
  stays).
- **CRM API Sentry test event**: Sentry was already wired (AA-CIS-Infra `crm_sentry_enabled = true`, secret
  `crm/dev/sentry-dsn`, AA-1111). `python -m app.observability.sentry_test_event` (container `api`) sends one
  `warning` tagged `test_event=aa-1119` through `init_sentry` (same options and scrubbers, tag `service=sentry-test`),
  flushes and prints the event id, environment and release; exit 1 when Sentry is off or the SDK dropped the event,
  2 when the settings do not load. No new secret, no new setting.
- Workflow Lint runs the script's unit tests (paths and run step).

## Tradeoffs

- A flaky post-deploy check now rolls back a good build; the next deploy of main brings it back and the issue records
  it. Accepted by the audit (R32).

## Should know

- The rollback job uses the deploy job's OIDC role and only calls it already makes (describe, ECR describe-images,
  update-service, wait); no IAM change.
