# AA-969 part 2 (lane l1-aa969-d16): the ADR 0019 d16 pilot protections in AA-Partner

Scope of this lane in AA-Partner: items (3) to (5) of the S265 re-scope comment on AA-969 for the CRM: clean-up skips
the pilot agency, a nightly per-agency export of the pilot agency through `crm.export_job`, and a one-agency restore
drill. Items (1) (Dev refuses real tenants except the pilot) and (2) (the PII read guard) live in CIS and in the root
repo / AA-CIS-Infra.

## Decisions

- **Where the CRM learns the pilot.** CIS holds the marker (`shared.tenants.is_pilot`, CIS 354) and already serves it
  on the account snapshot of `tenant.entitlements.v1` (`is_pilot`). `crm_entitlement_pull` reads that snapshot, so it
  projects the marker onto a new column `crm.tenant.is_pilot` (crm-044). No cross-schema read of `shared.tenants`
  (ADR 0008a), no environment variable that could drift from CIS.
- **Only the account feed writes the marker** (`crm.guard_pilot_marker`, CRM04 `platform_only`): not the L1 console,
  not a seeder, not a job. Otherwise a script could shelter a test agency from clean-up, or clear the marker to expose
  the pilot. An unscoped owner session (DB Migrate) is allowed, like the crm-008 guard.
- **One pilot at most** (`tenant_one_pilot_uq`), as CIS `tenants_one_pilot_key`. When CIS moves the pilot from one agency
  to another, the projection of the new one may hit the index before the old one is cleared: that agency is counted
  `rejected` and the next pass (2 minutes, or the hourly reconcile) converges.
- **The nightly backup is a scheduled kind that only queues** (`crm_pilot_backup`, due-now daily hook at
  `JOB_RETENTION_UTC_HOUR`): it inserts one `crm.export_job` row (scope `tenant`) and queues the existing
  `crm_data_export` job, so the ZIP, the seal under the agency `export` DEK, the object path
  `exports/tenants/<tenant>/portability/<export>.zip.enc` and the 7-day bucket rule are exactly the owner export's.
  `requested_by` is the job actor (`job:crm_pilot_backup`), set by the column default from `app.actor`.
- **Retention:** the existing DM-7.1 row of `crm.export_job` already covers the files (`exports/` prefix, 7 days, S3
  lifecycle) and the rows (kept). The root PR of this lane adds the nightly pilot backup to that row's text. 7 nights
  of copies are kept.
- **The owner's export list leaves the backups out** (`LIST_SQL` filters `requested_by <> 'job:crm_pilot_backup'`):
  they are AA's restore copies; 20 nightly rows would otherwise push the owner's own exports off the list.
- **Restore drill = temporary tables in the drill's own transaction** (`pg_temp`, `ON COMMIT DROP`): a throwaway
  schema no other session can see, no DDL rights needed beyond the default TEMP privilege, nothing to clean up. It runs
  as `crm_app` inside the API container (KMS + bucket + DSN are there), the same way `python -m app.seed` runs.
- **Restore fidelity:** a column the live table has keeps its live type (uuid, text, numbers, booleans, dates,
  timestamps, json, varchar / numeric with modifiers, and their arrays), so a value that no longer parses fails the
  drill; decrypted `*_enc` values and other types (bytea, interval, enums) are restored as text.

- **Review fix pass (S269): "restored" is not "complete".** A reviewer showed the drill passed while the backup
  could not bring back a document: the export caps documents at 25 MiB (the rest `skipped_size_cap`), and the S3
  files are sealed under the agency keys, which the export never holds. The drill now reads `documents/manifest.csv`
  (checksummed in the ZIP), counts skips per reason and reports `complete` (= `ok` and no document lost:
  `skipped_size_cap`, `object_missing`, `skipped_integrity`, `documents_not_configured`, or a reason it does not know);
  exit 3 = restored but incomplete, so a scheduled or scripted run cannot read it as a pass. `no_object` (a document
  row that never had a file) is not a loss. `not_in_backup` comes from `app/portability/tables.py`
  (`NEVER_EXPORT_TABLES`, `NEVER_EXPORT_COLUMNS`, `*_bidx`), so it cannot drift from what the export leaves out.
  The audit reason is `ok` / `incomplete_documents` / `mismatch`. The document cap is not raised for the pilot backup:
  the whole ZIP is built and decrypted in the 512 MB API task; the root runbook names the options for the tech lead.

## Tradeoffs

- **Inventory of `crm.job` kinds against "clean-up, E2E and wave jobs skip the pilot":**
  - `crm_lifecycle` (form payload redaction, LLM call purge, membership inbox purge, trash purge, auto-archive):
    **skips the pilot.** Its windows (90 / 180 days, trash windows) are longer than the pilot (8 weeks), so for data
    written during the pilot this changes nothing; after the pilot (CIS clears the marker) the next daily run catches up.
  - L1 `delete_test_agency` (the E2E / test clean-up path, with the `crm_partner_accounts` run it queues): **refuses
    the pilot.**
  - `crm_partner_accounts`: kept. It deletes only partner-pool accounts that no member, live invitation or studio
    invitation of any agency needs; a pilot member's account is never a candidate, and a lapsed invitation's unused
    account holds no agency data.
  - `crm_job_retention`: kept. It deletes `crm.job` rows (platform queue, ids and counts), not agency data.
  - `crm_stage_date_rule`'s deletion of e-mail codes older than 24 hours: kept (security hygiene; skipping it would
    keep live codes longer for the pilot).
  - `crm_offboard`, `crm_data_export`, `crm_client_import`, the owner's erasures: kept. They are the agency's own
    requests (the pilot agency must be able to erase or leave).
  - No wave or seed kind exists in `crm.job`; the Dev seeder (`python -m app.seed`) writes synthetic agencies only and
    cannot mark one pilot (crm-044 guard).
- The drill decrypts the whole export in the API task (512 MB). The export is capped (documents 25 MiB), so the peak is
  about the same as a download; run it when the task is not building another export.

## Re-review fix pass (S269)

- **The pilot's own deletions still run.** `crm_lifecycle` used to leave the pilot agency out of every step, including
  the trash purge, whose window is the agency's own `trash_days` (1 to 30 days): what the agency deleted would have
  stayed for the whole pilot. Now only the AA-initiated steps are skipped (form-submission redaction, the LLM call /
  membership inbox purge, auto-archive; `pilot_skipped_count`); the trash purge and the `lifecycle_run` row / audit
  event run as for any agency.
- **An absent `is_pilot` keeps the marker.** A CIS snapshot without the field (an older CIS, a partial answer) no
  longer clears `crm.tenant.is_pilot` (`Projection.is_pilot = None` = no write); only an explicit `false` clears it.
- **Restore drill errors carry no values.** The CLI reports any failure as `{"ok": false, "error": "unexpected",
  "error_class", "sqlstate"}` (`restore_drill.failure`), a connection error included; a known refusal keeps its code.
- **The owner's export wins the slot.** `export_job_open_uq` allows one open export per subject; when it is AA's
  nightly pilot backup, the owner's agency export cancels it and takes the slot (the backup job then skips, or drops
  what it built; the next night tries again). A client export or another open export still answers 409
  `export_running`.

  resolves once #223 (crm-044) is merged and applied.
