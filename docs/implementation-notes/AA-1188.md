# AA-1188 — Partner part: the studio BFF proxy forwards only listed CIS calls

S295 data-boundary audit, finding DB-01: CIS `GET /v1/tours/{id}/full` answers the raw source tour row (supplier name,
supplier id, source price text, links, manual facts, pipeline columns) to a tenant token, and the agency app's studio
proxy `web/app/api/tenant/[...path]/route.ts` forwarded ANY path with the member's studio token, so devtools could reach
it. This repo closes the browser path; the CIS projection fix is AA-CIS-App's part of the same issue.

## Decisions

- **Allow-list in `web/lib/studio/tenantRoutes.ts`**, a pure `matchTenantRoute(method, subPath)` over anchored regexes,
  same shape as the CRM BFF list (`web/lib/bff.ts`). A path parameter is one encoded segment (`[^/]+`); `proxyPath`
  already refused empty, dot and slash-carrying segments, and the match runs on its encoded output.
- **Order in the route: cross-site write check → `proxyPath` → allow-list (404) → `requireStudio` → facts check → CIS.**
  404 comes before the token is read, as in the CRM BFF ("Anything else is 404 before a token is read"), so a refused
  path costs no token verification or renewal and never reaches CIS. The list is public in this repo, so a signed-out
  404 vs 401 reveals nothing new.
- **404, not 403**: the path does not exist for the studio.
- **Method exact**: HEAD and PUT are refused (the studio never sends them; the route exports GET/POST/PATCH/DELETE).
- **Typed unions spelled out** where the web passes a union: `v1/integrations/(wordpress|facebook)`,
  `v1/progress/(tour|piece)/{id}`; the trailing actions are enumerated (`publish|put-back|move-to-draft`,
  `goal|choose|reopen`, `pick|cut`).
- `GET /v1/tours/{id}` and `/v1/tours/{id}/full` are NOT listed: the studio reads tours only through `v1/tours/pool`,
  `v1/marketplace` and its own versions (`v1/tours/my-versions`, `v1/tours/versions/{id}`).

## Changed

- `web/lib/studio/tenantRoutes.ts` (new): `TENANT_ROUTES`, `matchTenantRoute`.
- `web/app/api/tenant/[...path]/route.ts`: path built and checked before `requireStudio`; unlisted → 404.
- `web/tests/studio/tenantRoutes.test.ts` (new): a method table of every studio call (all allowed); a source scan of
  every `/api/tenant/...` literal in `web/app` + `web/lib` (all listed and all pinned in the table); no dead route line;
  21 refused cases (`/full`, `v1/tours/{id}`, admin-like, unknown methods, HEAD/PUT).
- `e2e/smoke-portal/aa911-portal-cross-site.spec.ts`: its three invented write paths (`v1/webhooks`,
  `v1/tenant/settings`) would now be 404 on the same-origin leg; replaced with real studio write routes.
- `e2e/smoke-portal/aa1188-tenant-proxy-allowlist.spec.ts` (new): signed out and signed in, `/full`, `v1/tours/{id}`
  and `openapi.json` are 404; a listed read is 401 signed out, 200 signed in.
- `.github/workflows/ci.yml` standalone smoke: `/api/tenant/v1/tours/x/full` 404, `/api/tenant/v1/billing` 401.
- `CONTEXT.md`: "Studio BFF allow-list" bullet under "One agency app".

## Tradeoffs

- A hand list can miss a call built in a way the scan does not see (a path assembled from a variable without the
  `/api/tenant/` literal). Only one such helper exists today (`FACTS_API` + `factCall` path in `lib/studio/facts.ts`),
  covered by the table. The cost of a miss is a 404 on one studio action, visible in the UI smoke, not a data leak.
- The list does not remove anything from CIS answers: list/detail fields such as `price_raw` on `v1/tours/pool` stay
  until the CIS projection fix (AA-CIS-App part).

## Should know

- A new studio call to CIS needs one line in `tenantRoutes.ts` and one row in the test's `CALLS` table; the unit test
  fails otherwise.
- The S294 lesson (studio components must not call `/bff/`) is unchanged; this is the `/api/tenant/` side.
- Review (S295, allow-list completeness): the source scan now also fails when a `/api/tenant/` literal is not read
  whole (a `${...}` holding a quote or a space would have been skipped silently) or when a quoted bare base
  (`"/api/tenant"` / `"/api/tenant/"`) could be extended by concatenation out of the scan's sight.
- Every allowed (method, pattern) was matched against the CIS route table (`docs/api/openapi.json` + `v1_progress.py`):
  it reaches only the intended CIS routes. One shape overlap is harmless: `GET v1/tours/versions/full` matches the
  `versions/{id}` line and CIS routes it to `/v1/tours/{tour_id}/full` (declared first) with `tour_id="versions"`,
  which `_require_uuid` answers 404. The AA-CIS-App part of AA-1188 removes `/full` for tenants anyway.

# AA-1188 — S296 lane l1-pricing: AA prices, booking conditions, studio prices (booking.b2b.v1 1.12)

The rest of the issue's Partner scope (roadmap S1 web half, S3, S4 of the S295 pricing audit; decisions D5 and D10).

## Decisions

- **Tolerant reader for 1.12.** Every new tariff field is optional in `contract.tariff` (absent = the old behaviour:
  `available`, no supplement column value, no coverage line), so this PR can merge before or after Booking's 1.12
  deploy. A present field that breaks the contract still fails the whole read (nothing half-shown).
- **B2B names for the new prices** (`b2b_child_price_per_person`, `b2b_infant_price`,
  `b2b_single_supplement_per_person`): the margin serializer strips them like the adult price (defence in depth; the
  route is owner/agent only).
- **"On request" keeps the computed amount as a guide** under the badge (D5 asks for "On request"; the number still
  helps an agent size a group quote). The CSV is Booking's file and carries both.
- **Booking conditions for every role**, not `aa_tariff_view`: deposit %, cancellation fees, clauses and ages are what
  any member needs before quoting AA; no price or margin crosses. Read live (no cache, no table): rare reads, rare
  changes. The credit amounts are not read (the AA invoices page shows them); only `holds_paused`.
- **Sidebar**: "AA prices" under Money (owner, agent), icon `book`; the Settings and builder links stay.
- **Studio (D10)**: the caveat under every "from" price reads "Suggested retail (RRP) for 2 travellers, not your
  agency's price"; "Price on request" replaces the empty price in the catalog card, the drawer and "In my catalog".
  "In my catalog" uses `from_price` from CIS `/v1/marketplace` (CIS #1718 already reads price.from.v1 there), falling
  back to its `price_usd` only for an older CIS answer without the field.
- **"Price on request" in the CRM too** (review fix): the proposal builder's AA drawer and the ledger's AA item form
  showed the public "from" price only when there was one and nothing otherwise. Both now render one shared line
  (`components/AaFromPriceLine.tsx`): the from price per person, else "Price on request." (`aa.priceOnRequest`, EN +
  VI, the studio's wording), so every agency-facing tour price surface answers the same.
- **The RRP column is twin share** once Booking's review fix is live (the matrix RRP of an odd computed band is scaled
  to the twin share there); the CRM shows `rrp_per_person` as Booking answers it, no label change.
- **No new setting**: the group size and the ages are Booking policy values shown as data; `MAX_CLAUSES` /
  `MAX_TIERS` are reader bounds (marked `technical-constant`).

## Changed

- API: `app/booking/contract.py` (tariff 1.7 / 1.12 fields, `partner_terms`), `app/booking/tariff.py` (view),
  `app/booking/client.py` (`terms`), `app/booking/aa_terms.py` (new), `app/routers/aa.py` (`GET /aa/terms`).
- Web: `app/(crm)/aa-tariff/page.tsx`, `components/aaTariff/AaTariffView.tsx` (eleven columns, On request badge,

- Web (review fix): `components/AaFromPriceLine.tsx` (new), used by `components/proposals/BuilderAaDrawer.tsx` and

- Tests: `api/tests/unit/test_aa1188_agency_prices.py`, the terms route in `tests/integration/test_aa1030_tariff_api.py`,
  `web/tests/aa1188AgencyPrices.test.ts`, updated tariff / from-price / tours tests and the studio price smoke copy.

- `app/booking/invoice_contract.py` (new): the 1.5 invoice and billing-status reader moved out of
  `app/booking/contract.py` unchanged (the file-size ratchet: contract.py was 795 lines and the 1.12 tariff fields plus

# AA-1188 — S296 lane l7-aaterms-bff: the AA prices page answered 500 (aa/terms not on the server allow-list)

S296 live check: `/aa-tariff` answered 500 for every signed-in agency user after the l1-pricing PR deployed. The page
reads the booking conditions on the server (`crmCall(..., "GET", AA_TERMS_PATH)`, `"aa/terms"`), but that path was on
neither `BFF_ROUTES` nor `SERVER_ONLY_ROUTES` of `web/lib/bff.ts`, so `crmCall` threw `not on the BFF allow-list: GET
aa/terms` and the whole page failed (CloudWatch, stream `web`). The page tests mock `crmCall`, so CI never saw it.

## Decisions

- **`GET ^aa/terms$` in `SERVER_ONLY_ROUTES`** (tenant: true, card AA-1188), like `aa/tariff/currencies`: only the
  page's server code reads it; the browser never asks for it, so it stays off the browser BFF. The API checks the
  membership itself (`tenant_tx(..., Action.TRIP_VIEW)`), so every role keeps reading it (decision of lane l1).
- **A static guard, not more mocks** (`web/tests/bffPathsAllowed.test.ts`): it reads app/, components/ and lib/ and
  checks every CRM API path the web calls against the list that call goes through: `crmCall` against `BFF_ROUTES` +
  `SERVER_ONLY_ROUTES` (path as written), `bffSend` / `bffFetch` / `bffDownload` and `"/bff/..."` literals against
  `BFF_ROUTES` only (query cut off) or a route folder of its own under `app/bff/` (identity). Literal methods are
  matched exactly; a method held in a variable may match any method.
- **How a path is read**: a string literal, an UPPER_CASE constant of the scanned sources (`AA_TERMS_PATH`), or a
  template literal whose placeholders are filled with sample values (a UUID, a word, a number, nothing; the last
  placeholder also with the words of the lists' alternations such as `approve|reject|execute`). A path in a variable
  (a wrapper's `path` argument) or a template that starts with a placeholder is not readable and is counted, not
  failed. On S296 main: 270 of 322 calls readable, 0 refused; the test asserts more than 220 readable so a parser that
  goes blind fails.

## Changed

- `web/lib/bff.ts`: one line in `SERVER_ONLY_ROUTES`.
- `web/tests/bffPathsAllowed.test.ts` (new): the reader's unit cases (constant, template, generic, declaration skip),
  the S296 case refused when the line is missing (checked by removing the line: 3 tests red), a server-only path or a
  wrong method from the browser refused, the whole-source scan, and the AA prices page's aa/terms call.

## Tradeoffs

- Sample filling accepts a template when SOME filling matches, so it can pass a call whose real values never match
  (e.g. a placeholder that is always a word where the route wants a UUID). It cannot pass a missing route or a wrong
  literal segment, which is the failure class seen live (S278 inclusion-items, S296 aa/terms).
- About 50 calls go through small wrappers (`run(path, method)`, `send(method, path)`) and stay unchecked; following
  each wrapper's callers would need a TypeScript AST walk. Not worth it until one of them breaks.

## Should know

- Why the signed-in visual run did not catch the 500: `Visual (agency host, signed in)` never runs on a pull request
  (it runs after Deploy Web Dev, `workflow_run`, or a dispatch with `base_url`), so "skipped" on the PR is by design.
  After the deploys of S296 it ran twice (runs for the l1 merge and the next commit, the first cancelled by the shared
  concurrency group) and every CRM page (186 tests, `aa-tariff` included) was skipped: the e2e studio user has no CRM
  membership, so each CRM page sends it away and `visual.spec.ts` skips it by rule. No signed-in CRM page has been
  captured by that run. Making it cover the CRM needs a CRM sign-in in the deployed job (the E2E agency owner of
  `e2e-dev.yml`, environment `e2e` secrets) or a CRM membership for the e2e studio user on the E2E agency (a Dev data
  step): neither is cheap or testable from a lane, so it is a follow-up, not part of this PR.
