# AA-1069 — Agency service catalogue and supplier booking requests per supplier

S277 lane l3-crm-1069. Study items crm-23 and crm-24 (root `docs/research/2026-11-10-odoo-tour-travel-plugin-
comparison.md`): behaviour only, nothing copied from the OPL-1 app. Built with the proposed defaults; the business owner
may adjust them later.

## Decisions

- **Migrations**: crm-052 (expand: `crm.agency_service`, `crm.agency_service_tier`, guard CRM52) and crm-053 (contract:
  `crm.booking_line` status `requested` + `requested_at` + `request_ref`, `crm.booking_line_confirm` accepts a requested
  line, `crm.conversation.agency_supplier_id`). One migration-only PR (batch crm 052-053), then the code PR.
- **Categories** = root ADR 0019 b6 ancillaries only: `flight`, `insurance`, `visa`, `transfer`, `fee`. No
  `accommodation` / `activity` / `other`: tours and ground services are AA's (b6). A fee may have no supplier (the
  agency's own service fee), so `agency_supplier_id` is nullable; when set it must be a live own supplier (never the AA
  row: CRM52).
- **Quantity basis** (proposed default): `per_person` = every traveller (adults + children + infants), `per_adult`,
  `per_booking` = 1, `per_room` = the proposal's rooms (1 when no room list), `per_night` = the trip's nights,
  `per_person_night` = travellers x nights. Travellers come from the proposal's room list when set, else the trip
  party (as the AA quote does, `rules.room_pax`). Nights: the request's value, else the trip's `nights`, else the
  builder's days minus one (at least 1). The member may override the quantity in the dialog.
- **Tiers** carry a unit net only (the issue): the sell price stays the service's `unit_sell`. Tier chosen by the
  party size; ranges of one service never overlap (CRM52).
- **Snapshot, no live link**: "Add from catalogue" writes a normal agency option (title "<name> x <qty>", supplier,
  sell = unit_sell x qty, net = unit_net x qty) and keeps no key to the service.
- **Currency**: a service in another currency than the proposal is converted at today's rate (`crm.fx_resolve`, agency
  date); no rate -> 409 `fx_rate_missing`. The rate used is returned with the option.
- **Who**: the catalogue is read by every role (the assistant gets no `unit_net`, built only for `view_margin` roles and
  stripped by the serializer as a backstop); written by owner / agent (`MONEY_FIELDS_EDIT` + the CRM52 guard). "Add
  from catalogue" is `PROPOSAL_DRAFT` for every role: the prices are the owner's catalogue prices, so the assistant
  adds them without typing money.
- **Supplier requests**: one e-mail conversation per (trip, supplier) (`crm.conversation.agency_supplier_id`, trip set,
  no client). "Request from suppliers" builds one draft per supplier of the trip's planning agency lines (dates,
  travellers by type, rooms; names only when asked, default on for flight / insurance / visa suppliers) and returns
  them; "Send" on each draft goes through the normal send path (`conversations.send`, the agency mailbox, dispatch with
  the trip's lead as the dispatch subject, 10 s Undo) and marks those lines `requested` (`requested_at`, `request_ref`
  = the message id). The sender reads the supplier's address from `agency_supplier.contact_email_enc` at send time.
- **Confirm**: the supplier's reply threads on the supplier conversation by its headers (the normal ingest). The member
  types the confirmation number on the requested line ("Record confirmation"), which saves it and runs
  `crm.booking_line_confirm` in one call. No automatic number parsing (a wrong guess would confirm a line).
- **Back to planning**: a requested line can go back to planning (clears `requested_at` / `request_ref`), e.g. after an
  Undo of the request e-mail.

## Changed

- The issue names `crm.booking_line_confirm` for the supplier's answer: reused as is (crm-053 only widens the status
  it accepts). The answer is typed by the member ("Record confirmation"); a reply e-mail is not parsed.
- "Sent from the agency mailbox and threaded on the trip" needed a recipient that is not a client: the mail send path
  only wrote to the conversation's client. A conversation now names an own supplier (`agency_supplier_id`, crm-053),
  the sender writes to the supplier's contact e-mail, and the dispatch row names the trip's lead (the gate's subject).
- A service in another currency than the proposal is converted at today's rate (the issue was silent).
- The P&L view (crm-051) counts only planning lines as "not counted yet"; the API adds the requested ones in
  `app/finance/pnl.py` instead of replacing the view.
- `crm.agency_service` hangs off `crm.tenant_settings` (as crm-049 does) so the agency erase takes it; the create path
  makes sure the settings row exists.

## Tradeoffs

- No foreign key from `crm.conversation.agency_supplier_id` to the supplier: the supplier is trashed and purged on its
  own schedule while the trip keeps its message history; the sender fails a message whose supplier has no address
  (`no_supplier_address`).
- A request is marked when the e-mail is queued, not when the provider accepts it: a held mailbox keeps the line
  requested while the message waits (the Messages tab shows the held chip).
