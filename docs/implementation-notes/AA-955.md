## Decisions

- **Numbering and base**: crm-025, rebased on `main` after AA-952 (crm-024, Partner #130/#131/#132) merged.
  `crm.erase_subject` in crm-025 is the **crm-024 text** (byte-identical to main's file) plus this card's changes;
  Guard 0 needs crm-024 registered, so DB Migrate applies 024 before 025.
- **Tables are the design's names** (`terms_acceptance`, `signature_event`; DM-7 registry rows already exist) and v0's
  `signature_request` stays the per-traveller envelope row (no second "envelope" table): the envelope is the request
  plus the terms / declination versions it carries. `crm.document` is not used for the sealed envelope (see Tradeoffs).
- **The signed evidence has no foreign key on trip / proposal / traveller / link / request** (only tenant and, for
  terms, `agreement_doc`, which leaves only with the agency). That is how the DM-7 claim-period exception works
  without rewriting every erase step: a trip or traveller erase never touches these two tables and its receipt counts
  them (`terms_acceptance_kept`, `signature_event_kept`); the agency erase deletes them; `crm.lifecycle_purge_expired`
  deletes them after `keep_until` (trip end, else start, else the write day, + 3 years; clamped to today) once the
  trip is gone or ended more than 3 years ago, never a row under a trip or traveller hold. `signature_request` (with
  the typed name under the vault DEK) still leaves with its trip / traveller, as in v0.
- **Guardian signing (O-6)**: minor = under 18 on the trip start date from the F1 DOB (decrypted only to compare; one
  `guardian_check` audit event with the ids). No DOB or no start date = adult (Stage 3 asks for the DOB, so a
  minor's Stage 3 cannot be complete without it). The lead, when an adult, signs each minor's envelope from **their
  own** portal access: `signature_request.signer_traveler_id` + `signer_role = guardian`, and the crm-016 access key
  is now on a generated `access_traveler_id = coalesce(signer_traveler_id, traveler_id)` so the key still proves the
  access belongs to the signer and the trip. A minor's own access is 403 `guardian_signs`; another adult signing for
  someone else is 403 `not_guardian`. A lead who is a minor cannot sign for others (the agent's `manual_stage3`
  override stays the way out).
- **Envelope documents**: the published booking terms (when there is one), the waiver (required: no waiver = nothing
  to sign), and the insurance declination only when the traveller declines insurance. Whenever a declination version
  is published the choice is required (`insurance` insured | declined); without one it is not asked. R13 is "decline
  only": the CRM records the choice, it sells nothing. The signer sends every document's id + SHA-256 as shown; the v0
  body (`doc_id` + `doc_sha256` of the waiver) still works when the envelope is the waiver alone.
- **Merge fields** (`app/esign/merge.py`): trip and signing facts only (`agency.name`, `trip.title`,
  `trip.start_date`, `trip.end_date`, `traveller.role`, `signer.name`, `signer.role`, `signed.date`); never an F1
  field, so rendering decrypts nothing. Unknown `{{name}}` is 422 at draft. The pinned hash stays the version text's
  (`body_sha256`, the database's); the evidence record adds each document's rendered SHA-256.
- **Seal** (`app/esign/seal.py`, provider-neutral): `kms:Sign` RSASSA-PSS SHA-256, `MessageType = DIGEST`, over the
  envelope SHA-256, with `KMS_SEAL_KEY_ID` (the RSA_3072 `alias/crm-<env>/seal` AA-932 created); the seal keeps the key
  ARN the answer names (an alias can move). Without the setting: an HMAC-SHA256 stub (`dev-stub-hmac-sha256`, public
  key, labelled "test seal (not legal evidence)" in the UI) on dev / test / local; 503 `esign_not_configured` on
  stg / prod. KMS errors are 503 `seal_unavailable` (the message is never echoed). No paid e-sign vendor (BYO later
  behind the same protocol).
- **The envelope** is canonical UTF-8 text (`aa-partner-envelope/1`): header, each document (kind, version, version
  hash, rendered text), the audit page (who signed for whom, insurance choice, time, code id + delivery, SHA-256 of
  the client address and of the user agent, the evidence record and its SHA-256). Stored on the `signature_event` row
  kind `signed` under the tenant **docs** DEK (AAD signature_event / envelope / event id), at most 2 MiB.
- **Client address and user agent** (the task's "IP / user agent"): the same address the per-address limit uses
  (`client_address`, XFF hops), the `User-Agent` header (printable, 400 characters); stored under the vault DEK on
  `terms_acceptance` / `signature_event`; only their SHA-256 in the evidence records (no PII there).
- **Card R**: every refused signing code is a `signature_event` row kind `code_refused` with reason `code_expired`,
  `code_invalid`, `code_missing` or `attempts_exhausted`, plus the existing denied audit event (an expired code now
  writes one too); every signing code sent is `code_sent`. The refusal answer is unchanged (422 with
  `attempts_left`).
- **Card E** (terms updated after viewing): the rule is "a trip whose accepted proposal's deposit is unpaid while a
  published booking terms version has no acceptance on the trip". The accepted proposal page shows `terms_reaccept`
  (merge fields rendered) and the client accepts it there (`POST /crm/public/v1/proposal/terms`, also
  `/p/{token}/terms`; 409 `terms_changed` / `nothing_to_accept`; a bell item `proposal.terms_reaccepted`); the
  deposit "Mark paid" is 409 `terms_reaccept_required` until then. A paid deposit is never reopened. The proposal's
  own `price_hash` (which hashes the terms version it was sent with) is not changed: the re-accept row pins the new
  version with the accepted proposal's price hash.
- **The agency's view** (`GET /crm/v1/trips/{id}/agreements`, every role): per traveller signed or not, self /
  guardian, insurance choice, envelope hash, seal kind; the terms acceptances; the re-accept state; the last 100 log
  events. The sealed envelope opens as a reveal (`POST /crm/v1/signatures/{id}/envelope`, `DOCUMENT_DOWNLOAD`, a
  reason from `REVEAL_REASONS`, one `reveal` event; the digest is checked before decrypting; `seal.verified`).
- **Migration class**: contract (ADR 0017 §3): widened `agreement_doc_kind_chk`, replaced
  `signature_request_access_fk` and `signature_request_sealed`, replaced `erase_subject` / `lifecycle_purge_expired`.
  No `-- migrate: expand` header; MIG-4 order (migration PR, Infra copy, manual DB Migrate apply, then the code PR).

## Changed (vs the card / plan)

- **PAdES is not done**: the seal is a detached KMS RSASSA-PSS signature over a canonical text envelope, not a PDF
  with an embedded CMS signature. A PAdES-B-B PDF needs (1) a Unicode PDF renderer with an embedded font (the agency
  texts are EN and VI; the standard 14 fonts cannot draw Vietnamese), (2) a CMS / PAdES library (pyHanko, new
  dependency) driven through an external signer that calls `kms:Sign`, and (3) an X.509 certificate for the seal key
  (self-signed by the key, or issued by a CA the insurer accepts). The envelope format, hash and evidence stay the
  same, so v1.1 adds the PDF beside the text envelope without a data move. Follow-up proposed for the orchestrator.
- `crm-018`'s test re-applies its file; crm-018's own Guard 0 now refuses that (a later key replaced
  `lifecycle_purge_expired`), so `test_crm018_schema.py` expects the refusal when crm-025 is registered; the crm-010 /
  crm-018 purge tests list the two new result keys (`EVIDENCE_PURGED`).
- `test_crm002_tenancy.py` lists the two tables as append-only (`crm.ledger_append_only`).
- The v0 sign unit tests moved to `tests/unit/test_esign.py` (v1 behaviour); `tests/integration/test_lifecycle_api.py`
  signs with the v1 body (the AA-946 flow publishes booking terms, so the envelope holds them).
- The settings page lists the three kinds; the merge field hints are translated on the web (`agreements.merge.*`),
  the API's English descriptions are the fallback.
- The re-accept check is one helper, `proposals.service.require_terms_current` (deposit rows only), called by both
  payment paths: "Mark paid" and a payment on the deposit's invoice (`payments.service.record_payment`, AA-952);
  `tests/unit/test_payments.py`'s schedule fake gains its `kind`.

## Tradeoffs

- Envelope in the database (docs DEK) rather than the documents bucket: the evidence must survive the trip /
  traveller erase, and the erase path deletes every `crm.document` object of the trip / traveller; a separate object
  key family would need its own erase and purge code in `app/lifecycle/erase.py`. Size is small (text, < 2 MiB CHECK).
  When the PDF lands (it is bigger) it can move to the bucket under a key the purge knows.
- Typed name on `terms_acceptance`: only its SHA-256 (the proposal keeps the encrypted typed name as in v0, erased with
  the traveller); the signing envelope keeps the name in clear inside the sealed text (docs DEK) under the exception.
- `keep_until` is fixed at write; a trip moved later keeps its evidence longer through the purge's "trip still within
  3 years" condition, a trip moved earlier does not shorten it (conservative).
- The hold rule: `crm.erase_held` is unchanged; a guardian's erase that would delete a held minor's signature is
  refused by the row's hold guard trigger (CRM10) during the erase rather than by the pre-check.
- The portal decrypts party DOBs (lead's home and every signing) to find minors: one audit event per read with the
  ids. A stored `minor` flag would avoid it but adds a column that must follow DOB and start-date edits.

- Seal check at reveal: KMS `Verify` never answers `SignatureValid=false`; a signature that does not match fails the
  call with `KMSInvalidSignatureException`. `KmsSealer.verify` maps that one error code to `False`
  (`seal.verified = false`: tampered or forged seal). Every other KMS error (transport, throttling, key state, access)
  answers `seal.verified = null` ("not checked"), not a 503: the envelope digest is checked before decrypting, so the
  reveal still opens; signing still answers 503 `seal_unavailable` when KMS cannot seal. The unit `FakeKms` raises the
  exception like real KMS (and the test uses the client's modeled exception class too).
- Seal key rotation: a new seal key is a new key + alias move (crm_data.tf). Old seals keep the old key ARN in
  `seal_key_ref`; the task role grant names only the current key, so after a rotation the old key ARN must stay in
  `CrmSealSignVerify` (Verify only) or old seals show "not checked".
