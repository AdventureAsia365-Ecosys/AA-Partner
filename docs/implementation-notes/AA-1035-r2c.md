# AA-1035 R2 close-out (S269, lane l2-aa1035-r2c) — AA-Partner half

Sources: root ADR 0019 d3–d5 ("the crm.ops.v1 relay forwards the staff member's scope. admin bypasses scope"), the
role matrix in root `docs/audits/2026-11-03-S265-ecosystem-restructure/clarifications.md` section 3, the S267 and S268
Linear comments on AA-1035 (follow-ups: "a support resend that keeps the sealed address (Partner)", "the AA-Partner
byte copy of schema_gate.py"). CIS half: AA-CIS-App `docs/implementation-notes/AA-1035-r2c.md`.

## Decisions
- **The CRM reads the scope from CIS; it never trusts one sent with the request.** The CIS admin relays the staff
  member's OWN WORKFORCE access token, which the staff member can also use directly (devtools), so a scope header CIS
  added could be written by the staff member. For a desk caller the CRM asks CIS `tenant.membership.v1` 1.3
  `GET /staff-scope?iss=&sub=&desk_role=` with the membership feed's own M2M client and scope (`cis.tenant/read`, no new
  grant) and serves only those tenant ids. This is how "the relay forwards the scope" is implemented: CIS still relays,
  and the scope CIS holds is what reaches the CRM, from CIS, not from the caller.
- **Who is a desk caller** (`app/ops/staff_scope.py`): the OPS class now admits `cis-customer_success` and
  `cis-support` (identity_config `OPS.groups_any`). A caller in `cis-admin` or `crm-platform-admin` keeps every agency
  (scope `all`, no CIS call). Otherwise the role is the highest desk group (`customer_success` before `support`, the CIS
  precedence); CIS decides the tenants (book, or book and pool).
- **What a desk caller may do**: the per-agency reads of its scope (`TenantReader`: 403 `tenant_outside_scope` outside,
  existing or not, before the agency is opened, so no `ops_read` event either); the list (`allowed` ids filter the
  registry before any agency is opened); `/console` (`can_write` false and the new `scope`); the studio invitation relay
  for a tenant of its scope. Never a platform-wide read (`FullReader` on `/jobs/summary`, `/llm/usage`,
  `/llm/app-profile` GET, `/llm/calls`, `/data-coverage`, `/insights`: 403 `missing_group`) and never a
  `crm-platform-admin` write (unchanged).
- **Fail closed**: CIS unreachable, a token failure, any status but 200 or a body off the contract (another role than
  asked, an unknown scope kind, a bad id, "none" with ids) is 503 `cis_unavailable` for the desk caller only. The answer
  is cached 30 s per (iss, sub, role): an assignment removed in CIS stops working here within 30 s.
- **The kept address (crm-045)**: every issue with an address also seals it under a one-off data key from the CRM KMS
  data key (GenerateDataKey with the context `{tenant_id: the CIS tenant, purpose: mail}`), the key stored wrapped in
  the row. `keep_address: true` (no `email`) opens it and re-issues to it. The purpose is the existing `mail` (the key
  policy allows only a fixed purpose list; a new purpose would need an AA-CIS-Infra key policy change and a manual
  key-policy apply); the address only ever addresses the invitation mail, so `mail` is accurate. The CIS tenant id is
  the context tenant (a studio-only tenant has no `crm.tenant` row, so no vault DEK): the per-row DEK keeps the
  tenant isolation of the context without the vault store.
- **A desk caller never delivers the owner seat** (review fix, S269): the desk caller holds the relayed WORKFORCE
  token and can call `POST /tenants/{id}/studio-invitations` without CIS, so CIS's owner-tier rule
  (`admin_tenant360._require_owner_tier`) alone is not enough. For any desk caller the CRM asks CIS
  (`studio.check_desk_invitation`: `tenant.membership.v1` getTenantMembers of the PATH tenant, the lookup the E2E check
  already used) and requires an `invited` membership with this invitation id and the role `viewer` or `editor`:
  403 `owner_invitation_not_allowed` otherwise (a new address or the kept one), 403 `invitation_not_invited` when CIS
  holds no open invitation with that id on that tenant (this also closes the cross-tenant variant: an invitation of a
  tenant outside the scope is not on the in-scope tenant's member list, so the INSERT branch never stores it under the
  wrong tenant), 503 `cis_unavailable` fail closed. Rejected alternative: refusing the INSERT branch for desk callers
  (keep_address only). customer_success holds tenant.member.write at CIS and invites new viewers / editors through
  this same relay (CIS `invite_tenant_member` -> `_deliver`), so that would break a CIS flow; the CIS lookup covers
  both the owner rule and the tenant binding without it.
- **support never names an address** (`may_readdress`): 403 `readdress_not_allowed` on a studio invitation with
  `email` from a support-only caller; CIS refuses the same before relaying. The Dev E2E CIS admin must always name an
  E2E mailbox address (403 `e2e_read_only` on `keep_address`).
- **The claim clears the kept address** (`CLAIM_SQL`): once the person opened the invitation it is never sent again,
  so the address is not kept a minute longer. The guard lets the holder only clear it.
- **Review fix pass (S269, adversarial review)**:
  - Support never reads the agency account: `GET /tenants/{id}/usage` and `/entitlements` take
    `TenantAccountReader` (`staff_scope.require_account_reader`): a support-only desk caller is 403 `missing_group`
    before CIS is asked or the agency is opened. The role matrix gives support no plan and no usage; CIS guards its
    relays of these two reads with `tenant.book.account.read` (admin, customer_success), and a desk caller can reach
    the CRM without CIS. The code `missing_group` (not a new one) keeps the crm.ops.v1 error set unchanged; the 1.12
    text names the two routes.
  - The scope answer must be about the caller: `parse_scope` checks the `identity` CIS echoes (`iss` and `sub`) next
    to `desk_role`; another identity is 503 `cis_unavailable` (fail closed), never a scope for this caller.
  - A revoke clears the kept address: the crm-045 guard refuses a platform revoke that keeps it (crm-045 is not
    merged, so the file itself changed; the same commit is in the crm-045 PR). The CRM has no revoke path today, so
    there is no code to change; the guard makes any future one clear it.
  - An expiry KEEPS the kept address (review point rejected): crm-020 re-issues a pending or expired invitation, and
    the send again after the expiry is the usual one (the person did not open it in time). Clearing it at the expiry
    would make support's only send again (`keep_address`) answer 409 `address_not_kept` exactly then, and the
    expiry is only marked when the holder opens a late link, so it would hit the person who did try to join. The
    address lives as long as the row (crm-020 retention, proposed 90 days after expired / revoked) and the claim
    clears it.
- `schema_gate.py` is the byte copy of the CIS file (REQUIRED_CIS_ABOVE_GAP, `strict_top`); identical in CIS, Booking
  and Partner again. A no-op for crm (its branch reads REQUIRED_SCHEMA_VERSIONS only); the CIS above-gap tests are
  copied into `tests/unit/test_schema_gate_script.py` with one crm no-op case.

## Tradeoffs
- A desk caller's studio invitation costs one more CIS call (getTenantMembers, not cached: the status must be
  current) and fails closed when CIS is down; admin callers skip it.
- One CIS call per desk identity per 30 s (cached) instead of a signed scope assertion: no new secret or key to
  operate, the scope is always CIS's current one, and the CRM keeps "CIS over HTTP only, no DB grant" (root ADR 0008a).
- Rows issued before crm-045 keep no address: a support send again of such a row answers 409 `address_not_kept` (CIS
  shows it; a customer success member or an admin sends it to a typed address once, after which it is kept).
- The kept address weakens crm-020's "the database alone cannot open it": with crm-045 the CRM task role (KMS Decrypt
  on the data key) can open it too, like every vault-encrypted CRM field. Limited to the row's life before the claim.
