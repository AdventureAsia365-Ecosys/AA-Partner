## Decisions

- **Two tables, not one.** `crm.support_grant` is the owner's window (1 to 7 days, "show identity"); `crm.support_session`
  is one AA staff member working in the agency (ticket, expiry, who). L3 break-glass is a `support_session` with
  `kind = 'breakglass'` and no grant, so every read path (and the agency's history list) treats both the same way.
- **crm-033 is contract.** Grants on existing tables (`relacl`), rows in `crm.status_transition` and a replaced
  `crm.erase_subject` are each contract under ADR 0017 d3.
- **`crm.erase_subject` replaced** (the crm-027 text + `support_session`, `support_grant` in the agency scope, before
  the members). Without it an agency erase with a grant row fails CRM16 (`erase_incomplete`), and the grant's FK to
  `crm.member` would block deleting the members. The rows are not on the keep list: the audit already records every
  grant, session and read; the two tables are agency data and go with it.
- **The support reader gets column grants on four non-F1 tables**, not "SELECT on every non-F1 table" (design §3.1
  wording). Least privilege: exactly what the staff read routes serve — `tenant` (id, status, name, locale),
  `tenant_settings` (configuration codes and numbers; not the data-request contact, consent text or refund threshold),
  `trip` (no title: `title` is tagged `pii:travel` and agencies often write client names into it; no mail token;
  no import index), `trip_stage_history` (codes). The migration guard refuses the file if the reader can write
  anything or read any other relation; the schema test pins the column sets.
- **No INSERT on `crm.audit_event` for the reader** (design §3.1 says "plus INSERT on audit_event"): the audit is
  written by `app.tenancy._write_audit` after `SET LOCAL ROLE NONE`, as `crm_app`, so the reader needs none.
- **One active session per agency and kind** (partial unique index): "one staff member at a time" (design §4.8). A
  break-glass session can still open while a support session runs (an emergency is not blocked by routine support).
- **Break-glass reasons are a fixed list** (`security_incident`, `data_corruption`, `legal_request`,
  `owner_unreachable`, `service_outage`) plus a ticket reference. Free text is never stored: the audit takes codes and
  ids only, and a free-text reason would be a place for personal data.
- **Expiry is lazy.** A row whose window passed stays `active` until someone meets it; every check compares
  `expires_at` with `now()`, and the next grant / session start marks stale rows `expired` first (the guard lets any
  actor do that, only once the window passed).
- **DB write guard** (`crm.guard_support_access`, CRM43 / CRM44): only an owner grants / revokes, in their own name; a
  session is opened and ended by its own staff actor (`support:<sub>` / `breakglass:<sub>`); an owner can revoke a
  support session but not a break-glass one; nothing is deleted by `crm_app`. `crm_owner` is not guarded (migrations
  and `crm.erase_subject`; integration tests use it to move time).

## Changed (vs. the card)

- L3 is built **in the app** (crm-staff client, group `crm-ops`, reason + ticket, at most 1 hour, owners mailed,
  AA ops alerted by a structured log line). The AWS-level path of design §4.8 (IAM role `aa-crm-<env>-breakglass`
  with MFA, session tag `tenant_id`, the KMS condition `CrmBreakGlassOneAgency` that crm_data.tf already holds,
  CloudTrail Decrypt copied into the agency audit) needs Infra and the tech lead's MFA: listed as a follow-up.

## Tradeoffs

- Column-level grants mean `SELECT *` as the reader fails (42501). The staff read code names its columns; that is the
  point (a later column is not readable until a migration grants it).
