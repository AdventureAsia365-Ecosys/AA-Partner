## Decisions

- **Two tables, not one.** `crm.support_grant` is the owner's window (1 to 7 days, "show identity"); `crm.support_session`
  is one AA staff member working in the agency (ticket, expiry, who). L3 break-glass is a `support_session` with
  `kind = 'breakglass'` and no grant, so every read path (and the agency's history list) treats both the same way.
- **crm-033 is contract.** Grants on existing tables (`relacl`), rows in `crm.status_transition` and a replaced
  `crm.erase_subject` are each contract under ADR 0017 d3.
- **`crm.erase_subject` replaced** (the crm-027 text + `support_session`, `support_grant` in the agency scope, before
  the members). Without it an agency erase with a grant row fails CRM16 (`erase_incomplete`), and the grant's FK to
  `crm.member` would block deleting the members. The rows are not on the keep list: the audit already records every
  grant, session and read; the two tables are agency data and go with it.
- **The support reader gets column grants on four non-F1 tables**, not "SELECT on every non-F1 table" (design §3.1
  wording). Least privilege: exactly what the staff read routes serve — `tenant` (id, status, name, locale),
  `tenant_settings` (configuration codes and numbers; not the data-request contact, consent text or refund threshold),
  `trip` (no title: `title` is tagged `pii:travel` and agencies often write client names into it; no mail token;
  no import index), `trip_stage_history` (codes). The migration guard refuses the file if the reader can write
  anything or read any other relation; the schema test pins the column sets.
- **No INSERT on `crm.audit_event` for the reader** (design §3.1 says "plus INSERT on audit_event"): the audit is
  written by `app.tenancy._write_audit` after `SET LOCAL ROLE NONE`, as `crm_app`, so the reader needs none.
- **One active session per agency and kind** (partial unique index): "one staff member at a time" (design §4.8). A
  break-glass session can still open while a support session runs (an emergency is not blocked by routine support).
- **Break-glass never shows identity** (review fix, S262): the in-app path trusts the WORKFORCE sign-in plus group
  `crm-ops` with no MFA step-up (the pool's MFA is OPTIONAL) and skips the owner's consent, so it must not reach F1.
  Three layers: the crm-033 CHECK (`kind = 'breakglass' ... AND NOT show_identity`), the start SQL writes `false`, and
  `support_tx()` sets `show_identity` only for kind `support`. A break-glass trip read returns `party: null`,
  `identity_hidden: true`, no `reveal` event; the owner mail says client names are not shown. Lifting this needs the
  AWS-level role with MFA and a later migration. Chosen over an `auth_time` check: a fresh sign-in is not MFA, and
  the CHECK keeps the rule in the database while the migration is still unmerged.
- **Break-glass reasons are a fixed list** (`security_incident`, `data_corruption`, `legal_request`,
  `owner_unreachable`, `service_outage`) plus a ticket reference. Free text is never stored: the audit takes codes and
  ids only, and a free-text reason would be a place for personal data.
- **Expiry is lazy.** A row whose window passed stays `active` until someone meets it; every check compares
  `expires_at` with `now()`, and the next grant / session start marks stale rows `expired` first (the guard lets any
  actor do that, only once the window passed).
- **DB write guard** (`crm.guard_support_access`, CRM43 / CRM44): only an owner grants / revokes, in their own name; a
  session is opened and ended by its own staff actor (`support:<sub>` / `breakglass:<sub>`); an owner can revoke a
  support session but not a break-glass one; nothing is deleted by `crm_app`. `crm_owner` is not guarded (migrations
  and `crm.erase_subject`; integration tests use it to move time).

### Code (PR 2)

- **Two new request contexts in `app/tenancy.py`**: `staff_tx()` (the staff member's own session rows, as
  `crm_app`, actor `support:<sub>` / `breakglass:<sub>`) and `support_tx()` (reads as `crm_support_reader`). Kept
  apart so the code that can write session rows never holds the reader context and the reads can never write; the
  code-rules test pins each to one module.
- **Every request re-checks the session and the grant** (`support_tx`): no session token or cache, so an owner's
  "End now" or a passed window refuses the very next read (card E test). Refusals are committed `denied` events with
  the reason code, so the agency also sees refused attempts.
- **Session length**: support = min(grant end, 8 hours); break-glass = 15 to 60 minutes (default 60, the design's
  "<= 1 h").
- **Break-glass needs group `crm-ops`** (root ADR 0006b names `crm-ops` and `crm-support` only); support needs
  `crm-support`. Reads and "end my session" take any staff group: the session decides.
- **Identity**: only display names of a trip's party, only when the session shows identity, through
  `as_login_role()` (one savepoint as `crm_app`), one `reveal` event naming the travellers. Nothing else of F1 is
  reachable from the staff class.
- **Ops alert = a structured log line** (`crm_breakglass_opened`, ids and codes), turned into an alarm by Infra
  (like the membership-feed alarms), not an SNS call from the API: the API task has no SNS permission and needs none.
- **Owner notice = AA system mail right away** (design says "within 24 h"), plus the red banner; if no owner could be
  mailed, `crm_breakglass_owner_not_mailed` raises its own alarm.
- **Agency UI** lives in Settings > Data and privacy (design WF-12 puts "AA support access" there) and the shell
  banner; the access log got labels for the new action codes and they are in its action filter.
- **Sender table**: `breakglass_notice` added (`app/mail/senders.py`, the test that every mail kind is listed).

## Changed (vs. the card)

- L3 is built **in the app** (crm-staff client, group `crm-ops`, reason + ticket, at most 1 hour, owners mailed,
  AA ops alerted by a structured log line) and **without identity**: no MFA step-up exists on this path, so a
  break-glass session never sees F1 display names (crm-033 CHECK). The AWS-level path of design §4.8 (IAM role
  `aa-crm-<env>-breakglass` with MFA, session tag `tenant_id`, the KMS condition `CrmBreakGlassOneAgency` that
  crm_data.tf already holds, CloudTrail Decrypt copied into the agency audit) needs Infra and the tech lead's MFA:
  follow-up, and AA-971 (or a linked issue) stays open for it.
- **S-04 staff screen descoped to a follow-up** (review fix, S262). Design v3 S-04 asks for a read-only agency UI with
  banners on both sides; this card ships the agency side (Settings > Data and privacy, the shell banner) and the whole
  staff API (`/crm/staff/v1`), not the staff screen. The follow-up covers: a staff sign-in in AA-Partner web with the
  WORKFORCE `crm-staff` client (its callback `/staff/auth/callback` and sign-out `/staff/signed-out` on the partner
  host already exist in AA-CIS-Infra `identity_variables.tf`; the web task still needs that client's id and secret),
  the S-04 pages (granted agencies, start / end a support session, break-glass form, overview, trips, trip) with the
  staff-side banner (kind and expiry), and a Dev E2E WORKFORCE user in `crm-support` / `crm-ops` that can get a
  `crm-staff` token, so the staff read and break-glass steps run live. **AA-971 is not Done until the staff read path
  (grant -> support read -> agency sees the audit row -> revoke -> 403; break-glass -> alarm + mail + audit) has run
  live on Dev**; until then only the owner side and the migration are live-verified.

## Tradeoffs

- Column-level grants mean `SELECT *` as the reader fails (42501). The staff read code names its columns; that is the
  point (a later column is not readable until a migration grants it).

## Should know

- The staff side is API-only until the S-04 follow-up (see Changed). A live check of it needs a `crm-staff` access
  token of a WORKFORCE user in `crm-support` / `crm-ops`; no Dev E2E path issues one today (root ADR 0006a A10 issues
  only `cis-admin`).
- The WORKFORCE pool has MFA OPTIONAL (staff sign in through the company IdP). That is why in-app break-glass reads
  codes only (see Decisions); the AWS-level role (MFA enforced in its trust policy) is the follow-up that may lift it.
- Live data: Dev holds synthetic agencies only (`is_synthetic`); the integration tests use the existing invented
  fixtures.

- Order: apply crm-033 on Dev before the code PR deploys (the code PR raises `REQUIRED_SCHEMA_VERSIONS`).
- `tests/integration/test_crm027_schema.py` re-applies crm-027, which puts back the crm-027 `erase_subject`; the
  crm-033 test re-applies crm-033 before its erase test.
