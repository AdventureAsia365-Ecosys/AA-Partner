## Decisions

- **`reveal(field, reason)` is its own module** (`app/travellers/reveal.py`) and replaces AA-936's
  `pipeline.reveal_contact`. A reason code from a fixed list is **required** (`contact_client`, `prepare_booking`,
  `verify_identity`, `client_request`, `fill_forms`, `ops_handoff`, `other`; 422 `reason_required`): the mockup says
  "each view is logged with a reason", and free text would put personal data into the audit. Fields: names, e-mail,
  phone, DOB, nationality, passport number / expiry / country, emergency contact, health codes. Every role may reveal
  (design §4.6). The route path stays `POST /crm/v1/travelers/{id}/reveal` (now in `app/routers/travellers.py`), the
  body gains `reason`; the trip page sends one.
- **Boundary test by import graph, not by a list** (`tests/unit/test_reveal_boundary.py`): every router module whose
  `APIRouter(prefix=...)` starts with `/crm/public` or `/crm/client` is a root; the transitive `app.*` import closure
  must not contain `app.travellers.reveal` nor import any name `reveal`. The R test injects such an import (directly,
  through a helper, and in a new client-portal router) and expects the checker to name it. `app/travellers/__init__.py`
  re-exports nothing, so importing the package never pulls `reveal` in.
- **`traveller_self_reveal(ctx, vault, session)` now, the session later.** `TravellerSession` = agency, trip,
  traveller, access (lead / companion); the traveller must be on that trip (a companion never opens the lead and the
  reverse), passport number masked to the last three characters, no health / emergency contact / relationships,
  one `self_view` event with actor kind `traveler`. The OTP session itself is CRM-24a (AA-953). It accepts any context
  (`AnyContext`); the portal will open a dedicated traveller context.
- **Reader grants: views only for `crm_ai_reader` and `crm_insights`.** `v_ai_traveler_profile`, `v_ai_trip_party`,
  `v_ai_trip_context` (AI) and `v_insight_fact` (insights: no token, no trip id) are owned by `crm_owner` and run with
  its rights (not `security_invoker`): FORCE RLS binds the owner and every tenant policy names it, so a view shows only
  the agency of `app.tenant_id` and nothing without it (tested). The migration guard refuses any base-table privilege
  for those two roles and any privilege of any reader on an F1 table (`traveler`, `traveler_health`,
  `traveler_relation`, `document`, `trip_traveler`, `note`, `consent`, `form_submission`, `tenant_key`,
  `integration_credential`, `member`). "F2 queries need no decrypt": the readers cannot even read `tenant_key`.
- **`crm_support_reader` gets nothing yet.** Design §3.1 gives it SELECT on non-F1 tables, but that is the
  owner-granted L2 support layer (CRM-13b, AA-971), and crm-005's guard (re-run by the "reapply is a no-op" test)
  refuses reader grants on its tables. The R test (42501 on `trip_traveler`) holds for all four readers.
- **Relationships: the database writes the inverse** (`crm.traveler_relation_mirror()` AFTER trigger): one INSERT
  makes the pair, trash and hard delete follow the inverse, `from` / `to` / `kind` are fixed (BEFORE trigger). A row
  (A, B, K) reads "B is A's K"; inverses spouse/partner/sibling/friend = same, parent <-> child, referrer <-> referred
  (added: the inverse of "referrer" needs a name). One live relation per ordered pair, one live referrer per traveller.
  The app keeps `traveler.referrer_traveler_id` in step (set when empty, cleared on removal).
- **Age band at departure** (`trip_party.age_band_at_departure`, R32): bands `under_2`, `2_11`, `12_17`, `18_24`,
  `25_34`, `35_44`, `45_54`, `55_64`, `65_74`, `75_plus` (child bands match tour pricing, adult bands the WF-3 mockup
  "35-44"). Recomputed only when the traveller's DOB really changes (old value decrypted and compared), when the trip's
  start date really changes (`PATCH /trips/{id}` gained `start_date` / `end_date`), or for the one new row when a
  traveller joins a trip. One `age_band_recompute` event per run (field `dob`, the trips in `object_ids`), not one per
  traveller (lane §5.7). No `traveler_profile.age_band` column: the band lives per trip, the profile page shows it per
  trip.
- **List views name their ids**: `audit_event.object_ids TEXT[]` (≤ 200, id pattern, crm-006) so a list view records
  which travellers were shown (design §4.4 "with the object ids and the field name"). The board's `list_view` (AA-936)
  now fills it with the lead travellers shown; the directory and the trip documents list too.
- **Directory search is exact only** (R35): `@` -> e-mail blind index; `+digits` -> phone blind index; otherwise name
  tokens (4-byte token indexes, `@>` all tokens), then candidates confirmed after decrypting their display names
  (collisions dropped). Offset pages of 50 (≤ 200 pages).
- **Documents**: the API encrypts with the tenant `docs` DEK (AAD tenant ‖ `document` ‖ `content` ‖ document id), keeps
  the SHA-256 of the **stored** object (integrity before decrypting; no plaintext fingerprint), encrypts the file name
  (vault DEK), and stores under `tenants/<tenant>/documents/<document>` (CHECK: no name, no traveller in the key). The
  bucket adds SSE-KMS as the default (no SSE header sent; the bucket policy refuses another key). Type checked by magic
  number, at most 10 MiB, PDF / JPEG / PNG / WebP / HEIC. Passport scans are write-only and never visible to
  travellers (CHECK + 422/409). Download is a reveal (reason required, one event). Row first, object second inside the
  transaction: a failed PUT rolls the row back; an object orphaned by a failed commit is the accepted rare case (no
  row points at it; the trash purge of CRM-14 can sweep `tenants/*/documents/` against the table).
- **Documents travel as base64 JSON through the BFF** (one route-specific body limit of 14 MiB in `web/lib/bff.ts`):
  the BFF forwards JSON only and the vendored proxy response copies only `Content-Type`; a 10 MiB cap makes base64
  acceptable on Dev. A streaming upload is a later optimisation.
- **Health codes need a `health_data` consent** (trigger on `crm.traveler_health`); the member can record it in the
  same call (`consent_recorded: true`, source `agent_recorded`). Dietary and mobility codes are mirrored to F2;
  medical codes stay F1 only. Withdrawing the consent (and clearing the mirror) is CRM-14 / CRM-24a.
- **Party removal is a hard delete of both twins** (removing a person from a trip is not deleting their data;
  `trip_traveler` has a plain UNIQUE (trip, traveller), so a trashed row would block re-adding). The lead cannot be
  removed (409 `lead_required`).
- **`profile_history` (F2) is created now without a writer**: the Booking feed (CRM-29b) writes it; the table belongs
  to F2 "complete" and costs nothing until then.

## Changed (vs. the card / AA-936)

- `app.pipeline.reveal_contact` and its route body `{field}` are gone; `POST /travelers/{id}/reveal` takes
  `{field, reason}`. AA-936 tests updated accordingly (unit `test_pipeline.py`, `test_slice1_routes.py`, integration
  `test_crm005_intake.py`).
- `AuditEvent` gained `object_ids`; `ctx.audit(..., object_ids=...)` on `TenantContext` and `SystemContext`.
- `PATCH /crm/v1/trips/{id}` accepts `start_date` / `end_date` (needed to make "recompute only on a date change"
  real).
- `REQUIRED_SCHEMA_VERSIONS` includes `crm-006`: `/crm/health/ready` stays 503 until DB Migrate applies it.

## Tradeoffs

- Views with owner rights vs. `security_invoker` + base-table grants: invoker views would need SELECT on
  `traveler_profile` / `trip_party` for the readers, which the "views only" rule exists to avoid.
- A required reason adds one click per reveal; the alternative (no reason) loses the "why" the mockup and §4.9 ask for.
- Base64 documents cost ~33 % more bytes per transfer; accepted for a 10 MiB cap on Dev.

## Should know

- **Threat model, stated honestly (design §4.3)**: the F1 / F2 split protects against the three readers. It does not
  protect against `crm_app` or the RDS master: the lead row of any trip (and a solo trip) joins F2 to identity
  through `trip_id`. The DPA draft says so (root branch).
- **Security reviewer sign-off (design §4.4)**: list views decrypt `display_name` only (board, directory, trip
  documents list = file names), each page writes one `list_view` with the ids, no partial digits anywhere (the profile
  shows `filled` booleans, not masks with digits); every other field is click-to-reveal with a reason.
- **Infra before deploy**: the documents bucket grant + `DOCUMENTS_BUCKET` (branch `feat/aa-937-documents-grant`)
  must be applied before the document routes work on Dev (without it they answer 503 `documents_not_configured`, the
  rest of the card works).
- Tests: unit (`test_travellers.py`, `test_documents.py`, `test_reveal_boundary.py`, `test_travellers_routes.py`),
  integration on PostgreSQL with crm-001..006 (`test_crm006_schema.py`, `test_crm006_travellers.py`), web vitest
  (`tests/clients.test.ts`).
