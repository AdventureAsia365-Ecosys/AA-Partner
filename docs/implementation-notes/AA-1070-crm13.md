## crm-13: AA cancels a departure

### Decisions

- **A case table, not a computed flag.** `crm.aa_cancel_case` (one row per trip and departure) makes the feed
  idempotent beyond the inbox (another event id for the same departure opens nothing), records what the agent did
  (re-quoted: the version and, for a booked trip, the new trip; cancelled) and drives the flag. A flag computed from
  `aa_departure_state` would re-open the owner task on every replay and could not say "done".
- **No status column**: `resolution` NULL (open) -> `requoted` | `cancelled` (requoted -> cancelled when the old trip
  of a re-booking is cancelled). A `status` column needs `crm.status_transition` rows (an INSERT into an existing
  table = a contract file); the API only moves it forward.
- **Who is affected**: every live trip (not lost, cancelled, completed or being cancelled) with a live AA booking line
  on the departure (held or confirmed: Booking sends the event to agencies with a live hold or a confirmed line) or an
  AA option on it in a draft / published / sent / accepted builder version (a proposal out with the client).
- **The flag** = an open case, or a case re-quoted onto a new trip while this trip is not cancelled yet. A trip
  re-quoted before booking is settled (the new version goes out as usual).
- **Task**: one urgent `aa_departure_cancelled` task for the trip owner per new case (the open-task unique index keeps
  it single). **Workflow**: the trip event `departure.aa_cancelled` (event id = uuid5 of trip and departure: one run
  per rule); the AA library's `aa_departure_cancelled_notice` mails the lead traveller from the agency mailbox,
  installed paused with a starter message (opt-in, the Linear scope's "workflow template ... (opt-in)"). The starter
  text names no supplier and no money.
- **(a) Re-quote = a NEW builder version prefilled from the trip's latest version with the tour (accepted first)**:
  the AA options on the cancelled departure move to the picked departure, their quote is cleared (the builder's
  "Refresh AA prices" quotes them on the new departure, the sell stays the agent's), `starts_on` moves so the tour's
  first day falls on the picked start date. The agent picks the departure from `GET /aa/products/{source_id}` (live
  Booking departures: open, not the cancelled one, from today).
- **A trip with an accepted version gets a new trip.** One accepted version per trip (crm-016
  `proposal_one_accepted_uq`) and `accepted` is final, and a booked trip takes no new version (draftable stages only):
  superseding an accepted version would also have to move a paid deposit between proposals. So the re-quote opens a
  new trip in Proposal (same title, client party via `trip_traveler` + `trip_party` twins, owner, destinations, lead
  source, sales partner, Stage 1/2 completeness; dates moved, same length; stage history reason `aa_rebook`) with
  version 1 copied from the accepted version (no lineage: the old trip's picks are not carried). The old trip stays
  flagged until the agent cancels it with (b).
- **(b) Cancel = the existing trip cancel with reason `aa_cancelled`**: on a flagged trip the API forces the charge
  decision to `waive` (reason `aa_departure_cancelled`, `Decision.forced`), never the owner's call (`needs_owner`
  false), whatever the dialog sent; the refunds are then prefilled with every payment in full as `proposed` refund
  requests (approved under §4.6 as usual, never sent). Booking's reason `departure_cancelled` (crm-012 mapping) costs
  the agency no fee. The cancel run closes the case (`cancelled`); the owner task is skipped with the other tasks.
  `aa_cancelled` without a flagged case keeps the agent's own decision (as before).
- **Audit**: `aa_sync` per departure (reason `departure_cancelled_cases`, the trips as object ids),
  `aa_cancel_case` (`requoted_version` / `requoted_new_trip` / `cancelled`), `create` trip (`aa_rebook`). Codes and
  ids only; no amount in any reason (integration test).
- **UI**: the trip page card (`components/pipeline/AaCancelCard.tsx`, kit only): the tour and its date, "Offer another
  date" (a select of open departures with seats), "Cancel at no charge" (opens the cancel dialog on the reason; the
  charge box shows the fixed no-charge line instead of the charge controls); the pipeline chip "AA cancelled" and the
  card badge. EN default, VI.

### Changed

- The Linear scope says "re-quote ... into a new proposal version": for a booked (or accepted) trip that is a new
  trip with a new version (see Decisions).
- The refund requests' reason reads "Trip cancelled: AA cancelled the departure (aa_departure_cancelled). No
  cancellation charge." (the reason code the lane asked for, in the refund's free text).

### Tradeoffs

- New trip vs superseding the accepted version: no money moves between proposals, the old trip's deposit is refunded
  by (b) and the new trip takes its own deposit; the cost is one more step for the agent (and the client pays again,
  or the agency books the refund against the new deposit outside the CRM).
- A trip copy, not a full clone: notes, documents, tasks, rooming and visas stay on the old trip.

### Should know

- Registries touched: `app/task_kinds.py` (task `aa_departure_cancelled`, stage reason `aa_rebook`),
  `app/workflows/model.py` (event `departure.aa_cancelled`), `app/workflows/library.py` (template),
  `app/db.py` (crm-060), `tests/integration/test_crm010_schema.py` (`CASCADE_ERASED`, in the migration PR),
  `web/lib/bff.ts`, `web/lib/i18n.ts`.
- `app/cancel_policy/rules.Decision` gained `forced`; `Assessment.view()` gained `forced` (the web hides the charge
  controls on it).
- The integration test file removes its catalog row, feed rows, pending AA requests and accepted hold sets at the end
  (the later `test_aa_lines_api.py` counts the agencies and tours the sync touches).

## crm-21: agency branding on the server PDFs

### Decisions

- **What the CRM reads today from CIS**: the membership feed (`tenant.membership.v1`), the account snapshot and its
  events (`tenant.entitlements.v1`: in service, pilot, subscriptions, entitlements), the add-ons and the invitation
  look-up. None carries a brand.
- **What CIS has**: `shared.tenant_brand_rules` (brand voice, `brand_name`, no colour, no logo; read by the Content
  studio with the tenant user's token, `/api/tenant/admin/brand-identity`, not an M2M route), and a colour only in the
  TripPlanner site theme (`shared.tenant_tripplanner_site`, served to TripPlanner by the database view
  `catalog.v_tenant_tripplanner_v1`, role `tripplanner` only). No logo anywhere.
- **So no new CIS read in this lane** (a cross-repo contract change for a colour no CIS screen sets for the CRM, and a
  logo nothing stores): the PDFs keep the agency's display name (`crm.tenant.display_name`) as the brand, now from one
  seam, `app.documents.pdf_job.agency_brand`, used by all four renders (the voucher used the voucher view's name
  before). A follow-up that adds a brand colour / logo to `tenant.entitlements.v1` (or a `tenant.profile` read) only
  changes that function and `renders._doc`.
