# AA-1096 lane L4 (S279): the CRM's admin-editable settings

Plan: root `docs/audits/2026-11-13-S279-session/thresholds-audit/README.md` (sections 3.1 CRM rows, 5, 6 lane L4,
7 Q1 / Q2 / Q5 / Q7). L1 (CIS 407, AA-CIS-App `shared/settings`, Platform › Settings) is the mechanism this lane copies.
$0: no provider call.

## Decisions

- **Own tables in `crm`, the CIS 407 shape** (root ADR 0008a: the CRM reads no shared table). `crm.setting_definition`
  (migration-only writes, guard trigger) and `crm.setting_value` (append-only, versioned, maker-checker). The value
  trigger re-checks type and bounds, so the API's 422 and the database agree.
- **crm-064 is contract, not expand.** The expand post-check requires ENABLE + FORCE RLS on every new `crm` table
  (owners.yaml `expand_rls_schemas`), and the definition table has no agency rows: its only honest policy is
  `USING (true)`, which the RLS catalogue guard refuses (rule t). So the definition table stays a platform table
  without RLS (like `crm.llm_stage_profile`) and the file ships contract: migration-only PR, Infra Migration Apply when
  the job tables are idle, then the code PR, which raises readiness to crm-064.
- **RLS on the values**: a platform row only outside any agency context, an agency's row only inside its own. Hence the
  binding reads an agency's override through the caller's own context connection (`tenant_get(ctx.conn, ...)`, a
  per-process cache of 30 s per agency), not in the process snapshot. The two-person flag is a platform row, so the
  service and the trigger read it with `app.tenant_id` cleared for that one statement when the decision is on an
  agency's row (then put it back).
- **The reader is a byte copy** of the CIS reader (`api/settings_reader.lock.json` pins the CIS commit and the sha256;
  excluded from ruff and coverage like `app/aa_llm`). The CRM binding adds only what RLS needs (the agency cache) and
  the `limit` / `dry_run` / `decimal` helpers.
- **Env vars stay one release as an emergency override** (tech lead Q5). The override is the Settings' own env value
  (`Settings.settings_env()`): set by the environment (`load_settings` records which names it saw), or, for a test app
  built from a Settings object, any field that differs from its code default. So tests that build an app with
  `rate_limit_intake_per_minute=50` still get 50, and on Dev the Terraform-set vars (`RATE_LIMIT_PUBLIC_PER_MINUTE` 60,
  `RATE_LIMIT_INTAKE_PER_MINUTE` 5, `RATE_LIMIT_INTAKE_FORM_PER_HOUR` 200, `CRM_LLM_MAX_TOKENS` 800) show
  "overridden by env" on the page until lane L6 removes them from Terraform.
- **Dry-run switches: two keys** (tech lead Q7 default). Terraform's `*_DRY_RUN` env stays a hard never-delete floor; the
  admin switch (`crm.retention.*`, maker-checker, seeded from today's effective value) is the second key; the handlers
  read both at each run (`flag(dry_run(...))`), so a switch change takes effect at the next run with no restart.
- **AI budget**: the ceiling (`crm.ai.budget_max_usd`) is `platform+tenant` (an administrator may give one agency more),
  and the gateway now enforces `min(agency budget, ceiling)`, so lowering the ceiling lowers every budget above it at
  once (it used to bound only the owner's next write). The L1 usage meter shows the same enforced budget.
- **Form quota per agency**: `crm.rate.intake_form_per_hour` is `platform+tenant`. The three intake services read the
  agency's value inside their intake context and pass it to the quota callable (`form_quota(form_id, limit=...)`); the
  limiter keeps its per-key buckets.
- **New agency defaults**: `provision_agency` writes the agency's `crm.tenant_settings` row from today's platform
  defaults (AI budget, discount limit, refund threshold, trash, archive, price checks), so the column defaults no longer
  decide; an agency without a row reads the same defaults in code.
- **Ranges the owner may pick** are settings inside the column CHECKs (which stay the hard bounds, technical); the API
  returns them (`setting_ranges` on `GET /crm/v1/lifecycle`, `markup_max_pct` on the retail markup read,
  `price_checks_bounds` already existed) and the web reads them instead of mirroring 1..30 / 12..120 / 300.
- **Range groups are checked together (review fix).** Each key was checked alone, so `trash_days_max` 5 could be
  approved while the default stayed 7, or `_min` above `_max`. Now a change of any key of a range group (trash days,
  auto-archive months, price checks) and again its approval read the group's other values in force at the same scope
  in the same transaction, under one advisory lock per group, and refuse a break of `min <= default <= max` with 422
  `range_inconsistent`. Backstop for a value written around the service: readers clamp the default into the range
  (`ps.clamped_default`: new agencies, an agency without a settings row, the lifecycle job) and swap an inverted range
  (`ps.int_range`, logged once), so the owner can always still edit. The AI budget default was already clamped to its
  ceiling and stays outside the groups (its ceiling is `platform+tenant`).
- **A narrowed range never blocks the owner (review fix).** An agency that picked 20 trash days before AA lowered the
  maximum to 10 still saves the Data and privacy form (which sends both windows): a value equal to the agency's current
  one passes; the web widens the input bounds to the current value (`inputRange`). Any new value must be in range.
- **Env override vs an agency's own value (review fix): option "refuse + remove the env var".** The env override wins
  over every agency's value (`resolve`), and Terraform sets `RATE_LIMIT_INTAKE_FORM_PER_HOUR=200` on Dev, so a per-agency
  form quota would have been approved and done nothing. (1) The service refuses an agency-scope change, and the approval
  of an open one, while the key's env override is in force: 409 `env_override_active` naming the env var (the CIS relay
  passes the message on). (2) The AA-CIS-Infra PR of this lane removes `RATE_LIMIT_INTAKE_FORM_PER_HOUR` from the CRM
  task definition (its value equals the seed and the code default, 200), so after its apply and the next Partner deploy
  the per-agency override works now instead of after lane L6. `AI_BUDGET_MAX_USD` is not set by Terraform; the same
  refusal covers it if it ever is. A history-response flag was not added: the CIS page has no agency-scope view yet.
- **Unit-test isolation**: an app built from a Settings hands its env overrides to the process-wide reader, so a file
  that built an app with a form quota of 2 changed the next file's quota (seen in a local run). `tests/unit/conftest.py`
  resets the reader's env at the start of every test file (an autouse module fixture, before the file's own module
  fixtures; CI keeps each file on one worker with `--dist loadfile`).
- **Response keys**: `crm.ops.v1` forbids the word "proposal" in a key, so the open changes are `pending` and the write
  routes are `/settings/{key}/changes` and `/settings/changes/{id}/approve|reject`; the CIS relay maps them to its page's
  shape (`proposals`).
- **Audit**: a platform value has no agency audit (it is no agency's data; the setting_value row keeps who, when and
  why, and CIS audits every relayed write). An agency's own value writes one `setting_change` event in that agency's
  audit (the owner sees AA changed one of its limits) and a history read one `ops_read`.

## Tradeoffs

- One extra SELECT per AI call and per inquiry submission (the agency's override, cached 30 s per agency and process).
- The platform snapshot is per process (30 s); an approval invalidates this process at once, other API tasks within
  one window. Same as CIS.
- The range check uses the values in force now: a sibling change approved with a future `effective_from` is checked
  when it is approved, against the values in force then, not against later scheduled values.
- Pending agency changes are not listed on the settings page (RLS: they are only visible in their agency's context, and
  listing them would open one context per agency). The history of a key for one agency shows them; changes applied in
  one step (the dev-phase self-approval) never wait.

## Should know

- Writes need the WORKFORCE group `crm-platform-admin` (as the app profile); the Dev-only E2E CIS admin is read-only
  (403 `e2e_read_only`). The live write check therefore needs a real crm-platform-admin token.
- Low-risk key for the Dev write check: `crm.payments.invoice_reminder_every_days` (single approval, no env override,
  the reminder job reads it once an hour). Change 3 -> 4, read it back on `GET /crm/ops/v1/settings` (source
  `platform`, value 4), then change it back to 3 (each change is a new version: send `base_version` = the version the
  list shows).
- Follow-ups: lane L6 removes the env vars from Terraform after one release; a stage profile / route editor (the
  `crm.llm_stage_profile` / `route` rows) is not in this lane; pending agency changes on the page.
