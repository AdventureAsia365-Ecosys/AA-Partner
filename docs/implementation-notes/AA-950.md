## Decisions

- **Migration key crm-021** (`api/migrations/021_crm_client_proposal.sql`), not "latest on main + 1" (= crm-020):
  crm-020 is already taken by AA-979's `crm.studio_invitation` (local branches `feat/aa-979-crm-studio-invitation`,
  `feat/aa-979-studio-invitations-api`, Infra worktree `infra-aa979-crm020`, SQLSTATE CRM37). crm-021 touches no
  object of crm-020, needs only crm-019 in Guard 0, adds no SQLSTATE (the next key starts at CRM38), so the two apply
  in either order.
- **Hold set on the proposal row, as the design ERD says** (group E: `proposal.hold_set_ref` UNIQUE (proposal,
  version), `recheck_count_day`), not a new hold table: a builder version is one `crm.proposal` row, so "one hold set
  per (proposal, version)" is one set of hold columns per row. `hold_set_ref` = `crm-proposal:<proposal_id>` = the
  Booking `proposal_ref` the builder quotes already use (AA-949), `proposal_version` = the version. Booking keeps one
  active hold per (partner, proposal_ref, version) and refuses another quote for that version until the first is
  released (AA-Booking `app/b2b/holds.py`), so one hold = one multi-line quote of every chosen AA option.
- **Re-checks = re-holds, counted per version per UTC day** (`recheck_day`, `recheck_count_day`, CHECK <= 3 as the
  database's backstop): the first hold of a version is free, every later hold (after expiry, or after the client
  changed an AA pick) is a re-check. UTC because Booking's own limit (429 `rehold_limit`) resets at 00:00 UTC and
  counts per `proposal_ref` too: both limits count the same thing. The 4th is refused before Booking is called
  (429 `recheck_limit`, "Ask your agent").
- **`crm.metric_event` is the bell** (design group D names it; DM-7 row exists; R4 "metric_event proposal.viewed"):
  one row per event; an event addressed to a member (`bell_member_id` = the trip owner) is a bell item until they mark
  it `seen_at` (set once). No separate notification table: the bell is a read of unseen events, grouped per
  (proposal, name) at read time, which is also the "bundled" notice (several picks -> one bell line with a count).
  crm_app inserts / reads and has a column grant on `seen_at` only (guard trigger: nothing else ever changes).
  `detail` holds ids, codes, counts and product titles only (never names, contacts or free text).
- **"Ask for a change" carries no free text**: the client sends a reason code (rooms, dates, activities, budget,
  other) and the page bundles their current choice diff (R19) into one event + one task for the trip owner. A free
  text box would store client-written personal data in a new place; the client still writes to the agent by mail /
  WhatsApp.
- **The builder acceptance gets its own columns** (`accepted_selection_sha256`, `accepted_total_amount`,
  `accepted_deposit_amount`, `accepted_hold_id`) under the crm-016 acceptance seal: the published `total_amount` /
  `price_hash` are the defaults' and sealed; the client's picks change the charged total, so the accepted amounts are
  stored apart and the payment schedule follows them. `accepted_price_hash = price_hash` (crm-016 CHECK) still pins
  the published version; the picks hash pins the choice.
- **Link cookie exchange (Fix B11) in the web, cookie routes in the API.** The link the client gets stays
  `/c/p/<token>` (AA-946). The web answers it with a redirect to `/c/p` and the host-only cookie `aa_proposal_link`
  (httpOnly, Secure, SameSite=Strict, Path `/crm/public/v1/proposal`, max 30 days = the longest link life): the token
  leaves the URL bar and history, the page script never sees it, and only the API path receives it. The API's
  `/crm/public/v1/proposal[/pick|/hold|/accept|/change-request]` read the cookie; `/p/{token}` (GET, accept) stays for
  old links and tests. No device binding: the token stays valid until `expires_at`, so a second device that opens the
  same link does the same exchange (card E). "Re-issue link" revokes it (every device loses access) and moves every
  version that carried it to the new link. One cookie per client host: opening a second agency's link replaces it
  (the first link still works when opened again).
- **A new version takes over the live link** (`service._send_builder`): when the version sent before it has a live
  link (sent / opened, same lead, at least 3 days left) the new version gets the same `link_id`; the old version is
  superseded but keeps the `link_id`, so the page finds "the superseded version on this link" and shows one bundled
  notice (added / changed / removed items by title, default changes, days count, total before and after, picks carried
  over). No per-line price in the notice (§2.9 rule 3). The send then returns `link_path: null`, `link_reused: true`
  (the token is never stored, only its hash); otherwise a new link is made as before.
- **Hold flow = three steps around Booking** (`app/proposals/holds.py`, AA-947 rule "no connection held while Booking
  answers"): plan (in the link's transaction: the AA options of the effective choice, reuse when the current hold
  covers them and is live, the re-check reserved before Booking), place (release the version's old hold when the AA
  choice changed, one multi-line quote, `POST /holds` with `Idempotency-Key = crm-proposal:<id>:v<N>:h<n>`), store (a
  new transaction). Outcomes are returned, not raised (the router sets the status), so the side effects of a refusal
  commit: the sold-out fallback, the bell, the task. 200 `held` / `not_needed`; 409 `option_sold_out` (+
  `fallback_blocks`, `ask_agent` when the default itself is gone: urgent task `proposal_hold_problem`); 429
  `recheck_limit` (ours or Booking's `rehold_limit`); 409 `hold_unavailable` (Booking refused: task); 503
  `booking_unavailable` (one bell an hour). Every answer carries the fresh page.
- **Accept of a builder version** checks, in order: price hash (published version), terms, rooms confirmed (Fix B10),
  `selection_hash` = the current effective choice (409 `choice_changed` with the new hash: another device changed it),
  then the hold box: `missing` / `stale` -> 409 `hold_required`, `expired` -> 409 `hold_expired` with `requote:
  {available, rechecks_left}` (card R; a denied audit row is kept). The schedule follows the accepted picks; the
  `collect_deposit` task is due at the hold expiry (`due_anchor = hold_expiry`, C31: the deposit must come before the
  hold runs out).
- **Viewed (R4)**: every page read moves `view_count` / `last_viewed_at`; one `proposal.viewed` event an hour; only the
  first view of a version rings. **Nudge**: the hourly `crm_stage_date_rule` run (step 7) gives the trip owner one
  `proposal_follow_up` task + bell when a sent version was first viewed 2 days ago, has no client pick and is not
  accepted; `nudged_at` makes it once per version. A follow-up task for the agent, not an automatic client message: the
  dispatcher has no proposal mail body yet (link messages are held `no_message`), and the workflow engine (M10,
  CRM-29) owns automatic client messages.
- **The bell API** (`GET /crm/v1/bell`, `POST /crm/v1/bell/seen`, `TRIP_VIEW`, every role, the caller's own items):
  unseen events grouped per (proposal, name) with a count and the latest detail. `GET
  /crm/v1/proposals/{id}/client-activity` (`TRIP_VIEW`): viewed, the hold box, R19 choices (titles + sell delta; no
  net), totals published vs current, recent events. Re-issue needs `PROPOSAL_PUBLISH` (owner / agent).
- **Choose later (Fix B9)** is a pick of the block's default with `choose_later = true`, allowed only when that default
  is an agency item with `choose_later_allowed`; an AA block answers 422 `choose_later_not_allowed`. The total counts
  the default (indicative), R26 lists it under "your agent books".
- **Option sold out mid-session (card E)**: the quote of the hold set says `sold_out` for a chosen option -> the option
  is marked sold out (crm-019 allows availability changes on a sent version), the client's pick on it deleted (the
  block falls back to its default, `selection_seq` moves), the total recomputed, a bell for the agent. A pick on a
  sold-out option is 409 `option_sold_out` (AA-949 `record_pick`).

## Tradeoffs

- **Columns on `crm.proposal` instead of a hold table**: follows the design ERD and keeps "one hold set per version"
  structural (one row = one version = one set of hold columns). Cost: the history of earlier holds of a version lives
  in `crm.metric_event` (hold_placed / rehold with the count), not in its own rows.
- **Re-checks counted per version, not per trip**: matches Booking's count (per `proposal_ref` = per version row). A
  new version from the agent resets the client's 3 a day; the agent decides to send one, the anonymous link cannot.
- **Outcomes instead of exceptions for the hold**: the router maps them to 200 / 409 / 429 / 503 and every answer
  carries the fresh page; a raised error would roll the sold-out fallback and the bell back with the savepoint.
- **The bell bundles at read time** (group by proposal and event) instead of writing one updatable row per bundle:
  events stay append-only; the bell query reads unseen rows only (partial index on `bell_member_id` where unseen).
- **A follow-up task as the R4 nudge**, not an automatic client message (see Decisions).
- **No local `next build`, no browser** (RAM rule): web `tsc --noEmit` + vitest; the page's 390 px layout is checked by
  the E2E spec (no sideways scroll) and by style (one column, `minWidth: 0`, wrapping), not by a local screenshot.
