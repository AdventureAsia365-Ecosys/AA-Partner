## Decisions

- **Rules, runs, and the library in code.** The design lists `workflow_template` (scope system | agency),
  `workflow_rule` and `workflow_run`. The AA library (system templates) lives in `app/workflows/library.py` (versioned,
  worded by the web like every other code); installing a template creates the agency's own `workflow_rule` (with
  `template_key` / `template_version`, one live rule per template). An agency "task list" (R9) is a rule with the
  `manual` trigger that a member applies to a trip. So no `workflow_template` table: the agency's templates are its
  rules, AA's are code (a later AA content feed can add a source without a schema change).
- **Triggers.** `stage_enter` (the stage), `event` (a trip event name: the `crm.metric_event` names such as
  `proposal.viewed`, `proposal.accepted`, `invoice.payment_claimed`, `invoice.overdue`, and the AA-958 seam
  `message.received` / `message.sent`), `date_anchor` (departure, return, stage_entered, last_activity, hold_expiry +
  offset days), `special_date` (birthday, passport_expiry, trip_anniversary of a client + offset days), `manual`.
  `tag` is CRM-29b (AA-960); the conditions object already has a `tags_any` key reserved for it.
- **Idempotency = the run's trigger key.** `UNIQUE (tenant, rule, trigger_key)` with keys `stage:<history id>`,
  `event:<event or message id>`, `date:<trip id>:<anchor>:<offset>:<anchor date>`,
  `special:<code>:<client id>:<date>` (anniversary: `special:trip_anniversary:<trip id>:<date>`),
  `manual:<request id>:<trip>`. A tick or a signal that runs twice inserts nothing the second time (card E). A trip
  whose departure moves gets a new key for the new date (the T-21 nudge follows the new date). **Every key names its
  subject** (S263 review fix): the constraint has no trip or client column, so a date key without the trip let only
  the first of two trips leaving on one day (or two clients with one birthday) start; the rest were dropped by
  `ON CONFLICT DO NOTHING`. Fixed in the key, not the constraint (no NULLS NOT DISTINCT / expression index needed).
- **Custom tasks keep crm-005's index.** `task_open_kind_uq` (one open task per trip and kind) stays as it is, because
  17 `ON CONFLICT (trip_id, kind) WHERE …` clauses infer it (changing its predicate would break every one of them in
  the MIG-4 window). A custom task (a member's own or a workflow step's) gets the kind family `custom_<hex>`: a random
  suffix for a member's task, a hash of (rule, step) for a workflow step, so the same step never opens twice on one
  trip while it is open. The family is worded by the title (`title_enc`, CHECK: present exactly for `custom_*`), like
  the `lost_` / `cancel_` reason families of `app/task_kinds.py`.
- **A task names a trip or a client, never both** (CHECK). Client tasks are the special dates. This keeps
  `crm.erase_held` unchanged (a trip-scope erase never deletes a task naming a client, and the other way round).
- **Runs start inside the triggering change, steps run in a job.** The trigger (one SELECT of the active rules, the
  conditions on the trip's facts, one INSERT ... ON CONFLICT DO NOTHING and one `crm_workflow_run` job) runs in the
  member's (or job's) transaction, in a savepoint that never fails the change; the steps run later in the job's own
  `system_tx` (actor `job:crm_workflow_run`). A member's stage move or apply starts after the Undo window (20 s = the
  15 s stage Undo + a margin, Fix B8): Undo stops the run before any step (`stop_for_trigger`, key
  `stage:<history id>`).
- **Waits are never queued-ahead job rows.** A queued `crm.job` row of a non-exempt kind makes the AA-CIS-Infra DB
  Migrate idle check busy, so a wait only sets `next_at`; the hourly `crm_workflow_tick` queues the run again (due now)
  once `next_at` has passed. A wait of hours is therefore precise to the hour. The only delayed rows are the 20 s
  Undo window starts (like `crm_dispatch`'s 10 s).
- **Message events through the seam.** `message.received` / `message.sent` start runs through the AA-958 listener
  (`app.messaging.events.subscribe`, installed in `app.main` with the cancel hook); `app.proposals.events.record`
  skips `message.*` names so a message never starts a rule twice (both paths would also share the key
  `event:<message id>`).
- **No message loops** (S263 review fix). A workflow's own text emits `message.sent` with a new message id, so a
  `message.sent` rule with a `send_text` step would start itself for ever (unbounded SMS / WhatsApp on the agency's
  Twilio). Three guards: `validate` refuses `send_text` in a `message.sent` rule (422 `message_loop`, the editor does
  not offer it); `on_message` skips a sent message whose dispatch row has `origin workflow`; and every message rule
  starts at most one run per trip per `MESSAGE_COOLDOWN_HOURS` (12), which caps a `message.received` rule that answers
  a client's auto-responder.
- **Conditions are checked when the run starts** (the trip as it is then); later steps check only whether the run may
  go on (rule archived / paused, trip lost / trashed / cancelled, client archived / trashed). CRM-29b's coverage
  report (R30) reads the runs.
- **Consent for marketing sends at both ends.** The engine refuses a marketing send without the client's current
  marketing yes (the step is logged `skipped_no_consent`, an audit event `workflow_send` denied, card R); the
  dispatcher's gate (`no_consent`) checks again at send time. A marketing SMS / WhatsApp is decided by the template's
  WhatsApp category, like the composer (AA-958).
- **A greeting is always marketing** (S263 review fix). A birthday or trip-anniversary rule (`model.marketing_only`):
  `validate` stores `purpose: marketing` on its send steps and refuses an explicit `transactional` (422
  `marketing_only`); `service.install` keeps each library step's purpose (an override cannot turn the greeting
  transactional); the engine treats such a run's sends as marketing whatever the stored step says. Passport expiry
  stays the owner's choice (a service notice). The editor shows the purpose locked with a hint.
- **A workflow never sends free text over WhatsApp** (the 24 h window): `send_text` always names an approved template.
  A task list (`manual`) holds no send step: a member's message to a client goes through the composer and its Undo.
- **New automations start paused** in the web editor (the owner switches them on from the card): a rule fires for
  every trip that matches, so switching it on is a deliberate step. The API accepts `status` active or paused.
- **Morning digest default off** (`tenant_settings.task_digest`): Dev agencies are synthetic and their members' mail
  goes to real test inboxes; the owner switches it on on the Tasks page.
- **Special dates are opened once or twice a day** (local 08:00-09:59) and only when a rule needs them: the DOB and
  passport expiry are F1 values under the vault DEK (at most 5,000 clients per agency per pass). Archived clients are
  left out (R: suppressed).

## Tradeoffs

- Message cool-down by a query (a run of this rule on this trip created in the last 12 hours), not by a bucketed key:
  no fixed window edges, and the key stays `event:<message id>`. Two messages in two concurrent transactions could
  both pass the check; the loops it caps are sequential (each text answers the previous one), so no advisory lock.

- Rule names and step titles are stored as plain text (agency configuration, like a message template's title): a rule
  runs for many trips, so it carries no client data by design; the editor says so. A task title is sealed (vault DEK)
  because a member's own task often names a client.

- The library lives in code: an AA template's change is a code release (a new `version`); installed rules keep the
  version they were copied from (no silent change of an agency's automation).
- A run uses the rule's current steps (it records the version it started on): an edit applies to the steps not run
  yet. Simpler than keeping a copy of the steps per run; the run log shows what was done.
