# AA-1115: the Trip planner launcher snippet on the agency's Add-ons page

The AA-Partner half of AA-1115 (the TripPlanner half, agency-only branding and the retired traveller sign-in, is in
AA-TripPlanner-Web). The S282 progress report found that the launcher (`tp.launcher`, part of every TripPlanner plan)
had no code: an agency could only send travellers to its hosted planner by hand.

## Decisions

- **A link, not an embed.** The snippet is one `<a href target="_blank" rel="noopener">`: a text link, or a link styled
  as a button with inline CSS (no stylesheet or class that could clash with the agency's site builder). No iframe and
  no script, so TripPlanner's CSP (`frame-ancestors 'none'`) stays as it is and nothing of ours runs on the agency's
  site.
- **Where it opens.** The agency's own planner domain (`https://<domain>/plan`, which TripPlanner maps to its planner)
  first, then the hosted `/{slug}/plan`; a select when there are several. https only, no credentials in the URL, the
  label HTML-escaped and capped at 60 characters (`web/lib/plannerLauncher.ts`).
- **Data from CIS, contract proposed here.** The studio session knows the tenant id but not its slug, its active
  planner domains or its plan's launcher flag. The page reads them from the tripplanner entry of
  `GET /v1/account/add-ons` as `planner: {url: string, domains: string[], launcher: boolean}` (url = the hosted planner
  URL of the tenant, domains = its ACTIVE custom planner hosts, launcher = the `tp.launcher` entitlement). Until CIS
  sends `planner`, nothing is shown (no broken snippet).
- **Every studio role sees it** (owner, editor, viewer): it is read-only information about an add-on the agency
  already has; only the add-on request stays owner-only.
- **Default label** follows the studio language ("Plan your trip" / "Lên kế hoạch chuyến đi"); the agency can type
  its own.

## Changed

- `web/lib/plannerLauncher.ts` (new), `web/app/(studio)/portal/_components/AccountAddOns.tsx` (`PlannerLauncher`),
  `account.messages.ts` (EN + VI), `CONTEXT.md`.
- Tests: `web/tests/plannerLauncher.test.ts` (new), `web/tests/studio/addOns.test.ts` (three launcher cases).

## Tradeoffs

- The button colour is a fixed dark blue in the snippet: the agency's brand colours live in CIS site settings, which
  the add-ons answer does not carry. The agency can restyle the pasted link on its own site.
- The CRM's own Settings › Add-ons page (for an owner without a studio membership) does not show the launcher yet:
  its list comes through the CRM API relay (`app/cis/addons.py`), which would need the same field passed through.

## Should know

- **The CIS half ships in the same wave** (AA-CIS-App branch `feat/aa-1115-addons-planner-site`):
  `GET /v1/account/add-ons` answers `planner` {url, domains, launcher} on an active tripplanner entry
  (`services/tenant_account/planner_site.py`). The URL is set only when the tenant is in service and `tp.hosted`
  resolves; domains are the ACTIVE `shared.tenant_tripplanner_domain` hosts; launcher is `tp.launcher`. Until the CIS
  API is deployed, this page shows no launcher (no broken snippet), so the launcher is verified live only after both
  deploys. The CRM relay (`tenant.addons.v1`) does not carry `planner` (see Tradeoffs).
