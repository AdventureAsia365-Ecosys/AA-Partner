# AA-1066 — CRM retail pricing: price per traveller type, agency price rules, discount with owner approval

Lane l8 of S275. Source: the S275 study of a tour and travel app (root
`docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`, items crm-05, crm-06, crm-07; build plan Phase 1
ranks 1, 5 and 6). The app is OPL-1: only its behaviour was read, no code was copied. Business defaults follow the
S275 questions to the business owner (discount limit 10 %); every default is a per-agency setting.

## Decisions

- **One contract migration, crm-048**, for the three items: ALTERs of `crm.tenant_settings` (age bands 11 / 1,
  discount limit 10), `crm.proposal.discount_pct`, `crm.option.price_rules`, three new base-template tables and the
  `crm.status_transition` rows of `discount_approval`. MIG-4: migration-only PR, then the code PR.
- **Erasure by cascade, no new `crm.erase_subject`.** `crm.option_price` cascades from its option
  (`(tenant_id, proposal_id, option_id)`), `crm.discount_approval` from its proposal, `crm.retail_price_rule` from the
  agency's `tenant_settings` row (the agency erase deletes it). Listed in `CASCADE_ERASED` of
  `tests/integration/test_crm010_schema.py` (the crm-029 / crm-040 pattern). Deleting a draft option in the API takes
  its rows along, so no child-first delete was added to `_delete_blocks` / `delete_option`.
- **Draft-only rows** reuse `crm.guard_proposal_draft` (it reads `proposal_id` and passes the eraser), so a
  published version's traveller prices never change (CRM35) whatever path writes. No hold guard on `option_price`:
  `crm.guard_held_change` must not run inside a cascade (it would read every agency's holds with row security off,
  see crm-019 / crm-029), and the option's own hold guard already protects the parent.
- **Price per traveller type** (item crm-05):
  - Types `adult`, `child`, `infant`, `single_supp` (the single room supplement). The sell of an option with rows is
    the sum of `unit_sell x qty`; an agency item's net the sum of the unit nets when every row has one (a partial set
    is 422 `unit_net_partial`); an AA item never takes a unit net (403 `aa_net_from_quote`).
  - No currency column on the rows: the proposal has one currency and every option uses it.
  - While rows exist a typed sell / net / `use_suggested` on the option is 409 `amount_from_prices` (the rows decide).
    `[]` removes the rows and keeps the sell they summed to.
  - **The grid** (`suggested_prices`) shares the suggestion (else the current sell) per adult and child head, rounded
    up to the cent; infants and the supplement start at 0. booking.b2b.v1 quotes a line total, not a price per
    traveller type, so the grid cannot start from an AA split today (a Booking contract change, the study's bk-15).
  - **Age bands** are the agency's retail bands only (Settings > Pricing). The Booking quote keeps AA's rule
    (`rules.room_pax`: infants under 2), so an infant is never a seat in the quote; nothing sent to Booking changed.
  - The client page shows the types and counts (`price_lines`: "Adult × 2 · Child × 1 · Single room × 1"), never a
    unit price (design rule §2.9 / D1: never a per-line price).
  - The price hash adds `option_prices` and `discount_pct` only when a version has them, so the hash of every version
    published before this change stays the same.
- **Retail price rules** (item crm-06):
  - Kinds: `season` (the option's service date in a date range, at most a year), `group_size` (the party, at least
    `min_pax`), `early_booking` (`days_before` days or more before the service date), `last_minute` (`days_before`
    days or fewer). Each kind carries exactly its own condition (a CHECK and the service's 422).
  - Scope: all AA products or one Booking component kind, optionally one AA tour. Agency items get no rule: they have
    no base price the rule could adjust (the agent's own sell is the price; adjusting it would compound on each use).
  - Stacking: every matching `add` rule sums; of the matching `best_only` rules only the first by priority (then the
    lower percent) applies, on top of the add rules; the total never below -90 %. Rules apply after the AA-1030
    suggestion (agency markup on the B2B price, else AA's RRP x party), rounded up to the cent.
  - "Today" is the agency's time zone date; no service date (day 1 not set) = season and booking-window rules do not
    match (group rules still do).
  - The rules used are stored on the option (`option.price_rules`, a snapshot of id, name, percent) when the sell
    comes from the suggestion; a typed sell clears them. The suggestion itself stays computed at read time (AA-1030).
  - Owner only, under `PAYMENT_SETTINGS` like the retail markup; at most 50 rules per agency.
- **Discount with owner approval** (item crm-07):
  - A percent (`proposal.discount_pct`), not an amount: it scales with the client's picks and the limit is a percent.
    It comes off the charged total, never off pay-on-arrival items. `builder._charged` is the one place, so the
    builder totals, the deposit, the client page, the hold / accept amounts and the text proposal all follow it.
  - Needs the owner when above the agency limit or when the discounted total is below the net (a sale at a loss;
    known only when every chosen option has a net). Covered by an approved row **of the trip** at that percent or more
    (and approving the loss for a loss), so a working copy at the same discount does not ask again; a raised discount
    is no longer covered (the approval re-opens).
  - Agents ask (`POST .../discount-approval`, one pending row per version, a new request supersedes it, an urgent
    `discount_approval` task for the first active owner); owners decide (`DISCOUNT_APPROVE`, new matrix row, owner
    only). An owner's Publish records their own approval (decided by themselves) instead of asking.
  - The publish refusal is 409 `discount_needs_approval` (raised after the other publish checks), and the builder
    view lists it as the blocking check for a non-owner and as the warning `discount_owner_approves` for the owner.
  - The database guard (CRM48) also lets only an owner decide, as themselves, and only the decision columns change;
    `crm_app` has no DELETE on the table.
  - `below_cost` is margin data: the service never builds it for the assistant (and the serializer strips `*_cost`).

## Tradeoffs

- Rows as a child table rather than JSON on the option: one row per type keeps the CHECKs, the draft guard and the
  cascade simple, and the client page and the price hash read them like any other builder row. The option keeps its
  `sell_amount` (the sum), so every existing total, hold and invoice path is unchanged.
- The discount in the ledger (review fix): the AA lines an accepted version writes
  (`app/booking/proposal_lines.py`) record each option's sell less its share of the discount
  (`builder.line_sells`: `sell × (1 − pct/100)` to the cent per charged option, the rounding remainder on the
  largest charged option, pay-on-arrival untouched), so the charged sells add up to exactly the accepted total and
  the line margin and the sales reports are not overstated. Chosen over one ledger adjustment row: the ledger has no
  trip-level adjustment kind, and a per-line sell keeps each line's margin right. A re-quote keeps the line's
  recorded (discounted) sell, as before. Agency items are not written to the ledger from a proposal (the agent adds
  them), so their share of the discount only matters for the sum.
- The discount is sealed (review fix): crm-048 recreates `crm.proposal_sealed` with the crm-019 column list plus
  `discount_pct`, so no write path changes the discount of a published, sent or accepted version (CRM31); app code
  only writes it on a draft (`update_settings` under `_lock`, the copy into a new draft).
- Approvals cover the trip, not one version: an agent who copies a version keeps the owner's decision; the cost is that
  an approval stays valid for the trip until the discount rises above it.
- No rule on agency items, no per-traveller split from AA: both need a base this release does not have (see above).
- The rule matching runs on every builder view of a version with AA options (one extra read of the rules and the
  agency time zone): read-time like AA-1030, so a re-quote or a rule change shows at once.
