# AA-1067 — CRM retail: payment schedule with instalments, traveller reminders, cancellation policy, charge and refund

Lane l2-crm-1067 of S276. Source: the S275 study of a tour and travel app (root
`docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`, items crm-08, crm-09, crm-11, crm-12). The app is
OPL-1: only its behaviour was read, no code or text was copied. Business defaults follow the S275 proposals to the
business owner (30 % now / 40 % at T-60 / rest at T-30; the cancellation table "31+ days 10 %, 15-30 days 25 %, 8-14
days 50 %, 7 days or fewer 100 %"); each one is a per-agency setting the owner edits.

## Decisions

- **Two migrations, one batch (crm 049-050).** `crm-049` is **expand** (three new tables and one guard function, no
  change to an existing object): `crm.cancellation_policy` (versions), `crm.cancellation_policy_tier`,
  `crm.cancellation_charge`. `crm-050` is **contract** (ALTERs of `payment_schedule`, `proposal`, `tenant_settings`,
  `invoice`; seal triggers recreated; a unique index replaced; the view). Both ship in one migration-only PR, applied
  before the code PR (MIG-4 for the contract file; the expand file is auto-applied first by number).
- **Instalments in the existing table.** `payment_schedule.kind` gains `instalment`; `seq` is the instalment number
  (1..10; 1 for the deposit and the balance, so every existing row is valid without a backfill UPDATE); `percent` is
  the planned share. The live unique index becomes `(tenant_id, proposal_id, kind, seq)`.
- **Partial and overdue are derived, not stored.** The stored status stays `due | paid | void` (no new status moves,
  no settle-path changes); `crm.v_schedule_status` (security_invoker) derives `live_status` paid / void / overdue /
  partial / due from the payments on the row (every invoice payment and refund carries `schedule_id`) and the agency's
  day; `paid_at` stays per row. The issue text said "status adds partial / overdue (overdue derived)": deriving both
  keeps one source (the payments) and avoids a status the settle code would have to keep in step.
- **The plan lives on the proposal.** `proposal.schedule_plan` (builder versions only) holds the lines the agent set;
  `deposit_pct` and `balance_due_on` mirror its deposit and last line so every reader of the old pair (the client
  page's deposit, the proposal_amounts CHECK, the text proposal) keeps working. A new skeleton starts from the agency
  template (`tenant_settings.schedule_template`, NULL = the AA default) dated from day 1; a line keeps `days_before`
  while it follows the template, so a new day 1 moves it; a typed date drops it. The price hash adds `schedule` (and
  `cancellation_policy_id`) only when present, so every version published before keeps its hash. The seal covers both.
- **Money per currency.** Amounts round half up to the currency's unit (whole units for VND, JPY, KRW, …; cents
  otherwise; `ZERO_DECIMAL` now lives in `app.payments.schedule_plan`, `text_render` imports it); the deposit is at
  least one unit; the last line takes the rest, so the rows always add up to exactly the accepted total. A version
  without a plan keeps the crm-019 deposit math (cents) unchanged.
- **The stage gate still keys on the deposit row** (crm-016 unchanged): instalments never move a stage.
- **Text proposals keep the deposit / balance pair** (the issue scopes the editable lines to the builder). They do
  pin the cancellation policy at Send like the builder does at Publish.
- **Reminders (crm-09) use the existing `date_anchor` trigger** with two new anchor values, `schedule_due_soon`
  (offset -60..0) and `schedule_overdue` (offset 1..60), so the `crm.workflow_rule` CHECK did not change. The hourly
  tick starts one run per open schedule row of the accepted proposal (`schedule:<row>:<anchor>:<offset>:<due date>`),
  never for a row paid in full, and at most one reminder run per row every 3 days (any rule). The engine re-checks at
  send time (`skipped_paid`) and fills `{{payment_amount}}` (the open amount) / `{{payment_due_date}}`.
- **Opt-in.** The two library templates (`payment_due_soon` at T-7, `payment_overdue` at +3) install **paused** even
  with a message template (`starts_paused`); `starter_mail: true` copies an EN or VI starter message (the agency's
  default language) into the agency's own message templates. The CRM mails a traveller only after the owner switches
  the rule on. Mail goes from the trip owner's mailbox, else the agency's (the engine's existing rule).
- **Cancellation policy versions are immutable once published** (guard CRM49): a change is a new version
  (`replaces_policy_id`); publishing it retires the old one and takes over its default flag. A proposal pins the
  agency default when it goes out (builder Publish, text Send) unless the agent chose a version; the client sees it on
  the proposal page (`cancellation_policy`) and in the booking terms through the merge field
  `{{cancellation.policy}}` (also on the portal signing pages, from the accepted proposal). "Frozen at accept" in the
  issue is met earlier: the version the client reads is sealed from publish / send.
- **The cancel dialog's charge** (`charge` block of `POST /trips/{id}/cancel`): days before departure (agency day; a
  started trip or no date = 0 days), the frozen policy (else the current default, warning `policy_not_frozen`), its
  tier and charge, the decision (`policy`, `override` with amount + reason, `waive` with reason), money paid, the part
  kept, the refund due and the fee invoice amount. Refund requests are **prefilled** with what is left of each payment
  once the charge is kept from the oldest payments (the member may still change each amount). An agent lowering the
  policy charge by more than `refund_owner_threshold_base` (base currency; no rate = owner) gets 403
  `cancel_charge_owner_only`: the owner does it (synchronous, no new approval table).
- **AA fee warning**: the dry run, after Booking's fee per booking, adds `charge_below_aa_fee` when the charge is
  below the sum of AA's fees in the trip currency (`aa_fee_amount`), `aa_fee_other_currency` when a fee cannot be
  compared.
- **The fee invoice (crm-12)** bills only the charge **not covered by money the agency keeps** (`charge - kept`),
  issued at once by the run (kind `cancellation_fee`, one charge line naming the policy, tax included); money already
  paid is not moved between invoices. Nothing to bill = no invoice.
- **`crm.cancellation_charge`** records each cancellation's figures once (insert-only, CRM49). It is the **seam for
  crm-30's trip P&L** (AA-1068): fee = `charge_amount`; AA's cost stays the booking line money `cancellation_cost`;
  `GET /trips/{id}/cancellation-charge` reads it. No P&L view is built here.

## Changed

  (new: `rules.py` pure, `service.py`), `app/proposals/{builder,public,client_page,service,text_proposal,text_render}`,
  `app/cancellation.py`, `app/stages.py`, `app/invoices/{service,render}.py`, `app/payments/claims.py`,
  `app/portal/public.py`, `app/esign/{merge,signing}.py`, `app/calendar/ics.py`, `app/workflows/{model,library,
  service,tick,engine}.py`, routers `builder`, `pipeline`, `ledger`, `workflows`.
- Cancel run: due **instalments** are voided with the due balance (S262 rule), the date rule's sweep too.
- Invoices: `instalment` rows bill like deposit / balance (`create_from_schedule`, the client pay box).

## Tradeoffs

- Deriving partial / overdue in a view costs a per-row payment sum on read (an index on `payment (tenant_id,
  schedule_id)` was added); the tables are small per agency.
- A waiver above the threshold needs the owner to do it (Forbidden for an agent) instead of a request / approve flow
  like discounts: cancellations are rare and urgent, and the refund requests the run creates already go through the
  §4.6 approval.
- The fee invoice bills the shortfall, not the full charge: an invoice for the full charge would need the payments to
  move from the deposit / instalment invoices, which the ledger (append-only, one invoice per payment) does not do.
