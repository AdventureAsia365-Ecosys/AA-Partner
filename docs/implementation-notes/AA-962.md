## Decisions

- **No new table, an expand migration (`crm-030`).** Every new tenant table must be added to `crm.erase_subject`
  (its agency scope refuses `erase_incomplete` for an unknown table), which makes the file a contract and means
  replacing the function from the latest text. Two other S261 lanes (crm-028, crm-029) may replace that function too,
  so a new table here would have to be rebased on their text. Instead: `import_ref_bidx` columns on `traveler` / `trip`
  / `note` and onboarding / controller / acknowledgement columns on `tenant_settings`. All go with their rows on erase,
  the `*_bidx` columns are never exported (portability rule), and ADR 0017 lets the file auto-apply on Dev and ship
  with the code (`REQUIRED_SCHEMA_VERSIONS` += `crm-030`, one PR). The Infra expand lint (`run_migration.lint`) passes.
- **No CHECK / unique index in the migration** (an expand file may not add one to an existing table): values are
  checked in `app/onboarding.py` / `app/imports/spec.py`, and like every blind index the import refs have a partial
  non-unique index; uniqueness is kept under the per-agency import lock.
- **The import record is the job.** Preview stores nothing (the report is the response). Start stores the file in the
  ingest bucket (`imports/<tenant>/client-<id>`, deleted after the last slice; the bucket's 1-day rule is the
  backstop), and the progress / history endpoints read the `crm_client_import` job rows of the agency
  (`payload.import_id`, counts in `result`). So a run leaves no personal data in the database beyond the rows it
  created, and the history lives as long as the job retention (30 days succeeded).
- **One engine for dry run and apply** (`app/imports/engine.py` `run(apply=...)`): the preview shows exactly what the
  job will do. Outcomes `create` / `match` / `already_imported` / `duplicate_in_file` / `invalid`, warning
  `possible_duplicate`. Any invalid value makes the row invalid (skipped, listed): the agency fixes the file and runs it
  again; the rows already in are skipped (idempotent), so "fix and re-run" is the whole workflow.
- **Idempotency key per entity**: clients `client_ref`, trips `trip_ref`, notes `note_ref` or a SHA-256 of
  (client_ref, trip_ref, date, text); relationships the pair. Refs are blind-indexed (16-byte HMAC, `Vault.ref_index`,
  normalised NFKC + casefold + collapsed spaces).
- **Matching existing clients**: e-mail, then phone blind index (R6). A match links the ref (when the client has none)
  and changes nothing else; a marketing consent column is written for **new** clients only, so a re-import never turns
  a client's marketing back on (also what CRM-36 needs: "an unsubscribed contact re-imported stays suppressed").
- **Trips** arrive closed (`completed` default when the dates are past, `cancelled` / `lost` with reason `other`) or as
  an open `inquiry`; booked / travelling trips are not importable (their money and gates are not in a file).
- **Permissions**: new actions `CLIENT_IMPORT` (owner: a bulk write of client data, like the agency export),
  `CLIENT_MERGE` (owner: one client goes to the trash, like a client delete), `ONBOARDING_MANAGE` (owner). Reading the
  checklist and duplicates: every role. Controller settings and the acknowledgement: `DATA_SETTINGS` (owner).
- **Merge refuses evidence it cannot move**: client links, portal access, signatures and accepted terms are tied to
  the traveller through composite keys and sealed rows; moving them would rewrite evidence. The API answers 409
  `merge_blocked` with the blockers and whether keeping the other client would work; the page offers the swap.
- **Duplicates list** = live clients sharing `name_bidx`, `email_bidx` or `phone_bidx` (exact, no decrypt to find
  them), 50 pairs per page, one `list_view` event. No "not a duplicate" dismissal is stored in v1 (it would need a
  table, see Should know).
- **Acknowledgement text** is a proposal (EN / VI in `web/lib/i18nOnboarding.ts`), version `2026-10-31.1` in
  `app/onboarding.py` and `web/lib/onboarding.ts`; the business owner's legal wording replaces it with a new version.
- **`.xlsx` without a dependency**: a small `zipfile` + `xml.etree` reader of the first sheet (shared / inline strings,
  numbers, booleans; dates arrive as serial numbers and the date cleaner accepts them), every zip member size-checked.
- **Help links** point to `/help#<topic>`; the Help section, an empty state until now, becomes a page of short EN / VI
  guides (the full help centre with videos stays with its own card).

## Changed (vs. the card text)

- "CSV import" also accepts `.xlsx` (the lane brief asked for CSV/XLSX).
- The checklist's "connect Stripe or choose bank transfer" counts either an active Stripe or an active manual payment
  method; "deposit rules", "kickoff call", "help centre" are owner-marked (no data shows them yet).
- Connections: SMS / WhatsApp has no setup page yet (CRM-28), so its card says the setup arrives later; the calendar
  card reflects the ICS feed (the only calendar connection today).

## Tradeoffs

- No import table: no list beyond 30 days and a retried slice counts the rows its failed attempt committed as
  `already_imported` instead of `create`. Accepted for no erase / contract change; a table can come later in a
  contract file once the S261 lanes have landed.
- Dedupe of rows with neither e-mail nor phone relies on the ref only: two files that give the same person different
  refs create two clients, shown as possible duplicates for the merge screen.
- After a merge, the merged client's ref is carried to the kept client only when the kept one has no ref; re-importing
  a row with the other ref then matches by e-mail / phone, or creates a duplicate when the row has neither.

## Should know

- Migration number: `crm-030` was given to this lane; `test_every_file_registers_its_key` and the Migration preflight
  need `main` max + 1 at merge. If crm-028 / crm-029 have not landed first, renumber (`git grep '030_'` and
  `git grep crm-030`). Its Guard needs only crm-027 objects.
- The import job reads the file from the ingest bucket: it needs `CRM_INGEST_BUCKET` (set on Dev for the mail
  import); without it `POST /client-imports` answers 503 `mail_ingest_not_configured`.
- New job kind `crm_client_import` (not deploy-gate exempt, not Infra idle exempt): it exists only while a slice is
  queued / running.
- `payload_guard.CONTROL_KEYS` gained `region` (an ISO country code for local phone numbers).
- The margin contract test lists `/crm/v1/client-imports/{import_id}` as unseeded (owner-only counts).
- Follow-ups not in this slice: a stored "not a duplicate" dismissal; Google / Microsoft calendar and Twilio rows in
  Connections once those connectors exist; the business owner's acknowledgement wording.
