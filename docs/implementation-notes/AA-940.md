## Decisions

- **The crm-003 table becomes the first partition, it is not copied.** PostgreSQL cannot turn a table into a
  partitioned one in place. crm-007 renames `crm.audit_event` to `crm.audit_event_legacy`, creates the partitioned
  parent with the same columns, CHECK names, index names and the tenant FK, and ATTACHes the old table FOR VALUES
  FROM (MINVALUE) TO (start of next UTC month). No row is rewritten (append-only holds literally), no `DROP TABLE`
  (so no `-- migrate: destructive` snapshot), and the index names stay the crm-003 ones so a crm-003 re-run is a
  no-op. The primary key becomes `(event_id, at)` (a partitioned key must hold the partition column); the legacy PK
  is replaced by the same pair before ATTACH. `event_id` stays a random UUID, so the lost global uniqueness on
  `event_id` alone is not a practical risk.
- **`at` = insert time (`clock_timestamp()`), and only the owner may set it.** The export closes an hour and never
  re-reads it; an event must not appear in an hour after that hour is exported. `now()` is the transaction start
  (tenant_tx writes its events at the end of the transaction), so the default moved to `clock_timestamp()`, and a
  trigger refuses an explicit `at` more than a minute away from the insert time unless `current_user = crm_owner`
  (tests, a future restore). The trigger only checks, it never changes `at`: a BEFORE ROW trigger that moved a row
  across a month boundary would fail the partition routing. The export also waits a lag (15 min) after an hour ends.
- **Partitions: one per UTC month, three months ahead, made by a SECURITY DEFINER function without arguments**
  (`crm.audit_ensure_partitions()`), so `crm_app` can run it from the hourly job but cannot make anything else. Each
  partition gets ENABLE + FORCE RLS, its own `tenant_isolation` policy, the TRUNCATE trigger (statement triggers are
  not cloned) and `REVOKE ALL ... FROM crm_app` (the schema's default privileges grant DML on every new table; a query
  through the parent checks the parent's privileges and policy only). No DEFAULT partition: a row with no partition
  fails the insert, which fails the request (fail closed, like a failed audit write fails a reveal); the metric
  `AuditPartitionMonthsAhead` and its alarm warn long before.
- **Retention = dropping whole partitions, only after verification** (`crm.audit_drop_expired_partitions(dry_run)`):
  a partition goes when it ends at or before the start of the UTC month twelve months ago (the agency always sees
  at least 12 months) and every agency in the registry has `verified_until >= its end` (DM-7: "a partition is
  dropped only after its export is verified"). `DROP TABLE` fires no row trigger, so every row the database keeps
  stays append-only. Dry run by default (DM-7.2), like the job retention.
- **Offboarding path without DELETE.** The design keeps the audit after an erasure (§4.10: "audit_event has no PII
  and is kept"), so no DELETE path is added at all: the agency is locked / trashed (its tenant row stays and the FK
  holds), the export keeps running for it (the export context accepts a locked or trashed agency), its rows leave
  with the monthly partition drops (at most 13 months after its last event), then nothing references the tenant row
  and CRM-35 can delete it. The registry row cascades; the manifests have no FK and stay with the archive. Tested
  end to end in `test_crm007_schema.py::test_offboarding_waits_for_the_partition_drop`.
- **Export registry `crm.audit_export_tenant` with RLS enabled but not forced.** The hourly job needs the list of
  agencies and the drop needs every agency's verification mark, but `crm_app` cannot list `crm.tenant` (FORCE RLS)
  and FORCE RLS also binds the owner's SECURITY DEFINER functions. The registry therefore enables RLS (the tenant
  policy: `crm_app` sees and updates the row of `app.tenant_id` only, and the ecosystem catalogue rule a is met)
  without FORCE, so the owner functions `crm.audit_export_agencies()` and the drop see every row. Rows come from an
  AFTER INSERT trigger on `crm.tenant` and a one-off backfill (FORCE lifted on `crm.tenant` and the audit parent for
  that one statement, restored in the same transaction; Guard 1 checks). ON DELETE CASCADE with the tenant row.
- **Manifest table `crm.audit_export_manifest`**: one row per agency per hour, append-only template variant, a
  BEFORE INSERT trigger enforces the chain in the database (seq 1 with 64 zeros, then seq + 1, the previous
  `manifest_sha256`, `period_start` = previous `period_end`). No FK to `crm.tenant` (DM-7: the manifest "follows the
  archive", seven years) and no partitions yet (about 8,800 rows per agency per year; a retention job is due only
  when the first rows reach seven years).
- **Export format 1: one object per agency per hour, carrying its own manifest.** Line 1 is the canonical manifest
  (`format`, tenant, seq, period, `event_count`, `content_sha256`, `prev_manifest_sha256`) with its hash; then one
  canonical JSON line per event, ordered by `(at, event_id)`. Key
  `audit/v1/tenants/<tenant>/<yyyy>/<mm>/<dd>/<hh>00Z-<seq>.jsonl`. The chain can therefore be walked from the archive
  alone after the database rows are gone. Per agency, not one object for all agencies: the archive follows the
  agency (download, offboarding, a regulator's request) and the chain lives under the same RLS as the agency's data.
  Empty hours get an object too (`event_count` 0): every hour of an agency is covered by exactly one manifest, which
  is what lets verification say "nothing was added or removed later". Cost of the empty hours: 24 x 2 PUTs per agency
  per day (about $0.007 per agency per month).
- **Retry safety by determinism, not by read-back.** One transaction per agency per hour: lock the registry row, read
  the last manifest and the hour's rows, build, PUT compliance, PUT governance, insert the manifest, move the
  registry, commit. Any failure rolls back; the retry rebuilds the same bytes (closed hour, same previous hash) under
  the same key, so a bucket that already had the first copy just gets a second identical locked version. The card's
  E test does exactly this with an outage after the first bucket.
- **Verification is a separate step** (`python -m app.audit_export.verify`, and the daily `crm_audit_retention`
  incrementally from `verified_until`): rows re-read and re-hashed per hour while the partition exists, chain links,
  manifest hashes, and both archived copies byte for byte. `verified_until` only moves when an archive is configured
  and the agency is clean, so without the buckets nothing can ever be dropped.
- **Sign-ins are recorded by the web, through the API.** The API never sees a sign-in as such (Cognito managed
  login, then the web's session); the moment a session opens an agency is `/auth/agency` (auto-pick or the chooser).
  It now sends `POST /crm/v1/audit/sign-in` with that agency, best effort (a failed audit call does not block the
  sign-in; the API logs its own failures). Action `sign_in`, object `member:<id>`.
- **Refused owner-only actions are audited as `denied`** (form create / change, reassigning a trip, an assistant
  deleting a document), and the access log's own views / downloads are audited (`audit_view`, `audit_export`).
- **AI context builds**: one `ai_context_build` event per LLM gateway call, actor kind `ai_agent`, actor ref
  `ai:<stage>`, object the `llm_call` row (whose `created_by` names the member or job that asked); a refusal is
  `denied` with the refusal code. Gives the WF-8 [AI] chip something to show.
- **Key operations**: `key_create` (first DEK of a purpose), `key_rotate`, `key_rewrap` (one per run), `key_destroy`,
  object `tenant_key` / `<purpose>:v<version>`.
- **Access log page = owner only, codes and ids.** The permission matrix gives the access log to the owner only
  (agent: trip Activity only, a later card). The page never decrypts a traveller's name (that would itself be a list
  view to audit, and the log is meant to be safe to download); lines name the member's role and a short id and link
  a client or trip id to its page, where the reveal rules apply. Download CSV (spreadsheet formula guard) or JSON
  lines, at most 50,000 rows, through the BFF as a blob (the BFF forwards only Content-Type, so the file name is set
  by the page). Non-owners see an explanation and the page does not call the API.

## Changed (vs. the card text)

- "hourly export to both buckets" is per agency per hour (see Decisions); the 12-month compliance tier stays
  GOVERNANCE on Dev (the Infra precondition refuses COMPLIANCE outside Go-real).
- The card names no offboarding path; the AA-934 comment asks for one. It is "no DELETE at all, wait for the
  partition drop", not a privileged purge function (Decisions).
- Added two metrics + alarms (`AuditExportLagMinutes`, `AuditPartitionMonthsAhead`) that the card does not list: an
  export that stops or a partition that is missing would otherwise be silent until a request fails.
- Agent "trip Activity" view of the audit is not in this card (the trip workspace Activity tab belongs to the trip
  cards); the API shape (`object_id` filter, matching `object_ids` too) is ready for it.

## Tradeoffs

- Attaching the crm-003 table (no copy, no DROP, no snapshot) vs. a copy into a fresh partitioned table (cleaner
  partition names, but `DROP TABLE` = destructive migration + RDS snapshot, and rows rewritten). The legacy partition
  holds everything up to the end of the month the migration runs in and is dropped as one unit 12 months later.
- Registry with RLS enabled but not forced vs. a BYPASSRLS role (needs role DDL in Infra) vs. a FORCE'd registry and
  a GUC-gated permissive policy (equivalent power for `crm_app`, but disguised). The owner functions need to see every
  agency; `crm_app` still sees one row at a time.
- No DEFAULT partition: a DEFAULT partition never fails an insert, but a row in it blocks creating that month's
  partition later (and moving it needs DELETE on an append-only table). Fail closed + alarm instead.
- Hourly per-agency objects vs. daily: the design says hourly; at 100 agencies that is ~144k PUTs a month (~$0.72).
