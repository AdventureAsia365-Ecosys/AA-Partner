# AA-1096 — settings and threshold editing UIs (S280 "check and fix everything", lane crm)

The verified findings of the CRM settings audit (S280, 14 items) fixed in one branch. Earlier AA-1096 notes of this repo:
`AA-1096-l4.md` (the registry, lane L4) and `AA-1096-settings-lint.md`. $0: no provider call.

## Decisions

- **Per-agency values on the settings list (high).** `GET /crm/ops/v1/settings` now carries, per setting,
  `agency_overrides` (each agency's own value in force) and `agency_pending` (each agency's open change), both with
  `tenant_id` and `agency_name`; empty for a platform-only key. crm.setting_value is FORCE RLS, so the service opens one
  platform context per agency of the registry (as the L1 agency list does) and reads only the platform+tenant keys.
  No migration: a SECURITY DEFINER summary function was the alternative; one transaction per agency is fine at today's
  agency count. An agency gets an `ops_read` audit event (reason `settings`) only when it has rows (nothing of the
  others is shown). The CIS relay passes unknown keys through (`_page_row` copies the setting), so no CIS change is
  needed for the data; the CIS page has to render it (live step). crm.ops.v1 1.14, additive.
- **Backdated `effective_from`**: refused (422 `effective_from_in_past`) when older than now minus 5 minutes (clock
  skew, a technical constant). At approval a second check: when an approved row of the same scope with a later
  effective_from is already in force, the approval is refused (409 `superseded_by_later`): it would be recorded as
  approved and never apply. Clamping on approval was not possible without a migration (the crm-064 trigger keeps
  effective_from fixed after the proposal).
- **Change body**: `reason` min 20 and `evidence_ref` 3 to 500 characters in the request model (the crm-064 CHECKs),
  so a 1-2 character evidence no longer reaches the database as a CheckViolation (500). The service mirrors both with
  422 codes (`reason_too_short`, `evidence_invalid`). The definition carries `reason_min`, `evidence_min`,
  `evidence_max` so the CIS page can say it before sending.
- **History diff of an agency**: the value an agency's first own value replaced is the platform value in force at
  that row's effective_from (from the platform history, read outside the agency context), else the compiled default.
- **Staff agency overview**: `ai_budget_usd` is now the budget the gateway enforces (min(saved, ceiling)); new keys
  `ai_budget_max_usd`, `ai_budget_max_own`, `intake_form_per_hour`, `intake_form_per_hour_own`. The support reader
  role has no grant on crm.setting_value, so `app/support/reads.py` `_policy_reader` steps out of it for that one read
  (a savepoint, back to the reader after; kept private to the read module, not in `tenancy.py`, which is at its
  code-health line ceiling). Those rows are AA's own values for the
  agency, not agency data, so no identity consent applies.
- **Retail markup after a lowered ceiling**: a value equal to the stored one passes even above the current ceiling
  (as the lifecycle windows); a new value must be inside it. The refusal names the product type (`kind`, `max`) and the
  form marks a stored value above AA's limit and sends only the changed kinds.
- **Price checks a minute**: the same rule (the current value stays savable after AA narrowed the range); the refusal
  carries `min` / `max`; the form maps it to the range message, flags a stored value outside the range and gives the
  range hint through the kit Field `hint` (announced with the input).
- **Refund owner-approval threshold**: the owner now sees and sets `refund_owner_threshold_base` on Settings ›
  Payments (`GET` / `PUT /settings/payments`, 0 to 10 000 000, the crm-008 column CHECK), in the agency's base
  currency, with a warning that a base-currency change keeps the number. An agent's `above_threshold` refusal carries
  `limit` and `limit_currency`, and the refund panel shows the amount.
- **Platform-default guides** now say the truth: a new-agency default applies to agencies created after the change
  (and to older agencies without settings); an existing agency keeps the value it started with. The AI ceiling and the
  form quota guides say that a per-agency value also creates the agency's settings (freezing its other defaults) when
  it had none. The definition texts (migration seed) were already accurate ("an agency with no settings row").
- **AI settings page**: rate limit 0 reads "No per-minute limit"; the ceiling is "the most Adventure Asia allows for
  your agency", not a plan limit, with "contact AA to raise it".
- **Forms**: a failed pipeline-settings read shows an error to the owner (not "only the owner"); allowed-website
  refusals say the rules (https://host[:port], no path, at most 10) inside that form's panel; each form card shows and
  edits its privacy link (empty = the agency's link from Connections) and default owner; the hourly submission quota
  is shown read-only (from `GET /intake-forms`).
- **Settings › Payments**: a panel whose read failed shows an error in a panel with its title instead of vanishing.

## Tradeoffs

- One platform transaction per agency on every settings list read: simple and RLS-honest; if the agency count grows
  past a few hundred, replace it with a SECURITY DEFINER summary (a crm migration).
- The refund threshold default stays one number in "the agency's base currency" (a product decision, see Should know).

## Should know

- **Not fixed here (needs a decision)**: a currency-aware refund threshold default. Proposed answer: keep the per-agency
  value (now editable by the owner) and replace the platform default by a USD amount converted to the agency's base
  currency at provisioning (a crm migration: new key `crm.payments.refund_owner_threshold_default_usd`, unit USD).
- **Not fixed here (needs a migration)**: "follow the platform default" for agencies (NULL settings columns resolved
  at read time). Today the guides describe the copy-at-creation behaviour truthfully.
- The CIS Platform › Settings page needs to show `agency_overrides` / `agency_pending` (approve / reject with the row's
  `tenant_id`) and use `reason_min` / `evidence_min` — the CIS lane. The root contract `crm.ops.v1` gets a 1.14 note.
- Code-health follow-up (second commit): the support read module keeps its own `_policy_reader` (no new helper in
  `tenancy.py`, at its line ceiling), `staffSettings.settingValue` is a format table (its complexity entry left the
  baseline), and the Forms page / card are split into small parts (`FormLinks`, `FormOrigins`, `FormDetails`). No
  behaviour change. Checked locally: `scripts/pre-push.sh` (13 checks), and the touched + related integration tests
  (`test_aa1096_settings_db`, `test_support_access_api`, retail / payments / book-now / crm-064 / crm-008, 109 tests)
  on a throwaway PostgreSQL 16.
