# AA-1027 slice F3: AI draft UI in the CRM trip workspace

S263 gateway gap plan row F3 (gap CRM-4), design v3 R39 / M14 / A-21. Lane l6 of S264.

## Decisions

- **Table `crm.ai_draft` (crm-040, expand).** The schema reference (crm-039) had no such table, so one migration
  creates it. Columns: trip, `kind` (`reply` | `follow_up`, the draft endpoint's kinds), `llm_call_id` (the ledger row
  of the call), `prompt_version`, `output_enc`, `decision`, `feedback_code`, `decided_at`, `decided_by`, plus the base
  template columns. One draft per ledger call (`UNIQUE (tenant_id, llm_call_id)`).
- **The draft is stored as the model wrote it** (placeholders such as `<PERSON_1>` kept, never restored at rest), and
  encrypted under the agency's vault DEK (`output_enc`, `pii:free_text`). The scrubber is best effort (the terms say
  so), so the text may still hold a detail it missed; every other CRM free text (notes, messages) is vault-encrypted
  too.
- **No prompt is stored.** Design v3 lists `prompt_scrubbed` (kept 30 days). It is left out: nothing reads it yet, the
  ledger row keeps the prompt hash, and storing it would need a 30-day clearing job. A later slice (R39 learning,
  33b) adds it together with that job.
- **No `validation jsonb` yet** (R39 rule checks against Booking): that is CRM-33b work; the column comes with it.
- **`decision`, not `status`.** The catalogue guard requires a `status` column to use `crm.status_transition` rows,
  which a migration would have to INSERT (config rows = contract class). The one move (pending -> accepted |
  discarded, once) is held by the guard trigger `crm.guard_ai_draft` (CRM47) instead, so crm-040 stays expand: one
  PR, auto-applied by Migration Apply.
- **No key to `crm.llm_call`.** The ledger is purged after 180 days (crm_lifecycle); the draft stays with its trip.
- **Erasure:** cascades from its trip (`ON DELETE CASCADE`), listed in `CASCADE_ERASED`; no `erase_subject` change.
- **Entitlement `ai_assist` enforced on the draft endpoint** (AA-964 left it for later). Order: trip exists ->
  plan has `ai_assist` (else 403 `feature_not_allowed` with a `denied` audit event) -> AI switched on (409
  `ai_disabled`) -> gateway. A missing `crm.tenant_entitlement` row means no (the default `allowed_features` is
  empty). `GET /settings/ai` carries `ai_assist_allowed` so the web can disable the action and say why.
- **Accept / discard:** `POST /crm/v1/ai/drafts/{id}/accept|discard` with an optional `feedback_code` from a fixed
  list (`good`, `wrong_facts`, `wrong_tone`, `not_relevant`, `too_long`, `other`). Accept needs `ai_draft_approve`
  (owner, agent; assistant only on a trip assigned to them, like `message_send`); discard is every role's (`ai_use`).
  Accepting sends nothing: the panel copies the draft to the clipboard; the member pastes it into the message and
  sends it (R39 "humans send").
- **Web:** an "AI draft" card under the trip panel with a Draft button that opens the kit `Drawer`; the drawer has the
  kind, the client's message, an optional instruction, the draft with the kit `AiNotice` (staff variant) under it, a
  feedback select and Copy and accept / Discard. Without the plan or with AI off the button is disabled and the
  reason is shown (the owner gets a link to Settings > AI). Strings in `lib/i18nAiDraft.ts` (EN + VI).
- **The draft row is stored in a savepoint (review fix).** It is written after the paid call, inside the same
  `tenant_tx`. Like the gateway's placeholder map, a draft row that cannot be stored (vault/KMS error, a CHECK or the
  guard, the trip gone in between) rolls back only its savepoint: the `crm.llm_call` ledger row, the rollup and the
  map commit, the member still gets the restored text, and `ai_draft_id` is null (the panel then offers no
  accept / discard). Only the error class is logged (no audit outcome fits: audit outcomes are allowed / denied).

## Changed

- `agency_ai.draft` now returns `ai_draft_id` (null when the gateway gave no usable answer) and checks the plan.
- `agency_ai.ai_settings` returns `ai_assist_allowed`.
- `agency_ai.draft` keeps the paid call logged when the draft row fails (savepoint); unit tests cover a KMS failure,
  a refused INSERT and the released savepoint; the integration test `test_a_draft_row_the_database_refuses_keeps_the_paid_call`
  proves on PostgreSQL that a CHECK violation on `crm.ai_draft` leaves the `crm.llm_call` row committed.
- Integration helper `_trip()` of `test_aa964_ai_gateway.py` allows `ai_assist` for the agency by default (the
  drafts of those tests now need it).

## Tradeoffs

- Enforcing `ai_assist` turns AI drafts off for every agency until AA allows the feature in the L1 console (CIS admin
  Platform > Agencies drawer, "Allow features"). On Dev the E2E agency needs that one step before the live check.
- Storing the draft encrypted means a later report on edit distance must decrypt in the agency's session; that is
  fine for the R39 metrics (computed per agency).
