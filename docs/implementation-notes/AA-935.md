Card: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §6.3 CRM-07 and `lanes/delivery-plan.md` CRM-07;
`final/crm-design-final.md` §1.4 ("Sign-in before P2b") and §4.4 (row "CRM skeleton": cross-links both ways); the

## Decisions

- **The web runs as its own Fargate service, not on Vercel.** CONTEXT.md and ADR 0010 decision 2 put the agency host
  on CloudFront -> VPC origin -> ALB; the AA-931 spike proved SSR streaming there, and `crm_edge.tf` already said
  "AA-935 changes this action to a forward to the web target group". So: Next.js `output: "standalone"`, image on a
  native arm64 runner, ECS service `aa-crm-dev-web`, ALB default rule of the partner host -> web; `/crm`, `/crm/*`
  stay on the API rule above it. One host, no CORS.
- **The web reaches the API through the public partner host** (`CRM_API_ORIGIN` = `https://partner-dev.…`) over the
  NAT, not the internal ALB: the ALB rule for `/crm/*` requires the CloudFront origin secret, which the web would then
  have to hold. Cost: NAT bytes of JSON at Dev volume (cents). The API sees the same path and checks as for any client.
- **Sign-in = Cognito managed login, code + PKCE, confidential `cis-portal` client** on Dev (card "same `cis-portal`
  client as the portal"; design-final §1.4 corrects v3: the portal still signs in with its API key, so there is no
  shared session yet). AA-939 swaps the env values to the partner pool and its web client; no code change.
- **Server session in sealed cookies, no session store.** AES-256-GCM with a per-purpose HKDF key; the access token
  cookie is `__Host-` (host-only, Path=/), the refresh token cookie `__Secure-` with Path=`/auth` so pages and BFF
  calls never carry it. A store (DynamoDB / Redis) would be new infrastructure and cost for one value per person.
  The web never verifies the token signature itself: the API does on every call; the web only reads `sub`/`exp` and
  refuses a token of another client.
- **Refresh by redirect.** A page whose access token is expired (60 s skew) goes through `/auth/refresh?next=…`
  (the only route that sees the refresh token), which renews it (rotation on, the new refresh token replaces the old)
  or falls back to sign-in. BFF calls answer 401 `session_expired` instead of redirecting.
- **Membership lookup needs a migration (`crm-004`).** After sign-in the web knows only `(iss, sub)`; the crm-002
  policies show a member row only once `app.tenant_id` is set, so nothing could list a person's agencies. Two
  SELECT-only permissive policies TO `crm_app` keyed on `app.caller_iss` / `app.caller_sub`, set only by
  `caller_memberships()` from the verified token. Inside `tenant_tx()` they are false, so isolation is unchanged; they
  give no write (INSERT/UPDATE/DELETE still need `tenant_isolation`); the NOLOGIN readers get neither. Integration
  tests prove: own rows only, never a colleague's row, no write, no foreign rows inside `tenant_tx()`.
- **`crm.tenant.display_name` + `default_locale` in `crm-004`.** The sidebar needs the agency name and R32 needs a
  default locale. The CRM keeps its own label until the CIS membership feed (AA-978) carries the CIS agency name. The
  name column default `'Unnamed agency'` only fills older rows and tests that insert without a name (the AA-934 lane's
  tests, for one); `app/agencies.py` always passes a name.
- **The 422 rule lives in `app/agencies.py` (`provision_agency`)**, shared by the seeder now and the L1 console's
  "create agency" (CRM-13a / AA-941) later, raised as `Invalid` (the existing 422 `ServiceError`). No `/crm/ops/v1`
  route is added here: that card owns the contract, the audit event and the group rule. The reverse rule (prod refuses
  synthetic) is in the same check, so CRM-38 only adds tests.
- **`provisioning_tx()`** is a second context in `app/tenancy.py` for creating an agency before any member exists; the
  DB-access lint accepts it, a new static test allows it only in `app/agencies.py` and `app/seed/`.
- **Seeder = a module in the API image** (`python -m app.seed`), run with ECS Exec on `aa-crm-dev-api` (it has the
  `crm_app` DSN). DRY RUN by default, `--apply` converges; fixed UUIDv5 ids, so idempotent by construction. Three
  synthetic agencies (card: 2–3): `sen-vang` "Lữ hành Sen Vàng" (vi-VN, owner/agent/assistant), `southern-cross`
  (en-AU, owner/agent), `harbour-lights` (en-US, owner). Members only from `--member KEY:ROLE:SUB`: the seeder never
  invents a Cognito subject.
- **Faker travellers are generated, not written.** `crm.traveler` exists since the AA-934 vault (`crm-003`), but rows go in
  only through its field encryption, with the intake card (AA-936 intake / AA-937 F1). `app/seed/travellers.py` is the
  deterministic EN/VI generator those cards import (Vietnamese order family-middle-given, NFC, `.invalid` e-mail,
  E.164 phones); the seeder reports the planned counts and `nfc_round_trip`.
- **EN/VI without a library.** Two plain dictionaries with a test that both have every key; the date locale (en-AU,
  en-GB, en-US, vi-VN) decides the UI language. `Intl.DateTimeFormat` in UTC for calendar dates; display always spells
  the month, typed dates follow the locale order and the field shows its reading (card E test: 2026-04-03 is "3 Apr"
  for en-AU and "Apr 3" for en-US; "03/04" typed is 3 April day-first, March 4 for en-US).
- **The UI kit is vendored, byte for byte** (`app/_kit/*`, `app/_brand/tokens.ts`, `lib/{sameOrigin,crossSiteGuard,
  bffPath,proxyResponse}.ts`), checked by CI "Vendored CIS copies" against AA-CIS-App main, as the portal does
  (design-final §4.2 "one kit"; shared package AA-655 later). The palette CSS is copied from the portal globals.
- **The CSP is set per request in `proxy.ts`**, because its `form-action` must name the Cognito domain from the
  environment (the sign-out form is answered with a redirect to the managed-login logout page).
- **Host routing in the proxy**: partner host, client host (`/c/*` only), anything else 404; `/healthz` for any Host
  (ALB health checks use the task IP).
- **vitest 4.1.12 with `legacy-peer-deps`** (`web/.npmrc`): vitest 3.x carries a critical dev-only advisory (tinypool)
  and npm 10 crashes resolving vitest 4's optional browser peers. The flag applies locally, in CI and in the image.

- **Review round 1 (independent agent review, approve with non-blocking items).** Fixed:
  - `/robots.txt` and `/icon.svg` are public on both hosts (`lib/hosts.ts`): without a session they went to
    `/auth/refresh` and sign-in, so crawlers never read `Disallow: /` and every signed-out page started an OAuth chain
    for its favicon.
  - **One-shot refresh marker** (`_rf=1`, `withRefreshMarker` / `hasRefreshMarker` in `lib/hosts.ts`): a page whose
    `/crm/v1/me` or `/crm/v1/memberships` answers 401 goes to `/auth/refresh` once, with the marker on the return path;
    a second 401 there shows an error state ("did not accept your sign-in", link to sign in) instead of looping
    page -> refresh -> page (and calling the Cognito token endpoint every round) when the API refuses tokens this web
    accepts, e.g. a wrong EXTERNAL issuer or `cis-portal` client id in the API's environment.
  - `/health` caches its two API probes for 10 s per process: they leave through the NAT and share the API's public
    per-viewer rate-limit bucket, so anonymous traffic on `/health` could make the API look down.
  - `select-agency` encodes the inner `next` of its refresh return path (a `next` with `&` lost its tail).
  - The crm-002 catalogue guard now lists every non-`tenant_isolation` policy by `(table, name)` with its command and
    roles (`EXTRA_POLICIES`): an unlisted permissive policy fails it. This makes the crm-004 header comment true
    without touching the migration file (which stays byte-identical in all three places).
  - Comments: the seeder catalogue names `tools/identity/crm_dev_identity.py e2e-users`; the Deploy Web Dev smoke
    comment no longer claims the web answers `/crm/*` 404.
  - Not changed: `Faker` stays a runtime dependency (the seeder runs in the image on Dev; a seed-only image or extra
    is a prod-readiness item); `workflow_dispatch` + environment `dev` can deploy an unmerged branch, the same as the
    existing API deploy (restrict the `dev` environment's branches before prod).

- **S249 sign-in check fixes (branch `fix/aa-935-signout-settings-date`).** The live check of the deployed web
  (root `docs/audits/2026-10-24-S249-aa935-signin/`) failed two items:
  - **Sign-out answered 403 and left the session.** Root cause: the vendored AA-911 rule compares the browser's
    `Origin` with `request.nextUrl.origin`. Next standalone behind CloudFront -> ALB builds that URL from its own
    bind address (`HOSTNAME=0.0.0.0`, `PORT=3000`: `http://0.0.0.0:3000`, Next `attachRequestMeta`), never from the
    partner host, so every same-origin browser POST looked cross-site. The same 403 hit the language switch
    (`/prefs/locale`), the agency pick (`/auth/agency`) and every BFF write; unit tests missed it because they built
    requests on the public URL. Fix: `web/lib/writeGuard.ts` `refuseForeignWrite(cfg, request)` hands the vendored
    guard `WEB_PUBLIC_ORIGIN` as the expected origin (the request's own origin only when that is unset), and all four
    write routes use it. The vendored `sameOrigin.ts` / `crossSiteGuard.ts` stay byte copies. CSRF protection is
    unchanged: a foreign `Origin`, `Sec-Fetch-Site: cross-site` or `same-site` (another `*.lumiguides.it.com` host) is
    still 403; sign-out stays a POST-only form (GET 405), no GET logout was opened. The UI already posts the form from
    the top bar and the agency chooser, so no UI change. Sign-out itself was right once past the guard: it revokes the
    refresh token, expires `__Host-aa_crm_s` (Path=/), `__Secure-aa_crm_r` and `__Secure-aa_crm_tx` (Path=/auth), and
    303s to `<COGNITO_DOMAIN>/logout?client_id=…&logout_uri=<WEB_PUBLIC_ORIGIN>/signed-out` (the registered URL).
  - **The /settings date field read nothing.** Root cause: the check typed into the server-rendered field before
    React hydrated it. React 19 keeps the DOM text of a controlled input on hydration (`initInput(…, isHydrating)`)
    but fires no onChange, so `DateInput` state stayed `""`: no reading, empty hidden ISO value, until the next
    keystroke. The parser was right (`parseDateInput("03/04/2026", "vi-VN")` = `2026-04-03`). A real person on a slow
    phone hits the same. Fix: on mount `DateInput` adopts the value already in the DOM and marks the field
    `data-hydrated="true"` (browser checks can wait on it).
  - Tests: `web/tests/writeGuard.test.ts` (requests built like the ALB delivers them, `http://0.0.0.0:3000/...`:
    sign-out 303 + three expired cookies + logout URL, foreign origin 403 with no cookie change and no revoke, locale /
    agency / BFF past the guard, and a static check that every route with a write method calls `refuseForeignWrite`
    and none calls the vendored guard directly); `web/tests/dateInput.test.ts` (jsdom: `renderToString` +
    `hydrateRoot` with text typed before hydration, vi-VN "3 thg 4, 2026" and en-AU "3 Apr 2026", plus typing after
    hydration and en-US). Both files fail on the old code. New dev dependency `jsdom` 30.1.2 (exact pin, tests only;
    vitest stays `node` by default, a file opts in with `// @vitest-environment jsdom`).

## Tradeoffs

- **Sealed cookies vs a session store.** Revocation before expiry is coarse (sign-out revokes the refresh token at
  Cognito; a stolen access token lives up to 30 minutes, the same as for every Cognito client). A store would allow
  instant revocation at the price of new infrastructure; revisit with the partner pool (AA-939).
- **Public-host hairpin vs internal ALB** for web -> API: one extra CloudFront hop per call (~10–30 ms) against not
  spreading the origin secret.
- **Empty pages for the whole IA now** vs only the built ones: an agency (and the reviewer) sees the final navigation
  from day one; every page says what will be there, nothing pretends to work.

## Should know

- **Write routes must call `refuseForeignWrite(cfg, request)`, not the vendored `refuseCrossSiteWrite(request)`**:
  behind the ALB `request.nextUrl.origin` is the server's bind address. `tests/writeGuard.test.ts` fails a route that
  forgets. Any route that builds a URL from `request.nextUrl` / `request.url` has the same trap (`lib/respond.ts`
  already builds redirects on `WEB_PUBLIC_ORIGIN`).
