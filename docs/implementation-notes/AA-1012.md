# AA-1012 (CRM-25b) — PAdES-B-B signed PDF of a signed envelope

Card: design v3 §6.3 CRM-25 checklist item "e-sign v1 with PAdES via `seal`" (left open by AA-955, see
`AA-955.md` "Changed"). Builds on AA-955 (the sealed text envelope) and AA-1070 (the server PDF writer
`app/documents/pdf.py` with Liberation Sans embedded).

Branch: AA-Partner `feat/aa-1012-pades-signed-pdf` (one code PR, no migration).

## Decisions

- **The PDF is built at download, not stored.** The evidence stays the AA-955 text envelope (docs DEK, on the
  `signature_event` row, DM-7 claim-period exception). The PDF is a rendering of that envelope plus a PAdES signature
  made when it is downloaded. Storing it would need a new object family the trip / traveller erase skips (the erase
  deletes every `crm.document` object of the trip) and the purge knows: not worth it for a file we can rebuild
  byte-for-byte from the evidence. Each download costs one `kms:Sign` (and the existing `kms:Verify` of the stored
  seal); Dev signs a handful.
- **The PDF carries the envelope itself.** `envelope.txt` (the exact sealed bytes) and `seal.json` (envelope SHA-256,
  seal algorithm, seal value, the KMS key id without the account part, evidence SHA-256, signed-at) are embedded files,
  so anyone can recompute the SHA-256 and check the original KMS seal from the PDF alone. The visible pages render the
  same text: the envelope parser (`app.esign.envelope.parse`) splits the canonical format into header, documents and
  audit page; a text it cannot split (an agency text holding a 72-dash rule line) is printed as one block, never
  refused.
- **Renderer**: a new builder `renders.signed_agreement` on the existing writer (`app/documents/pdf.py`, Liberation
  Sans embedded whole as a CID font: Vietnamese renders, no new font pipeline). Labels EN / VI by the agency's locale
  like the AA-1070 documents; the agreement texts are the agency's own words. It is not a `crm_pdf_render` job kind:
  nothing is stored, so no job and no `crm.document` kind.
- **Signature**: pyHanko `async_sign_pdf` with `SigSeedSubFilter.PADES` (`/ETSI.CAdES.detached`), SHA-256, no
  timestamp (= PAdES-B-B), an invisible signature field `PlatformSeal`. The signer (`app.esign.pades`) is a pyHanko
  `Signer` whose `async_sign_raw` hashes the signed attributes and calls the existing `KmsSealer.seal` (`kms:Sign`,
  `RSASSA_PSS_SHA_256`, `MessageType = DIGEST`): the same call, key and IAM conditions as the AA-955 seal, so no IAM
  change. The CMS signature mechanism is `rsassa_pss` (SHA-256, MGF1-SHA-256, salt 32 = what KMS uses). The private key
  never leaves KMS; the app holds only the certificate chain.
- **Certificate (Dev)**: a self-issued company CA and a leaf certificate for the seal key's public key.
  `api/scripts/esign_seal_certificate.py` (run by the orchestrator with the admin profile: `kms:GetPublicKey` only,
  allowed to the account's IAM admins by the key policy's `IamAdministration` statement) builds them with
  `app.esign.certificate.issue_chain`: the CA key is generated in memory, signs the CA and the leaf, and is dropped
  (never written anywhere). The chain (leaf then CA, PEM, public data only) is committed at
  `api/app/esign/certs/seal-chain-<environment>.pem`; the app picks the file of its `ENVIRONMENT`. Renewal or a seal
  key rotation = run the script again (a new CA) and commit the new file. The prod CA decision stays at go-live.
- **The app checks the chain against KMS** at the first PDF of each process: `kms:GetPublicKey` (granted:
  `CrmSealPublicKey`) must equal the leaf's public key, else 503 `pdf_seal_mismatch` (a rotated key with an old
  certificate never produces a PDF that names the wrong key).
- **When a PDF cannot be signed**: no KMS seal key (local / test without `KMS_SEAL_KEY_ID`) or no chain file for the
  environment = 503 `pdf_seal_not_configured`; KMS not answering = 503 `seal_unavailable` (the AA-955 code). A stored
  KMS seal that KMS rejects (tampered) = 503 `document_integrity`, no PDF.
- **Routes**: staff `POST /crm/v1/signatures/{id}/pdf` (`DOCUMENT_DOWNLOAD`, a reveal reason like the envelope, one
  `reveal` audit event with field `envelope_pdf`); traveller `GET /crm/public/v1/traveller/agreements/{traveler_id}/pdf`
  (signed-in session; the acting traveller's own envelope, or one they signed as guardian; else 403
  `envelope_not_yours`; one `portal_document` audit event). Both answer the documents shape
  `{filename, content_type, content_b64}` (+ hashes) the web already downloads.

## Changed (vs the card / plan)

- Nothing is stored (see Decisions); the card's "signed PDFs an insurer accepts" depends on the prod CA decision.
- The old `/crm/public/v1/portal/{token}/...` routes get no PDF route: the web portal uses the cookie routes
  (`/traveller/*`) only.

## Tradeoffs

- pyHanko brings aiohttp, lxml, oscrypto, tzlocal, uritools, certifi (Python wheels; no system package, so the
  Dockerfile's "install nothing new" rule holds). It is imported lazily (first PDF), so the API start and memory do not
  change until a PDF is asked.
- A per-download signature means two downloads of one envelope are two different PDF files (signing time differs);
  both carry the same embedded envelope and the same envelope SHA-256.
- The certificate chain is in the public repo: it is public material (a certificate and a public key, no account id,
  no ARN). A Secrets Manager secret would need Infra (secret shell, execution role, task def) for no secrecy gain.

## Should know

- Live steps: run the certificate script, commit the chain (second PR), deploy, then download a signed envelope on Dev
  and validate it with pyHanko (`pyhanko sign validate --pretty-print --trust <chain CA> file.pdf`).
- No migration, no IAM change: `CrmSealSignVerify` already allows `kms:Sign` with exactly `RSASSA_PSS_SHA_256` +
  `DIGEST`, and `CrmSealPublicKey` allows `kms:GetPublicKey`.
