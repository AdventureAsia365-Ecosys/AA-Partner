# AA-1072: "Book now" on the public tour page and online deposit / instalment payment

Items crm-02 and crm-03 of the S275 study (root `docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`).
Behaviour only; no code of the studied app. Migration crm-057 (contract), then this code PR.

## Decisions

- **Business-owner defaults (S275 Jira draft, proposed answers):** "Book now" is a per-agency switch, **off by
  default** (`tenant_settings.public_booking_enabled`, owner only, Settings > Online booking); the first online gateway
  is **VNPay** (`vn_gateway`, the agency's own merchant account); Stripe stays behind its existing paused provider
  name (ADR 0019 b14) and still answers `provider_not_available`.
- **Which agency a public tour page books for:** the trip page is AA's catalogue page (no agency in it). The agency's
  link carries its intake form key: `/trip/<tourId>?f=<form key>`. The public routes open `intake_tx(form key)`, so
  the agency is decided exactly as for the inquiry form (an unknown, disabled or locked form is 404, keys cannot be
  probed), and the form's honeypot field, allowed origins and default owner are reused.
- **Which AA product the page is:** the CIS trip page answer has no catalogue key today. The widget sends the tour
  page id and an optional `p=<catalog source id>` from the link; the API takes `p` when it names a served tour of the
  catalogue cache, else the page id when it is itself a catalogue key (a tour without a source group: CIS 258
  `source_key = COALESCE(source_group_id, tour_id)`). Neither = no widget (the page shows "Ask the agency" only).
  Follow-up for CIS: add `source_id` to `GET /v1/trip/{id}`; the web already reads it when present.
- **Live price** = the agency's retail on the live Booking quote: the AA-1030 suggestion (owner markup on the B2B
  price, else AA's RRP x party) with the AA-1066 price rules, rounded up to the cent; the same function the builder
  uses (`builder._suggestion`). No suggestion = 409 `no_retail_price` (the page says to ask the agency). The B2B price
  never leaves the server.
- **What a booking creates** (one transaction after the quote, `app/intake/booking.py`): always a new traveller (see
  the next point), a trip at stage `proposal` with
  `lead_source = web_booking`, the party and the departure dates, a one-option builder proposal (day 0, day 1 with one
  "Tour" block holding the AA option at the retail price, per-traveller price rows), published and sent through the
  builder's own `publish` / `send` (price hash, terms, cancellation policy, schedule plan from the agency template).
  The answer is the client link path `/c/p/<token>`; the page goes there and the existing client page does the hold,
  the accept and the deposit. A repeated press answers `already_created` without a second link.
- **A booking never reuses an existing client (review fix, S277).** The first build deduped the traveller by e-mail
  then phone like the inquiry form. The inquiry form never hands back a link, but Book now answers a live client link,
  so the dedupe became an unverified identity binding: anyone who typed a known client's e-mail got a link to a trip
  led by that client and could accept (terms acceptance pinned to that client's traveller id), place the hold and
  trigger the deposit invoice, with the client's F2 profile pre-filled. Now every booking makes a new client with its
  own F2 profile; an archived client with the same e-mail stays archived. When another live client already has the
  e-mail or phone (one `EXISTS` on the blind indexes), the trip gets an `internal` note asking the agent to confirm
  with the client and merge the two on Clients > Duplicates (the existing AA-962 merge), plus an audit event
  `public_booking_known_contact`. The answer is the same in both cases, so it still never says whether an e-mail is
  known.
- **Deposit invoice at accept for a web booking:** a client who booked online expects to pay at once. When the
  accepted version's trip has `lead_source = web_booking`, the accept also issues the deposit invoice (the agent's
  own `create_from_schedule` + `issue`, actor the client link), so the pay box shows the bank details or "Pay online"
  right away. Other trips keep the agent-issued invoice.
- **Online payment = hosted page + signed webhook (VNPay 2.1.0).** The client page's card button (existing route
  `POST /crm/public/v1/proposal/invoices/{id}/card`) now creates a `crm.payment_session` for the invoice's open amount
  (computed on the server from the invoice and its payments, never from the browser) and answers the gateway URL; the
  card never touches the CRM. The gateway's IPN (`GET /crm/public/v1/hooks/vnpay/ipn`) is verified with the agency's
  own hash secret (HMAC-SHA512 over the sorted `vnp_*` fields) before anything is read beyond the reference; the
  payment is written once per gateway transaction (unique index of crm-057) through the same code as "Record payment"
  (settles the schedule row, Proposal -> Booked, the Booking confirm, the re-hold of a late deposit).
- **Never block on a business error:** money the gateway took is always recorded. When it cannot settle the invoice
  (invoice void or paid meanwhile, amount above what is left, newer terms waiting), the session goes to `review`, the
  payment row is still written (against the invoice) and the trip owner gets an urgent `payment_review` task; the IPN
  answers success so the gateway does not retry forever. A bad signature answers `97`, an unknown reference `01`, a
  wrong amount `04`, a repeat `02` (VNPay's codes).
- **Credentials:** the merchant code is the account row's `external_account_id`; the hash secret and the mode are a
  `vn_gateway` `integration_credential` sealed under the agency's integration DEK (the Twilio pattern). Mode
  `sandbox` (VNPay's sandbox host), `live`, or `stub` (a deterministic simulator page of this API, refused on prod,
  which signs a VNPay-shaped IPN with the agency's own secret and runs the real handler: the Dev live check without a
  merchant account).

## Tradeoffs

- **New client per booking vs an e-mail code before the redirect.** A one-time code would keep one record per person,
  but the CRM has no platform sender: client mail goes only through the agency's own connected mailbox (card R, no
  fallback to AA's SES), and the proposal send's dispatch row carries no message (it ends `held / no_message`), so
  nothing would deliver the code for an agency without a mailbox. "Answer without the link and e-mail it" fails for the
  same reason. A new client per booking needs no mail, keeps the redirect to the pay page, and uses the existing
  Duplicates merge; the cost is that a returning client who books online twice shows up twice until the agent merges.

- **Synchronous booking vs a job**: the client waits on the page and needs the link at once, so the booking is made
  in the request (three steps, no connection held while Booking answers). The cost is one Booking product read and
  one quote per press, bounded by the per-address intake limit and 5 attempts an hour per address and agency.
- **Reusing the builder with a non-member context**: `builder.publish` and `proposal_service.send` run with the
  intake form's `SystemContext` (they only use `ctx.conn`, the audit queue and `member_role`, which is None). There is
  no discount, but the owner-approval gate also checks a total below the net (`below_cost`): the S277 live check hit
  it for one adult (see "S277 live check fixes" below), so the public path now refuses such a party itself first. The alternative, a second publish / send path, would drift
  from the builder's checks (price hash, terms, policy pin).
- **Rounding up per head** (whole dong for VND): the client may pay up to (heads - 1) units more than the exact
  retail total, so a gateway can charge every line exactly; shown before booking, never hidden.
- **The deposit invoice at accept only for web bookings**: agent-built proposals keep the agent-issued invoice (an
  agency may want to adjust it); a client who booked alone has nobody to issue it.
- **Stub gateway in the API** (an HTML page on the client host) instead of a web page: it must sign with the agency's
  secret, which only the API may open; dev / test / local and stub-mode accounts only.
- **Refunds through the gateway API** are not built: the agency refunds in its VNPay portal and records it (the
  provider's `refund` records the reference), as with manual payments. Follow-up when an agency asks.

  oldest live client, as before.

- The CIS trip page answer has no catalogue key: on Dev the live check uses a link with `p=<source id>` (or a tour
  without versions, whose page id is its key). Follow-up (CIS, one field): `source_id` in `GET /v1/trip/{id}`.
- The VNPay protocol is implemented from VNPay's public 2.1.0 integration guide (sorted `vnp_*`, `quote_plus`,
  HMAC-SHA512, IPN codes 00/01/02/04/97/99). It has been exercised against the stub only (no merchant account in this

## S277 live check fixes (lane l34)

The S277 live verification on Dev (root `docs/audits/2026-11-11-S277-crm-live-verify/README.md`, synthetic agency)
found four issues; one PR, no migration.

### Decisions

- **Gateway status follows the active account** (finding 1). `gateway.status()` read the `vn_gateway` credential,
  which a disconnect keeps on purpose (webhooks of sessions already started must still verify), so it said
  "Connected" after a disconnect. It now answers `connected: true` only with an **active** `vn_gateway` account and
  its credential (the same condition `pay_online` and the card button use). The credential is not removed or
  deactivated: that would break the IPN of a session started just before the disconnect.
- **A reconnect reuses the account row** (finding 1). `connect` takes the agency's active `vn_gateway` row, else its
  most recently connected one (`FOR UPDATE`) and reactivates it (`disconnected -> active` is an allowed transition
  since crm-024) with the new merchant code; a row is inserted only when the agency never had one. The Dev agency
  keeps its three old disconnected rows (history, harmless); the newest is the one reactivated.
- **Book now never sells below cost; it refuses with its own code** (finding 2). With no agency markup the retail is
  AA's RRP x heads; for one adult that was under the B2B price (a single traveller's supplement), so the builder's
  owner discount gate (`below_cost`) stopped `publish` and the page showed the generic error. Pricing the line at the
  RRP anyway would make the agency pay out of pocket on every single traveller without anyone approving it, and a
  floor at the net would invent a price with no margin. So `price` and the booking answer 409 `price_on_request`
  ("the agency prices this trip for your party on request: send them a question") when the grid total is under the
  quote's B2B price, the same comparison as the gate (`sell < money(b2b)`). The widget shows it at the price check,
  so the visitor never reaches "Book now" for that party; the booking repeats the check (prices can move between the
  two) before anything is written.
- **Such a refusal does not use an attempt** (finding 2): the per-address count skips attempts `refused` with a code
  in `UNCOUNTED_REFUSALS` (only `price_on_request`). The row is still written (the agency sees the demand).
- **The price check has its own limit** (finding 3): `booking_price_limiter`, `RATE_LIMIT_BOOKING_PRICE_PER_MINUTE`
  (default 20 per address) instead of the intake bucket (5) that the booking, hold, accept and "Pay online" share.
- **The client page's dates follow its schedule** (finding 4), on the API side (`client_page.client_dates`, one place
  for the builder and the text page): accepted, `balance_due_on` = the last schedule row after the deposit (the rows
  the accept wrote, a past date already moved to that day); not accepted yet, every plan date already past reads as
  the agency's today (`TODAY_SQL`, the date the accept would write), also each line of `totals.schedule`. The stored
  plan, the price hash and the rows are unchanged: only what the page shows.

  `PRICE_ON_REQUEST`, `UNCOUNTED_REFUSALS`, the count SQL), `app/settings.py` + `app/main.py` (the price limiter),
  `app/routers/public.py` (the price route's limiter, docstring), `app/proposals/client_page.py` (`due_from`,
  `schedule_balance_due`, `client_dates`), `app/proposals/public.py` (`_page` applies them).
- Web: the `price_on_request` refusal and its EN / VI words (`lib/bookNow.ts`, `lib/i18nBookNow.ts`).
- Tests: unit (gateway status / reconnect, below-cost price and booking, the limiter split, the page dates), web
  (the refusal word, the panel's Not connected, no "Pay online" when `pay_online` is false), integration (1 adult
  below cost, disconnect / reconnect, a departure 9 days out).

### Tradeoffs

- `price_on_request` means an agency without a markup cannot sell some parties online (typically one traveller). The
  owner fixes it by setting a markup on AA tours (Settings > Pricing): the retail is then always above the B2B price.
- Not counting `price_on_request` refusals lets a caller who skips the page make up to the intake limit of such
  refusals a minute (each one Booking quote and one attempt row, purged after 90 days); the price check already
  allows more quotes than that, so the exposure does not grow.
- 20 price checks a minute per address: enough to compare dates and party sizes, still a ceiling on Booking quotes.

### Should know

- Live check after deploy (synthetic agency only): a 1-adult VND price on a tour whose single-traveller B2B price is
  above the RRP answers 409 `price_on_request` and the widget says so (no generic error); with a markup, or 2+
  adults, the booking passes. Disconnect shows "Not connected" and the pay box has no "Pay online"; price twice then
  pay is not 429.
