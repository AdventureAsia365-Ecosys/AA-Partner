## Decisions

- **Platform table, not a tenant table.** A CIS tenant may have no CRM agency, so the row cannot reference
  `crm.tenant`, cannot carry the tenant template's `tenant_id` (FORCE RLS on `app.tenant_id` would need a CRM agency
  context, and every tenant table must be named in `crm.erase_subject`). `cis_tenant_id` is a plain reference;
  `test_crm002_tenancy.PLATFORM_TABLES` lists the table.
- **The e-mail is sealed with a key derived from the invitation token** (HKDF-SHA256 -> AES-256-GCM, app code in the
  API PR). There is no agency DEK for a studio-only tenant; this way the database alone (a dump, a reader) cannot open
  the address, and the claim, which holds the token, can. Re-issuing (send again) writes a new token and a new sealed
  copy from the address CIS relays again; CIS never stores the address.
- **Row security on the actor and the token** (FORCE, crm_owner included): `platform:*` and
  `job:crm_studio_activation` see rows; the token holder sees and moves its one row (`app.invite_token_hash`, the
  crm-008 pattern). No NOLOGIN reader has any privilege; crm_app never deletes.
- **Guard CRM37** (`crm.guard_studio_invitation_write`): issue / re-issue / revoke = platform only; claim / accept /
  expire = the token holder only; record an attempt / activate = the job only; tenant, CIS invitation, issuer and a
  bound identity never change. The extra state `accepted` (between claim and CIS activation) lets the job retry the CIS
  call (outbox) without the person.
- **Statuses**: pending -> claimed -> accepted -> activated; pending | claimed -> expired | revoked; expired -> pending
  (re-issue). Eight rows in `crm.status_transition`.

## Changed

- Design said "status pending -> claimed -> activated/expired/revoked"; `accepted` was added so a CIS outage after the
  person accepted is retried by a job (design §2.3 "on failure a crm_studio_activation job retries").

## Tradeoffs

- A platform table holds a sealed personal field; accepted because the key is not in the database and the rows carry
  ids and codes otherwise. Retention (DM-7) proposed: 90 days after activated / expired / revoked; the purge comes with
  the root data-standards row (root PR) and a later lifecycle step.
