# AA-1147 — Agency extras follow the trip from proposal to invoice

Lane l3-crm-agency-extras of S287 (21/11/2026). Sources: Linear AA-1147, root
`docs/audits/2026-11-19-S285-session/advisory-crm-agency-extras.md` (items b to e), `advisory-r2-b2b-crm.md` (T18,
B10), `advisory-r2-plan.md` (L2). Builds on AA-1144 (crm-080 closed list).

## Decisions

- **Where the lines are written.** In the client's accept transaction, not in a job: the client link has no member
  role, so `crm.booking_line_money_put` refuses it; a new SECURITY DEFINER function
  `crm.agency_lines_from_proposal(proposal, lines jsonb)` (crm-083) writes the planning lines and their money. It
  re-checks the version is accepted and builder, each item is a live agency item of it, and no sell is above the
  item's own (the caller passes the after-discount share). Idempotent through `booking_line.option_id` (unique per
  agency). The Booking sync job was not used: it returns early when Booking is not configured and it is the AA path.
- **Line id.** A fresh id with `option_id` as provenance (no foreign key: an option leaves with its version's purge).
  Reusing the option id as the line id (the AA pattern) would make `proposal_lines.DUE_SQL` think the AA lines of the
  version are written.
- **"Handled by the agency" = NULL supplier** (advisory question 5): `agency_supplier_id` drops NOT NULL;
  `booking_line_supplier_chk` keeps it on AA lines. Supplier requests (needs an e-mail address) and supplier bills
  skip such lines; the voucher and the confirmation PDF name the agency.
- **Deadline task kinds per item type** (`agency_flight_due`, `agency_visa_due`, `agency_insurance_due`, else
  `agency_line_due`): `crm.task` keeps one open task per trip and kind (`task_open_kind_uq`, used by every
  `ON CONFLICT` of the app, so it was not changed). Two lines of one type due together: the second gets its task once
  the first is done (next hourly tick). Once per line and deadline (`task.due_at = line.due_at`): moving the deadline
  opens a new one.
- **Lead time and disclaimer are settings** (tech lead S279): `crm.agency_lines.due_lead_days` (int days, default 3,
  0..60) and `crm.agency_lines.disclaimer` (json `{en, vi}`), both `platform+tenant`, single approval. The CRM registry
  has no text type, so the disclaimer is a json object per language.
- **Prices on client documents.** T18 asks the agency's services to show their price (visa and insurance always): the
  group is the one place a client text prints a price per item; AA items keep D1 / design §2.9 rule 3. Invoice
  `included` rows of source `agency_line` carry the price (crm-083 widens `invoice_line_amount_chk`); totals and the
  issue check read charge rows only, so nothing is counted twice.
- **The group lists the version's choice.** The client page: the client's current choice; the proposal text / PDF:
  the defaults (the version as sent, like the rest of the text); the invoice: the trip's live agency lines.
- **Readiness** raised to crm-083 (crm-082, already applied on Dev, added to the list too).

- **Deadline after the accept (review fix).** The lines an accepted proposal writes start without a deadline, and
  the builder item has no deadline field, so the Bookings tab gives every planning or requested agency line a
  "Deadline and supplier" form (`components/ledger/LineServiceEdit.tsx`): set or clear the deadline (`PATCH
  lines/{id}` `{due_at}` / `{due_at: null}`), move a planning line to another own supplier or to "Handled by the
  agency" (null), fold a flight or the fee into the tour price. Only the fields that changed are sent
  (`lib/ledger.ts` `lineChangeBody`); a requested line keeps its supplier (the API answers 422 line_not_editable). A
  separate component keeps `LinesPanel.actions` within its code-health baseline.

## Changed

- Two migrations: crm-083 (schema, contract) in a migration-only PR; crm-084 (the two settings, contract config rows)
  ships in the code PR with its readers like crm-082, because the settings lint binds seed, compiled defaults and
  readers in one PR and the code PR must pass its own unit tests (pre-push) before crm-083 is on main. Readiness waits
  for crm-083 only; until crm-084 is applied the readers serve the compiled defaults (the same values). Dev therefore
  needs two Migration Apply runs (crm-083 before the code PR, crm-084 after it).
- The ledger "Add line" form no longer needs a supplier first (the hint "Add your own suppliers first" is gone).
- Code-health ratchets (no baseline entry may grow): the invoice "included" rows moved to `app/invoices/included.py`,
  the option flag to `app/proposals/option_fields.py` (`set_bundled`, `bundled_after`, `copy_note` copies it), the
  accept reaches `app.ledger.agency_lines` through `app.booking.proposal_lines.write_agency_lines`, and the web form
  bodies and pickers are small helpers (`lib/ledger.ts` `newLineBody` / `serviceLines`, `lib/clients.ts`). The stale
  baseline entry `LinesPanel.add` was removed.

## Tradeoffs

- Disclaimer rendered at render time, not frozen on an issued invoice: a later wording change shows on a re-render
  of an old invoice. Freezing needs a column; not worth it before a pilot.
- An agency item with a sell in another currency than the invoice prints "Included in the trip price" (no price):
  proposals are single-currency today, so this does not happen from an accept.
- Structured flight legs (advisory item g) and the visa tracker link to a line wait for pilot-agency feedback.
