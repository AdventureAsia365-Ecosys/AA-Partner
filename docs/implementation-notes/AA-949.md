## Decisions

- **Migration key crm-019** (`api/migrations/019_crm_proposal_builder.sql`): the latest crm migration on origin/main is
  crm-018 (AA-978 follow-up), no open branch holds a 019 file (checked every remote branch). Guard 0 needs crm-018
  (and crm-017, whose `erase_subject` text this key extends). SQLSTATEs CRM35 `proposal_not_draft`, CRM36
  `selection_closed`; the next key starts at CRM37.
- **One proposal table, two kinds.** The builder is a `crm.proposal` row with `kind = builder` (AA-946's rows stay
  `kind = text`), so versions, the accepted-version rule, the price hash, the payment schedule and the acceptance of
  AA-946 keep working for both. Builder columns: `price_visibility`, `room_config`, `deposit_pct`, `starts_on`,
  `edit_seq`, `selection_seq`, `based_on_proposal_id` / `based_on_selection_seq`, `published_at`. A builder draft may
  hold zero amounts (they are recomputed on every write and fixed at publish); the strict amount rule applies from
  the first publish.
- **Publish is not send.** Design F3.5 "Publish vN" then F4 "Send" (format: link, email or WhatsApp text, one
  `price_hash`). New status `published` (builder only): draft -> published -> sent | superseded | withdrawn. This card
  publishes; sending a published version (the link, C-03) is AA-950 (CRM-21b). To leave that seam open, `sent_at`
  leaves the draft-only seal and gets `crm.guard_set_once` (set once, never changed); every other sealed column of
  crm-016 stays sealed, plus the builder columns. One published version per trip (partial UNIQUE). Publishing vN
  supersedes the published v(N-1); a *sent* version is left to AA-950's send (which supersedes it as AA-946 does).
- **Table and column names follow the design ERD page** (`erd/design/crm.md` group E): `proposal_day_id`,
  `option_block_id` (+ `type`, `default_option_id`), `option_rule_id`, `agency_supplier_id`, `selection` (the ERD's
  `by` is `chosen_by`: `by` is an SQL keyword). The ERD's `option.net_delta` is stored as the absolute `net_amount`
  (cost of the option for the party): deltas are computed against the block's default, so changing the default never
  rewrites the other options. Every table name already has its DM-7 row (root data standards Part B §7), so no
  registry change is needed for the Infra retention check.
- **Default option on the block** (`option_block.default_option_id`, ERD), not a flag per option: exactly one default
  by construction, and the key `(tenant_id, option_block_id, default_option_id)` makes it one of the block's own
  options.
- **Draft-only builder rows in the database** (`crm.guard_proposal_draft`, CRM35): a published version's days,
  blocks, options and rules never change, whatever path writes. One exception for AA-950: an option of a published /
  sent version may change only `availability` / `availability_checked_at` (an option that sells out mid-session).
  Picks (`crm.selection`) only on a published / sent version (CRM36).
- **No `ON DELETE` actions on any builder key** (found while testing): a referential action runs its query, and the
  triggers it fires, with row security off for the table owner, so `crm.guard_held_change` inside a cascade saw the
  legal holds of *every* agency and refused a cascade in an agency with no hold (`legal_hold (delete of a held
  option_rule row refused)`, only when the full suite had left holds in other agencies). The API deletes a draft's
  rows child first (picks, rules, the block's default, options, blocks, days); the two circular keys
  (`option_block.default_option_id`, `proposal.based_on_proposal_id`) are `DEFERRABLE INITIALLY DEFERRED` so one
  transaction (and the erase) can delete both ends.
- **Draft rows are deleted, not trashed.** Days, blocks, options and rules of a working copy are hard-deleted (the
  trash columns of the template stay NULL): they are parts of one draft version, not objects a member restores. The
  proposal version itself is never deleted by crm_app (crm-016).
- **Day notes under the vault DEK** (`proposal_day.notes_enc`, pii:free_text), like the proposal text: they are free
  text the agent writes to the client. Titles of days, blocks and options are product / place names (plain text,
  like `booking_line.title`).
