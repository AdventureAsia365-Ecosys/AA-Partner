## Decisions

- **Migration key crm-019** (`api/migrations/019_crm_proposal_builder.sql`): the latest crm migration on origin/main is
  crm-018 (AA-978 follow-up), no open branch holds a 019 file (checked every remote branch). Guard 0 needs crm-018
  (and crm-017, whose `erase_subject` text this key extends). SQLSTATEs CRM35 `proposal_not_draft`, CRM36
  `selection_closed`; the next key starts at CRM37.
- **One proposal table, two kinds.** The builder is a `crm.proposal` row with `kind = builder` (AA-946's rows stay
  `kind = text`), so versions, the accepted-version rule, the price hash, the payment schedule and the acceptance of
  AA-946 keep working for both. Builder columns: `price_visibility`, `room_config`, `deposit_pct`, `starts_on`,
  `edit_seq`, `selection_seq`, `based_on_proposal_id` / `based_on_selection_seq`, `published_at`. A builder draft may
  hold zero amounts (they are recomputed on every write and fixed at publish); the strict amount rule applies from
  the first publish.
- **Publish is not send.** Design F3.5 "Publish vN" then F4 "Send" (format: link, email or WhatsApp text, one
  `price_hash`). New status `published` (builder only): draft -> published -> sent | superseded | withdrawn. This card
  publishes; sending a published version (the link, C-03) is AA-950 (CRM-21b). To leave that seam open, `sent_at`
  leaves the draft-only seal and gets `crm.guard_set_once` (set once, never changed); every other sealed column of
  crm-016 stays sealed, plus the builder columns. One published version per trip (partial UNIQUE). Publishing vN
  supersedes the published v(N-1); a *sent* version is left to AA-950's send (which supersedes it as AA-946 does).
- **Table and column names follow the design ERD page** (`erd/design/crm.md` group E): `proposal_day_id`,
  `option_block_id` (+ `type`, `default_option_id`), `option_rule_id`, `agency_supplier_id`, `selection` (the ERD's
  `by` is `chosen_by`: `by` is an SQL keyword). The ERD's `option.net_delta` is stored as the absolute `net_amount`
  (cost of the option for the party): deltas are computed against the block's default, so changing the default never
  rewrites the other options. Every table name already has its DM-7 row (root data standards Part B §7), so no
  registry change is needed for the Infra retention check.
- **Default option on the block** (`option_block.default_option_id`, ERD), not a flag per option: exactly one default
  by construction, and the key `(tenant_id, option_block_id, default_option_id)` makes it one of the block's own
  options.
- **Draft-only builder rows in the database** (`crm.guard_proposal_draft`, CRM35): a published version's days,
  blocks, options and rules never change, whatever path writes. One exception for AA-950: an option of a published /
  sent version may change only `availability` / `availability_checked_at` (an option that sells out mid-session).
  Picks (`crm.selection`) only on a published / sent version (CRM36).
- **No `ON DELETE` actions on any builder key** (found while testing): a referential action runs its query, and the
  triggers it fires, with row security off for the table owner, so `crm.guard_held_change` inside a cascade saw the
  legal holds of *every* agency and refused a cascade in an agency with no hold (`legal_hold (delete of a held
  option_rule row refused)`, only when the full suite had left holds in other agencies). The API deletes a draft's
  rows child first (picks, rules, the block's default, options, blocks, days); the two circular keys
  (`option_block.default_option_id`, `proposal.based_on_proposal_id`) are `DEFERRABLE INITIALLY DEFERRED` so one
  transaction (and the erase) can delete both ends.
- **Draft rows are deleted, not trashed.** Days, blocks, options and rules of a working copy are hard-deleted (the
  trash columns of the template stay NULL): they are parts of one draft version, not objects a member restores. The
  proposal version itself is never deleted by crm_app (crm-016).
- **Day notes under the vault DEK** (`proposal_day.notes_enc`, pii:free_text), like the proposal text: they are free
  text the agent writes to the client. Titles of days, blocks and options are product / place names (plain text,
  like `booking_line.title`).

- **Concurrency (§11.2, card E) with two counters on the proposal row.** `edit_seq`: every builder write sends the
  counter the page read (body `seq`, or `?seq=` on a DELETE); the service locks the row `FOR UPDATE`, compares and
  answers 409 `version_conflict` `{reason: edited, current_seq}` on a mismatch (two editors, two tabs), else writes
  and bumps it. `selection_seq`: every client pick on a published / sent version bumps it; a working copy records
  the base's value (`based_on_selection_seq`) when it is copied; Publish answers 409 `version_conflict`
  `{reason: client_selected, base_version, selection_seq, picks: [block, option, chosen_by, at]}` while the base has
  picks the agent has not acknowledged (`acknowledge_selection_seq` = the shown counter publishes). The builder page
  shows the count ("client picks since copy") before the agent even tries. Chosen over a row-level `updated_at`
  compare: one integer per version is cheap to send with every write and needs no clock.
- **Picks carry over at publish** (lineage `source_*_id` on day / block / option): a pick on the base version moves
  to the copied option as `chosen_by = carried` when the option is still there, not sold out, the block still allows
  a swap (or it is the default), and the rules still hold; otherwise that block falls back to its default. Carried
  picks do not move `selection_seq` (they are not new client choices).
- **One working copy per trip** (409 `builder_draft_exists` with its id): two drafts of one trip would turn every
  concurrent edit into two diverging versions; the second editor opens the same copy and meets `edit_seq`.
- **Stage 2 defaults (spec rule 5, Fix B10, R33, R38).** Skeleton: one day per date between the trip's start and end
  (or nights + 1, at most 30), day 0 "Before you go" (kept, never deleted; CRM-22 fills it), a Lodging block (may swap)
  on every night, every day in the zone of the trip's first known destination (Nepal -> `Asia/Kathmandu`; else the
  agency's `tenant_settings.timezone`; else Vietnam), the rooms from the party (pairs share a double, twin for
  friends / groups, an odd adult a single, children join the first room as a family room), deposit 30 %, D1 default
  visibility. The lodging default follows the lead's F2 `accommodation_tier` (an option with that `tier` becomes the
  default); any block without a default takes its first open option. Group preference and pace are shown on the
  page as the basis but set no default yet (no option attribute carries them; noted as an open question).
- **AA items (Fix E1 drawer) are priced by a live Booking quote** in the proposal currency (`proposal_ref
  crm-proposal:<id>`, `proposal_version` = the version, `line_ref` = the new option id — the reference AA-950 holds one
  set per version with). Net = the quote's `b2b_price`; availability from the quote (`available` -> Instant,
  `on_request`, `sold_out` = "cannot add", 409 `aa_sold_out`); the public "from" price (trip plans) and
  `below_from_price` warn only. Booking is called between two transactions (plan -> quote -> store, the AA-947 rule:
  no connection held while Booking answers); Booking down is 503 `booking_unavailable` and nothing is written (the
  drawer disables AA adds). "Refresh AA prices" re-quotes every AA item (at most 40), keeps the agent's sell, marks
  sold-out ones; an expired quote blocks Publish (`aa_prices_stale`). A builder quote is a price check only: no hold,
  no AA line, no money row, nothing in the outage queue (AA lines still come only from quote / hold / feed after
  accept, AA-947). An AA item's net is never typed (403 `aa_net_from_quote`) and is never "choose later" (Fix B9).
- **Money fields and roles (§4.6).** Every role drafts (`PROPOSAL_DRAFT`): structure, titles, days, rules, AA items
  without a sell. Sell / net / deposit share need `MONEY_FIELDS_EDIT` (owner, agent; 403 for the assistant, checked
  in the router before the service runs). Publish needs `PROPOSAL_PUBLISH` (owner, agent). The view builds `net_*`
  and `margin_*` keys only for a role that `sees_margin` (and the serializer strips them again). Audit: `view`
  (fields `builder`), `proposal_draft` (reason `builder` / `builder_copy`), `proposal_builder_edit` (reason = the
  operation: `settings`, `day_add`, `option_add`, `aa_option_add`, `aa_refresh`, `rule_add` ...),
  `proposal_publish` (reason `v<N>`), `proposal_pick` (reason = chosen_by).
- **Totals**: the charged total is the default options' sell amounts minus pay-on-arrival items (R25: listed, never
  charged), the deposit = `deposit_pct` of it (half up, at least one cent), the balance date is required when a
  balance is left (as AA-946). The draft row's `total_amount` / `deposit_amount` follow every write, so the Proposal
  tab lists a builder draft with its running total.
- **Price hash of a builder version**: SHA-256 of the canonical record the client sees (no net, no margin): settings,
  every day (number, zone, title, place, hash of the sealed notes), block (default, may swap), option (sell, pay on
  arrival, choose later, availability), the rules, the computed amounts and the terms hash. AA-950's acceptance sends
  it back like AA-946's.
- **Text proposal routes leave builder versions alone** (409 `proposal_is_builder` on edit / send); `withdraw` also
  withdraws a published version. The trip's lifecycle answer lists both kinds (`kind`, `published_at`).

- **Review round 2 (S252, six blocking findings, fixed in place: crm-019 is not applied anywhere yet).**
  - *b2b price to the assistant*: an AA item added without a sell keeps **sell 0**, never the quote's b2b price (the
    assistant reads `sell_amount`, `sell_delta` and `totals.sell_total`); a new blocking check `aa_item_unpriced`
    (any AA option with sell 0) holds Publish until an owner / agent sets the sell; no "from"-price warning while
    unpriced (`below_from_price` NULL). The view adds `aa.unpriced`. Option (a) of the review, kept over hiding fields
    per role: one rule, no field that means different things to different roles.
  - *Publish 500 at a 100 % deposit*: `_checks` adds `balance_due_on_not_needed` when the deposit covers the total and
    a balance date is set (the published row's `proposal_amounts_chk` needs no date then). A check, not a silent clear:
    the agent sees why and clears the date (the settings form already allows it).
  - *Refresh dropped items past 40*: the plan sorts AA items by `aa_quote_valid_until` (never-checked / oldest first)
    so the next run continues where the last stopped; `aa_options.refresh` reports every item it did not quote
    (`refresh_limit`, `day_has_no_date` for an item whose day has no date) and the route answers
    `refresh.skipped`. The page gets the "Refresh AA prices" button (it was missing) and says how many were checked,
    left and refused.
  - *Nights lost on refresh*: new column `option.aa_nights` (1-60; required for a `hotel_room` by
    `option_source_chk`, as AA-947's `invalid_nights`; NULL on agency items); the add stores it, the refresh plan
    re-sends it, the copy keeps it, the price hash covers it. `aa_plan` refuses a hotel room without nights (422
    `invalid_nights`); the drawer checks it first.
  - *Rule 5 overrode a hand-picked default*: new column `option_block.default_pinned` (true when the agent sets the
    default through `PATCH /blocks/{id}`, false when the default is cleared or deleted, copied with the version).
    `_settle_default` never moves a pinned default; an auto-chosen default still follows the Stage 2 tier as options
    are added. Kept over "only when the block has no default" (the review's simpler fix) because that one breaks rule 5
    in the common order "budget option first, then the comfort one".
  - *Explicit null skipped the money gate*: `_money_check` fires on the key's presence (`net_amount: null` from the
    assistant is 403); `deposit_pct: null` is 422 `invalid_deposit_pct` (was a 500); a null yes / no field
    (`pay_on_arrival`, `choose_later_allowed`, `client_may_swap`, `sort_order`) keeps the current value instead of
    turning into false.
- **Review round 3 (S252, one blocking finding): a sold-out AA alternative blocked Publish for good.** Refresh marks a
  sold-out AA item without a new quote (Booking gives none), so its old `aa_quote_valid_until` runs out and never
  moves again; `aa_prices_stale` counted it, so a non-default sold-out item held Publish forever while Refresh said it
  had succeeded. `_quote_expired` (used by the check and the view's `aa.quote_expired`) now leaves out
  `availability = sold_out`: such an item can never be the default (a sold-out default is already
  `default_sold_out`, and `update_block` refuses it) and a client cannot pick it, so its price is never charged. An
  item that becomes available again gets a fresh quote from the next Refresh. Kept over clearing
  `aa_quote_valid_until` on sold out: the old quote stays visible as history and no row shape changes.

## Tradeoffs

- **A builder quote per AA item, synchronous**, instead of queuing it in `crm.aa_request`: the drawer needs the price
  now (WF-4: "Net, sell, margin, availability"), and a builder item is not a booking line. Cost: one Booking quote row
  per add / refresh (cheap records on Booking's side); when Booking is down the agent cannot add AA items (the drawer
  says so), which is the design's behaviour.
- **One quote per item on refresh** (at most 40, sequential): the contract parser reads one line per quote
  (`contract.quote_line`), and the fake Booking answers one line; a multi-line quote would be faster for long
  proposals. Revisit if refresh time matters.
- **The price hash covers the sealed notes' ciphertext**, not the plain text: the hash is fixed once at publish and the
  sealed row never changes (CRM35), so it stays verifiable; a key rotation that re-seals notes would need the hash
  recomputed from the plain text (none exists today).
- **Version counters, not row locks across requests**: an agent can lose a typed edit to a conflict (the banner asks
  to reload and redo it). Merging field by field was not worth it for a working copy one agent usually owns.
- **Stage 2 defaults use the accommodation tier only** (lodging blocks). Group preference (private / small group) and
  pace have no option attribute to match yet; the page shows them as the basis.
- **No local `next build`, no browser** (RAM rule): `tsc --noEmit` and vitest only; CI "Web Build" builds.

- **Sell 0 for an unpriced AA item** rather than a NULL sell: `sell_amount` stays NOT NULL (totals, deltas and the
  price hash need no NULL branch); the cost is that "0" cannot mean "free" for an AA item, which is never wanted.
- **Two more columns in crm-019 instead of a later key**: the file is not applied on Dev yet, so the fix lands in the
  same key (no forward migration); the Infra copy must be refreshed with it (RUNBOOK step 3, `cmp`).
