## Decisions

- **Migration key crm-022** (`api/migrations/022_crm_text_proposal_prep_packs.sql`): the latest key on `main` is
  crm-021 (AA-950); no remote branch holds a 022 file (checked S253). Guard 0 needs crm-021 (erase_subject builds on
  its text). No new SQLSTATE (the next key still starts at CRM38).
- **Three objects.** `crm.aa_content` = a platform cache (no tenant, no PII, like `crm.aa_catalog_tour`) of the latest
  published version of each CIS AA content item (kinds `prep_pack` and `starter_template` are synced; one row per
  `content_id`, one locale each, EN / VI paired by `group_key`). `crm.prep_pack_selection` (design group E) = the packs
  of **one builder proposal version** (not of the trip, as the ERD sketch has it): it carries `trip_id` (the ERD key,
  the hold guard, the trip erase) and `proposal_id`, because a published / sent version must keep the text it was
  sent with. `crm.message_template` (group G) = the agency's library.
- **Packs are copied, not referenced.** A pick stores the pinned version's title, body, applies_to and hash. The card
  E of CRM-B5 ("the CRM keeps the pack version in use when a new version is published") then holds without calling
  CIS at render time, and `guard_proposal_draft` (CRM35) keeps a published version's packs unchanged. Every locale CIS
  has of a picked group is copied, so the same version renders EN and VI.
- **Pack suggestions follow the AA items only** (card E): the countries / tours of the version's AA options and of
  the trip's live AA booking lines (tours from the catalog cache). The trip's own destination codes are not used
  (they are free codes such as `ha_giang`, no country). Without an AA item there is no suggestion, a pick is 422
  `no_aa_items`, and rendering shows no pack even if one was picked earlier (the AA item was removed since). A pack for
  "everywhere" (empty `applies_to`) is not suggested.
- **Visa = the official link only** (Q1 2.3): the renderer cuts a pack into sections (Markdown headings; else blank-line
  paragraphs); a section that mentions a visa (`visa`, `e-visa`, `thị thực`, NFC, payment-card phrases excluded as in
  CIS AA-977 validate) keeps its heading and its `https://` links and nothing else; without a link it says "check the
  official government website". The insurance reminder and the fitness warning are the CRM's own sentences (EN / VI),
  not pack text. Fitness: an AA tour with `facets.intensity` challenging / strenuous, or trek / hike / climb / summit /
  altitude / base camp in its title or activities.
- **The price hash is not redefined.** The text carries the version's existing `price_hash` (builder: fixed at
  publish; text kind: computed exactly as `service.send` fixes it). Packs are not in the hash: a published version's
  packs cannot change (CRM35), so the hash still identifies one text.
- **Card R in the send path**: `POST /proposals/{id}/text/send` names the `price_hash` the preview showed; the API
  locks the version, computes its current hash and answers 409 `price_hash_mismatch` (`current_price_hash`,
  `current_reference`) before any write. Statuses: a builder version renders from `published` (draft = 409
  `proposal_not_published`), a text version from `draft`; superseded / withdrawn = 409 `proposal_not_sendable`.
- **Send = the link send + the text.** A version not yet sent (builder `published`, text `draft`) goes out through
  `service.send` (AA-946 / AA-950: price hash fixed, previous version superseded, link made or reused) inside the same
  transaction, then the text is rendered again with `<client origin>/c/p/<token>`; an already-sent version keeps its
  link (the text says nothing about a link: the client has it). The client origin is the first `INTAKE_PAGE_ORIGINS`
  entry (the client host, set by Terraform): no new environment variable.
- **E-mail goes through the AA-945 composer path** (`conversations.send`: send-as, 10 s Undo, held on a dead mailbox);
  no mailbox = 409 `mailbox_not_connected` and the whole send rolls back (the version stays unsent). The assistant is
  refused before anything (send needs `PROPOSAL_PUBLISH`; e-mail also `MESSAGE_SEND` on the trip).
- **WhatsApp has no channel in the CRM** (BYO errata S247: no platform sender, no WhatsApp integration yet). The send
  returns the final text (and the link path once) for the agent to paste; it is recorded as audit
  `proposal_text_send` reason `whatsapp`. The link send's dispatch row stays as AA-950 leaves it.
- **Templates (R9)**: body under the agency mail DEK (as `saved_reply`: agents may type names), owner-only writes
  (`WORKFLOW_EDIT`), every role reads. "Add AA starter templates" copies each CIS starter (every locale) once per
  `(group_key, locale)` (partial UNIQUE, `ON CONFLICT DO NOTHING`), so a second import never overwrites an edit.
  Templates are not seeded automatically: the library lists the starters not copied yet and the owner adds them.
- **Merge fields** = the CIS seed names (`{{traveller_first_name}}`, `{{trip_name}}`, `{{agency_name}}`,
  `{{agent_name}}`, `{{destination}}`, `{{departure_date}}`) plus `{{proposal}}` (where the proposal goes; else it
  follows the template). `{{traveller_first_name}}` = the first word of the lead's **display name**, read only when
  the template asks for it (audit field `display_name`). **Never `given_name`** (review fix, S253): it is an F1
  click-to-reveal field (`REVEAL_COLUMNS`, design §4.4 / §4.9: each view logged with a reason), and opening it in a
  preview any role can load would bypass the reveal control; the display name is what every agency view shows
  already. `agent_name` has no source (a member has no stored name) and is reported `unfilled`; a line holding only
  unfilled fields is dropped.
- **Day 0 items are rendered** (review fix, S253): `add_block` accepts day 0 and the builder offers it, the client page
  shows day 0 blocks and the sell total counts them, so the texts list day 0's priced items (a visa service, an airport
  transfer) under "Before you go" too (`text_render.BeforeYouGo.items`). Refusing blocks on day 0 was the other option;
  rejected because an arrival transfer or a visa-service fee genuinely belongs before day 1.
- **One Before you go in all three forms** (review fix, S253, R38 lists C-03; F4): the client page
  (`GET /crm/public/v1/proposal`, builder versions) now carries `before_you_go` from `prep_packs.client_view` (every
  locale of each picked pack cut into sections, a visa section = its official links only, the insurance reminder,
  the fitness warning; no agency-only fields). The texts and the page share `prep_packs.rendered` (the card E gate:
  no AA item, no pack). The web picks the copy in the page's language, else English, and shows it inside day 0 (or as
  its own section when the page has no day 0 entry).
- **A link lost to an undone e-mail** (review fix, S253): an e-mail text send of an unsent version sends the version
  (link made); the link's own dispatch row has no message, so that e-mail is the only copy of the link. Undo cancels
  the e-mail but the version stays sent. The send body takes `new_link` (default false): for an already-sent version
  the API re-issues the link (`service.reissue_link`: the old token is revoked) and puts the new one in the text
  (`link_reissued` in the answer). The page sets it after undoing an e-mail that carried the link (`linkLostOnUndo`),
  says so ("the next send adds a new link"), and reloads the preview after every send and undo. Undoing the whole
  version send was rejected: un-superseding the previous version and its link inside a 10 s window is far riskier
  than one re-issue.
- **The CIS content sync rides `crm_catalog_sync`** (hourly, after the tour pass): list per kind, fetch a body only when
  version or hash changed (at most 60 a run), unlist what CIS no longer lists (only after a complete list). A content
  failure is counted (`content_error_count`) and never fails the tour pass.

- **No new environment variable, no Infra change** besides the migration copy: the CIS content uses the existing
  `CIS_API_URL` + `M2M_CLIENT` (scope `cis.catalog/read`, already granted for the tour cache); the client link origin
  is the existing `INTAKE_PAGE_ORIGINS`.

## Tradeoffs

- **A platform cache table** (`crm.aa_content`) instead of calling CIS live when the agent opens the builder: the
  suggestion needs `applies_to`, which only the full version carries, so a live call would be one request per pack per
  page load. The cost is one more platform table and its DM-7 row (root registers PR, below).
- **Packs per version, copied** rather than a reference per trip: a few kB per pick and per version, but a sent text
  can always be rendered again exactly, and CRM35 already protects published rows.
- **The hash does not cover the packs or the template**: the template is the agent's message around the proposal and
  may change between two sends of one version; the packs of a published version cannot change. Folding them into the
  hash would have changed every existing published version's hash.
- **WhatsApp text is returned, not sent**: recording the send without delivering it is honest about the channel; a
  wa.me link with the client's number would put the phone number in a URL the browser history keeps.
- **Fitness from catalog facets and title words**: CIS has no "fitness level" field; intensity + activity words is the
  best signal the contract carries. A false positive only adds a warning.
