## Decisions

- **Migration key crm-009 depends on crm-006 only.** The orchestrator fixed crm-007 (AA-940) and crm-008 (AA-939) for
  the parallel lanes; crm-009 touches none of their objects, so Guard 0 checks crm-006 and DB Migrate may apply the
  three in any order (the runner applies one named file, it has no gap rule). `REQUIRED_SCHEMA_VERSIONS` gains
  `crm-009` only.
- **`crm.placeholder_map` keyed by the LLM call, not the draft.** `ai_draft` arrives with CRM-33a (AA-964), so the
  map row points at its `crm.llm_call` with a same-agency `(tenant_id, llm_call_id)` key (`UNIQUE (tenant_id,
  llm_call_id)` added to `llm_call`), and carries a nullable `ai_draft_id` that CRM-33a turns into a key. A map is
  stored only for an `ok` call that replaced something; refusals and errors store nothing.
- **Seal before the call, store after the log.** The map is encrypted under the tenant `scrub` DEK after the
  budget / `ai_enabled` checks and **before** the model is paid; a key failure refuses (`scrub_failed`). The row is
  inserted after the `llm_call` row in the same transaction. Without a key provider a call that would need a map is
  refused: an output whose placeholders can never be restored is useless.
- **Written once, deleted by a policy.** `crm_app` has no UPDATE on the map. The purge is one `DELETE` without WHERE
  under the DELETE-only policy `placeholder_map_expired_purge` (TO `crm_app`, `app.purge_scope = 'placeholder_map'`
  and `expires_at < now()`); `crm.tenant` is FORCE RLS too, so a per-agency loop would need a tenant listing path
  that does not exist. The scope grants no SELECT (tested: the purge transaction counts 0 rows). Reads refuse a map
  from the minute it expires; the hourly job removes it within the hour.
- **Hourly purge kind, due-now hook.** `crm_placeholder_purge` follows `DailyRetentionSchedule` with an hourly slot
  (idempotency key per UTC hour, never queued ahead), so the deploy gate and DB Migrate see it only while it runs.
- **Receipt keys fixed in the DB.** `llm_call_receipt_keys_chk` allows only `scrubber`, `detector`, `entities`,
  `counts`, `passes`, `known_persons`; the AA-936 stub receipts pass.
- **Name rules** (pass 1): full name and any 2+ word run always; a given name alone only with a capital ("An" yes,
  "an toàn" no); a family name alone only after an honorific ("ông Nguyễn" yes, "Nguyễn Huệ street" no); a display name
  without parts is read family-first when its first word is a common Vietnamese family name (middle words alone are
  never matched). One word inside a known place name is skipped ("Bình" in "Ninh Bình", `app/privacy/places.py`), a
  full name never is (the E test: "Hà Giang" the traveller is caught). Each known person keeps one placeholder for
  every spelling and restores to the stored display name.
- **Dates of birth** (pass 2): a date next to a birth cue, a bare year after a birth cue, or any full date at least two
  years in the past. Trip dates are in the future and survive; an old trip date is over-scrubbed (accepted).
- **Cues stay in their clause.** "DOB 1/2/1985, trip 3/4/2027": a cue is looked up only back to the last `,` `;` `|`
  newline, ". ", "and" / "và".
- **Digit runs** are read across single spaces / dots / dashes and tried window by window, so "room 12 0912 345 678"
  finds the phone. UUIDs and placeholders are protected spans; 13-19 digits need Luhn; a 12-digit run with a leading 0
  is a CCCD.
- **Guardrails call**: `source=INPUT`, `outputScope=FULL` (detect-mode findings), botocore one attempt with the
  scrubber's timeout, errors by class only; URL and AGE entities are ignored (catalog links and age bands are planning
  data). No custom regexes in the guardrail (pass 2 runs them locally, free).
- **No guardrail = no AI.** `build_scrubber` uses `UnavailableDetector` when `SCRUB_GUARDRAIL_ID` is empty: every
  scrub fails closed. There is no "two passes only" mode in app code (`NoDetector` lives in the test corpus runner).
- **Restore only in a member's session**, audited (`placeholder_restore` allowed / denied with reason `expired`), 410
  `placeholder_map_expired`. No route yet: CRM-33a's draft approval calls it.
- **Known values audit**: opening the trip's identity fields for the scrubber writes one `scrub_known_values` event
  (trip id, the fields, the traveller ids). It is not a reveal (no human sees the values), so the reveal meter does not
  count it.
- **Log scrubber** reuses the pass-2 detectors for cards, CCCD, phones without `+`, passports, OTPs and signed links;
  dates are left alone (log lines are full of timestamps).
- **Corpus**: 242 synthetic samples (129 VI, 113 EN; 20 need Guardrails: names nobody stored), generated
  deterministically (`python -m tests.scrub_corpus.generate`, `--check` in Unit Tests and in the workflow). A leak =
  a `pii` value readable folded as whole words, or its 6+ digits anywhere once placeholders are removed; over-scrub of
  `keep` strings may not exceed 5 %. Offline result: 0 leaks, 0 over-scrubs.
- **Corpus workflow runs on main only** (nightly + push to main touching `api/app/privacy/**` or the corpus +
  dispatch), never on pull requests: it assumes an AWS role and the repo is public. The PR-time gate is the offline
  half inside Unit Tests.
- **No web page.** `final/ui-mockups.html` has no F3 screen; "reply by hand" belongs to the A-21 AI cards (CRM-33a),
  which read `GatewayResult.fallback`.

## Changed (vs. the card text)

- "Nightly + on scrubber change" = nightly + on every push to `main` that changes the scrubber or the corpus (not on
  the PR itself), plus the free offline half on every PR.
- The scrubber accepts extra `KnownPerson` rows for agency members and supplier contacts; the loader does not add
  them yet (`crm.member` has no names, suppliers arrive later).
- Pulled ahead from CRM-33a: the guardrail itself and the task role's `bedrock:ApplyGuardrail` (AA-930 §2 had put
  them there), because pass 3 cannot run without them.

## Tradeoffs

- **Over-scrub over leak.** A given name that is also a word with a capital at a sentence start, or an old trip date,
  is replaced; drafts lose a little detail, the model never sees an identity value. The corpus keeps the rate visible.
- **One placeholder per person** reads better for the model and restores to the full stored name, so "chị <PERSON_1>"
  restores as "chị Nguyễn Thị Hoa" rather than "chị Hoa". Accepted for drafts the agent edits anyway.
- **Unbounded purge DELETE.** One statement per hour over a table that holds at most a day of AI calls; batching
  would need a WHERE clause, which brings SELECT policies into play.
- **Guardrails on unaccented Vietnamese names** is unproven; the nightly run will show it. Known travellers are
  covered by pass 1 regardless.

## Review round 1 (S249)

Blocking items fixed:

- **Cubic digit windowing (DoS).** `patterns._digit_runs` and `scrubber._known_phones` tried every window of a digit
  run and rebuilt its string: O(k³). Measured before the fix: a 4,000-char "1 1 1 ..." took 50 s in `patterns.find`
  and 85 s in `PiiScrubber.scrub`. Now a window holds at most 19 digits (`MAX_WINDOW_DIGITS`, the longest kind; for
  known phones the longest stored form), only digit counts a kind can accept are tried (`_Cues.lengths`), the cues of
  a start are looked up once, Luhn comes from prefix sums, and span selection uses `patterns.Ranges` (bisect) instead
  of pairwise checks. The e-mail regexes (patterns and the log scrubber) start only where a local part can start; they
  were quadratic on a long run without "@". Measured after: 24,000 chars of the worst shapes scan in about 0.2 s
  (`find`), the full scrub in about 0.35 s. Perf regression tests: `test_find_is_linear_on_adversarial_text`
  (patterns and `scrub_text`) and `test_scrub_of_a_large_prompt_is_fast_and_off_the_event_loop`, budget 3 s at
  20,000 chars (about 0.2 s locally, 0.5 s under coverage; the old code took hours).
- **Passes 1-2 off the event loop.** They run in `asyncio.to_thread` under one deadline shared with pass 3
  (`timeout_s`): a slow local pass is `scrub_timeout` and the detector is never called. A thread cannot be cancelled;
  it finishes in the background and its result is dropped.
- **Pass 3 failed open.** `_apply_detections` now: locates a finding verbatim, then with any whitespace between words,
  then case-insensitively, then without word boundaries, then folded; keeps placeholders inside a finding and replaces
  every other fragment ("12 <PERSON_1> street, Ward 5, Da Nang" -> `<ADDRESS_1> <PERSON_1> <ADDRESS_2>`); merges
  overlapping findings into one placeholder instead of dropping one; raises `ScrubError` for a mapped finding that
  cannot be located or has no value. `parse_assessments` keeps a typed finding without `match` (empty value, so the
  scrubber refuses) and refuses an entity without a type. A one-letter finding is replaced (case-sensitive, word
  boundaries), not skipped.

Non-blocking items:

- Gateway: `seal_map` checks the sealed size against the crm-009 bounds (30..65,536 bytes) and the gateway checks the
  scrubber version against `placeholder_map_version_chk`, both before the call; `store_map` runs in a savepoint, and a
  failure keeps the paid `llm_call` row (budget and rollup keep the cost) and returns `error` /
  `PlaceholderMapStoreError` with no text (`manual_reply_needed`). The `llm_call` row still says `ok` (crm_app cannot
  UPDATE it); the warning log names the class only.
- crm-009 `llm_call_receipt_keys_chk` is closed at every level: version strings as short codes, numbers as numbers,
  `counts` keys `^[A-Z][A-Z_]{1,23}$` with number values, `passes` keys known / regex / detector with number values
  (`jsonb_path_exists` strict, no helper function, so no new owned object). DB Migrate `check` must confirm that no Dev
  `llm_call` row holds anything else before `apply` (AA-936 stub receipts and `{}` pass).
- Pass 1: a given name in lower case right after an honorific ("chị hoa", "anh an") is the person. Over-scrub risk
  ("anh an tâm") accepted: over-scrub over leak.
- Known values: travellers related to the party (crm-006 `traveler_relation`, one hop, either direction, live, not on
  the trip) are loaded as role `related` and audited with the others. Members and suppliers stay deferred.
- Infra: the apply-role guardrail grant is split like the CRM-04 keys: create (and tag on create) only with
  `aws:RequestTag/App = crm`; update / delete / version / tag only with `aws:ResourceTag/App = crm`; untag never the App
  key; Get / ListTagsForResource / ListGuardrails unscoped. App (not Service) because it is the existing CRM tag the
  boundary and KMS grants key on, and `crm_scrub_tags` carries it. Known gap, same as the KMS precedent: TagResource
  with the request tag App = crm could tag a foreign guardrail; the apply role already manages most of acc2.
- Corpus: a red "Scrub corpus" run opens (or comments on) the issue "Scrub corpus is red on main" (`issues: write`;
  the workflow never runs on pull requests). Chosen over a deploy gate: a gate in deploy-dev.yml would race the corpus
  run of the same push and block every deploy on a Guardrails flake.
- `test_split_contact` is async now (no PytestWarning).

## Option C: typed place placeholders (S249)

Context: the first live "Scrub corpus" run (Actions run 40076803898) had 0 leaks but 103 over-scrubbed `keep`
strings out of 362 (28.45 %, limit 5 %; 242 is the sample count, 362 the keep count). Bedrock Guardrails labels a bare
destination ("Hà Giang", "Hạ Long", "Hội An") `ADDRESS`. A global "keep known places" rule was rejected in review:
many destinations are also Vietnamese personal names (Mai Châu, Thái Bình, Hà Giang, Kim Liên), the guardrail often
types a bare person name `ADDRESS`, and keeping those leaked companions' names (live probe, 20 texts). Nghiệp chose
option C.

### Decisions

- **Still masked, typed.** A detector `ADDRESS` finding whose whole value (outer spaces / punctuation ignored) is
  exactly one known destination, matched folded, becomes `<PLACE_n>` instead of `<ADDRESS_n>`. The value goes into the
  same placeholder map, is sealed with the rest and restored by `restore_placeholders` (member session only, audited).
  The typing changes a label only: what is replaced is exactly what was replaced before.
- **`NAME` findings stay `PERSON`**, even when the value equals a place ("Contact person: Hà Nam."). The scrubber never
  tells the model that a person is a place. Cost: the guardrail sometimes types a destination `NAME` ("prefers
  Sapa", "đi Sa Pa rồi Hạ Long" with `NAME` on "Hạ Long"), and those stay over-scrubbed (`<PERSON_n>`).
- **Place plus more keeps its kind.** "45 Hải Phòng, Đà Nẵng", "Ninh Bình + Hải Dương", "12 Hội An road" stay
  `<ADDRESS_n>`. In a merge of overlapping findings the span is `PLACE` only when every piece came from a place-typed
  finding and the merged text is itself one destination; otherwise the merge picks the kind it always picked
  (`PLACE` pieces sort and count as `ADDRESS`), so a `NAME` + `ADDRESS` tie on the same words is still `<ADDRESS_n>`.
- **Typing list wider than the pass-1 list.** `places.TYPED_PLACE_PHRASES` = `PLACE_PHRASES` plus English spellings and
  destinations whose one word is also a common given name ("Huế", "Sapa", "Hanoi", "Ha Long Bay", "Mekong Delta",
  country names). They must not join `PLACE_PHRASES`: there they would make pass 1 skip a traveller called Huế. In
  the typing list they cannot unmask anything.
- **Scrubber version `f3-1` -> `f3-2`.** Rule (now written next to `VERSION`): bump whenever the same input can scrub
  to a different output, so a receipt and a stored map say which rules produced them.
- **No migration.** crm-009 has no kind list: `llm_call_receipt_keys_chk` accepts any `counts` key matching
  `^[A-Z][A-Z_]{1,23}$` (`PLACE` fits), `placeholder_map_version_chk` accepts `f3-2`, and the kinds otherwise live only
  inside the sealed map. `patterns.PLACEHOLDER` (restore / neutralise) already matches `<PLACE_n>`. The crm-009 schema
  test now also inserts an `f3-2` receipt with a `PLACE` count (passes against Postgres 15).
- **Corpus metric.** `tests/scrub_corpus/run.py`: a `keep` string missing from the output but back once only the
  `<PLACE_n>` entries are restored counts as `typed_place` (reported with its rate and ids), not as over-scrub. Leaks
  and the 5 % over-scrub threshold are unchanged.

### Evidence

- Offline corpus (passes 1-2): 222 samples, 0 leaks, 0 over-scrub, 0 typed (no detector).
- Offline corpus with `PlaceTagger` (a detector that tags every destination `ADDRESS`, replaying the live run):
  before option C 111 / 332 keep strings over-scrubbed (33.4 %); with option C 0 over-scrub, 111 typed places, 0 leaks
  (`test_option_c_destinations_tagged_as_address_are_typed_places_not_overscrub`).
- Reviewer's live probe findings replayed (`test_people_named_like_places_stay_masked`): every name stays masked;
  `ADDRESS` on a bare name-like place becomes `<PLACE_n>`, `NAME` stays `<PERSON_n>`, restore round-trips.
- Live ApplyGuardrail check (acc2, 30 calls on synthetic corpus samples biased toward destination keeps): 26 samples,
  0 leaks, 9 typed places (Hà Giang, Hội An, Mai Châu, Ninh Bình, Phú Quốc, Sa Pa, Huế, Ha Long Bay), 4 over-scrubs
  left: 3 are `NAME` findings on destinations (Sapa twice, Hạ Long) kept `PERSON` by design, 1 is "Loop" of "Northern
  Loop" tagged `ADDRESS`.

### Should know

- The full live rate is known only after the "Scrub corpus" workflow runs on main (it never runs on PRs). Expect it
  well under 28.5 %, but not necessarily under 5 %: the remaining over-scrubs are destinations the guardrail types
  `NAME`, which option C deliberately leaves `PERSON`. If the run stays red for that reason, the next lever is
  option B (keep the trip's own destinations, from the tour / inquiry) or a reviewed exception, not a global keep.
- Semantic cost accepted: a companion named like a place and typed `ADDRESS` reads to the model as a place
  ("Travellers: <PLACE_1> and <PLACE_2>"); the reply restores the real value, nothing reaches the model.

## Option B: the trip's own destinations in clear (S250, scrubber f3-3)

Context: GitHub issue #27 ("Scrub corpus is red on main"). Live run 40081230173 (f3-2): 242 samples, 0 leaks,
33 / 362 keep strings over-scrubbed (9.12 %, limit 5 %), 70 typed places. The 33: 25 destinations the guardrail
tagged `NAME` (option C deliberately leaves them `<PERSON_n>`), 6 "expiry 2030" years, 2 "Northern Loop" tour names.
The S249 Linear comment defines option B: keep only the trip's own destinations, minus names that are common personal
names. The S249 lesson: a keep rule is scoped to the record's own context, never a global list, and is probed with
person names that match places.

### Decisions

- **Scope = the trip's countries, then an explicit list.** `crm.trip.destinations` holds country codes only
  (`stage1.DESTINATIONS`; nothing writes city codes), so "the trip's own destinations" is
  `places.KEEPABLE_PLACES[country]` for the trip's countries. A place not listed is never kept (fail closed); a code
  without a list (`not_sure`) keeps nothing. `known_values_for_trip` reads
  `SELECT destinations FROM crm.trip WHERE trip_id = $1 AND deleted_at IS NULL` in the same tenant / system context;
  nothing is opened through the vault, the `scrub_known_values` audit event is unchanged.
- **The name-likeness rule** (`app/privacy/names.py`, `name_like`): a phrase reads as a person's name when its first
  word is a Vietnamese family name (the pass-1 list plus rarer ones such as Ninh, Cù, Lưu) or an honorific, or when
  every word is a common given name. It drops Hà Giang, Hà Nam, Mai Châu, Thái Bình, Cao Bằng, Lâm Đồng, Kim Liên,
  Hòa Bình, Long An, Thanh Hóa, Hải Dương, Phú Quốc, An Giang, Kiên Giang, Phan Thiết, Huế, Ninh Bình, Ba Bể.
  `test_keepable_places_guard` holds every listed phrase to the rule and every key to `stage1.DESTINATIONS`;
  `is_keepable_place` checks the rule again at run time (belt and braces).
- **Marks decide the reading** (a change from the plan's "folded fullmatch"). Folding makes "Hạ Long" (the bay) and
  "Hà Long" (a family name + a given name) the same string, so a folded keep would leave a "Hà Long" visible. Keepable
  phrases are matched NFC + case folded with their diacritics; the rule reads a marked word marked ("Hạ" is not "Hà")
  and an unmarked word folded ("Ha" may be "Hà"). So "Hạ Long", "Halong Bay" and "Hạ Long Bay" are listed, "Ha Long"
  and "Ha Long Bay" are not (the rule drops them).
- **Ninh Bình dropped.** Ninh is a family name and Bình a given name; dropping it costs 3 corpus keeps (Ninh Binh in
  the live run) and still fits the budget. Reviewer to confirm.
- **Person guard before the place.** A keepable finding right after an honorific or a person word ("chị Sa Pa", "Mrs
  Hoi An", "Mr. Đà Lạt", "khách Hạ Long", "guest Hội An", "Travellers: Đà Lạt") stays masked. The plan named
  honorifics only; the person words (khách, guest(s), traveller(s), traveler(s), passenger(s)) and a colon / comma
  after them were added because the S249 probe texts use exactly those shapes. The check reads the 16 characters
  before the finding **with marks**: folded, "đi Sa Pa" (go to Sa Pa, the most common shape) would read as "dì Sa Pa"
  (aunt). The unmarked honorifics still match unmarked writing ("di", "chi", "ba").
- **Where it acts.** Only `NAME` and `ADDRESS` findings; the value must be keepable and so must the exact text it was
  located on (a folded locate on another spelling keeps nothing), standing as whole words. Overlapping findings merge
  as before; a merged span is left in clear only when every piece is keepable and the merged text is itself exactly
  one keepable place, so "12 Hội An road", "Hội An + Sa Pa" and a person's name overlapping a place are masked whole.
  Any span not kept is replaced exactly as in f3-2 (same kind rules). With no destinations nothing is keepable and the
  output, map and receipt are f3-2's, byte for byte (tested on the option C cases).
- **Receipt.** A kept finding takes no placeholder; the receipt's `counts` gains `PLACE_KEPT` (only when > 0), left out
  of `entities` and of `passes.detector` (nothing was replaced). crm-009 lets `f3-3` and `PLACE_KEPT` through (schema
  test added); no migration.
- **Name lists moved** to `app/privacy/names.py` (`scrubber.VN_FAMILY_NAMES` / `HONORIFICS` stay as aliases):
  `places.py` needs them and `scrubber.py` imports `places.py`.
- **Corpus.** Every sample carries `destinations` (`vietnam`, plus `cambodia` when it names Siem Reap); the first 242
  samples are otherwise unchanged. Added 9 `needs_detector` samples: the S249 live-probe texts (people named Mai
  Châu, Thái Bình, Hà Giang, Hòa Bình, Long An, Thanh Hóa, Kim Liên, Hải Dương, Ninh Bình) on a Vietnam trip, as
  `pii`: an allow-list widened to a name-like place turns the live corpus red with a leak. Added 3 samples on a Laos /
  Cambodia / Thailand trip naming a Vietnamese destination as `outside` (masked or typed as in f3-2, checked
  offline). `run.py` passes the destinations and reports `kept_place`.
- **Offline replays** (`tests/unit/test_scrub_corpus.py`): `NameTagger` (every destination `NAME`, the worst case):
  0 leaks and every remaining over-scrub is a name-like place. `LiveReplay` (per sample, the labels of run
  40081230173: its 33 over-scrubbed keep strings as the finding that masked them, every other destination
  `ADDRESS`): without destinations it reproduces the live 33 exactly (the replay is faithful); with them 13 are left
  (Ninh Binh x3, Mai Châu, Ha Long Bay, 2030 x6, Northern Loop x2), 13 / 335 = 3.9 % offline.

### Tradeoffs

- **Accepted residual risk**: a person nobody stored whose full name is exactly a listed, non-name-like destination of
  the trip's countries (say "Hội An") is left visible when the guardrail tags them `NAME` / `ADDRESS` and no
  honorific or person word precedes them. Limited by the trip-country scope, the explicit list, the rule, the person
  guard, and pass 1, which masks every stored person first (a stored companion called "Hội An" is `<PERSON_n>` before
  pass 3 runs). The review round below narrows it further (cue punctuation, kin and naming words, full-name
  neighbours) and lists the shapes still left.
- Name-like destinations still over-scrub when the guardrail tags them `NAME` (Ninh Bình, Mai Châu, Ha Long Bay in the
  corpus). Over-scrub over leak.
- Country scope is coarse: a Vietnam trip keeps "Côn Đảo" even if the trip never goes there. A city-level scope needs
  a trip-destination edit UI / API that does not exist.

### Evidence

- Unit: option B cases in `tests/unit/test_privacy_scrubber.py` (kept / byte-identical without destinations / other
  countries / every name-like place never kept / marks / honorific and person-word guard / merges / restore / the
  S249 LIVE_PROBE rows with `destinations=("vietnam",)`: every person stays masked, only Sa Pa and Hạ Long clear /
  list guard). Known values read the destinations (`test_privacy_store.py`); integration (Postgres 16 locally):
  `test_crm009_scrub.py` (destinations through RLS, f3-3 stored) and `test_crm009_schema.py` (f3-3 + `PLACE_KEPT`
  receipt accepted by the crm-009 CHECK).
- Offline corpus: 260 samples (225 offline, 35 need the detector after the review round), 0 leaks, 0 over-scrub. Live replay: 13 / 335.
- Live estimate for the "Scrub corpus" run on main: about 13 / 371 = 3.5 % (if the guardrail labels the first 242
  samples as in run 40081230173 and the new keeps survive), 0 leaks. Not run from this branch (no paid calls in the
  implementer lane; the workflow never runs on PRs).

### Should know

- The real gate is the "Scrub corpus" workflow after merge (push to main touching `api/app/privacy/**`). The "2030"
