# AA-1070 item crm-35 — included / not included lists on the proposal

Lane l1-crm35-inclusions of S278 (the first AA-1070 lane, `AA-1070.md`, left crm-35 out). Source: the S275 study
(root `docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`, row 24). Behaviour only: no code or text of
the studied app.

Migration crm-059 (expand: two new tables) ships alone in a migration-only PR; the code PR raises the readiness to
crm-059 and merges after Migration Apply registered it (MIG-4 chain).

## Decisions

- **Two tables.** `crm.inclusion_item` is the agency library (kind `included` / `not_included`, `text_en` default +
  optional `text_vi`, `sort_order`, `archived`); `crm.proposal_inclusion` holds the lines of one builder version
  (per `proposal_id`, so per version). Both follow the tenant base template (RLS ENABLE + FORCE, `tenant_isolation` to
  the six CRM roles, trash columns, `set_updated_at`); `crm_app` gets SELECT / INSERT / UPDATE / DELETE (the same as
  the crm-001 default privileges; no REVOKE in an expand file). No reader grant.
- **Snapshot by copy.** A version line copies its text; `inclusion_item_id` is a snapshot reference without a foreign
  key (like `visa_application.visa_template_id`), so editing, archiving or deleting a library line never changes a
  version. The table is draft-only through the existing `crm.guard_proposal_draft` (CRM35), so a published / sent /
  accepted version is frozen by the database, whatever path writes.
- **One replace, not pick / unpick / reorder routes.** `PUT /proposals/{id}/inclusions` with the version counter
  takes the whole new list (library ids or typed lines, in order per kind), like `PUT /before-you-go`. It answers the
  whole builder page. A line already on the draft keeps its copied text even when its library line was archived or
  edited since; a new pick copies the library text now; a new pick of an archived line is 409
  `inclusion_item_archived`; an unknown id 404 `inclusion_item_not_found`; repeats are one line; at most 60 lines.
- **Typed lines are folded to one line** (whitespace runs, newlines included, become one space; 1..300 characters).
  The database allows 500 so an AA tour's line is copied as CIS wrote it (longer ones are cut with an ellipsis).
- **Who.** Every role reads the library and picks lines on a draft (`proposal_draft`, like the other builder
  writes); the owner and agents write the library (`money_fields_edit`, like the service catalogue: it is the agency's
  commercial wording of what its prices cover). The assistant sees Settings > Proposal lines read-only.
- **AA tours: live on a draft, copied at Publish.** The lists come from the CIS tour content the CRM already caches
  (`crm.aa_catalog_tour.body`: `inclusions` strings and `exclusions[].text`, contract catalog.http.v1). Publish (still a
  draft at that moment) copies the lists of every AA tour among the version's options as source `aa_tour` rows, then
  computes the price hash; the rows are then frozen like the rest. Each page shows the tours of the chosen options:
  the defaults in the builder and in the e-mail / WhatsApp / PDF text (the version as sent), the client's current
  picks on the client page. A version published before this card has no copy and reads the cache.
- **Price hash.** The lines join the hash record only when the version has some (`record["inclusions"]`), so the hash
  of every older version is unchanged (the AA-1066 / AA-1067 rule).
- **One section, three forms.** `text_render.Snapshot` gains `included`, `not_included`, `aa_tours`; the e-mail /
  WhatsApp text prints "Included" then "Not included" after the days (the agency's lines, then each AA tour's under its
  title). The proposal PDF renders that e-mail text, so it shows the lists with no PDF change. The client page gets
  `inclusions` (both languages per line, no ids) and shows it above the amounts.
- **Working copy** copies the agency's lines (`source_inclusion_id` = the base row); the AA copy is made again at its
  Publish.
- **Text proposals** (kind `text`) have no lists: the GET answers 409 `proposal_not_builder`, the PUT goes through the
  builder lock (same refusal).

## Changed

- The issue sketched `crm.inclusion_item(tenant_id, kind include|exclude, text, locale, sort, active)`. Built: kind
  `included` / `not_included`, one row with `text_en` + optional `text_vi` (the lane brief: EN default, optional VI)
  instead of a row per locale, `archived` instead of `active`.
- The issue sketched `proposal_inclusion(proposal_id, item_id or free text)`. Built with a `source` column and the
  copied text on every row, plus `aa_tour` rows so the published version's AA block is frozen too.
- Library management is a Settings page (Settings > Payments > "Proposal lines"), linked from the builder panel.

## Tradeoffs

- Copy at pick vs a live library reference: a draft does not follow later library edits (re-pick to refresh), but a
  version never changes under the client and archived lines need no special read.
- AA lists copied for every AA tour among the options (not only the defaults): a few more rows per version, but the
  client's later swaps show the right tour's frozen lists.
- One replace route vs pick / unpick / reorder routes: one write per Save and one version-counter bump, the same
  pattern as Before you go; the page sends the whole list.
