## Decisions

- **Table names are the design's** (`proposal`, `payment_schedule`, `payment`, `traveler_access`, `otp_challenge`,
  `agreement_doc`, `signature_request`): every one already has its DM-7 row in root data standards Part B §7, so the
  Infra retention-row check passes without a registry change. `terms_acceptance` and `signature_event` (also in the
  registry) are not created: v0 keeps the acceptance on the proposal row and the signing evidence on the signature row
  (one hash of the evidence record). CRM-25 (e-sign v1, PAdES) can split them out.
- **Proposal = text + sell amounts only** (M4 base): body under the tenant `vault` DEK, `total_amount`,
  `deposit_amount` (> 0, <= total), `balance_due_on` exactly when a balance is left, optional booking terms version.
  No net, cost or margin column, so nothing for the margin serializer to strip. Day-by-day builder, options and AA
  lines are CRM-21a / 21b / 22.
- **`price_hash`** = SHA-256 of the canonical record the client sees (proposal id, version, currency, amounts, balance
  date, SHA-256 of the text, the terms version and its hash), set at send. Acceptance must send the same hash back
  (409 `price_changed` otherwise) and the database pins `accepted_price_hash = price_hash` (CHECK).
- **One sent and one accepted version per trip** (partial UNIQUE). A new send supersedes the open one and revokes its
  link. A proposal can be sent only while the trip is at Proposal (the Stage 2 gate stays the way in).
- **Sealed rows in the database** (`crm.guard_sealed_row`, one generic trigger with the editable status and the sealed
  columns as arguments; SQLSTATE CRM31): a sent proposal's content, the acceptance once written, a paid / void
  schedule row, a published / retired agreement, a signed signature. The acceptance has its own trigger (editable only
  while `sent`), so the move sent -> accepted can write it and nothing can change it afterwards.
- **The agreement hash is the database's**: `body_sha256` is set by a BEFORE trigger on every write (a generated
  column cannot call `convert_to`, which is only STABLE). One published version per kind (partial UNIQUE).
- **Payment schedule from the accepted proposal**: acceptance creates the deposit row (due today in the agency
  timezone) and, when a balance is left, the balance row (due `balance_due_on`). "Mark paid" (owner / agent:
  `PAYMENT_MARK_RECEIVED`) writes one `crm.payment` row (append-only, the crm-014 `ledger_append_only` rule), moves the
  schedule row to paid and writes a `trip_commitment` row kind `payment` / `succeeded` (the crm-010 delete block then
  answers `has_money`). One payment per schedule row in this card; partial / card payments and refunds are CRM-23.
- **Deposit paid -> Booked in the same transaction** (F6.6): the stage engine's `booking` gate is now computable
  (a paid deposit of the accepted proposal); the move is written with reason `deposit_paid`, no override, and every
  traveller of the trip gets a portal invite (their own link). The database checks the same gate (crm-016
  `crm.enforce_stage_transition`), so a direct UPDATE cannot skip it either. The manual override (`manual_booking`)
  stays for agencies that took the deposit outside the CRM.
- **Stage 3 gate** (booked -> pre_departure) is computable too: `intake_completeness.s3 = 100`, where s3 = the share
  of (traveller x item) done: Stage 3 details (the F1 identity fields on `crm.traveler`) for every traveller, and the
  published waiver signed by every traveller when the agency has one. `manual_stage3` override stays.
- **Stage 3 locked before the deposit** (card R) in two places: the portal answers 403 `stage3_locked` before it reads
  the body, and the database refuses `traveler_access.stage3_submitted_at` without a paid deposit (CRM32). Signing the
  waiver is locked the same way (it is part of the pre-departure set; C-08 comes after the deposit in F8).
- **Per-person portal (M11 base)**: one signed link per traveller (`client_link` purpose `portal`, 30 days, the
  crm-012 maximum; "Re-issue link" revokes the old one), then a 6-digit e-mail code to that traveller's own address
  (purpose `sign_in`, 10 minutes, 5 attempts, at most 5 codes per hour per access). A verified code opens a 12-hour
  portal session: the API sets an httpOnly, Secure, SameSite=Strict cookie scoped to `/crm/public/v1/portal/` on the
  client host (the browser calls the API on its own origin, like C-02), and only its SHA-256 is stored. The "Who are
  you?" picker (two travellers on one e-mail) is CRM-24a: one link per person avoids it in v0.
- **Code delivery through the agency's own mailbox** (errata S247: no platform sender; "AA never messages
  travellers"): the code mail is a `crm.message` in the trip conversation with that traveller, sender kind
  `agency_mailbox` (the trip owner's own mailbox, else the agency's), queued with origin `system` (no Undo delay) and
  sent by the AA-945 sender. No mailbox -> 409 `code_delivery_unavailable` and nothing is stored.
- **Dev echo of the code** (`PORTAL_OTP_DEV_ECHO`, default off, refused at start-up outside dev / test / local): the
  synthetic Dev agencies have no mailbox, so the E2E and a manual check could not sign in at all. With it on, the code
  answer carries `dev_code`. Same model as the EXTERNAL `cis-portal` bridge (dev only).
- **E-sign v0** (M12 v0, §5.7 minus the PDF and seal): the traveller reads the published waiver, asks for a signing code
  (purpose `sign`: "code asked again at signing"), types their full name and ticks the consent; the API verifies and
  consumes the code, pins the waiver's SHA-256 and writes `signature_request` signed with `evidence_sha256` = SHA-256 of
  the canonical evidence record (request, trip, traveller, access, document hash, code id, signed at, SHA-256 of the
  typed name, consent ticks), plus a `trip_commitment` kind `signature` / `signed`. Each traveller signs their own
  (guardian signing for minors is CRM-25).
- **Date ticks** (`crm_stage_date_rule`, AA-943, extended): booked -> travelling on the start date now says
  `date_rule` when s3 = 100 and `date_rule_gate_unmet` + the urgent task only when Stage 3 or the waiver is missing
  (Fix B4 as written); new T-21 tick: a booked trip within 21 days of departure with s3 < 100 gets one
  `stage3_due_t21` task; the OTP purge (codes older than 24 hours, DM-7 row) runs in the same hourly pass. The card E
  rule (no return date -> stays Travelling + `return_date_missing` task) is AA-943's and keeps its test; the AA-946
  API test repeats it end to end.
- **waiting_on**: a hook `portal_stage3` (priority 60, after AA-944's `supplier_lines` at 50) answers `client` for a
  booked trip whose s3 < 100.
- **OTP rows have no hold guard**: a code is a credential with a 24-hour life; a legal hold has nothing to keep there,
  and a guard would make the purge fail for a held trip. `crm.erase_held` still counts their trip / traveller.
- **crm-016 test re-applies its own file first** (`test_crm016_is_registered_and_runs_again_as_a_no_op`): the crm-012
  to crm-015 schema tests re-apply their files, which put back their older `erase_subject`, stage trigger and link
  purpose CHECK; the AA-945 test does the same.
- **The signature keeps its own evidence** (re-review S251): `signature_request.code_delivery` (`mailbox` |
  `dev_echo`, copied from the signing code) and `evidence_record` (the canonical evidence JSON exactly as hashed:
  ids, document hash, code id, delivery, signed at, SHA-256 of the typed name, consent; no PII) are written at signing
  and sealed with the rest (CRM31). CHECK `signature_request_evidence_chk` ties `evidence_sha256 = sha256(evidence_record)`,
  so the hash can be re-verified after the 24-hour code purge sets `otp_id` NULL. `evidence_record` is BYTEA, not TEXT
  or JSONB: JSONB reorders keys, and hashing TEXT in a CHECK would need `convert_to` (only STABLE).
- **`mailbox` does not mean "only the traveller saw the code"** (e-sign v0 limit, re-review S251): the code goes out
  from the agency's mailbox and the mail provider keeps a Sent copy that the owner of that mailbox can read; the column
  comments say so. Fix options are Nghiệp's decision (see the code branch notes).

## Changed (vs the card / plan)

- `test_crm002_tenancy.py` lists `payment` as an append-only table with the `ledger_append_only` trigger;
  `test_crm012_schema.py` checks an unknown link purpose with `contract` (crm-016 made `proposal` valid).
- `app/stages.py`: the booking and Stage 3 gates are computed (`_gate_met`); an override on a met gate is 422
  `override_not_needed` like the Stage 2 gate; the bulk preview reads `deposit_paid` and `s3` per trip;
  `move(..., reason=)` lets a system rule write its own history code (`deposit_paid`).
- `test_reveal_boundary.py` lists the new public router module `app.routers.client_pages`; `test_stages.py` saves and
  restores the registered `waiting_on` hooks (the portal hook registers at import) and covers the new gates;
  `test_code_rules.py` allows `client_link_tx` in the two new public modules.
- **The `waiting_on` hook answers only when the trip has portal access** (not in the first draft): a booked trip whose
  travellers were never invited (an override booking, or a trip booked before CRM-18) keeps the base rule; the AA-944
  ledger test showed the difference.
- No HTTP-level "Undo" for "mark paid": a payment is a record of money received (append-only); a mistake is a later
  correction (CRM-23 refunds). The deposit's stage move is not offered for Undo either.

## Tradeoffs

- **Signed-agreement and accounting retention exceptions** (DM-7 rows: signatures kept until trip end + 3 years,
  payments for the statutory period, also through an erasure) are not implemented in v0: a trip / agency erase deletes
  them with the trip. The delete block already stops a trash purge of a trip with a payment or a signature; only an
  erasure or an offboarding reaches them. Dev holds synthetic agencies only. CRM-23 / CRM-25 implement the exceptions.
- The portal link stays in the URL path (like C-02) instead of the §2.9 rule 1 exchange for a cookie and a redirect;
  the page sets `Referrer-Policy: no-referrer`. The token exchange is CRM-24a.
- The code mail is visible in the trip's Messages tab (it is a normal sent message of the agency's mailbox), so an
  agent could read a code. The code lives 10 minutes and the agency is the controller; a template send path that does
  not store the code is a follow-up (CRM-24a / CRM-28).
