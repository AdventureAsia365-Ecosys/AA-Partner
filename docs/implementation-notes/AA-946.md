## Decisions

- **Table names are the design's** (`proposal`, `payment_schedule`, `payment`, `traveler_access`, `otp_challenge`,
  `agreement_doc`, `signature_request`): every one already has its DM-7 row in root data standards Part B §7, so the
  Infra retention-row check passes without a registry change. `terms_acceptance` and `signature_event` (also in the
  registry) are not created: v0 keeps the acceptance on the proposal row and the signing evidence on the signature row
  (one hash of the evidence record). CRM-25 (e-sign v1, PAdES) can split them out.
- **Proposal = text + sell amounts only** (M4 base): body under the tenant `vault` DEK, `total_amount`,
  `deposit_amount` (> 0, <= total), `balance_due_on` exactly when a balance is left, optional booking terms version.
  No net, cost or margin column, so nothing for the margin serializer to strip. Day-by-day builder, options and AA
  lines are CRM-21a / 21b / 22.
- **`price_hash`** = SHA-256 of the canonical record the client sees (proposal id, version, currency, amounts, balance
  date, SHA-256 of the text, the terms version and its hash), set at send. Acceptance must send the same hash back
  (409 `price_changed` otherwise) and the database pins `accepted_price_hash = price_hash` (CHECK).
- **One sent and one accepted version per trip** (partial UNIQUE). A new send supersedes the open one and revokes its
  link. A proposal can be sent only while the trip is at Proposal (the Stage 2 gate stays the way in).
- **Sealed rows in the database** (`crm.guard_sealed_row`, one generic trigger with the editable status and the sealed
  columns as arguments; SQLSTATE CRM31): a sent proposal's content, the acceptance once written, a paid / void
  schedule row, a published / retired agreement, a signed signature. The acceptance has its own trigger (editable only
  while `sent`), so the move sent -> accepted can write it and nothing can change it afterwards.
- **The agreement hash is the database's**: `body_sha256` is set by a BEFORE trigger on every write (a generated
  column cannot call `convert_to`, which is only STABLE). One published version per kind (partial UNIQUE).
- **Payment schedule from the accepted proposal**: acceptance creates the deposit row (due today in the agency
  timezone) and, when a balance is left, the balance row (due `balance_due_on`). "Mark paid" (owner / agent:
  `PAYMENT_MARK_RECEIVED`) writes one `crm.payment` row (append-only, the crm-014 `ledger_append_only` rule), moves the
  schedule row to paid and writes a `trip_commitment` row kind `payment` / `succeeded` (the crm-010 delete block then
  answers `has_money`). One payment per schedule row in this card; partial / card payments and refunds are CRM-23.
- **Deposit paid -> Booked in the same transaction** (F6.6): the stage engine's `booking` gate is now computable
  (a paid deposit of the accepted proposal); the move is written with reason `deposit_paid`, no override, and every
  traveller of the trip gets a portal invite (their own link). The database checks the same gate (crm-016
  `crm.enforce_stage_transition`), so a direct UPDATE cannot skip it either. The manual override (`manual_booking`)
  stays for agencies that took the deposit outside the CRM.
- **Stage 3 gate** (booked -> pre_departure) is computable too: `intake_completeness.s3 = 100`, where s3 = the share
  of (traveller x item) done: Stage 3 details (the F1 identity fields on `crm.traveler`) for every traveller, and the
  published waiver signed by every traveller when the agency has one. `manual_stage3` override stays.
- **Stage 3 locked before the deposit** (card R) in two places: the portal answers 403 `stage3_locked` before it reads
  the body, and the database refuses `traveler_access.stage3_submitted_at` without a paid deposit (CRM32). Signing the
  waiver is locked the same way (it is part of the pre-departure set; C-08 comes after the deposit in F8).
- **Per-person portal (M11 base)**: one signed link per traveller (`client_link` purpose `portal`, 30 days, the
  crm-012 maximum; "Re-issue link" revokes the old one), then a 6-digit e-mail code to that traveller's own address
  (purpose `sign_in`, 10 minutes, 5 attempts, at most 5 codes per hour per access). A verified code opens a 12-hour
  portal session: the API sets an httpOnly, Secure, SameSite=Strict cookie scoped to `/crm/public/v1/portal/` on the
  client host (the browser calls the API on its own origin, like C-02), and only its SHA-256 is stored. The "Who are
  you?" picker (two travellers on one e-mail) is CRM-24a: one link per person avoids it in v0.
- **Code delivery through the agency's own mailbox** (errata S247: no platform sender; "AA never messages
  travellers"): the code mail is a `crm.message` in the trip conversation with that traveller, sender kind
  `agency_mailbox` (the trip owner's own mailbox, else the agency's), queued with origin `system` (no Undo delay) and
  sent by the AA-945 sender. No mailbox -> 409 `code_delivery_unavailable` and nothing is stored.
- **Dev echo of the code** (`PORTAL_OTP_DEV_ECHO`, default off, refused at start-up outside dev / test / local): the
  synthetic Dev agencies have no mailbox, so the E2E and a manual check could not sign in at all. With it on, the code
  answer carries `dev_code`. Same model as the EXTERNAL `cis-portal` bridge (dev only).
- **E-sign v0** (M12 v0, §5.7 minus the PDF and seal): the traveller reads the published waiver, asks for a signing code
  (purpose `sign`: "code asked again at signing"), types their full name and ticks the consent; the API verifies and
  consumes the code, pins the waiver's SHA-256 and writes `signature_request` signed with `evidence_sha256` = SHA-256 of
  the canonical evidence record (request, trip, traveller, access, document hash, code id, signed at, SHA-256 of the
  typed name, consent ticks), plus a `trip_commitment` kind `signature` / `signed`. Each traveller signs their own
  (guardian signing for minors is CRM-25).
- **Date ticks** (`crm_stage_date_rule`, AA-943, extended): booked -> travelling on the start date now says
  `date_rule` when s3 = 100 and `date_rule_gate_unmet` + the urgent task only when Stage 3 or the waiver is missing
  (Fix B4 as written); new T-21 tick: a booked trip within 21 days of departure with s3 < 100 gets one
  `stage3_due_t21` task; the OTP purge (codes older than 24 hours, DM-7 row) runs in the same hourly pass. The card E
  rule (no return date -> stays Travelling + `return_date_missing` task) is AA-943's and keeps its test; the AA-946
  API test repeats it end to end.
- **waiting_on**: a hook `portal_stage3` (priority 60, after AA-944's `supplier_lines` at 50) answers `client` for a
  booked trip whose s3 < 100.
- **OTP rows have no hold guard**: a code is a credential with a 24-hour life; a legal hold has nothing to keep there,
  and a guard would make the purge fail for a held trip. `crm.erase_held` still counts their trip / traveller.
- **crm-016 test re-applies its own file first** (`test_crm016_is_registered_and_runs_again_as_a_no_op`): the crm-012
  to crm-015 schema tests re-apply their files, which put back their older `erase_subject`, stage trigger and link
  purpose CHECK; the AA-945 test does the same.
- **The signature keeps its own evidence** (re-review S251): `signature_request.code_delivery` (`mailbox` |
  `dev_echo`, copied from the signing code) and `evidence_record` (the canonical evidence JSON exactly as hashed:
  ids, document hash, code id, delivery, signed at, SHA-256 of the typed name, consent; no PII) are written at signing
  and sealed with the rest (CRM31). CHECK `signature_request_evidence_chk` ties `evidence_sha256 = sha256(evidence_record)`,
  so the hash can be re-verified after the 24-hour code purge sets `otp_id` NULL. `evidence_record` is BYTEA, not TEXT
  or JSONB: JSONB reorders keys, and hashing TEXT in a CHECK would need `convert_to` (only STABLE).
- **`mailbox` does not mean "only the traveller saw the code"** (e-sign v0 limit, re-review S251): the code goes out
  from the agency's mailbox and the mail provider keeps a Sent copy that the owner of that mailbox can read; the column
  comments say so. Fix options are Nghiệp's decision (see the code branch notes).

## Tradeoffs

- **Signed-agreement and accounting retention exceptions** (DM-7 rows: signatures kept until trip end + 3 years,
  payments for the statutory period, also through an erasure) are not implemented in v0: a trip / agency erase deletes
  them with the trip. The delete block already stops a trash purge of a trip with a payment or a signature; only an
  erasure or an offboarding reaches them. Dev holds synthetic agencies only. CRM-23 / CRM-25 implement the exceptions.
- The portal link stays in the URL path (like C-02) instead of the §2.9 rule 1 exchange for a cookie and a redirect;
  the page sets `Referrer-Policy: no-referrer`. The token exchange is CRM-24a.
- ~~The code mail is visible in the trip's Messages tab~~: fixed after the independent review (S251), see "Review
  fixes" below.

## Review fixes (S251, independent review of the AA-946 PRs)

1. **Codes the agency could read (should-fix, e-sign evidence).** The code mail is now stored with the code masked
   (`app/portal/codes.py` `CODE_MASK`, shown as "[code sent to the traveller only]" in the Messages tab). The code
   itself waits under the tenant vault DEK in the new `otp_challenge.code_enc`, linked to its mail by
   `otp_challenge.message_id`; `app.mail.sender` opens it only at send time, puts it into the outgoing text and clears
   it once the provider accepted the mail. A code that left `pending` or expired before the mailbox could send it is
   never sent (the message `failed`, `code_expired`). The database keeps `code_enc` only while the code is pending
   (`otp_challenge_code_enc_chk`), and every status change in `app/portal/public.py` clears it. A new
   `otp_challenge.delivery` (`mailbox` | `dev_echo`) records whether the Dev echo also returned the code in the API
   answer, and the signature evidence record now carries it (`code_delivery`), so a Dev signature never claims e-mail
   control. Chosen over "redact after dispatch": a held mailbox (`held_reconnect`) would keep a readable code in the
   tab until reconnect, and a redact step would rewrite a sent message. Remaining trust boundary: a platform operator
   with the vault key; that is the same for every sealed field.
2. **Override bookings locked out of the portal (should-fix).** One predicate, `crm.portal_unlocked(trip)` (crm-016,
   invoker rights, `crm_app` EXECUTE), used by the DB guard (CRM32) and the API (`stages.PORTAL_UNLOCKED_SQL`; the
   portal `home.stage3.locked`, `submit_stage3`, `sign`, and `portal_unlocked` in the trip lifecycle answer): a paid
   deposit of the accepted proposal **or** a `trip_stage_history` row into `booked` with `override_reason_code =
   manual_booking` that no later row undoes (`undo_of`). The agency invites the travellers from the Proposal tab
   ("Send portal link"); invites already work at any open stage. And a **deposit row is never void**: CHECK
   `payment_schedule_deposit_void_chk`, API 409 `deposit_not_voidable`, the Void button is hidden on deposit rows. A
   deposit taken outside the CRM on a trip with an accepted proposal is "Mark paid" with method `cash` / `other`; a
   deal that is off is marked Lost (or cancelled once booked; wording fixed in the re-review). Chosen over "re-issue a voided deposit": no second deposit row semantics to
   define, and the accepted proposal's price stays the one the client accepted. An unpaid deposit of a cancelled trip
   stays `due` on that closed trip; CRM-23 (refunds, write-offs) revisits it.
3. **The typed acceptance name outliving an erasure (should-fix).** New `proposal.accepted_name_erased_at`;
   `crm.erase_subject` traveller scope now first sets `accepted_name_enc = NULL, accepted_name_erased_at = now()` on
   every accepted proposal whose `link_id` is one of the traveller's links (count key
   `proposal_acceptance_name_erased`), before their links are deleted. `proposal_accepted_chk` accepts an accepted row
   with exactly one of the name or the erasure time. `crm.guard_sealed_row` now lets only `crm_owner` with
   `app.erasing = on` (inside `crm.erase_subject`) change a sealed column, the rule the crm-010/014 append-only guards
   use; `crm_app` still gets CRM31 (tested: the sealed-row parametrize). The acceptance time, price hash and terms
   version stay (no personal data).

Spec gaps the review listed that stay open on purpose (v0 scope; each has a later card):

- DM-7 retention exceptions for signed agreements (trip end + 3 years) and accounting records (statutory period, also
  through an erasure): CRM-23 (payments/refunds) and CRM-25 (e-sign v1, PAdES). v0 still erases them with the trip or
  the agency; the delete block keeps a trip with money or a signature out of the trash purge. Dev holds synthetic data
  only. Done item for CRM-23 / CRM-25: "an erasure keeps signature_request + payment rows under the DM-7 exception".
- The §2.9 rule 1 token-to-cookie exchange + redirect and the "Who are you?" picker: CRM-24a. The token stays in the
  path with `Referrer-Policy: no-referrer`.
- `terms_acceptance` and `signature_event` (DM-7 registry names) are not created: the acceptance lives on the proposal
  row and the signing evidence on the signature row (one evidence hash). CRM-25 can split them out without a data
  move.
- Item 1 of the review is fixed here, not deferred: the code mail no longer exposes the code in the Messages tab.
  The re-review found the provider's Sent copy (below).

## Re-review fixes (S251, second independent review)

1. **The Sent copy (should-fix; wording fixed, the real fix is Nghiệp's decision).** Gmail `users/me/messages/send`,
   Graph `sendMail` (MIME) and Gmail SMTP all keep a Sent copy in the sending mailbox, so the owner of the agency
   mailbox can read every code there; the same staff are shown each traveller's portal link. `delivery = mailbox` /
   `code_delivery = mailbox` therefore means "sent from the agency's mailbox to the traveller's address", not "only the
   traveller saw the code". Changed: the comments in crm-016 (`otp_challenge.delivery`,
   `signature_request.code_delivery`, the table comment), `app/portal/public.py` (module docstring, the evidence
   comment), CONTEXT.md ("E-sign v0 limit"). **Known e-sign v0 limit**: a v0 signature is agency-attested evidence,
   not proof of the traveller's sole control of the code. Options for Nghiệp (not built):
   (a) Microsoft: send code mails with JSON `sendMail` and `saveToSentItems=false`;
   (b) Gmail: delete the SENT copy after sending (needs the `gmail.modify` scope, a re-consent for every mailbox);
   (c) a platform (SES) sender exception for OTP mails only (conflicts with errata S247, needs a decision);
   (d) stop showing staff the traveller portal links and send them only by e-mail (also from the agency mailbox, so
   (d) alone still leaves the Sent copy of the link; it pairs with (a)/(b)).
   SMTP mailboxes have no API to suppress the copy; (c) is the only full fix for them.
2. **The evidence outlives the code purge (should-fix).** crm-016 (edited in place: it is applied nowhere yet):
   `signature_request.code_delivery` (`mailbox` | `dev_echo`, NULL exactly while unsigned) and `evidence_record`
   (BYTEA: the canonical evidence JSON exactly as hashed; ids, document hash, code id, delivery, signed at, SHA-256 of
   the typed name, consent; no PII), both in the `signature_request_sealed` column list; CHECK
   `signature_request_evidence_chk`: `sha256(evidence_record) = evidence_sha256` (at most 4 KiB). `SIGN_SQL` writes
   both. BYTEA, not TEXT / JSONB: JSONB reorders keys, and a TEXT hash in a CHECK needs `convert_to` (STABLE only).
   The `evidence_sha256` comment lists access_id and code_delivery now. No DM-7 change: the record is a column of
   `signature_request` (its row, its retention, erased with it by `crm.erase_subject`) and holds no personal data
   beyond the ids the row already has.
3. **Nits applied:** an integration test runs `MailSender` through the dispatcher on PostgreSQL with the real vault
   (`test_the_mail_sender_fills_in_the_code_and_clears_it`: the provider gets the code, the stored body keeps
   `CODE_MASK`, `code_enc` is cleared; a superseded code and a code past its 10 minutes are never sent); the hourly
   `crm_stage_date_rule` run now first expires pending codes past `expires_at` and clears `code_enc`
   (`OTP_EXPIRE_SQL`, count `codes_expired`), so a held or unsent code mail does not keep the code until the 24 h
   purge; a `sign` code request is 403 `stage3_locked` while signing is locked (no mail, no hourly code spent); the
   `deposit_not_voidable` text (API, EN, VI) says "mark the trip Lost (or cancel it once booked)".
4. **Not done (noted):** a Lost trip keeps its portal links and its lead still sees the `due` deposit in the portal
   (`portal._access` has no stage check, the move to Lost does not revoke links). Candidate for CRM-23 / CRM-24a:
   refuse the portal for closed stages or revoke the links on the move to Lost. Infra #385's failed plan was a state
   lock clash with #384 (re-run only); #384's copy check waits for Partner #49.

Spec gaps from the re-review (for Nghiệp): whether a mailbox-sent code is acceptable evidence for e-sign v0 (option
list above), and what the evidence must keep after the 24 h code purge (answered for v0 by item 2; CRM-25 PAdES may

## Web + E2E (same branch)

Decisions:

- **The trip's Proposal tab** (`components/proposals/ProposalPanel.tsx`) sits between the trip workspace and the
  Bookings tab: the current version (accepted, else the open draft / sent one), the draft form (text, currency, total,
  deposit, terms version, the balance date through the locale `DateInput`), Send / Withdraw / New version, the
  schedule rows with Mark paid (method + received date, empty = today) and Void, and the travellers' Stage 3 / waiver
  progress with "Send portal link" / "New portal link". Links come back from the API once and are shown in a
  "copy now" box (the AA-943 "Copy link" model: the dispatcher holds `no_message` until a template send exists).
- **Client pages call the API on their own origin** like C-02: `/c/p/<token>` and `/c/t/<token>` fetch
  `/crm/public/v1/...` from the browser (the per-address limits key on the visitor; the web server never calls the
  API with a token). The portal uses `credentials: "same-origin"` so the API's httpOnly session cookie (scoped to that
  portal's own path) goes along; the proposal page sends no cookie. Both paths get `Referrer-Policy: no-referrer`.
- **Only the client strings ship to the client pages** (`lib/clientMessages.ts`, prefixes `client.` / `common.`),
  EN by default (S249), VI complete.
- **Stage 3 in the portal is write-only**: the form shows which fields are on file ("on file"), never their values;
  empty fields are not sent (a traveller fixes one field without retyping the rest).
- **Settings > Agreements** (`/settings/agreements`): owner drafts and publishes; others read the published versions.
- **E2E** (`e2e/tests/lifecycle-thin.spec.ts`): one synthetic trip from the inquiry form to Pre-departure and a
  cancel; the portal steps read the Dev echo of the code from the page and are skipped (with a note) when the API does
  not echo. The E2E job timeout goes from 25 to 35 minutes (three long specs in one job).

Tradeoffs:

- No local `next build` (RAM shared by three lanes): `tsc --noEmit` and vitest only; CI "Web Build" builds.
- The kit's `Button` takes no `data-testid`; the E2E finds those buttons by role and name (EN), the rows and forms by
  test id.
