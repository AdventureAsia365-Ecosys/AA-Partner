# AA-957 (lane w9b) — pre-existing trip page defects from the S262 live evidence

Source: the AA-957 live run of S262 (root `docs/audits/2026-10-31-S262-evidence/AA-957/`, critic defects). Four
defects older than AA-957, fixed in one PR; item 3 is the AA-956 ops release area (`Refs AA-956`). The parallel lane
w9a (cancel dialog, LinesPanel, commissions page, trip billing) is not touched here; i18n additions live in a new
file (`web/lib/i18nTripCodes.ts`) so the two lanes do not edit the same lines.

## Decisions

- **One list of codes, checked from both sides.** `api/app/task_kinds.py` lists every `crm.task` kind (25) and every
  `crm.trip_stage_history` reason (8 whole codes + the families `lost_` / `cancel_`). The API unit test
  (`tests/unit/test_task_kinds.py`) scans `app/` (AST: `*_TASK` constants, literal kinds in `INSERT INTO crm.task`
  text, the kind argument of a `*TASK*` SQL call; reasons from the history INSERT's `reason_code` column, `move(...,
  reason=...)`, the `HISTORY_SQL` reason argument, `reason = ...` in the stage modules) and fails in both directions
  (unlisted / stale). The web test (`tests/tripCodes.test.ts`) reads that Python file plus `LOST_REASONS` /
  `CANCEL_REASONS` and fails when a code has no EN or VI label, then renders the trip panel with the three evidence
  kinds and `deposit_paid`. The modules keep their own constants; the list does not replace them (less churn, and
  the scan catches drift).
- **Labels added** (EN + VI): 10 task kinds (`aa_confirm_failed`, `aa_hold_expired`, `aa_incident`,
  `aa_line_declined`, `aa_lines_failed`, `collect_deposit`, `proposal_change_request`, `proposal_follow_up`,
  `proposal_hold_problem`, `stage3_due_t21`) and 2 reasons (`deposit_paid`, `import`).
- **Incident departure in words.** `GET /trips/{id}/incidents` and the Travelling now flags carry
  `departure: {title, date}`: the agency's own non-cancelled booking line on that departure (first by service day,
  then id). The web prints "<title>, from <date>", the title alone, or nothing; never the Booking `departure_id`
  (kept in the JSON and as a test hook). `TRIP_FLAGS_SQL` now joins the line with `LATERAL ... LIMIT 1` (same
  filter as the old `IN` subquery); `FLAG_TRIPS_SQL` became `DISTINCT ON (departure, start, trip)` so two lines of
  one trip on a departure still give one trip row.
- **Ops receipt vs activity: the receipt was right.** The receipt counts `view_count` and the deleted manifest rows
  (4 + 4 in the evidence); the API sent all 11 activity lines (cap 20) but the panel showed `activityLines(view, 8)`
  with no hint, cutting the oldest view, export and the "shared" line. Fix: the panel shows 8 and a "Show all n" /
  "Show fewer" toggle; the API fetches `MAX_ACTIVITY + 1` and says `activity_more` when older lines exist, and the
  panel then points to Settings > Access log. Counts are not deduplicated: each line is one audit event.
- **Dark mode lost after hydration: two causes, both fixed.**
  1. The trigger: `TripPanel` printed a task's due time with `toLocaleString` and no zone (server UTC, browser
     local), and `BuilderClientRow` the AA hold end the same way: a hydration text mismatch on every trip with an
     open task due date (that is why B1 before the cancel lost dark and B1 after the cancel, its tasks skipped, kept
     it). Both now use `formatInstant(..., agency zone)` (the zone of `GET /trips/{id}/invoices`, as `InvoicesPanel`
     already does; UTC labelled when that call fails).
  2. The loss: on a failed hydration React 19 renders the document again on the client and, taking over `<html>`,
     removes every attribute and writes the layout's props (`data-theme="light"`). The layout no longer renders a
     `data-theme` (the restore script is the only writer before paint) and `app/_kit/local/ThemeKeeper` re-applies
     the stored choice in a layout effect on every mount of the root. Any future mismatch elsewhere keeps the theme.

## Tradeoffs

- The due time now reads "1 Nov 2026, 6:30 am GMT+7" (year and zone label) instead of "1 Nov, 06:30": longer, but the
  same on server and browser and the format the invoices already use.
- `ThemeKeeper` is a layout effect, not a MutationObserver: it covers a rebuild of the root (the only path where React
  touches `<html>` attributes once the layout stops rendering `data-theme`) without watching the DOM forever.
- Keeping the Booking `departure_id` in the API (unused by the UI text) costs nothing and keeps the staff/debug link.

## Should know

- Other times printed without a zone remain: `ClientPayBox`, `ClientBuilderProposal` (the traveller's own pages) and
  `lib/accessLog.ts whenText` (Settings > Access log, browser zone by design, but its first page is server-rendered,
  so it can mismatch too). With the keeper the theme no longer depends on them; a follow-up can move them to
  `formatInstant` with the agency zone.
- The ICS feed still words a task as `kind.replace("_", " ")` ("Task due: aa incident"); out of scope here.
