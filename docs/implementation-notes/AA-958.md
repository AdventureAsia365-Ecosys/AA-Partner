## Decisions

- **One provider, two implementations.** `TextProvider` (`send`, `check`, `templates`) with `TwilioProvider` (the
  agency's own account: Messages API for SMS and WhatsApp, Content API for templates, the account read for health) and
  `SandboxProvider` (deterministic, no network; accepted on `dev` / `test` / `local` only, `build_providers`). Twilio
  is the only real provider: the errata §1 names it, and one SID + token covers both channels. A second vendor is one
  more class behind the same interface and one more value of `messaging_connection.provider`.
- **Messages stay in the AA-945 tables.** SMS / WhatsApp are `crm.message` rows (channel `sms` / `whatsapp`) in
  `crm.conversation`, so the trip Messages tab, Unmatched, Link, Undo / Edit, erasure and the held-row rules are shared
  with e-mail. Only the channel facts are new: `crm.message_delivery` (template, sealed variables, delivery state),
  the WhatsApp window and the opt-out on the conversation.
- **Credentials like the AA-945 SMTP login.** `crm.integration_credential` provider `twilio`, agency level
  (`member_id` NULL), the JSON sealed under the `integration` DEK, the Account SID as `account_ref`; the account is read
  before anything is stored. `Vault.decrypt_secret` is lint-allowed in `app/messaging/sender.py` only
  (`test_vault_rules`), everyone else calls `load_secret`.
- **Per-agency webhook by an opaque path id**, not by host: `hook_id` (128 random bits) in
  `/crm/public/v1/hooks/twilio/<hook_id>` (+ `/status`). A reconnect keeps it, so the URLs pasted into Twilio stay
  valid. Found through a SELECT-only RLS lookup policy keyed on `app.messaging_hook_id`
  (`app.tenancy.messaging_hook_tx`, the `ingest_address_lookup` pattern of crm-015).
- **Signature over the URL the CRM printed** (`MESSAGING_HOOK_BASE`, else the first `INTAKE_PAGE_ORIGINS` entry),
  never the request's Host header, plus `AccountSid` must equal the stored one; 403 `invalid_signature` before
  anything is stored (card R). No new Infra: the client host's ALB rule already sends `/crm/public/*` to the API.
- **Send and retry reuse `crm_dispatch`** (no new send kind): `POST /messaging/messages` stores the message + delivery
  row and queues one dispatch row with the 10 s Undo; the dispatcher gate gained the text opt-out (`no_consent`), and
  `ChannelSender` routes e-mail to the AA-945 sender and text to `TextSender`. A transient provider error raises, so
  the dispatch job's attempts are the retry; the G4b send marker (`dispatch_attempt`) keeps a crash from sending
  twice. New kinds: `crm_messaging_templates` (per connect / Refresh) and `crm_messaging_health` (daily due-now hook).
- **The window is checked twice**: the API answers 409 `template_required` (card R), the sender re-checks at send
  time (`window_closed`) because the window may close during the Undo delay or a retry.
- **Status callbacks are monotonic** by `status_rank` (queued < sending < sent < delivered < read; undelivered /
  failed rank as terminal) so a late `delivered` never overwrites `read` (card E).
- **Opt-out**: STOP / START words and Twilio's `OptOutType` on inbound, error 21610 on a status callback; it applies
  to every conversation of that client on that channel. The dispatcher drops a queued text message `no_consent` while
  any of them is opted out.
- **Events seam for AA-959 / AA-960**: `app.messaging.events.emit` writes `message.received` (bell for the trip owner)
  / `message.sent` as `crm.metric_event` rows on the trip (ids and codes only) and calls in-process listeners
  (`subscribe`). No listener is registered by this card.
- **Dev live check at $0**: `api/scripts/messaging_hook_probe.py` signs a Twilio-shaped inbound message or status
  callback with the sandbox token (read from `PROBE_AUTH_TOKEN`, never argv).

## Changed

- `app/mail/conversations.py`: a thread answer carries `channel`; text threads add `delivery` per message,
  `window_until` and `opted_out_at`. `POST /messages` (mail) refuses an SMS / WhatsApp conversation (422
  `channel_mismatch`): text goes through `POST /messaging/messages`.
- `app/mail/senders.py`: three sender rows (`client_text_message`, `messaging_test` via `agency_twilio`, and the
  `messaging_disconnected` owners' alert via AA SES).
- `app/onboarding.py`: the `sms_whatsapp` connection links to `/settings/channels`; the help text (`/help#sms`) now
  describes the setup instead of "arrives in a later release".
- `app/proposals/events.py`: two event names (`message.received`, `message.sent`).
- Web: Settings > SMS and WhatsApp (`/settings/channels`), the trip's WhatsApp / SMS panel, the channel in Unmatched,
  six BFF routes.

## Tradeoffs

- **Media are not downloaded** (`attachment_notes` `media_not_kept`): fetching Twilio media needs the agency's
  credentials and a malware / size policy; the client is asked to e-mail documents. A later card can add it.
- **No AA-hosted number pool, no Tech Provider onboarding** (errata §1): the agency registers its own WhatsApp sender in
  Twilio. More setup for the agency, zero cost and no vendor contract for AA.
- **Templates are read, not authored**: approval is Meta's process inside the agency's Twilio console; the CRM syncs
  the list (daily and on Refresh) and sends only `approved` ones.
- **The sandbox provider is code, not a Twilio test account**: Twilio test credentials do not cover WhatsApp or the
  Content API; a stub keeps Dev deterministic and free. Stg / prod never offer it.

## Should know

- Migration crm-036 is **expand** (three tables, two nullable columns, no change to an existing object): one PR with
  the code; the Migration Sync bot copies it to Infra and Migration Apply applies it; the Partner deploy's schema gate
  waits for it. The root PR with the three DM-7.1 retention rows must merge **before** the Infra copy PR (its
  "Retention rows" check fails without them).
- Erasure needs no `crm.erase_subject` change: every new table cascades from a row the erase already deletes
  (`test_crm010_schema` lists them as cascade-erased).
- PII tags: `messaging_connection.sms_sender` / `whatsapp_sender` `pii:contact`, `message_delivery.variables_enc`
  `pii:free_text`; numbers and texts are sealed under the mail DEK and never logged.
- Coverage: every `app/messaging` module 98-100 %; Partner unit TOTAL 91.20 %.
- Web: kit `Button` takes `testId`, not `data-testid` (its DOM props overwrite `data-testid`); and a change handler
  must read `e.currentTarget.value` before calling a state updater (React clears `currentTarget` after the handler).
