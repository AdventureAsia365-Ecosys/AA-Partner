# AA-993 M4b — Deploy Dev `schema-gate` + CI "Migration preflight" (29/10/2026, S257)

Root ADR 0017 decisions 1 and 7; design `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §D2.1, §D2.7,
§M4b; critic points 2, 4, 7, 17, 23. The same two scripts (`.github/scripts/schema_gate.py`,
`.github/scripts/migration_preflight.py`) and the same two tests ship byte-identical in AA-CIS-App, AA-Booking and
AA-Partner; only the workflow wiring differs.

## Decisions

- **Gate order: `schema-gate` → job guard → rollout.** The design says "between preflight and deploy"; the gate runs
  first so the job guard's answer is fresh when the rollout starts (the gate can wait 20 min). CIS builds the image in
  parallel with the gate.
- **What the commit needs** = the readiness keys (`REQUIRED_SCHEMA_VERSIONS`; CIS: baseline + 1 … `REQUIRED_CIS_SCHEMA`)
  **plus every migration file of the commit at or below the newest of them** (strict prefix, critic 2). Read from the
  deployed commit's own tree with `ast`, no import of app code.
- **What Dev has** = `registered_keys` of `/health/ready` (M4a); fallback for a pre-M4a task = `schema_version` +
  `missing_schema_versions` (critic 23). The readiness body is read whatever the HTTP status (a 503 carries it).
- **Infra run rule (critic 4):** the gate reads AA-CIS-Infra's public Actions API (`migration-apply.yml`, main, last 30
  runs). A run whose "Apply on Dev" job is queued/running/finished-not-skipped and that is not complete yet is waited
  for; then the newest completed run whose apply job ran must be `success` (probe included). Runs whose apply job was
  skipped (list only: `DB_AUTO_APPLY` off) do not count, so with auto-apply off the gate is exactly "keys registered".
  A 403/404 (Infra private again) skips the run check with a notice: auto-apply is then off too (ADR 0017 d8).
- **Bounded, fail closed:** 20 min (ADR), 30 s interval; a readiness that never answers JSON fails after 5 min
  ("scaled to 0 or down?") instead of burning 20 min. No override input: a stuck gate is fixed by applying the key or
  re-running the red Migration Apply jobs, then re-running Deploy Dev.
- **Preflight uses the pinned Infra tools** (`INFRA_TOOLS_SHA`, Infra main after M3): `run_migration.py --inspect`
  (directives, expand static lint, X1 role lint), `check_migration_ownership.py`, and `expand_check.py --classify` on a
  pgvector PG15 replay (same image digest as the Infra classify). Replay order = the latest Infra DB Schema Dump
  artifact when readable, else number order with `--files` (as the Infra Copy Guard does on a PR).
- **Out-of-order escape:** the ADR refuses any number other than main max + 1; a deliberate reserved number (CIS did
  this for 297) passes with PR label `migration:out-of-order` and is reported as "never auto-applied". In a merge
  group the label is read from the PR number in the queue ref.
- **Copied = immutable** is checked against Infra main's `db/migrations/<owner>/`; a file on main but not copied yet is
  a note (the sync bot copies within 10 min); an unreadable Infra list counts every main file as copied (fail closed).

## Changed (vs. the design)

- Not done here: the CIS "strict per-file apply" in `tests/integration/conftest.py` (design M4b CIS item). Turning the
  swallowed per-file `Warning` into a failure cannot be checked locally (needs the full replay DB) and could turn CIS
  Integration Tests red on legacy files; left as a follow-up. The preflight's classify replay already applies every new
  file for real.
- No separate "readiness-bump test": the preflight notes a new key that readiness does not require ("Deploy Dev does
  not wait for it") instead of failing, because some keys are deliberately not required (bk-025, bk-029, bk-031).
- TripPlanner: not in this slice (design Q14: optional M4-TP).

## Tradeoffs

- One Infra-side red run blocks every app's deploy until it is green. Accepted: a red probe is an isolation problem,
  and a red apply leaves the strict prefix uncertain. The message names the run and the recovery.
- Classify in app CI costs ~1–2 min only on PRs that add a migration; every other PR exits in seconds.
- The preflight is non-required until the ruleset/branch protection adds it (orchestrator step), so it cannot block a
  merge on its first runs.

## Should know

- Booking's Deploy Dev never ran on a migration-only push (`migrations/` is outside `backend/**`); CIS and Partner now
  exclude `api/migrations/**` too (ADR 0017 d7).
- `test_post_deploy_verify.py` `DEPLOY_JOBS` now lists `schema-gate`; the `result` job counts 5 needs.
- Bump `INFRA_TOOLS_SHA` in the three CI files when the Infra runner or classifier changes.
