# AA-993 M4b — Deploy Dev `schema-gate` + CI "Migration preflight" (29/10/2026, S257)

Root ADR 0017 decisions 1 and 7; design `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §D2.1, §D2.7,
§M4b; critic points 2, 4, 7, 17, 23. The same two scripts (`.github/scripts/schema_gate.py`,
`.github/scripts/migration_preflight.py`) and the same two tests ship byte-identical in AA-CIS-App, AA-Booking and
AA-Partner; only the workflow wiring differs.

## Decisions

- **Gate order: `schema-gate` → job guard → rollout.** The design says "between preflight and deploy"; the gate runs
  first so the job guard's answer is fresh when the rollout starts (the gate can wait 20 min). CIS builds the image in
  parallel with the gate.
- **What the commit needs** = the readiness keys (`REQUIRED_SCHEMA_VERSIONS`; CIS: baseline + 1 … `REQUIRED_CIS_SCHEMA`)
  **plus every migration file of the commit at or below the newest of them** (strict prefix, critic 2). Read from the
  deployed commit's own tree with `ast`, no import of app code.
- **What Dev has** = `registered_keys` of `/health/ready` (M4a); fallback for a pre-M4a task = `schema_version` +
  `missing_schema_versions` (critic 23). The readiness body is read whatever the HTTP status (a 503 carries it).
- **Infra run rule (critic 4; reworked after the S257 review):** the gate reads AA-CIS-Infra's Actions API
  (`migration-apply.yml`, main) and judges a run on its **"Apply on Dev" and "Isolation probe" jobs only**: a flaky
  dump dispatch or copy-PR summary job neither blocks nor delays deploys. (1) Any run in flight (`in_progress`,
  `queued`, `pending`, `waiting`) whose apply or probe is not finished, or any re-run in flight (`run_attempt > 1`), is
  waited for; a fresh run still in its plan job is not. (2) A red apply/probe can only hide in a run concluded
  `failure` / `cancelled` / `timed_out`, so the gate lists those (last 45 days, one page of 100 each) and reads jobs
  newest first until the newest one that applied files: green there = nothing red after it; red = blocking unless a
  newer `success` run applied files with apply and probe green. Success runs are never read otherwise, so with
  auto-apply off (every run list only) a check costs 7 list calls and the jobs of a few red-concluded runs.
- **Never a silent pass:** only a 404 of the repo itself (anonymous: private again) skips the run check (auto-apply is
  then off, ADR 0017 d8). A 404 of the workflow in a readable repo, a 403/429 (rate or abuse limit), any other error,
  a full page without a decision, or more than 80 jobs reads in one check = "cannot decide": not ok, checked again
  every `--infra-interval` (120 s) until the timeout. Completed runs' jobs are cached for the whole gate. The token
  (GITHUB_TOKEN, 1000 req/h per repo) is tried first; a 401/403/404/429 retries anonymously (60 req/h per IP).
- **Bounded, fail closed:** `SCHEMA_GATE_TIMEOUT_S` (repo variable; default 2400 s, clamped to 2580 s because the job
  has `timeout-minutes: 45`), 30 s interval. The original 20 min (ADR d7) is shorter than the design's 19 min copy-PR
  baseline plus the plan, apply and probe; root ADR 0017 d7 is updated in the M5 root branch. The pass line logs
  "keys registered after N s, gate passed after M s" (design §3 metric 3); a readiness that never answers JSON fails
  after 5 min ("scaled to 0 or down?") instead of burning the window. No override input: a stuck gate is fixed by applying the key or
  re-running the red Migration Apply jobs, then re-running Deploy Dev.
- **Preflight uses the pinned Infra tools** (`INFRA_TOOLS_SHA`, Infra main after M3): `run_migration.py --inspect`
  (directives, expand static lint, X1 role lint), `check_migration_ownership.py`, and `expand_check.py --classify` on a
  pgvector PG15 replay (same image digest as the Infra classify). Replay order = the latest Infra DB Schema Dump
  artifact when readable, else number order with `--files` (as the Infra Copy Guard does on a PR).
- **Out-of-order escape:** the ADR refuses any number other than main max + 1; a deliberate reserved number (CIS did
  this for 297) passes with PR label `migration:out-of-order` and is reported as "never auto-applied". The label is
  read live with `gh pr view` (PR number from the event, or from the queue ref in a merge group), so adding it and
  "Re-run jobs" is enough; the `pull_request` types are not widened (a label change would re-run every CI job).
- **Preflight vs Dev (S257 review):** with `--ready-url` (public `/health/ready`) a lower file of the same owner that
  Dev has not registered and that has no expand header is a warning, and the verdict says the added file waits behind
  it (the strict-prefix apply stops there); unregistered lower expand files are a note. A warning, not a refusal: the
  live state changes when a person applies, and the merge queue re-runs the check. An expand file without classify
  evidence (replay error, no artifact) is reported "expected expand (unverified)".
- **Copied = immutable** is checked against Infra main's `db/migrations/<owner>/`; a file on main but not copied yet is
  a note (the sync bot copies within 10 min); an unreadable Infra list counts every main file as copied (fail closed).

## Changed (vs. the design)

- Not done here: the CIS "strict per-file apply" in `tests/integration/conftest.py` (design M4b CIS item). Turning the
  swallowed per-file `Warning` into a failure cannot be checked locally (needs the full replay DB) and could turn CIS
  Integration Tests red on legacy files; left as a follow-up. The preflight's classify replay already applies every new
  file for real.
- No separate "readiness-bump test": the preflight notes a new key that readiness does not require ("Deploy Dev does
  not wait for it") instead of failing, because some keys are deliberately not required (bk-025, bk-029, bk-031).
- TripPlanner: not in this slice (design Q14: optional M4-TP).

## Tradeoffs

- One Infra-side red run blocks every app's deploy until it is green. Accepted: a red probe is an isolation problem,
  and a red apply leaves the strict prefix uncertain. The message names the run and the recovery.
- Classify in app CI costs ~1–2 min only on PRs that add a migration; every other PR exits in seconds.
- The preflight is non-required until the ruleset/branch protection adds it (orchestrator step), so it cannot block a
  merge on its first runs.

## Should know

- Booking's Deploy Dev never ran on a migration-only push (`migrations/` is outside `backend/**`); CIS and Partner now
  exclude `api/migrations/**` too (ADR 0017 d7).
- `test_post_deploy_verify.py` `DEPLOY_JOBS` now lists `schema-gate`; the `result` job counts 5 needs.
- Bump `INFRA_TOOLS_SHA` in the three CI files when the Infra runner or classifier changes.
- Infra job names are part of the contract: `Apply on Dev*` and `Isolation probe*` (the probe is a reusable
  workflow, listed as "Isolation probe (blocking) / Isolation probe"). Renaming them in migration-apply.yml needs the
  three `schema_gate.py` copies changed in the same breath.
- Recovery when the gate is red on an Infra run: fix the cause, then "Re-run failed jobs" on that Migration Apply run
  (or let a newer run apply files green), then re-run Deploy Dev. With auto-apply off, a person applies with DB Migrate
  within the gate window, or re-runs Deploy Dev after the apply.
