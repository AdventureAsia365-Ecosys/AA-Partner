## Decisions

- **Two PRs (MIG-4).** crm-035 is a contract file (widened CHECKs on `crm.aa_request.kind` and
  `crm.booking_line_money.kind`, rows in `crm.status_transition`, new columns on existing tables, new grants), so the
  migration ships alone first (with its own integration test), then the Infra copy, a manual DB Migrate apply, the
  schema-dump PR, then the code PR that raises `REQUIRED_SCHEMA_VERSIONS` to crm-035.
- **`crm.commission`: one live row per confirmed agency line with an expected commission.** The expected amount is
  NOT copied: it is the head of the line's `commission_expected` money chain (already frozen at the confirmation
  day's rate, R17 "booking_date"), so an owner correcting the expected commission never leaves two numbers. The row
  holds the follow-up: status `expected -> claimed -> received`, or `written_off` / `cancelled`; due date; the claim
  (time + the agency's own reference, e.g. its invoice number to the supplier); the receipt.
- **Who creates rows: `crm.commission_sync(trip)`** (SECURITY DEFINER, crm_owner), called after every line confirm,
  money change and line cancel, by the trip cancel, and by the hourly date rule for every live trip with agency lines
  (catch-all). Definer because the assistant may confirm a line (R18) but cannot read the money (RESTRICTIVE policy):
  the function reads the money as crm_owner and returns counts only. It also mirrors each row into
  `crm.trip_commitment` (kind `commission`; `written_off` maps to `cancelled`, the crm-010 CHECK has no written_off),
  which the delete block already reads (claimed / received block a trip delete, §3.5).
- **Sync rules**: an expected row whose line is cancelled (or trashed) becomes `cancelled` (`line_cancelled`) unless
  the agency kept it at the trip cancel ("supplier still pays", `keep_on_cancel`); an expected row whose line's
  expected commission is now 0 or gone becomes `cancelled` (`no_commission`), and a later positive amount creates a
  new row (the live unique index excludes cancelled rows); no new row on a lost / cancelled trip or one with a pending
  cancellation. Claimed rows are never cancelled by the sync (the agency already invoiced the supplier: it writes
  them off or records the money).
- **Due date** = the line's last service day (`service_to`, else `service_from`, else the trip's end / start date,
  else the confirmation day) + the supplier's `commission_due_days` (new nullable column on `crm.agency_supplier`,
  Suppliers form), default 30 days. The agency may change it per row. "Overdue" is derived (expected / claimed and
  due before today in the agency timezone), never stored, so no job has to flip a status; the hourly date rule opens
  one owner task `commission_overdue` per trip once (`overdue_alerted_at`), agent first (U8: the CRM never writes to
  the supplier).
- **Receipt (R17 E)**: `crm.commission_receive(id, amount, currency, received_on, reference)` (SECURITY DEFINER)
  freezes the receipt at the rate of the receipt day (`fx_basis receipt_date`, override -> platform -> latest earlier
  day within 30 days, `stale_days`; 409 `fx_rate_missing` without any), so a receipt in another currency uses the
  receipt-date rate. "Short" is judged in the original currency only: `short_amount` is set only when the receipt is
  in the expected currency and below it; `fx_difference_base` = expected base - received base only when the
  original-currency amounts match (an FX move never reads as underpaid). One receipt per row (a supplier paying in
  parts is recorded as the total when it is complete; a remaining gap is written off).
- **Margin protection**: `commission.*` is a margin field (§4.6). The table has a RESTRICTIVE SELECT policy to
  `crm_app` (owner / agent, or a job / seed actor), the routes use `VIEW_MARGIN` (reads) and
  `PAYMENT_MARK_RECEIVED` (claim, receive, write off, due date) so the assistant gets 403, and every response key
  starts `commission_` / carries the word commission so the serializer strips it on any other route.
- **Cancel = one row in `crm.trip_cancellation`, pending until Booking answers.** A trip with AA bookings
  (`bk_booking_id`, not cancelled) cannot be `cancelled` until Booking has cancelled them (card R: "never cancelled
  early"). The run applies every local effect at once (the agency's decision stands: clients must not keep paying
  into a cancelled trip), queues one `cancel` request per Booking booking in `crm.aa_request` (the outage queue: a
  down Booking is retried with backoff), and leaves the stage. The trip shows "Cancellation pending"; moves, the date
  rule and the overdue invoice reminders skip it. The Booking sync applies each answer (lines cancelled, the fee
  written, commitments `cancelled`) and, once no cancel request of the trip is pending, moves the trip to `cancelled`
  (history `cancel_<reason>`, actor `job:crm_booking_sync`) and marks the cancellation `done`. A trip without AA
  bookings is cancelled at once (row `done`). Pressing Cancel again on a pending trip re-queues any cancel Booking
  refused for a transient reason ("Retry now").
- **Booking refusals of a cancel** (review fix pass): only `not_found` counts as done with no fee. `invalid` is
  ambiguous: Booking sends it for a booking already cancelled at AA, but also for one still live and not cancellable
  by the agency (case `in_progress`), and for a request it could not read. `booking.b2b.v1` has no booking read
  (`GET /holds/{id}` keeps saying `confirmed`), so the CRM reads "the feed's last status": `invalid` counts as done
  only when no open AA line of that booking is left (the feed's `booking.cancelled` closed them); otherwise it is a
  refusal like `forbidden` / `unknown_partner`: request failed, cancellation pending, one urgent owner task
  `aa_cancel_failed`; the dialog's Cancel again re-queues it. When the feed's `booking.cancelled` later completes the
  cancellation, `finish_if_done` closes that task (`done`).
- **A cancel that runs out of attempts** (96 tries, about 24 h of no answer; Booking also answers 503 for permanent
  conditions such as "no cancellation policy in force"): `gave_up` also opens `aa_cancel_failed` (before the fix it
  only failed the request, leaving the trip pending with no task).
- **A pending cancellation closes the trip for new AA requests**: the sync drops a queued quote / requote / hold /
  refresh (`trip_closed`) when the trip has a `crm.trip_cancellation` row, not only when its stage is Lost /
  cancelled (`app.booking.sync.trip_closing`), and a hold that lands for such a trip is released at once. Before the
  fix a hold postponed by `close_trip` could still place a new AA hold after the Undo window, since a pending cancel
  keeps the trip's old stage.
- **The fee becomes a cost line (card E)**: a new money kind `cancellation_cost` on the cancelled AA line (one per
  Booking booking, on the request's line), written by `crm.booking_line_aa_cancel_fee` (job only) at the line's quote
  FX lock when the fee is in the quote currency (it always is per the contract), else the fee day's platform rate.
  The line stays `cancelled` (out of margins), the ledger totals add `cancellation_cost_base`, and the Bookings tab
  shows "Cancellation fee". Kept on the line instead of a new AA line: every "confirmed AA line" query (ops release,
  prep packs, reports) would otherwise see a fee line as a booked tour.
- **Dry run with Booking's fee**: the dry run calls `POST /bookings/{id}/cancel?dry_run=true` per AA booking outside
  any transaction (the request body never names a person) and lists each fee; Booking down -> the fee is "unknown"
  and the effect says the cancellation will stay pending until AA answers.
- **Invoices**: drafts and issued invoices that hold no money are voided (reason "Trip cancelled"). An invoice the
  client says they paid (`payment_claimed`) is kept and its `verify_transfer` task stays open (record the money, then
  refund; or "Not received", then void). Invoices holding money are kept: their payments get refund requests.
- **Refund requests follow the terms the client accepted** (§4.6 approval matrix unchanged): one `proposed` request
  per payment with something left to ask back, for the amount the member sets in the dialog (default: everything
  left; lower keeps the non-refundable part on the ledger, card E; 0 = no request). The reason names the accepted
  terms version (label + date of the latest booking-terms acceptance of the trip). Payments recorded without an
  invoice (the schedule's own "Mark paid") cannot take a refund request (409 `payment_without_invoice`): they are
  listed and one owner task `cancel_refund_review` is opened. Card checkout sessions: no provider has code yet (BYO
  Stripe is a paid vendor feature, out), so nothing to expire.
- **Agency suppliers: one task per trip, one checklist line per supplier.** `crm.task` has one open task per (trip,
  kind) (unique index used by every `ON CONFLICT` in the app) and no detail column, so "agency suppliers get one task
  each" (§2.7 item 2) is one task `cancel_with_suppliers` that carries a `checklist` on the trip page
  (`app.pipeline._supplier_checklist`, derived on read: one line per supplier, its confirmed lines with their
  confirmation numbers; web `supplierChecklistLine`). No schema change. The task is closed by the date rule once no
  confirmed agency line is left; a supplier line disappears from the checklist as soon as its line is cancelled. The
  dry run lists the suppliers and lines.
- **Workflows stop**: Module 10 (workflow tables) is not built yet; today every automated send is a
  `crm.dispatch_queue` row, all of which the cancel already stops. The effect `workflows_stopped` counts the
  `origin = 'workflow'` rows among them, and `app.stages.register_cancel_hook` lets the M10 card stop its runs here.

- **Review fix pass 2 (two reviewers, A1–A9)**:
  - A1: `stages._undo_one` (single and bulk Undo) calls `ensure_not_cancelling` first, as `move` / `bulk_move` do:
    an Undo inside the window can no longer move a trip whose cancellation waits for Booking.
  - A2: `GET /commissions/{id}` writes an audit `view` row (object `commission`), as the list writes `list_view`.
  - A3 (crm-035, one new commit on the migration branch, cherry-picked onto the code branch): crm_app has SELECT only
    on `crm.trip_cancellation`; the row is written by `crm.trip_cancellation_open(trip, reason, effects)` (owner /
    agent member; the database reads the stage left and counts the live AA bookings, and decides pending / done
    itself) and `crm.trip_cancellation_finish(trip)` (a job actor or owner / agent; pending -> done only when no AA
    booking of the trip is live and the trip is cancelled; returns false otherwise). Same shape as `crm.commission`
    (definer functions own the writes). No session can write a "done" cancellation while AA still holds a booking.
  - A4: the commission sweep (`SWEEP_SQL`) uses `crm.commission_sync`'s own conditions: no "missing row" pick on a
    trip with a pending cancellation (it was picked every hour for nothing); an expected row kept at the cancel whose
    commission became 0 is picked (sync cancels it).
  - A5: the AA fee's FX day is the agency-timezone day of Booking's `cancelled_at` (`fx.agency_day`), as every other
    FX basis date (`fx.agency_today`), not its UTC date.
  - A6: `GET /commissions?trip_id=` totals are the trip's own (TOTALS_SQL filtered by trip).
  - A7: decided per §2.7 item 3 ("invoices are voided"): an open / expired invoice the cancel kept because it held
    money is voided ("Trip cancelled", commitment `void`, reminder task settled) as soon as a refund executes and
    leaves nothing held and no refund request open (`app.cancellation.void_if_refunded`, called by
    `payments.execute_refund`). See "Should know" for what stays.
  - A8: documented, not changed (see "Should know").
  - A9: see "Agency suppliers" above.

## Changed

- `app.stages.cancel` now delegates to `app/cancellation.py`; its signature gained `refunds` / `keep_commission`;
  the dry run answers detail blocks besides `effects`; the effect `aa_bookings_kept` became `aa_bookings_cancelled`
  (the bookings are now cancelled through Booking, not kept). The run answers `stage` = the old stage and
  `cancellation.status = pending` while AA has not answered.
- A move (`app.stages.move`, bulk) of a trip with a pending cancellation is 409 / blocked `cancellation_pending`; the
  hourly date rule and the overdue invoice reminders skip such a trip.
- Ledger: the Bookings tab lines carry `commission` (owner / agent), the money block may carry `cancellation_cost`,
  the A-11 totals carry `cancellation_cost_base`. Suppliers carry `commission_due_days`.
- Reports: the Module 13 success metric `commission_unclaimed` (expected commissions past due, never claimed) is
  built; it is hidden from the assistant like `margin_known_share`.
- Web: A-12 `/commissions` replaces the empty section; the cancel dialog shows Booking's fee per AA booking, the
  supplier bookings, the refund per payment (editable), the commissions to keep, and on a pending trip "Ask AA
  again"; "Cancellation pending" badge on the trip and its board card.

## Tradeoffs

- Single receipt per commission vs partial receipts: simpler data, and the design's "expected vs received" is one
  figure per line; parts are summed by the agency before recording.
- Local cancel effects at request time vs at Booking's answer: chosen at request time; the only thing that waits is
  the stage (and its history line).

## Should know

- **Refund defaults (A8)**: the dialog proposes everything left on each payment and the member lowers it. Design v3
  §2.7 item 4 / lane §3.4 item 4 say the refund "follows the accepted terms version" and "needs approval": the CRM
  records the version (the reason names the label and date of the latest booking-terms acceptance) and the approval
  (§4.6) is unchanged. It cannot compute "the refund due under the terms": `crm.agreement_doc` holds the agency's terms
  as free text (`body_text`), with no machine-readable refund schedule, and the card (CRM-27 checklist / R / E) asks
  for no terms-based amount. AA's fee is what AA charges the agency, not the client: whether the agency passes it on
  is the agency's own terms, so it is shown next to the refunds (dry run) but not subtracted. A structured refund
  schedule on `agreement_doc` would be a new card (schema + terms editor), not this one.
- **Invoices that stay after a cancel (A7)**: an invoice keeping a non-refundable part (refund lowered, or rejected)
  still holds money: it stays `open` (crm-024 has no `open -> void` with money held, and no `open -> paid` short of
  the total); the overdue reminders skip a trip with a cancellation, so the client is never chased. A `paid` invoice
  has no `void` edge in crm-024: it stays `paid`, its refund entries (and the payment commitment `refunded`) show the
  money returned. A `payment_claimed` invoice is answered first (record the money, then refund; or "Not received").
- **crm-035 changed after the first review (A3)**: the migration branch now has two commits (8651d20 + the definer
  functions); the code branch carries the identical second commit (cherry-picked on top of a828da8, before the fix
  commits). After the migration PR squash-merges, rebase the code branch `--onto main` past both migration commits
  (their `api/migrations` diff equals the migration branch's).

- MIG-4 order: PR 1 = crm-035 + its tests only (`test_crm035_schema.py`, the two catalogue lists in
  `test_crm002_tenancy.py` / `test_crm010_schema.py`, CONTEXT row, these notes); PR 2 = the code (raises
  `REQUIRED_SCHEMA_VERSIONS` to crm-035). Merge PR 2 only after DB Migrate applied crm-035 on Dev.
- The design ERD page (`docs/architecture/erd/design/crm.md`, root) is `enforce=false`: the two new tables are not

- Booking already serves `POST /bookings/{id}/cancel` (+ dry run) on `booking.b2b.v1` 1.2 (AA-974), so no Booking
  change is needed.

- Paid vendor features are out (S262 rule): Stripe Checkout session expiry and Stripe refunds need the agency's own

## S262 live acceptance follow-up (lane w9a, Claude Code)

Findings: root `docs/audits/2026-10-31-S262-evidence/AA-957/` (live run of 31 Oct 2026, cancel lane B1/B2 and
commission lane A1-A4, plus the critic pass). No migration.

### Decisions

- **A cancelled trip bills no more, on the server too.** One helper, `app.cancellation.ensure_not_cancelled`: a trip
  with a `crm.trip_cancellation` row (pending or done) or at stage `cancelled` answers 409 `trip_cancelled` to a new
  invoice (from the schedule or typed), the issue of a draft invoice, "Mark paid" on a schedule row, a draft proposal
  edit, a re-issued proposal link and a portal invite (the stage check there already said `trip_closed` for a
  cancelled stage; the pending window keeps the old stage, so the helper closes it too). The pending window counts:
  the cancel applied every local effect at once ("clients must not keep paying into a cancelled trip"), so billing is
  closed from the run, not from AA's answer.
- **Not guarded on purpose**: recording a payment on an invoice the cancel kept (the client says they paid it:
  "record the money, then refund", design §2.7 / lane §3.4), "Not received", voiding an invoice or a schedule row
  (clean-up), refund requests and their decisions. A trip page's Request refund is hidden only while a refund of that
  payment is already open (the dialog proposed it).
- **The due balance rows are voided by the cancel** (§2.7 item 3 "invoices are voided": a schedule row is the
  not-yet-invoiced part of the same bill). A row a kept invoice bills (payment claimed, or money held) stays due: it
  settles through that invoice. A deposit row is never void (crm-016 CHECK) and a cancellable trip (booked or later)
  has paid it. New effect `schedule_rows_voided` in the dry run and the run, audit `payment_schedule_void` with reason
  `trip_cancelled`.
- **A-12 tells trips apart by their dates**: the commission view carries `trip_start_date`, `trip_end_date`,
  `trip_month` (not margin, no vault). The lead client's name was the other option; it would need the vault and a
  `display_name` audit on a margin page, for no more certainty than the dates.

## S262 fix pass (both reviewers approved, minors M1-M6)

### Decisions

- **M1, trips cancelled before the schedule step**: the hourly date rule (`app/stages_job.py`, step 10) calls
  `app.cancellation.void_cancelled_schedule`: every due **balance** row of a trip that is `cancelled` or has a
  `crm.trip_cancellation` row (pending or done), when no live invoice other than a draft bills it, is voided with the
  same SQL (`SCHEDULE_VOID_SQL`, now `RETURNING`) and audit as the run (`payment_schedule_void`, reason
  `trip_cancelled`); the drafts that bill it are voided too (`invoice_void`, reason `trip_cancelled`, `voided_by` the
  job actor), as the run voids drafts. A row an issued / claimed / paid invoice bills stays: it settles through that
  invoice (the run's rule). Idempotent: a void row is never picked again; at most 500 rows per agency per hour.
  Chosen over a one-off data fix: Dev's two trips (and any other agency's) heal on the next hourly run, with the
  audit trail of a normal void. Reports: `app.reports.queries.SCHEDULE_DUE_SQL` counts `status = 'due'` only, and
  A-10 receivables list invoices only, so a void row is no receivable (integration test asserts the report count
  drops from 1 to 0).
- **M2**: `cancelTrip.bookingFailed` is "Not cancelled yet. {reason}" (VI "Chưa huỷ được. {reason}"), the reason being
  one sentence: AA's refusal reads its `aa.result.*` sentence (unknown code: "AA refused this request. Ask AA.", said
  once); a request AA never answered is not called a refusal: `gave_up` reads `aa.result.gave_up`, and the retry
  classes the sync writes on `crm.aa_request.result_code` (`booking_*` such as `booking_timeout` /
  `booking_unavailable`, `token_*`) read `cancelTrip.aaNoAnswer` ("AA could not be reached. Ask AA again."),
  `lib/aa.ts` `aaNoAnswer` / `aaCancelFailedKey`.
- **M4**: `rateText` and `percentText` take the page locale and format with `Intl.NumberFormat` (4 and up to 2
  decimals), as `formatAmount` beside them (vi-VN "1 EUR = 1,0870 USD", "12,5 %").
- **M5**: the kit DataTable's card mode is a phone media query in kit core (not editable here, ADR 0016), so the table
  got narrower instead: five columns (Supplier and booking, Trip, Commission = expected + received, Status = badge +
  due date, Follow-up), the trip title and dates wrap at word breaks, `tableMinWidth` 590
  (`COMMISSIONS_TABLE_MIN_WIDTH`, at most the content width of a 900 px window beside the 240 px sidebar). Measured in
  Chromium on the rendered table inside the shell CSS: table 610 / 734 / 990 px at 900 / 1024 / 1280 px windows and
  766 px at 800 px (drawer sidebar), no horizontal scroll, every Follow-up cell inside the page (EN and VI).
- **M6**: the dialog frame's layout moved to `app/globals.css` (`[data-crm-dialog]`): `max-height: 90vh` first, then
  `min(90vh, calc(100dvh - 32px))`; under 480 px of height the whole box scrolls as one area (the body stops being
  its own scroll area, the footer is compact) and the "More below" cue also follows the box, so it says the confirm
  step is further down. Measured in Chromium: 844 x 390 and 667 x 375 the box scrolls (351 / 337 px max), 390 x 844
  and 1440 x 900 the body scrolls with the footer in view.
