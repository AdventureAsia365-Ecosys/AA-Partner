## Decisions

- **The BYO errata wins over the card text.** The Linear checklist still says "`allow_platform_sender` opt-in,
  owner-only, logged" and "send-as Gmail + Outlook". Errata S247 §1 removes `allow_platform_sender` (no
  `tenant_settings` column is added, and none exists), sender kinds are `agency_mailbox | system` only (CHECK
  `message_sender_kind_chk`), and send-as is **Gmail + Microsoft 365 + SMTP** (send only, no IMAP).
- **Key crm-015, Guard 0 needs crm-014.** `crm.erase_held` and `crm.erase_subject` are the crm-014 text plus the mail
  steps (a scripted, exact-match patch of the crm-014 text, so nothing of crm-012/013/014 is dropped); Guard 1 checks
  that every table an earlier key taught `erase_subject` is still named. SQLSTATEs **CRM28–CRM30** are this file's:
  CRM28 `message_not_deletable`, CRM29 `message_sealed`, CRM30 `mailbox_credential_mismatch`. The next key starts at
  CRM31.
- **Credentials per member.** Design §4.6 gives every role `OWN_MAILBOX_CONNECT`, but crm-003 had
  `UNIQUE (tenant_id, provider)`. crm-015 adds `integration_credential.member_id` (NULL = agency-level) and replaces the
  key with `UNIQUE NULLS NOT DISTINCT (tenant_id, provider, member_id)`: the agency still has at most one agency-level
  credential per provider (the crm-003 test that a second `stripe_key` is refused still holds).
- **One sending mailbox per member** (`channel_account_member_uq`, NULLS NOT DISTINCT: one agency-level one too). A
  reconnect updates the row (kind may change, e.g. Gmail -> SMTP). The DB checks the credential is the same member's
  and of the right provider (CRM30), and a `connected` mailbox has a credential. Disconnect = status `disconnected`
  first, then the credential row is deleted (`credential_id` ON DELETE SET NULL); the mailbox row stays as history.
- **`dispatch_queue.message_id`, not an FK on `message_ref`.** The plan asked for `dispatch_queue.message_ref ->
  crm.message`. AA-943 (crm-012, `app/intake/stage2.py`) already writes the Stage 2 `client_link` id into
  `message_ref`, so that FK would fail VALIDATE on Dev and every later Stage 2 send. crm-015 adds a separate
  `message_id` (same-agency key, ON DELETE SET NULL, NOT VALID + VALIDATE) and keeps `message_ref` as the generic
  reference. Gate codes added: `held_reconnect` (card R), `send_failed`, `no_message` (a row with nothing to send, e.g.
  rows queued before CRM-17).
- **Unmatched = both `traveler_id` and `trip_id` NULL.** A mail matched by the trip token from an unknown sender (a
  spouse) is on the trip, not Unmatched.
- **Drafts are rows** (`draft_autosaved`); crm_app may hard-delete a draft only (CRM28). Anything that is not a draft
  keeps its content (CRM29); Undo / "edit a held message" moves it back to `draft_autosaved` first.
- **`trip.mail_token`**: 12 hex characters from `gen_random_uuid()` (48 random bits, built in, no pgcrypto), a column
  default, so every existing and new trip has one; unique per agency. It is a reference, not a secret (the client sees
  it in the subject).
- **Erasure.** Trip and traveller scopes delete the messages of their conversations, then the conversations; a new
  scope `conversation` (the trash purge of an Unmatched thread); the agency erase deletes every mail table. Hold rule:
  `erase_held` reaches the travellers / trips a conversation names; `guard_held_change('trip_id', 'traveler_id')` on
  `conversation`; `crm.guard_message` checks a message through its conversation (no denormalised trip / traveller on
  `message`, so linking an Unmatched thread later does not need to rewrite its messages).
- **Attachments** are `crm.document` rows (docs DEK) with `uploaded_by_kind = 'mail'` (CHECK widened). `crm.document`
  needs a trip or traveller, so an Unmatched mail's attachments are not kept (`attachment_notes` code `no_subject`),
  nor oversized / unsupported ones (`too_large`, `type_not_allowed`); the UI shows the note.

## Changed (vs. the plan)

- File `015_crm_mail.sql` (plan said `012_crm_mail.sql`; schedule §1).
- `dispatch_queue.message_id` instead of an FK on `message_ref` (above).
- `crm.message` gained `body_html_enc`, `to_enc`, `rfc_message_id_enc` (the Message-ID itself under the mail DEK, so a reply sets `In-Reply-To` / `References` and the client's mail app threads it), `match_method`, `failure_code`, `occurred_at`, `sent_at`,
  `author_member_id`, `attachment_notes`, `channel` (the plan's "external_id UNIQUE per channel" needs it on the row).
- `crm.ingest_address.forwarding_code_at` (when the Gmail code arrived, for the UI).
- No NOLOGIN reader grant on any new table (plan: "support sees health only").

## Tradeoffs

- `message_external_id_uq` is per agency + channel, not per mailbox: provider ids are globally unique in practice
  (Gmail / Graph ids), and a per-mailbox key would break when a mailbox row is reconnected with another kind.
- The ingest-address lookup policy is SELECT only, like `intake_form_public_lookup`: the job writes the forwarding
  code only after `ingest_tx` has set `app.tenant_id`.
