# AA-969 — CRM-37a security review, SLOs, bounded load test (AA-Partner part)

The review itself (findings, severity, what was checked) is in the root repo:
`AA-Ecosys/docs/audits/2026-11-04-S268-crm-security-review/README.md`. This note covers the code.

## Decisions

- **F1 body ceiling as an ASGI middleware** (`app/bodylimit.py`), not per route: FastAPI reads and parses a JSON
  body before the route's dependencies (the class guard included), so only something in front of the router can
  refuse a large body from an anonymous caller. 1 MiB default; the four upload routes get their own cap + 64 KiB, so
  their existing codes (`import_too_large`, `body_too_large`) still answer a body just over their cap. A declared
  length is refused at once; a chunked body is counted while read and the read that passes the ceiling raises
  `HTTPException(413)`, which FastAPI re-raises as is.
- **F2 agency slots inside `tenant_tx()`** (`app/tenant_gate.py`), before `pool.acquire()`: the only place every agency
  request passes and the only moment that protects the pool. Keyed by the agency only after this caller's membership
  of it was verified in this task (a 5-minute in-memory mark), otherwise by the caller: a member of A who names B's
  id never takes B's slots. The mark grants nothing (the membership is checked on every request).
- **Bounded pool wait**: 10 s, then 503 `db_busy` with `Retry-After` (new `DatabaseBusy`, a `RateLimited` with 503).
- **Member ceiling** in the agency class guard, keyed `iss|sub|X-AA-Tenant-Id`: per member per agency, so the one
  load-test identity used for 50 agencies is not throttled as one, and a header naming another agency only spends the
  caller's own count.
- **Fair `crm.job` claim**: turn = rank inside the agency + the agency's jobs running or finished in the last 300 s;
  lowest turn first, then oldest. A plain round robin over the queued rows was tried first and does not work: after
  each claim the noisy agency's next row is again rank 1 and older than everyone else's (the integration test caught
  it). Rows without `tenant_id` are their own group. Fix pass (review finding): the first version ranked only the 500
  oldest due rows, so a noisy backlog over 500 rows filled the window and the calm agency waited behind it again. Now
  every due row is ranked inside its agency and each agency's 3 oldest rows are candidates (3, not 1, so a head row
  held by another worker under SKIP LOCKED does not leave the agency without a candidate). No new index: the partial
  `job_queued_due_idx` already selects the due rows, so the fix needs no migration.
- **F4 log redaction** in `request_completed`: path segments of 32+ URL-safe characters that are not a UUID become
  `[token]` (signed client links, calendar feed tokens, webhook ids). Sentry already scrubbed full URLs.
- **Load test**: k6 (no load tool in the repos yet), driven by a stdlib Python runner that the orchestrator runs; one
  load-test identity (`e2e-test-crm-lt-agent`, AA-CIS-Infra) that is an agent of `lt-01`..`lt-50` only, created by the
  seeder's new `--load-test N --load-test-sub SUB`. Read-only routes only.
- **Guards read the in-app samplers' log lines** (`ops_metrics_sampled` of CIS, Booking, CRM): the CloudWatch job
  alarms were removed in the S263 alert diet, so these lines are the job-lag signal. Only job and database checks
  stop the run; other findings (LLM stage coverage, spend) can be raised for days on Dev. The exact idle check stays
  the Infra idle gate run before (`terraform-apply.yml idle_gate_check=true`).
- Fix pass (review findings): the guards fail closed for real. A sampler line that lacks a required field
  (CIS `queued_due` / `running` / `oldest_queued_age_seconds`; Booking and CRM their k=v job fields and `checks`) or
  carries CIS `jobs_error` / `ops_checks_error` is a failure, not "idle" (a missing field used to read as 0). `aws`
  runs with stdin closed (an expired MFA session fails at once instead of waiting for a code), and a timeout or a
  missing CLI is a `Refused`; `--extra-guard` the same. `run_load` stops k6 in a `finally` and turns any runner
  error into an abort (exit 3), so k6 never outlives the runner.

- **Review round 2** (five findings, all real; one part declined, see Tradeoffs):
  - F1 (blocking): the per-request ceiling did not bound concurrent large bodies and did not depend on auth. Added a
    process-wide budget of body bytes in flight (`BodyBudget`, 32 MiB; a body is charged once it passes 64 KiB, chunk
    by chunk as bytes arrive, so a declared length reserves nothing; given back when the response is done; overflow
    is `503 server_busy` + `Retry-After: 2`). `POST /crm/v1/documents` now reads its JSON after the class guard
    (`_document_body`: same JSON, same 422 shape, OpenAPI request body kept via `openapi_extra`), so an anonymous
    caller never reaches the 9.4 MiB ceiling. Not done: uvicorn `--limit-concurrency` (it answers 503 to the ECS and
    ALB health checks too when full, which turns a connection flood into a task replacement; the byte budget bounds
    the memory directly).
  - F2 member ceiling: key = canonical `str(uuid.UUID(header))`, else one `none` bucket (any spelling of one agency
    shares one count; junk values never open fresh counts, so they cannot LRU-evict other members either).
  - F2 pool share: the gate is now a fair scheduler. A total of 2 request slots per task (pool 3 - 1 for the crm.job
    worker and the staff paths); per-key cap stays `CRM_TENANT_MAX_CONCURRENCY` (now 1..2); a freed slot goes to the
    waiting key with the fewest held slots, then the key served least recently, FIFO inside a key. Two busy agencies
    therefore get one slot each and a calm agency waits for at most one in-flight transaction. Every request-path
    acquire outside `tenant_tx()` goes through `tenancy._gated()` (gate + bounded acquire): `caller_memberships` by
    caller, `intake_tx`, `invitation_tx`, `studio_invitation_tx`, `client_link_tx`, `calendar_feed_tx`,
    `messaging_hook_tx` under one public key (503 `db_busy`). A nested gated block of the same task does not take a
    second slot (task-scoped ContextVar; a task started inside the block takes its own). Integration test with two
    noisy agencies added; the load test runs two noisy agencies by default (`--noisy-agencies`, 1..2). The slo.md
    sentence about "the third connection always reachable by another agency" was wrong and is rewritten.
  - F4 Twilio hook flood: refused signatures (403) count per hook id (`HOOK_REFUSALS_PER_MINUTE` 60), and a hook over
    it is 429 before the database; the webhook transaction takes a public-key slot. While a hook is over its ceiling,
    its own genuine callbacks are 429 too for the rest of the minute: only the agency whose hook id the flooder knows
    is affected, never the others (the trade the reviewer's "per-hook limiter" implies). Not counted per address (the
    reviewer's first suggestion): Twilio posts every agency's callbacks from shared addresses, so an agency with a
    drifted Auth Token (or a hostile one) would otherwise use up those addresses for every agency. Not done: checking
    the signature before the transaction with a cached token (it would keep decrypted Twilio Auth Tokens in process
    memory; the gate + per-hook ceiling already bound the cost).
  - F5 Sentry: `request.url` and breadcrumb `url` / `http.url` go through `redact_url` (query and fragment dropped,
    `redact_path` on the path, then the PII scrub); a raw-path `transaction` name too. Real-SDK test: a 500 on a path
    with a 43-character token sends no token.

- **Review round 3** (seven findings: six real and fixed, one part declined, see Tradeoffs):
  - Gate, one key holding both slots across slow work (major, real): reproduced (two holds of one key into an idle
    gate got 2 slots). A key's ordinary holds are now capped at total - 1 (`short_cap`, 1 by default), so one key
    never takes the last free slot even when idle. Work known to hold its slot across a slow external call asks for
    a **long** slot (`tenant_tx(..., long=True)`: `POST /trips/{id}/ai/draft`, `POST /documents`,
    `POST /documents/{id}/download`): at most total - 1 long slots process-wide, fair hand-out, wait 4 x `wait_s`.
    A long hold does not count against its key's short cap, so an agency running an AI draft keeps the other slot for
    its ordinary requests, and another agency then waits for at most one short transaction. Waiters queue per
    (key, long) so a waiting long request never blocks its key's short ones.
  - Body budget (blocking + major, real): reproduced against the round-2 middleware (33 anonymous 1 MiB trickles held
    31 MiB; the agency's 9 MiB upload got 503). Now: on the class routes a body is read past 64 KiB only once the
    bearer token verifies (`app.state.verifier`, then 401 `missing_bearer_token` / `invalid_token`, 503
    `auth_unavailable`); the budget is split (verified 32 MiB, owner cap = one mail import; anonymous 12 MiB, owner
    cap = one passport scan per client address); and a body past 64 KiB must arrive by
    `start + 20 s + received / 16 KiB/s`, else 408 `body_too_slow` (the read is wrapped in `asyncio.timeout`, so a
    stalled body is cut even when no byte arrives), and its charge is returned.
  - Hook refusal lockout (major, real): removed the per-hook refusal ceiling. A request without
    `X-Twilio-Signature` is 403 before the database, uncounted. `HookCache` (per task, 15 min, 10 000 entries, only
    ids that resolved to a live connection) keeps the Auth Token + Account SID; a signature that fails against it is
    403 in process, one database re-check per hook per 5 s (token rotation); a good one is verified again from the
    database (the cache only ever refuses).
  - Sentry transaction names of unmatched paths (major, real): reproduced with the real SDK (a 307/404 path names the
    transaction `http://<host>:<port>/<raw path>`). Every string transaction name goes through `redact_url`; span
    descriptions of HTTP spans and URL-bearing span data keys too.
  - Member ceiling with fresh uuids (major, real): the agency part of the key is used only when
    `TenantGate.is_member` already holds for the caller; everything else shares one `unverified` bucket per identity.
    A token holder therefore has at most (its agencies + 1) counts, so it can neither escape the ceiling nor fill
    the limiter's LRU table. The suggested extra per-identity ceiling across buckets is not added: that bound already
    follows.
  - Hooks sharing the public FIFO (major, real): known hook ids take `class:hook`, unknown ones `class:hook-unknown`
    (`messaging_hook_tx(..., known=)`), so neither a random-id flood nor anonymous browsing queues ahead of a known
    hook. Known hooks skip the per-address misses check, which allowed lowering `HOOK_MISSES_PER_MINUTE` 600 -> 120.

## Tradeoffs

- Slots and the member ceiling are per task, in memory (as every limiter here): two tasks during a deploy double them,
  which stays inside the role's 6 connections. A shared store would add Redis on the request path for no Dev gain.
- `CRM_TENANT_MAX_CONCURRENCY = 2` serialises a single agency's third parallel request; a page firing 4 BFF calls at
  once waits up to 5 s for a slot instead of being refused at once.
- The fair claim recomputes a window function over every due row per claim (one scan of `job_queued_due_idx` and a
  sort by agency): linear in the due queue, about 12 ms for 20 000 due rows of 50 agencies (local EXPLAIN ANALYZE,
  PostgreSQL 16). An expression index on `payload->>'tenant_id'` (a loose index scan per agency) would make it
  sublinear but needs a crm migration
  (MIG-4); only worth it if the due queue regularly reaches tens of thousands. The recent count uses the crm-001
  `job_finished_idx` / `job_running_idx`.
- The in-run job guards see the samplers every 5 minutes, so they react within about 5.5 minutes; the run is at most
  10 minutes, read-only, at most 30 RPS, and k6 aborts on its own when the calm agencies' error rate passes 1 %.

- Round 3: the long work still runs inside `tenant_tx()` (the AI gateway keeps the per-agency advisory lock and the
  budget rows in the same transaction as the model call, AA-964 / AA-1025); moving the model call and the S3 put out
  of the transaction would be the complete fix, but changes the budget accounting. The long sub-share bounds the
  damage: at most one request slot is ever held by such work. Calls not marked long (a KMS decrypt, a Cognito call,
  an SMTP send) hold a short slot, and the short cap still keeps one key from holding both.
- Round 3: one agency is now serialised to one short transaction at a time per task (two with a long one running);
  a page firing several BFF calls at once waits for each in turn (milliseconds each) instead of running two at once.
- Round 3: `HookCache` keeps decrypted Twilio Auth Tokens in process memory (up to 15 min after a lookup; round 2
  declined this). The token is needed to check a signature without the database, and that is the only fix that
  neither costs the database per refusal nor locks genuine callbacks out. It is never logged and only ever used to
  refuse.
- Round 3, residual: the anonymous budget (12 MiB) can still be held by two client addresses each trickling one
  passport scan at 16 KiB/s or more, for up to ~11 minutes per scan; that slows passport scans only, never agency
  uploads. The first callback of a hook after a deploy (cache cold) still queues under `class:hook-unknown` with any
  random-id flood.

## Should know

- Round 3: the body middleware verifies the bearer token itself (only for a class-route body over 64 KiB) to decide
  who is charged; the class guard still makes the access decision. 401 / 503 codes match the guard's.
- Round 3: `POST /crm/v1/...` bodies over 64 KiB that arrive slower than 16 KiB/s after 20 s are cut with 408; no
  known client is that slow (a phone on 3G uploads ~10x faster).

- Round 2: the Infra saved query `slo/fair-share-refusals` counts 429 `tenant_busy` / `rate_limited`; the new 503
  `server_busy` / `db_busy` refusals of the public key are not in it yet (an AA-CIS-Infra follow-up, no code here).
- `CRM_TENANT_MAX_CONCURRENCY=3` is now refused at start-up (it was accepted before); no environment sets it.

- No migration in this PR. The new settings are optional (defaults in code).
- Two integration tests fail locally around midnight Vietnam time on `main` too (date-boundary tests:
  `test_portability_api::test_a_logged_request_...`, `test_portal_person_api::test_flights_in_local_time...`); they
  are not touched here.
- `tenant_gate.GATE` is a process global set by `create_app()`; tests that need their own gate swap it and restore it.
- The load test is never run by CI or a lane; `loadtest/README.md` is the runbook for the orchestrator.
