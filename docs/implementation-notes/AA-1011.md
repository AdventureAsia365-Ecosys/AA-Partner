# AA-1011 — Microsoft 365 + BYO calendar connect

Linear AA-1011 (S279 scope update): (1) an Entra multi-tenant app registration owned by the company, values in
`crm/dev/mail-oauth`; (2) a live proof of the existing Microsoft 365 and SMTP send-as connectors (AA-945 code); (3) a
one-way calendar OAuth push (Google `calendar.events`, Microsoft Graph) of departures and tasks, revoke on disconnect,
tokens in the agency vault.

Status: parts 1-2 are blocked on the Entra registration and an SMTP test mailbox (tech lead); nothing was built for
them in this repo (the send-as code is AA-945's). **Part 3 is built here (S294, lane l8-crm-calendar)**: Google works
with the existing Google OAuth client once its consent screen lists the `calendar.events` scope; Microsoft is coded and
answers 503 `mail_oauth_not_configured` until the Entra values exist.

## Decisions

- **Two PRs (MIG-4).** crm-089 (table + provider CHECK, contract) ships alone first; the code PR raises the readiness to
  crm-089 and carries crm-090 (four setting rows, contract, shipped with their readers like crm-088).
- **The token is an `integration_credential` row**, provider `google_calendar` / `microsoft_calendar`, member = the
  member, sealed with `Vault.encrypt_secret` (integration DEK) exactly like a mailbox credential. Its own provider value
  keeps it apart from the member's Gmail / Microsoft 365 mailbox credential (one row per provider and member). Only
  `app/calendar/oauth_sync.py` decrypts it (added to the `decrypt_secret` lint allow-list).
- **`crm.calendar_connection` cascades from its credential and its member** (no `crm.erase_subject` change, the crm-069
  pattern, `CASCADE_ERASED`). Disconnect sets `revoked`; the push job then removes the events, revokes, and deletes
  the credential, which takes the connection row with it. So `revoked` is a short-lived "clean-up pending" state, and a
  reconnect while it lasts is 409 `calendar_disconnect_pending` (seconds), which avoids orphaning events in a
  different account.
- **No event table.** Each pushed event carries private extended properties (`aaCrm` = connection id, `aaCrmKey` = the
  CRM event id, `aaCrmHash` = digest of what was written). A run lists the CRM's own events and diffs: create the
  missing, update the changed, delete the gone (and duplicates). Google ids and Graph `transactionId`s are derived from
  (connection, key): a create retried after a lost answer never doubles (Google answers 409, we PUT). A half-finished
  run is completed by the next one.
- **What is pushed**: `departure` and `task` kinds from `app/calendar/events.py` (the issue's "departures and tasks"),
  with the ICS feed's privacy rule (fixed label + short trip reference + link; no title, client name or amount).
- **Scope** mine | agency like the ICS feed (any role, as the feed allows).
- **OAuth reuse**: the mailbox's clients, PKCE, state TTL and redirect URI. The calendar state is sealed to its own AAD
  column (`oauth_state.calendar_state`) and prefixed `cal.`; the mailbox completion refuses a `cal.` state up front.
  The web callback routes on the prefix only (the API decides).
- **Job**: one kind `crm_calendar_push`, hourly due-now sweep (the TripPlanner price publish pattern) + one row per
  connect / disconnect with `crm.calendar_push.max_attempts` tries. A push failure is recorded on the connection
  (`failure_class`) and not retried by the queue (the next hourly sweep is the retry); a disconnect's outage is
  retried (a rotated refresh token is stored before the retry), and its last attempt deletes the token anyway. A
  removal deletes every listed event in one run (no batch cap): the token is gone at its end, so a later run could not
  finish it.
- **Settings (tech lead S279)**: window days (120), past days (7), writes per connection per run (200), tries of a
  connect / disconnect run (3); all platform scope, area `calendar`, guides EN + VI.
- **Microsoft revoke**: Graph has no per-token revoke (only `revokeSignInSessions`, which signs the user out of
  everything); the token is deleted and the member may remove the app's consent in their account.

## Changed

- The issue said "tokens stay in the agency vault": they do (integration DEK), as a credential row rather than a
  column of the connection, because `decrypt_secret` is bound to `integration_credential.secret_enc`.
- SQLSTATE CRM57 (the lane brief expected CRM43, which crm-033 already uses for `support_grant`; CRM56 was the last).
- The Calendar card lives on Account > Integrations (`/portal/account/integrations`) as the brief asked.

## Tradeoffs

- No event table: fewer rows and no drift between CRM state and the calendar, at the cost of one list call per run
  (bounded by a page cap). A member editing our event by hand gets it overwritten on the next change of the CRM side
  only (the digest compares what we wrote, not the calendar's current text).
- Graph list is not filtered by date at the API (combining the extended-property filter and a date filter is not
  reliable); the client filters by start date so events outside the window are left as they are, like Google.
- The hourly sweep is a technical constant (like the planner price publish); connect and disconnect run at once.
