## Decisions

- **Migration key crm-010, Guard 0 needs crm-007 only.** crm-008 (AA-939) and crm-009 (AA-938) are taken and not on
  this base. crm-010 touches none of their objects; the tenant erase deletes their tables only when they exist
  (`to_regclass`), so DB Migrate can apply crm-010 after 007 whatever the order of 008 / 009.
- **One deletion path, in the database: `crm.erase_subject(scope, subject, profile_token, dry_run)`** (design §4.10,
  Fix B16), SECURITY DEFINER owned by `crm_owner`, EXECUTE only for `crm_eraser`, reached by `SET LOCAL ROLE
  crm_eraser` inside the lifecycle context. Scopes `trip`, `traveler`, `task`, `note`, `document`, `tenant`. Both the
  trash purge and an erasure call it, so "erasure bypasses trash" is literally the same delete run now instead of
  after the window. Dry run returns the same per-table counts without deleting.
- **Append-only tables that erasure must reach** (`consent`, `trip_stage_history`, `llm_call`) get a separate trigger
  function `crm.erasable_append_only()`: UPDATE and TRUNCATE are always refused; DELETE passes only when
  `current_user = crm_owner` (inside the definer functions; `crm_app` cannot become it) **and** the transaction set
  `app.erasing = on` (set by those functions only). `crm.reject_append_only_change()` and the triggers on
  `audit_event`, its partitions and `audit_export_manifest` are untouched: erasure never deletes an audit row; the
  audit leaves only through the AA-940 partition drop.
- **Delete block as a ledger, `crm.trip_commitment`.** The money, signature, commission and AA-line tables arrive with
  CRM-16/19/23/25/27. CRM-14 defines the rule now on one table those cards write (kind `aa_line | invoice | payment |
  signature | commission`, a status per kind, the Booking or row reference) and `crm.trip_delete_blockers(trip)`:
  `has_money` (invoice paid / payment_claimed / paid_unfulfillable, payment succeeded / refunded), `has_signature`
  (signed), `has_commission` (claimed / received), `has_aa_line` (held / confirmed). Released, expired, cancelled,
  declined AA lines do not block (card E).
- **Archive is enforced at the dispatcher.** There is no sender yet (CRM-17), so this card adds `crm.dispatch_queue`
  (the single choke point of design lane §2.8) and the `crm_dispatch` job: a queued row whose traveller is archived is
  `dropped` with `gate_result = archived` at send time (card R); trashed -> `traveler_trashed`; marketing without a
  current marketing consent -> `no_consent`; no sender configured -> `held` / `no_sender` (CRM-17 re-queues).
- **Legal hold** (`crm.legal_hold`, scope tenant / trip / traveler): an active hold suspends every deletion that would
  reach its subject: trash purge (skipped and counted), form-submission redaction, the LLM-call purge, erasure and
  offboarding (409 `legal_hold`; SQLSTATE `CRM10` from `erase_subject` itself). A hold on a trip also holds the
  travellers on it. A hold placed by a platform actor (`platform:*`, AA on a regulator's request) can be released only
  by a platform actor (trigger).
- **`crm.erase_subject` scopes grew `relation`** (trashed relationships, AA-937, had no purge) and the tenant erase
  deletes crm-008 / crm-009 tables only when they exist; the dry run of a tenant erase works on an active agency (the
  counts the owner sees before confirming), the real run needs status `offboarding`.
- **Offboarding = export then erase, one owner flow** (`erasure_request` scope `tenant`): request -> export job ->
  download -> typed confirmation (the agency id) -> agency `offboarding` (no member context opens) -> erase job
  (`erase_subject('tenant')`, document and export objects, `KeyProvider.destroy`) -> agency `offboarded` + receipt.
  The owner may waive the export. All of the erase step is one transaction; a refusal (a hold placed after the
  confirmation, CRM16) marks the request `failed` and nothing is deleted.
- **Crypto-shred and the DEK cache** (AA-934 TTL): `destroy` runs after the rows are deleted and before the commit,
  evicts this process's cache; other API / worker tasks can hold an unwrapped DEK for up to `DEK_CACHE_TTL_SECONDS`.
  That window is harmless (no row is left to decrypt, and no context opens for an offboarded agency) and is stated on
  the receipt (`dek_cache_expired_by`). No follow-up "wait out the TTL" job: the receipt is honest about the time.
- **Export format v1** = JSON lines: a header line, then `{"table", "row"}` per row of every exported table, `*_enc`
  columns decrypted (key without `_enc`), `*_bidx`, the F2 pointer and integration secrets left out, bytea base64.
  Document files are listed, not included (CRM-35 adds the zip with files). Sealed with the agency `export` DEK (AAD
  = tenant, `erasure_request`, `export`, request id), so it is unreadable after the crypto-shred even if a copy exists.
- **The daily run is one kind** (`crm_lifecycle`) with five steps per agency in one transaction per agency, each trash
  item in its own savepoint (a refusal keeps that item and is counted `trash_kept_<code>`).
- **DRY RUN default for every hard delete.** `LIFECYCLE_DRY_RUN` (default true): the daily `crm_lifecycle` job only
  counts (redaction, LLM-call purge, trash purge, auto-archive), and an owner's erasure or offboarding erase answers
  409 `deletion_dry_run` with the counts. Turning it off is an ops decision, like `JOB_RETENTION_DRY_RUN`.

- **Restore checks Booking through a seam**: `app.state.booking_checker` (`BookingLineChecker.line_statuses`) is None
  until CRM-19 / CRM-B1 bring the B2B client; a trip with an open AA line in the ledger then answers 503
  `booking_not_configured` and stays in the trash. A trip without AA lines restores without asking.
- **Snapshot-age alarm on the existing AA-869 function** instead of a new Lambda: it already lists every manual
  snapshot of the Dev instance; it now publishes `AA/RDS BackupCopyMaxAgeDays` (oldest manual copy left after the run,
  created on or after `COPY_AGE_SINCE` = 2026-10-21, the day the CRM design was approved: older snapshots hold no
  `crm`) and `AutomatedBackupRetentionDays`; one alarm per instance on `MAX` of both > 30 days, missing data breaching,
  2 of 2 daily periods (the metric arrives once a day; a 1-of-1 window could flap ALARM/OK every day).
  Cost about 0.70 USD/month (2 custom metrics + 1 alarm).

## Changed (vs the card text)

- The card lists checklist items for tables that do not exist yet (invoices, payments, signatures, commissions, AA
  lines, the dispatcher). Instead of waiting, the rules are built now on two small tables those cards will write:
  `trip_commitment` (delete block, card R/E tests run against it) and `dispatch_queue` (archive gate, card R test).
- The S249 brief asks for retention per data class, a legal hold, offboarding and a settings page beyond the card's
  checklist; all are in. Client erasure is in (it is the card's "erasure bypasses trash"); partial erasure that keeps
  signed-agreement and accounting evidence, the data-request log and the export zip with files stay with CRM-35.
- `crm_trash_purge` (design name) is not a kind of its own: the trash purge is a step of `crm_lifecycle`. The root
  DM-7 trash row is updated to say so (root branch `docs/aa-942-retention-rows`).
- Lost codes already existed (crm-005 CHECK, `app.pipeline.LOST_REASONS`, web list). This card adds the Booking-feed
  pre-selection helper (`rules.suggest_lost_reason`, used by CRM-19) and one test that the three lists agree.
- New web write routes: none outside the BFF. Every new browser call is a BFF allow-list line, and the BFF route is
  what calls the cross-site write refusal (`refuseForeignWrite` on main; this base predates that file, the rebase
  onto main brings it).

## Tradeoffs

- **One deletion function with dynamic per-table steps** (`crm.erase_rows`, owner-only helper, table names literal in
  the caller) vs. one function per scope: one place to review, and the tenant erase ends with a catalog sweep (any row
  left in a tenant table outside the keep list fails the erase), so a table a later card adds cannot silently survive
  an offboarding. The cost: a later card must add its table to the function in its own migration (integration test).
- **Profile-token check is a consistency guard only.** The DB cannot open `traveler.profile_token_enc`; the caller
  decrypts it (AAD binds the traveller row). The function checks every party row of the token twins one of the
  traveller's own party rows (same trip and role). A companion's token swapped for another companion on the same trip
  is not caught; the path is reachable only through `app/lifecycle/erase.py` as `crm_eraser`.
- **Traveller erasure refuses a client on a live trip** (409 `traveler_on_trip`): delete or erase the trips first.
  CRM-35 decides the finer rule (erasing a client whose completed trip keeps accounting records).
- **Holds reach both ways** (review S249): a trip hold holds the trip's travellers (their erasure would remove the
  trip's party evidence), and a client hold holds every trip they are on or are named on through a note or document
  (a trip erase deletes their F2 party rows, notes and documents). A relation is held when either end is held. The
  cost: a client hold blocks the trash purge of a whole group trip; the owner sees it as `trash_kept_legal_hold`.
- **Any hold suspends offboarding** (review S249): `crm.legal_hold_blocks('tenant', NULL)` is true for an active hold
  of any scope, because the agency erase reaches every subject. Subject-less data (`llm_call`) and children without a
  held parent still follow the agency hold only (`legal_hold_blocks('<scope>', NULL)`).
- **Document objects are deleted before the transaction commits** (`app/lifecycle/erase.py`): if a later step of the
  same agency transaction aborts, the purged rows come back pointing at missing objects; the next run deletes them
  again (a missing object counts as deleted). Deleting after commit was rejected: a crash between commit and delete
  would leave an orphan object with personal data and no row pointing at it, which nothing would ever find.
- **Owner offboards an active agency only**: `tenant_tx` refuses a locked agency; AA ops offboard a locked one from
  the L1 console (CRM-13a), which is not built yet.

## Review round 1 (S249) — fixed

- Blocking: offboarding erased data under a trip / client hold (`legal_hold_blocks('tenant', NULL)` matched agency
  holds only). Now any active hold of the agency refuses the request, the confirmation and the erase (CRM10).
  Tests: `test_any_hold_in_the_agency_suspends_its_offboarding_erase` (DB, trip and client hold, dry run included),
  `test_any_hold_suspends_offboarding_and_a_refused_erase_gives_the_agency_back` (app, end to end).
- Blocking: a member could hide an AA hold by setting its trash columns. Now `legal_hold_never_trashed_chk` keeps
  `deleted_at` / `deleted_by` / `purge_after` NULL, `crm.guard_legal_hold` refuses any change to them (and to
  `created_by`, and to the release fields of a released hold, and the release fields of a platform hold by a
  non-platform actor), and `legal_hold_blocks` no longer filters on `deleted_at`. Test:
  `test_a_hold_cannot_be_hidden_through_the_trash_columns`.
- Non-blocking, fixed: client hold reaches their trips and both relation ends
  (`test_a_client_hold_reaches_their_trips_and_both_ends_of_a_relation`); the order-dependent card E test asserts on
  the agency's own `lifecycle_run` row; per-agency catch of unexpected errors in the daily run; stuck offboarding gets
  an automatic path for refusals plus the documented platform recovery; copy-age alarm 2 of 2; Infra test guard at the
  end of the file.
