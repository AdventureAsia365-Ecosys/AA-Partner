# AA-1070 — CRM travel ops (departure roster, vouchers, server PDFs, rooming list, passport check, visa tracker)

Lane l15 of S277. Source: the S275 study of a tour and travel app (root
`docs/research/2026-11-10-odoo-tour-travel-plugin-comparison.md`, items crm-22, crm-20, crm-21, crm-17, crm-15,
crm-16). Behaviour only: no code, template or long text of the studied app (OPL-1) is used.

Migrations: crm-054 (expand: six tables) and crm-055 (contract: `tenant_settings.passport_valid_months`, two PDF
document kinds + uploader `system`, the visa status moves), one migration-only PR; the code PR follows once both are
applied on Dev.

Out of this lane (same issue, other items): the inclusion / exclusion library on the proposal (crm-35) and the guided
"AA cancelled the departure" flow (crm-13). This lane records the departure's cancelled state from the feed, which
that flow will read.

## Decisions

- **One package `app/travel_ops/`** (passport, rooming, vouchers, visas, departures) and one agency router
  `app/routers/travel_ops.py`; the traveller-portal routes sit in `app/routers/client_pages.py` (the portal's cookie
  and rate-limit plumbing) and call `app/travel_ops/portal.py`.
- **Passport check is computed, never stored.** `passport_ok = expiry >= trip end + passport_valid_months` (calendar
  months; the 31st clamps to the month's last day). Statuses: `ok`, `expires_too_soon`, `missing` (no expiry on file),
  `no_trip_end` (the trip has no end date yet). Only the status leaves the API, never the expiry date. A "passport
  issue" is `expires_too_soon` (a missing passport is already a Stage 3 gap). The pipeline filter `issue=passport`
  and the card badge compute it for booked / pre-departure / travelling trips only (the stages where it matters),
  so the board decrypts at most a few hundred values.
- **The workflow trigger is an event** `passport.invalid_for_trip` (trigger kind `event`, no CHECK change), fired by
  the hourly workflow tick for a trip that entered Booked in the last 3 days with a passport issue (key: the trip and
  the time it entered Booked, so one run per entry). The AA library gets a template
  `passport_invalid_for_trip` (an urgent `passport_invalid_for_trip` task) the owner installs, like every library rule.
- **Visa overdue task**: the same tick opens one `visa_deadline_overdue` task per trip while an application in
  `to_do` / `collecting` is past its deadline (the open-task unique index makes it idempotent).
- **Vouchers are released** when the trip is booked (booked, pre_departure, travelling, completed), the line is
  confirmed and `visible_to_travelers` is on. The agent sees every confirmed line's voucher (with a "not released"
  reason). An AA line's voucher carries the line's own Booking facts (title, departure, service dates, a short AA
  booking reference); Booking has no confirmation read in the CRM client yet (bk-12 adds pick-up times and points).
  The supplier contact name is opened for the voucher only (agency lines of an own supplier), never the e-mail.
- **Server PDFs without a browser.** The worker image has no headless browser and the Dockerfile installs no new
  system package (Trivy rule), so `app/documents/pdf.py` writes PDF 1.7 itself: A4 pages, text runs, rules and simple
  tables, wrapped by the font's own widths. Unicode text (Vietnamese) uses one embedded TrueType font
  (`app/documents/fonts/LiberationSans-Regular.ttf`, SIL OFL 1.1, licence next to it) as a CID font with
  Identity-H; bold is the same font drawn with fill + stroke. The job `crm_pdf_render` builds the PDF, seals it with
  the tenant docs DEK and stores it as `crm.document` (`confirmation_pdf`, `invoice_pdf`, `proposal_pdf`, `voucher`,
  uploader `system`). A member asks with `POST /trips/{id}/pdfs`.
- **Rooming list** is replaced whole (`PUT /trips/{id}/rooming`): every traveller in at most one room, a room's
  travellers within its type's capacity (single 1, double 2, twin 2, triple 3, quad 4, family 6), one type per room
  number, and — when the accepted proposal has a `room_config` — the room count per type no more than it says.
  The lead traveller edits it on the portal after the deposit (the Stage 3 lock), like flights.
  A traveller entry without a `bed_pref` key keeps the bed preference on file (`rooming.keep_beds`), `null` clears
  it: the lead never sees or sets bed preferences on the portal, so their save must not wipe what the agent set (the
  portal also sends each traveller's current value). The agent route dumps its body with `exclude_unset` for the
  same rule.
- **Ops release document v2** carries each traveller's `room` (`room_no`, `room_type`, `bed_pref`: codes and the
  number only, no names beyond what v1 already releases) and the manifest can print a `room` column.
- **Departure roster**: one row per AA departure id of the agency's live lines (`crm.booking_line.departure_id`, not
  cancelled), with the trips, pax (adults / children from the trip party), the feed state
  (`crm.aa_departure_state`, `scheduled` when no event came yet) and the Stage 3 progress. The merged manifest
  (`POST /departures/{ref}/manifest`) is field-picked like the ops manifest, watermarked, and audited
  (`report_export`, reason `departure_manifest`, the trip ids as objects); nothing is stored.
  It is a bulk reveal like the duty reveal (card R): a reason from the duty `BULK_REASONS` above 5 travellers or when
  a health column (dietary, mobility) is picked (422 `reason_required`), the member's hourly reveal limit (60, the
  reveal meter) checked before anything is opened (429 `reveal_rate_limited` + a denied `reveal` audit event), and one
  `reveal` audit event per traveller released so the reveal meter and its alarm count the export.
- **Feed**: `departure.guaranteed` / `departure.cancelled` upsert `crm.aa_departure_state` (they were recorded as
  `informational` before); an older event never overwrites a newer one.

## Changed

- Issue asked for a headless renderer in the worker; built a small PDF writer instead (see Decisions, Tradeoffs).
- Issue named `crm.aa_departure_state(departure_id, status, min_to_operate, guaranteed_at)`; the table also keeps
  `cancelled_at` and the last event id / time (crm-054).
- The calendar layer is `aa_departure` (one all-day event per AA departure on its first service day, with the feed
  state and the trip count; the ICS feed says "AA departure", no title), next to the trip departure / return events.
- Travelling now gets `passport_issues` per trip (the duty route now opens the vault for it).
- Settings > Travel is a page of its own (passport months + visa guidance); visa guidance is owner-only to change
  (`settings_forms_manage` + owner, like the other Settings sections that bind the agency); every role reads it.
- Visa applications: every role may create and move them (`trip_edit`), the one-application read with the number in
  clear is a logged reveal (`reveal_sensitive`); the merged departure manifest is `reveal_sensitive` too.
- **Agency branding on the server PDFs is the agency's display name only (`crm.tenant.display_name`), not the
  Content studio tenant profile the issue names.** That profile lives in CIS (`shared.tenants` /
  `shared.tenant_brand_rules`), the CRM has no read of it (no column in `crm.tenant` / `crm.tenant_settings`, no CIS
  M2M contract call for a profile, no colour or logo anywhere in the CRM), and adding one is a cross-repo contract
  change. Deferred: a follow-up adds a CIS `tenant.profile` read (brand name, colour, logo) to the CRM client and
  passes it to `renders._doc`. The issue's closing comment must say so; crm-21 is not fully done until then.
- The traveller portal's travel answer carries `voucher_header` (agency name, trip title and dates, the lead
  traveller's name opened server-side, party size) and every printable portal voucher prints it.
- The PDF of an invoice / proposal / voucher is asked from the trip panel per subject: the booking confirmation, one
  button per invoice that is not void, per sent / published / accepted proposal version, and per voucher.

## Tradeoffs

- Own PDF writer vs a library (fpdf2 LGPL + Pillow) or Chromium: no new dependency or image package, no CVE churn;
  the cost is a plain layout (no HTML/CSS) and a ~400 KB font embedded in every PDF (no subsetting).
- Passport check at read time vs a stored flag: always right after a passport or date change, at the cost of a
  bounded decrypt on the pipeline and the departure pages.
