## Decisions

- **crm-029 is an expand file with one new table, `crm.traveler_flight`** (the design's name and columns:
  `flight_no_enc` under the vault DEK, `airport_iata`, `sched_local`, `tz`, plus `direction`, `entered_by_kind`).
  A new tenant table normally means a replaced `crm.erase_subject` (contract), and a parallel lane (invoices) may
  replace it in crm-028 at the same time. Instead every foreign key of the table cascades (trip, traveler,
  trip_traveler), so the erase deletes the flights through the rows it already deletes, and its "nothing left" check
  finds none. `test_crm010_schema.py` gains `CASCADE_ERASED` (listed on purpose, never derived) and a catalog check
  that each listed parent key is `ON DELETE CASCADE`.
- **Its own hold guard, `crm.guard_held_flight`, not `crm.guard_held_change`** (found by the full integration run): an
  RI cascade runs as the table owner without FORCE RLS, so the generic guard read every agency's legal holds during a
  cascade and refused one agency's erase because another agency had an agency-wide hold. The new function lets a
  cascade (trigger depth > 1: the parent's own guard and `crm.erase_held` already ruled) pass and checks a direct
  statement with `crm.hold_row` under the agency's RLS (`test_another_agencys_hold_never_stops_this_agencys_erase`,
  `test_a_held_trip_keeps_its_flights`).
- **The test conftest skips a registered expand file on re-apply**: an expand file cannot use DROP, CREATE OR REPLACE
  or a DO block, so it cannot be written to run twice; DB Migrate never applies a registered file again either.
- **Plain airport / local time / zone, encrypted flight number** (data-privacy §2.3): the ops hand-off and the T-48 h
  task query by time; the flight number is the part that identifies the booking. All four columns are tagged
  `pii:travel`.
- **Number crm-029**: crm-028 is the invoices lane's (AA-952 slice 4, merged on main as an expand file); this branch
  is rebased on it, so the auto-apply takes crm-028 then crm-029.
- **"One family e-mail serves two travellers" (Fix E4) without a schema change.** The CRM refuses a second client with
  the same address (`app.travellers.service._refuse_duplicate`), so the only way one address serves two travellers is
  a companion **without** an address of their own. `app/portal/person.py` `delivery_of`: a person's codes go to their
  own address, else (a companion) to the lead's, else nowhere (409 `no_email_on_file`). `group_of` = the travellers
  with live portal access whose codes go to the same address. Chosen over a new `traveler_access.delivery_traveler_id`
  column: no FK could be added in an expand file, and the implicit rule needs no agent step.
- **The picker re-binds the verified code row.** A good code whose address reaches 2+ travellers answers
  `{"signed_in": false, "pick": [...]}` (names decrypted only after a correct code) and stays pending (no attempt
  spent); the same code with `traveler_id` opens the session. When the choice is not the link's own traveller, the
  `otp_challenge` row's `access_id` / `traveler_id` move to the chosen access (its composite FK keeps them on the same
  trip) before the session hash is written. Each pick is its own code and session row: card E "separate sessions".
- **A session is bound to the address its code went to** (review fix, S261): `request_code` stores the blind index of
  the address the code was sent to on the code row (`otp_challenge.sent_to_bidx`, new nullable column in crm-029),
  and `public._signed_in` accepts a session only while `person.delivery_bidx` of the traveller it acts as (and of the
  link's traveller) still equals it. The first version only checked that the session's access matched the link's
  access, so a lead's session acting as the child survived the child getting their own address (the lead could keep
  using it with the child's new link for the rest of the 12 hours). Binding the proof instead of expiring sessions at
  each write path also covers the agency changing a lead's address (`travellers.update_traveler`) without touching
  that code. A session with no recorded address (opened before crm-029) never passes: those travellers sign in again.
- **`POST /switch`** ("[Fill for Max]" in WF-8): a signed-in person moves their session to another traveller of the
  same group without a new code (the address owner already proved control). Chosen over "the lead fills Stage 3 for a
  minor": the minor rule needs a DOB on file, which Stage 3 itself collects.
- **One link, cookie exchange** (§2.9 rule 1, the Fix B11 model of AA-950): `/c/t/<token>` is now a route that sets
  `aa_portal_link` (Path `/crm/public/v1/traveller`) and redirects to `/c/t`; new cookie routes under
  `/crm/public/v1/traveller` call the same functions as the token routes, which stay (tests and any old caller).
- **Documents**: the portal lists only `visible_to_travelers AND NOT write_only` documents of the trip as a whole or of
  this traveller; opening one re-checks and refuses 403 `document_write_only` (a passport scan: card R),
  `document_not_shared`, `document_not_yours`; another agency's id is 404 (RLS). Download = JSON base64 like the agency
  route (7 MiB max), turned into a Blob in the page.
- **Passport scan upload-only**: `document` kind `passport_scan` (always write-only, never visible), `uploaded_by_kind
  = traveler` (new `uploaded_by_kind` argument of `app.documents.service.upload`), locked before the deposit like
  Stage 3, at most five live scans per traveller (409 `scan_limit`), a 10 MiB body cap on that route only.
- **Lines and days**: `booking_line` rows `visible_to_travelers AND status <> 'cancelled'` (the DB already hides a
  cancelled line, `booking_line_cancelled_hidden_chk`), title / dates / status / confirm class / pay on arrival only;
  the accepted proposal's `proposal_day` rows (title, place, IANA zone, offset).
- **Companion e-mails at the invite** (`POST /companions`, lead only; tightened by the S261 review):
  - A companion with an address of their own and a live portal access: 409 `already_invited`. The lead never
    re-issues (so never revokes) another adult's link.
  - The link comes back to the lead only when the companion is reached through the lead's own address (`reach =
    via_you`). For a companion with their own address (already, or set in this request) the link is re-issued to that
    address through the dispatcher and `link_path` is `null`; the page says the link went to their e-mail.
  - The address lands on the agency-wide `crm.traveler` record, so the lead may set it only for a companion on **this
    trip alone** (409 `ask_your_agent` otherwise: a lead must not choose where another trip's codes and links go).
    Never over an address on file (409 `email_on_file`); another client's address is 409 `email_in_use` (no name).
  - Every refusal of an address is a denied `portal_companion_email` audit event on the lead's access (written even
    though the request fails); after three in 24 hours the lead gets 429 `too_many_attempts` for any address, counted
    from `crm.audit_event` (crm_app has SELECT; index `audit_event_object_idx`). A set address is an allowed audit
    event naming the lead's access; the invite itself is `portal_companion_invite` (allowed / denied).
- **A lost or cancelled trip has no portal** (404 `link_not_found`): closes the AA-946 re-review note 4.

## Tradeoffs

- Cascade keys instead of naming the table in `crm.erase_subject`: the erase receipt does not count flights (they
  leave with their trip / traveller / party row). Accepted to keep crm-029 an expand file and avoid racing the invoices
  lane's possible `erase_subject` replacement in crm-028; a later contract key may name the table.
- The picker shows display names to whoever holds the code of that address (the address owner): acceptable, the same
  person is the lead or the family member the agency reaches through that address.
- `email_in_use` still tells a lead that some client of the agency has that address. Answering identically was
  considered (the review's first option) and not taken: the outcome shows anyway on the next home view (the companion's
  `has_email` / `portal` state), so an identical answer would hide nothing. Instead the probe is capped (three refused
  addresses per lead access per 24 hours, then 429 for any address) and every refusal is in the agency's access log.
- Binding sessions to a blind index (not the traveller id that received the code) also ends sessions when the agency
  edits an address in place; the cost is one party read per portal request (it was already read for non-own access).
- An address a lead sets stays on the client record if the agency later adds that companion to another trip; the
  agency sees it in the CRM and in the access log (allowed `portal_companion_email`). The address is not verified by a
  code round-trip before it is saved: within this trip the lead already reached that companion through their own
  address, and the companion's portal opens only with a code sent to the new address.
- No agency-side view of flights in this slice: an agent reading a flight number is a reveal (pii:travel); the ops
  hand-off card (CRM-26) owns it, with the reveal pattern.
- No `next build` locally (RAM shared by three lanes): `tsc --noEmit`, ESLint (with the suppressions prune) and vitest;
  CI "Web Build" builds.
