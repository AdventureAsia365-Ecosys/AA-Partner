# AA-990 (D2) — angle requests whose atom was replaced: a clear state in the portal

S252: 14 angle-gate requests (4 tenants) point at atoms a later atomize run replaced. CIS answers the typed 409
`atom_replaced` on write / regenerate (CIS #1013), but the portal only found out after a click. Decision D2 (Nghiệp's
standing approval, S252): no new status and no migration; CIS exposes a computed flag on the tenant's reads and the
portal shows the state and turns Write off. Requests with a unique replacement are re-pointed once by a CIS script
(root runbook), so the flag stays only on requests with no unique replacement.

## Decisions

- **CIS contract (AA-CIS-App, same issue):** `GET /v1/angle-gate/requests/{id}` (and the choose / reopen re-reads),
  `GET /v1/content-writing/reviews` and `GET /v1/content-writing/requests/{id}/review` add
  `atom_replaced: boolean` and `atom_replacement: {atom_id, place, itinerary_day} | null` (the unique matching part
  of the rewritten tour, a hint only). Both optional here: a CIS build without them reads as "not replaced".
- **Writer (`AngleGateWizard.tsx`):** a replaced request shows one notice ("This part of the tour was updated", the
  sentence from `lib/myContent.atomReplacedNote`, a "Go to Social Posts" button) and every action is off: goal cards,
  "Generate 3 angles", "Write with this angle", "Change angle", the CTA form, "Retry", and the automatic write on
  arrival at the Write step (it would only meet the 409). A piece written before the rewrite is still shown.
- **My Content (`lib/myContent.regenerateBlock`):** "Write again" is disabled with the reason
  `ATOM_REPLACED_BLOCK`. Order of reasons: published → being written → closed tour → replaced (a closed tour or a live
  post is the more useful thing to say first).
- **The way out is a new post from Social Posts**, not "Change angle": reopen + choose keep the same atom (CIS #1013
  review, S251).

## Changed

- `portal/lib/myContent.ts`: `ContentRow.atom_replaced`, `AtomReplacement`, `ATOM_REPLACED_BLOCK`,
  `atomReplacedNote`, the `regenerateBlock` rule; tests in `portal/lib/myContent.test.ts` (18 pass, `npm test`).
- `portal/app/portal/_components/reviewListApi.ts`: `ReviewItem.atom_replaced` / `atom_replacement`.
- `portal/app/portal/_components/AngleGateWizard.tsx`: the request fields, `AtomReplacedNotice`, the disabled actions.

## Tradeoffs

- **Computed, not stored:** no status to keep in sync with re-atomize runs; costs one main-pool read per request
  read on the CIS side (the MAIN exception pattern of the job-status read).
- **The hint is informational:** the portal does not offer "use the replacement" — the tenant picks the new part of
  the tour on the Slate, which makes a new request with the right Subject.

## Should know

- Not run here (RAM-tight lane): `next build`, type-check of the whole portal, browser screenshots. The three edited
  files pass a TypeScript syntax transpile; the UI check (aa-ui-verify) belongs to the PR preview.
- Deploy after the CIS change (the fields are optional, so the order is not breaking either way).

# AA-990 scope 5 (26/10/2026) — notice when Adventure Asia updated a tour after the tenant's version

Scope item 5: "Tenant versions older than Master: tenant informed, nothing silently overwritten." CIS (branch
`feat/aa-990-master-newer`) adds two read-only fields to `GET /v1/tours/my-versions` rows and
`GET /v1/tours/versions/{id}`: `master_updated_at` (when AA last changed the tour's text) and `master_newer` (true when
that is after the version's `created_at`). This half shows it in My Tours.

## Decisions

- **Where**: My Tours (`CatalogTab`, one row per tour = its latest version) gets a small info badge "Updated by
  Adventure Asia" under the tour name, whose tooltip is the full sentence; the version drawer (`CatalogDrawer`) shows
  the full notice under the created / edited line: "Adventure Asia updated this tour on <date>, after your version.
  Your text was not changed. Rewrite it if you want the new details." with a "Rewrite" button that calls the drawer's
  existing Request Rewrite action (a new version; the tenant's text is never touched).
- **Rules in `portal/lib/masterNotice.ts`** (no imports, `node --test`): show only on `master_newer === true` (absent,
  null, false or a non-boolean shows nothing, so the portal can ship before the CIS deploy); not on a paused or
  retired tour (its own served badge already says so and a rewrite would be refused with 409). The date is formatted
  by the caller (kit `fmtDate`); a missing or unformattable date drops "on <date>".
- **Look**: kit tokens only (`K.infoSoft` background, `K.line` border, `K.info` icon, `K.body` text), so dark mode
  follows the existing `--aa-info*` variables; the notice wraps (text `flex: 1 1 240px`, button below it) at 390 px.
- **Drawer source**: the detail response when it carries `master_newer`, else the list row (both come from the same
  CIS rule).

## Changed

- `portal/lib/masterNotice.ts` + `portal/lib/masterNotice.test.ts` (6 tests).
- `portal/app/portal/_components/MasterNewerNotice.tsx`: `MasterNewerBadge` (list) and `MasterNewerNotice` (drawer).
- `portal/app/portal/_components/catalogApi.ts`: `Version` gains optional `master_updated_at` / `master_newer`.
- `portal/app/portal/_components/CatalogTab.tsx`, `CatalogDrawer.tsx`: render the two.

## Tradeoffs

- Tour overview (Marketplace) and Browse Tours show nothing: the notice sits where the tenant reads and rewrites its
  text. The CIS marketplace route does not carry the field either.
- No dismiss: the notice is derived from the data and disappears by itself once the tenant makes a new version (its
  `created_at` is then after the Master change). A per-tenant "seen" state would need storage for little gain.

- Copy is content-only (tenant-sees-content-only): no gate, score, QA or flag words; a test asserts it.
- Checks run here: `npm test` (45 pass, incl. the 6 new), `tsc --noEmit -p .` clean, ESLint clean on the changed
  files. `next build` was NOT completed locally: it was OOM-killed (exit 137) on this RAM-limited machine; CI "Portal
  Build" runs it. Screenshots (390 px, dark mode) belong to the PR preview (aa-ui-verify).
- Live data on Dev: 2 latest tenant versions (of 15, 4 tenants) were older than their Master on 26/10, so the notice
  should appear on those rows once CIS is deployed.
