# AA-994 — slice S2a: the UI kit core vendored into the portal and the CRM web

Design: AA-Ecosys root ADR 0016 ("one design system, guarded kit copies") and the AA-994 plan
(`docs/audits/2026-10-27-S252-aa994-design-system/plan.md`, row S2a, guards G10, G12, G13). The canonical core is
AA-CIS-App `frontend/app/_kit/core/` (slices S1a tokens/code, S1b `tokens.css`, S1c `eslint-kit.mjs`). This slice
replaces the 16 portal and 6 CRM web file-by-file copies (plus both `_brand/tokens.ts`) with a full-profile copy of
that folder per app, synced by the root `tools/kit/kit-sync.sh` from CIS `main` at `1976bf94` (lock `ref`).

## Decisions

- **Sync, never hand-copy.** `portal/app/_kit/core/` and `web/app/_kit/core/` (23 files each) and both
  `kit.lock.json` were written by `tools/kit/kit-sync.sh portal|crm-web --dest-repo <this worktree>`. Nothing in
  `core/` was edited afterwards (the integrity check proves it).
- **`local/` next to `core/`** (ADR 0016 decision 3b) holds each app's own kit parts:
  - portal: `api.ts` (the fetch helpers; byte-identical to CIS `frontend/app/_kit/api.ts` today, but that file is
    CIS-local under ADR decision 1, so the copy is portal-owned from now on and leaves the live-compare list), the
    theme binding `theme.ts` / `useTheme.ts`, and the whole shell from `app/portal/_shell/` (8 files, `git mv`);
  - CRM web: the theme binding and `CrmShell.tsx` (from `app/(crm)/_shell/`).
- **Theme**: the old vendored `theme.ts` / `useTheme.ts` are gone; `local/theme.ts` is
  `createThemeStore({ storageKey: "cis_theme" })` (same key as before, so a stored choice survives), `local/useTheme.ts`
  binds `createThemeHooks`. Both root layouts put `themeStore.restoreScript` in `<head>` (as CIS admin does since
  S1a), so the key lives in `local/theme.ts` only; the portal keeps its sidebar-rail restore as a second inline script.
  The core script is the old hand-written one with the key filled in (same logic), so first paint is unchanged.
- **Barrels** (`_kit/index.ts`) re-export `./core` the way the CIS barrel does (tokens, brand constants, primitives,
  Modal, Drawer, Toast, DataTable, csv, savedViews, Providers, PageFrame names, useSidebarCollapsed, useHydrated, the
  theme types) plus `./local` (portal `api`, the theme hooks). Every name exported before is still exported. The
  shells are **not** re-exported: shell files import the barrel, so the layouts import them by path
  (`@/app/_kit/local/PortalShell`, `.../CrmShell`), exactly like CIS `admin/layout.tsx` imports `../_kit/AdminShell`.
- **CRM web barrel leaves out `core/useMediaQuery.ts`**: it calls `useSyncExternalStore` without a `"use client"`
  line, and ~30 CRM server components import the barrel, so Turbopack refused `next build` ("importing a module that
  depends on useSyncExternalStore into a React Server Component"). The CRM never used it. The portal barrel keeps it
  (no portal server module imports the barrel; its build is green). Fix belongs in CIS core (see Should know).
- **Deep imports** (`@/app/_kit/tokens`, `@/app/_kit/primitives`, `@/app/_brand/tokens`, `../_brand/tokens`,
  `./_kit/Providers`): client components now take those names from the barrel `@/app/_kit` (ADR 0016 decision 3;
  review follow-up). Only these deep imports remain, and both barrel headers list them as the allowed exceptions:
  - portal server modules (root layout, `_legal/LegalPage.tsx`, privacy, terms, `portal-access/*`) import
    `core/brand` / `core/Providers` / `local/theme` by path, because the portal barrel re-exports
    `core/useMediaQuery.ts` (no `"use client"`), which a server module must not load;
  - shell parts by path from `local/`: layouts import `PortalShell` / `SessionWatch` / `CrmShell`; pages import the
    shell-owned `ROUTES` (`local/portalNav`), `useCatalog` and `MY_VERSIONS_KEY` (`local/useShellData`). Not
    re-exported: the shell imports the barrel, and `useShellData` imports `app/portal/_components/ui.tsx`, which
    imports the barrel too;
  - CRM web `app/layout.tsx` imports `core/tokens.css` (no PostCSS).
- **Tokens**: the `--aa-*` blocks of `portal/app/globals.css` (old lines 3-250) and `web/app/globals.css` (old 1-227)
  are deleted. Portal: `@import "./_kit/core/tokens.css"` right after `@import "tailwindcss"` (Tailwind 4 inlines it,
  as in CIS S1b). CRM web has no PostCSS, so `app/layout.tsx` imports `./_kit/core/tokens.css` before
  `./globals.css` (same cascade: tokens first). The legacy `--bg-*` / `--text-*` blocks and every layout rule stay.
- **Provenance** (plan G13) is `api/scripts/check_kit_provenance.py` (stdlib, like `check_vendored_copies.py`): the
  lock names CIS `frontend/app/_kit/core` and a full sha (`"ref": "local"` refused); the copied `MANIFEST.json` has
  the lock's sha256 and is byte-identical to CIS's `MANIFEST.json` at `ref` (contents API); `ref` is on CIS `main`
  (compare `ref...main` = `ahead` | `identical`). With `--base <sha>` it diffs `<sha>..HEAD` over the lock and the
  core folder (fetching the base at depth 1 when the checkout lacks it) and passes without GitHub when neither
  changed; a ref name (`--base origin/main`, local runs) is resolved with `git rev-parse --verify` first (CI passes
  a sha); no base, an unresolvable ref or an unreadable diff = full check. Python, not Node, so the required Unit Tests job covers it.
- **CI**: Portal Build and Web Build gain two steps before `npm ci` (dependency-free): "Kit core integrity"
  (`check-kit-copy.mjs` and `--css .`) and "Kit core provenance" (`--base` = PR base, merge-group base or push
  `before`). Both jobs have no path filter, so they also report on `merge_group`. The task and plan row put
  provenance inside these jobs; ADR 0016 decision 5 / plan G13 also mention a separate "Kit provenance" job. Here
  the two build jobs are that check, so H3 for Partner means requiring Portal Build and Web Build (which H1 already
  does), not a third job.
- **`check_vendored_copies.py`** drops `_WEB_KIT`, `_PORTAL_KIT` and both `_brand/tokens.ts` entries; it keeps the
  job table template, the identity verifier and the four `lib/` BFF helpers per app. Run live against CIS `main`:
  11 files, 0 failed (it was red since CIS S1a moved the kit files).
- **Lint**: no kit-preset change in this slice. The plan gives the `inline` preset, suppressions and the lint step
  inside the build jobs to S2b, and the CRM web has no ESLint yet (also S2b). To keep today's level unchanged after
  the shell move, `portal/eslint.config.mjs` now holds `app/_kit/local/**/*.tsx` to the same AA-732 `error` rules as
  `app/portal/**` and exempts only `app/_kit/core/**`. Portal ESLint before and after: 0 errors, 4 warnings (same
  four).

## Tradeoffs

- **Visual change**: one token only. Diffing every `--aa-*` definition of the old `globals.css` blocks with

  identical; core adds 53 new definitions (44 names: scales, fonts, scrim, hero, shadows) that no portal or CRM file reads, except

- Provenance skips the GitHub reads when the kit did not change, so a GitHub outage cannot turn an unrelated PR red;

# S2b — kit lint at `error` in the portal and the CRM web, inside the required build jobs (S255)

Plan row S2b (guards G1-G9, G11, G19; ADR 0016 decision 7). The rules come from the vendored

## Decisions

# AA-994 — no internal issue IDs in user-visible text (portal + CRM web)

Standing rule (28/10/2026): no text a page renders carries an internal Linear ID (`AA-123`). IDs stay in code
comments, tests and commit text. Companion rule AA-998 (no "acc1/acc2/acc3" labels): neither app shows an account
label, so nothing changed for it here.

## Decisions

- **Guard by the TypeScript AST, not grep.** `portal/lib/noIssueIds.test.ts` (node:test) and
  `web/tests/noIssueIds.test.ts` (vitest) parse every runtime `.ts`/`.tsx` (tests and the vendored `app/_kit/core/`
  excluded) and check JSX text, string literals and template-literal parts against `\bAA-\d+\b`. Comments are trivia,
  not tokens, so they are never scanned; import/export module paths are skipped. A self-test proves the scanner sees
  JSX text, JSX attributes and template parts and ignores comments. It also asserts more than 50 files were scanned so
  a wrong root cannot pass silently.
- **Allow-list, each with a reason:** `lib/seal.ts` salt `"aa-crm-web/AA-935/v1"` (both apps; changing an HKDF salt
  invalidates every sealed session cookie), and in the web the `card` property of `lib/bff.ts` (the BFF allow-list
  review trail; the module is imported only by the route handler and server-side `lib/crmApi.ts`, never by a client
  component, and `card` is never in a response).
- **`data-card="AA-…"` attributes removed** (16 CRM pages, 3 components) and the `card` field of `lib/nav.ts` became a
  line comment, so no issue ID reaches the DOM at all. Nothing read those attributes (no unit or e2e test).

## Changed

- Portal: no user-visible hit existed; only the guard is added.
- CRM web: the attributes and the nav field above; `tests/routing.test.ts` and `tests/clients.test.ts` no longer
  assert the nav card (the clients test now asserts the section carries no issue ID).

## Should know

- Review follow-up (independent reviewer, S255): the CRM API is part of the same app, so it gets the rule too.
  `api/app/lifecycle/rules.py` `placeholder_map` now reports `enforced_by="crm_placeholder_purge"` (the job kind that
  really purges it, `app/jobs/kinds.py`; the value was the card ID, sent in the `/lifecycle` JSON and in the page's
  RSC props, though never rendered), and the `PORTAL_OTP_DEV_ECHO` settings error keeps its ID in a comment.
  New guard `api/tests/unit/test_no_issue_ids.py`: every string constant under `app/` (f-string parts included;
  docstrings and bare string statements excluded) must not match `\bAA-\d+\b`; no allow-list needed.
- Review follow-up: both TS guards' self-tests now run the real `visibleStrings()` on an in-memory sample (it takes
  optional source text), instead of a copy of the visitor, so breaking the scanner breaks its self-test.
- Review evidence: seeded `"Home (AA-123)"` in `web/lib/i18n.ts`, a template part and a `title=` in a web component,
  a string in a portal page, and an f-string in an API module: each guard went red naming the file and line; reverted
  → green. Web vitest 324/324, portal `npm test` 59/59, API unit 1977 passed, ruff clean, ESLint 0 errors in both
  apps, `tsc --noEmit` (web) clean, `next build` green for the CRM web and the portal.
