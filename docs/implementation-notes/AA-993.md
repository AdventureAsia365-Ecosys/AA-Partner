# AA-993 — slice V2: CRM api (AA-Partner) post-deploy verify workflow

Design: AA-Ecosys root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft, D3; slice
plan Phase A → V2) and the critic notes next to it (points 12, 13, 20). Same shape as the AA-CIS-App V1 slice
(`post-deploy-verify.yml`, `.github/scripts/post_deploy_verify.sh`, `.github/verify/cis.rows`, a `result` job).

## Decisions

- **One script for Booking and Partner.** `.github/scripts/post_deploy_verify.sh <app>` is byte-identical in
  AA-Booking (`booking`) and AA-Partner (`crm`); the app argument picks `.github/verify/<app>.rows` and the summary
  title. Everything app-specific (paths, schema prefix, service name) lives in the rows file and the workflow. The CIS
  script stays separate (it also checks the worker service and the job-runner worker rows). The root canonical copy +
  byte check (design D3, `tools/verify/`) is not part of this slice.
- **Concurrency** as in V1: dispatched runs share the job-level group `post-deploy-verify-crm`; the call from
  Deploy Dev gets `post-deploy-verify-crm-deploy-<run id>-<attempt>` (input `from_deploy`, `workflow_call` only),
  so a dispatch can never cancel the pending verify of a Deploy Dev run. Neither group is `deploy-dev`.
- **Required schema comes from the deployed commit**: the newest key of `REQUIRED_SCHEMA_VERSIONS` in
  `api/app/db.py` at `expected_sha` (a one-line `required_schema()` function in the workflow; a unit test runs it
  against the real `db.py` and compares with an AST read). The version comes from that commit's
  `.release-please-manifest.json`.
- **Expected image** = `<registry>/<ECR_REPOSITORY>:<sha>`, the exact string the build pushes. The registry comes
  from `aws-actions/amazon-ecr-login` in the verify job (the same output the build uses), so no account ID is written
  anywhere; the summary prints the tag only.
- **Rows format** `name|auth|METHOD path|expected HTTP|jq assertion`, the CIS V1 format. The CRM api has no admin secret for CI
  and its CI machine route (`/crm/ci/deploy-gate`) takes an OIDC token minted for `deploy-dev.yml` only, so
  `auth` must be `public` here (any other value is a red row).
- **No secrets.** The verify reads the same `dev` environment variables as Deploy Dev (`AWS_ROLE_ARN`, `AWS_REGION`,
  `ECR_REPOSITORY`, `ECS_CLUSTER`, `ECS_SERVICE`, `CRM_API_BASE_URL`) and assumes the deploy role (only
  `ecs:DescribeServices`, `ecs:DescribeTaskDefinition`, `ecr:GetAuthorizationToken` are used; all already granted).
  No Terraform/IAM change.

## Changed (vs. the brief and the design)

- **`config` fails instead of skipping.** It used to output `enabled=false` when `AWS_ROLE_ARN` is unset, which
  skipped every job and left the run green. Now it exits 1 with an `::error::`; `preflight`/`deploy` lose their
  `if:` (a failed `config` skips them), and `result` is red. This holds on every event, not only `push`.
- **Desired count 0 is red** (Q6: no automatic scale-up). The old smoke exited 0 with a warning at desired 0
  (`deploy-dev.yml` ~:196-199). The verify reports "desired count 0 (scaling Dev up is a separate approved step)".
  Consequence: while the service is scaled to 0, every Deploy Dev run is red. That is intended.
- **A missing base URL is red** (it skipped green before).
- **Schema check is `>=`, not `==`**: `/crm/health/ready` returns 200 only when every key the running code
  needs is registered; the row also requires `schema_version` = `crm-NNN` and its number >= the newest key of the
  deployed commit. The DB is often ahead of the code (MIG-4 applies migrations first), so an equality would go red
  on a healthy deploy. Readiness does not expose `git_sha` or the required key on 200, so the sha proof is `/health`.
- **ECS rollout checks are new**: service ACTIVE, running = desired, exactly one deployment, PRIMARY
  `rolloutState == COMPLETED` (the service has the deployment circuit breaker, so a rollback shows `FAILED`).
- The D1 "released on shutdown" count is not printed: the endpoint does not exist yet (slice G1).

## Tradeoffs

- One verify job (one OIDC sign-in, one summary table) instead of separate ECS / HTTP jobs.
- PATH-stub tests (fake `curl` and `aws` reading fixture JSON): the script under test is exactly what CI runs.
- The workflow structure is tested as text (the repo has no YAML parser in its test deps); the `config` and
  `result` shell bodies are extracted and executed with the inputs GitHub would pass.
- 3 tries, 10 s apart per check (`VERIFY_TRIES`, `VERIFY_RETRY_DELAY`) after an initial 10 s: a real failure costs
  ~30 s, a slow first request after the roll does not turn the deploy red.
- `result` is red for any non-`success` need on every event (the design asks this for `push`); no job in Deploy Dev
  is conditional any more, so a skip always means something did not run.

## Should know

- Read the **Deploy Dev result** job: `verify` is skipped when `deploy` fails, and GitHub shows a skipped job grey.
- No existing test asserted the removed smoke step; `test_deploy_preflight_script.py` (reads the `preflight`
  block) and `test_portal_guards.py` (no `portal/` in `deploy-dev.yml`) still pass.
- Out of scope here: `deploy-web-dev.yml` and `deploy-portal-dev.yml` keep their inline smoke (slice V3).
- `/crm/health*` carry the public rate limit (ADR 0010 decision 2); a verify makes at most 6 calls (2 rows x 3
  tries), far below it. The verify runs on `ubuntu-latest` (only `curl`/`jq`/`aws`; the arm runner is for the build).
- Pushes that change only the verify files (`post-deploy-verify.yml`, the script, `crm.rows`) do not trigger
  Deploy Dev (push paths unchanged); dispatch `Post-deploy verify` to exercise them. This PR changes `deploy-dev.yml`,
  so its merge runs a full Deploy Dev + verify.
- Review fixes (public logs): AWS error text in a row is scrubbed (`arn:aws…` -> `<arn>`, 12-digit numbers ->
  `<acct>`); an invalid `expected_sha` is never echoed (script, workflow, summary print `invalid`); the verify's
  `configure-aws-credentials` sets `mask-aws-account-id: true`; the deploy job prints task definitions as
  `family:revision` only. Tests: a describe-services error carrying an ARN/account stays out of stdout and the
  summary; `EXPECTED_SHA=not-a-sha-SENTINEL` is red and `SENTINEL` is printed nowhere.
- actionlint 1.7.12 and shellcheck (`-S warning`) pass on the new/changed workflow files and the script.
- Live proof (orchestrator): (1) the push-triggered Deploy Dev after merge shows `Post-deploy verify` green with the
  table (ecs-rollout, ecs-image, health, health-ready) and `Deploy Dev result` green; (2) a `Post-deploy verify`
  dispatch with `expected_sha=<previous main sha>` goes red on `health` and `ecs-image`; (3) the dispatch does not
  cancel or replace a pending Deploy Dev run.

# AA-993 — slice H1: pre-push hooks (local only) — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md`, D5 and Phase B → H1. Files:
`scripts/pre-push.sh`, `scripts/install-hooks.sh`, `.githooks/pre-push`, a paragraph in `README.md` (Run the tests).
No workflow file changes (H2 makes CI call the script). Same shape as the AA-Booking H1 script (after its review
fixes); the hook and the installer are the Booking files with the repo name changed.

## Decisions

- **Commands come from the current workflows**, each failure printed with its CI job/step and the exact command:
  `ci.yml` Lint (`ruff check .`, `ruff format --check .` in `api/`; the ruff version must equal the
  `api/requirements-dev.txt` pin, 0.16.9), Security Audit (`check_resource_ids.py` always; `pip-audit==2.10.1` on
  both requirement files when one of them changed; `npm audit --audit-level=high` in `web/` / `portal/` when that
  app's `package.json` or lockfile changed), Unit Tests, Docker Build Check's `check_trivyignore.py` (when
  `.trivyignore` or the checker changed), Web Build (`npm test`; the type check as `npm run typecheck`, never
  `npm run build`), Portal Build (`npx tsc --noEmit -p .`, `npm test`; never `next build`), Portal Lint, the e2e
  `npx tsc --noEmit` of `ui-smoke-portal.yml` (when `e2e/` changed), and `docs-lint.yml` (front-matter, ADR index,
  single-line AWS CLI, lychee offline; the tools' unit tests when `tools/docs/` changed).
- **Portal Lint only warns.** In CI it is non-required with `continue-on-error` (pre-existing errors came with the
  portal, AA-885/AA-979). Fast mode runs `npx eslint` on the changed portal `.ts/.tsx/.js/.jsx/.mjs` files only;
  `--full` / `--ci` run `npm run lint`. A failure (or a missing `portal/node_modules`) is a warning line, never a
  block.
- **Fast mode** (default) plans from `git -c core.quotePath=false diff --name-only -z origin/main...HEAD`
  (`AA_PREPUSH_BASE` overrides; no base ref, or a diff git cannot compute → every check). Unit tests (one serial
  `ENVIRONMENT=test` run, no coverage): the changed test files; `test_<stem>.py` / `test_<stem>_*.py` of a changed
  module; the tests importing it; the tests whose text names a changed file by basename (workflows, `.github`
  scripts, `.github/verify` rows, migrations read by name, `web/` and `portal/` files, scripts loaded by path); for
  any `api/app/*` change, the guards that walk `app/` (a line with `APP` and `rglob`: code rules, payload guard,
  reveal boundary, vault rules, mail send) plus `test_route_guard.py`; for any `portal/*` change, the portal guards
  (a line with `PORTAL` and `rglob`); plus the unit test files in pytest's `lastfailed` cache that still exist.
  `api/tests/__init__.py` and the other test package markers select nothing (import matching would pick the whole
  suite). Shared helpers (`tests/unit/fakes.py`, `slice_fakes.py`, `vault_fakes.py`, `tests/tokens.py`,
  `tests/aa_fakes.py`) select their importers. A change to `requirements*.txt`, `pyproject.toml` or a `conftest.py`
  runs the targeted selection and prints a warning naming `AA_PREPUSH=full` (the whole suite is ~2 min in CI).
- A migration change also prints that the catalogue guard, RLS and re-apply checks are CI Integration Tests
  (PostgreSQL), not run locally.
- A change to the hook files plans `hook-self-test` (0.1 s). A diff that deletes or renames a file plans
  `docs-links` (a moved link target breaks lychee).
- **`--full` / `AA_PREPUSH=full`** runs every local check, the unit step being the exact CI command
  (`ENVIRONMENT=test COVERAGE_CORE=sysmon pytest tests/unit -v --tb=short --cov=app --cov-report=term-missing
  --cov-fail-under=90`). **`--ci`** (reserved for H2) is `--full` that never looks at the diff and treats a missing
  lychee as a failure. Neither plans `e2e-typecheck` (CI runs it only in the portal UI smoke).
- **`--self-test`**: the planner on 29 fixture diffs, the unit_all warning, the ESLint target filter, the unit-test
  selection on a fixture tree (13 cases), the diff reader on a scratch git repo (non-ASCII and spaced names, a
  failing diff, deletes/renames) and the hook in that repo with stdin push lines and a stub `scripts/pre-push.sh`
  (another sha exits 1, delete-only exits 0, an annotated tag on HEAD and HEAD itself reach the checks with
  `--from-hook`, a dirty tracked file exits 1 before any check); no CI tool is invoked. `--plan` prints the checks a
  push would run.
- **Tool lookup:** `AA_PREPUSH_VENV`, then `api/.venv`, then the main checkout's `api/.venv` (via
  `git rev-parse --git-common-dir`, so worktrees reuse it), then `python3`; tools run as `python -m ruff|pytest|
  pip_audit`. A missing env, a wrong ruff or pip-audit version, missing pytest-cov for `unit-full`, a Python without
  jsonschema + PyYAML for the front-matter check, or a missing `web/`, `portal/` or `e2e/node_modules` fails that
  check with the install command (blocks rather than passing silently). Every check runs even after one fails.
- The hook refuses (exit 1) a push whose pushed commit is not `HEAD` (the checks read HEAD and the working tree);
  a delete-only push is skipped; an annotated tag is compared through its commit.
- **A dirty tree blocks a hook run.** The hook calls `scripts/pre-push.sh --from-hook`; with `--from-hook`, any
  tracked file that differs from HEAD (`git status --porcelain --untracked-files=no`) stops the push before any
  check: "tracked files differ from HEAD; commit or stash them (git stash), or git push --no-verify". Otherwise a
  committed ruff or test error fixed only in an uncommitted edit would pass (the checks read the working tree, the
  push sends HEAD). Manual runs keep the `note:` line only. Untracked files do not count (they are not in either).
- **`docs/contracts/`** (the vendored `tenant.membership.v1` contract and samples) plans the unit tests as well as
  docs lint: `test_cis_contract.py` pins the contract's sha256 and reads the samples, `test_ops_e2e_staff.py` reads
  the samples. They read the folder, not file names, so the selection is the tests whose text has `"contracts"` or
  `docs/contracts`. The root `.vercelignore` plans unit (`test_portal_guards.py` reads it by name).
- **`set -uo pipefail`, no `-e`, on purpose**: every planned check runs and each failure (a non-zero step or a
  missing tool) is collected in `FAILED`; a non-empty `FAILED` exits 1. `-e` would stop at the first failure and
  hide the rest.
- The failure summary stores `id`, dir, command and CI step joined with the ASCII unit separator (`\x1f`), not `|`,
  because the docs-links command contains a pipe.
- A local lychee other than 0.24.2 (the CI version) adds a warning, as ruff and pip-audit versions are checked.

## Changed (vs. the design)

- Not run locally (CI only): Integration Tests (PostgreSQL), the API / Web / Portal Docker Build Checks, Trivy, SBOM,
  the web standalone smoke, Vendored CIS copies (network), gitleaks, PR title, `next build`.
- The design lists `npm run lint` for every frontend; the web has no lint script, and Portal Lint is non-required,
  hence warn-only (above). The design's "+ `npm test` where present" is followed: `web-test` and `portal-test`.
- The aa-ship note (install, bypass) belongs to the root repo and is not in this change.

## Tradeoffs

- Basename and import matching can miss a test that reaches a module indirectly; `--full` and CI still run all.
  Over-selecting is cheap (13 files / 296 tests for a one-line change to `app/db.py`).
- A frontend-only push still needs the api Python env, because the portal guards and the tests that read web/portal
  files are pytest tests.

## Should know

- Install once per clone: `scripts/install-hooks.sh` (not run on the workspace clone by this change: it sets
  `core.hooksPath` for the clone and every worktree). Undo: `git config --unset core.hooksPath`. Skip once: push
  with `--no-verify`. The installer was tried on a scratch repo: it sets `.githooks` and lists the existing
  non-sample hooks that stop running.
- Checks (27/10/2026): shellcheck 0.11.0 `-S warning` clean on the three files (one SC2016 info, intended: `$0`
  expands inside `bash -c`); `bash -n` clean; `--self-test` 43/43 in 0.1 s (52/52 after the review fixes). `--plan` with a bad base
  (`HEAD^{tree}`) prints `cannot diff`, switches to full mode. The hook fed a push line for another branch exits 1
  with the HEAD message; a delete-only line exits 0.
- Planted error: a new `api/app/prepush_demo.py` with `ruff format` drift, committed, the hook fed one push line:
  `ruff-format` FAILED, exit 1; the summary printed `CI: ci.yml / Lint / ruff format --check`,
  `(cd api && ruff format --check .)` and the `--no-verify` bypass; the app guards (6 files, 109 tests) ran green;
  wall 13.2 s, peak RSS 189 MB. Commit and file reverted.
- Timing on a one-line diff to `api/app/db.py` (fast mode): resource IDs 1 s, ruff 0 s, 13 selected unit test files
  (296 tests) 16 s, docs 1 s; wall 17.8 s, peak RSS 190 MB (target ≤ 90 s). The probe line (a trailing comment) also
  tripped `ruff format --check`, as in Booking.
- lychee is not installed on this machine: `docs-links` was a warning (it is a failure only in `--ci`).
- For H2: `--ci` plans the web/portal checks (needs their `node_modules`) and the docs checks (needs lychee and the
  tools/docs requirements); the CI Lint and Unit jobs have neither, so H2 needs per-job check selection (for
  example `--ci --only lint,unit`) rather than one `--ci` call.

# AA-993 — slice V3: CRM web + Content studio post-deploy verify — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` D3 and Phase A → V3, critic point 13
(`target` only under `workflow_dispatch`; a missing `E2E_TENANT_API_KEY` skips instead of failing). Same shape as V2
in this repo (`post-deploy-verify.yml`, `.github/scripts/post_deploy_verify.sh`, a `result` job).

## Decisions

- **One verify workflow for the three services.** `post-deploy-verify.yml` gains an `app` input (`crm` default,
  `crm-web`, `crm-portal`; a choice on dispatch). A "Resolve the app" step maps it to the ECR repository, ECS service
  and base URL from the same `dev` variables and defaults the deploy workflows read, and refuses any other value.
  `deploy-dev.yml` passes no `app`, so the api verify is unchanged. Concurrency: `post-deploy-verify-<app>` for
  dispatches, `post-deploy-verify-<app>-deploy-<run>-<attempt>` for deploy calls (V2's rule, per app).
- **The shared script is untouched** (`post_deploy_verify.sh` stays byte-identical to AA-Booking's). New rows files
  `.github/verify/crm-web.rows` and `crm-portal.rows`; `REQUIRED_SCHEMA` is still computed (the script requires it) but
  no web/portal row uses `$required`.
- **What a row cannot express goes to a second, small script**: `.github/scripts/edge_verify.sh <crm-web|crm-portal>`
  (redirect `Location`, a page's linked asset), same retry/summary style. It runs after the rows step with
  `!cancelled()`, so the job summary always shows both tables.
- **The studio's commit is read at `/api/healthz`**, a new route with the `/healthz` body (`portal/lib/health.ts`,
  shared by both routes). Reason: on the agency host the ALB sends `/healthz` to the CRM web (only `/portal*`, `/api/*`,
  `/tenant-login*`, legal pages and `/assets/*` reach the studio), which is why the old smoke never checked the
  studio's sha. `/api/*` goes through the proxy's Host guard and nothing else (BFF routes answer for themselves).
- **The web's API rows check routing and readiness, not the API's commit.** The brief says "/crm/health +
  /crm/health/ready report the deployed git_sha / expected version"; a web deploy does not deploy the API (its own
  verify, `crm.rows`, compares the sha), and a web-only push leaves the API on an older commit, so a sha/version
  comparison there would make every web-only deploy red. `api-health` requires 200 + `service == "aa-crm-api"`
  (the host's API rule above the web default); `api-ready` requires 200 + `status`/`db` ok. Neither compares the
  schema key with the web commit's: web and api deploys of one push run in parallel.
- **Pinning (`resolve_via`).** Optional in both the verify and the smoke. The portal deploy passes
  `vars.CRM_AGENCY_CF_DOMAIN` through a `deploy` job output (a job that calls a reusable workflow cannot read
  environment variables): empty = DNS (the normal state since the S253 cutover); set = the host is pinned to the
  agency distribution in `/etc/hosts`, which keeps the checks on the Fargate studio during a rollback to Vercel (the
  same behaviour as the old `curl --connect-to`).
- **`ui-smoke-portal.yml`**: `target`, `resolve_via` and a new boolean `require_tenant_key` on `workflow_call`
  (and `require_tenant_key` on dispatch). With it, the smoke step exits 1 before Playwright when the key is empty.
  The preview caller (`vercel-deploy-portal.yml`) is unchanged: its logged-in tests still skip without the key.
  The deploy passes only `E2E_TENANT_API_KEY` (no Vercel bypass, never `inherit`) and grants `pull-requests: write`
  on the smoke job (the called workflow comments on the PR).
- **PR comment per target**: the Fargate smoke uses its own marker (`ui-smoke-report-portal-fargate`) so it never
  overwrites the preview's result on the merged PR.

## Changed (vs. the brief and the design)

- **`config` fails instead of skipping** in both deploys (as V2 did for Deploy Dev): `CRM_WEB_ENABLED` /
  `CRM_PORTAL_ENABLED` not `true` or `AWS_ROLE_ARN` unset is red on every event; `deploy` lost its `if:`.
- **Desired count 0 is red** for web and portal (it skipped green with a warning).
- The `/crm/health` 503 tolerance of the old smokes ("API at desired 0 is not this deploy's concern") is gone: an API
  that is down or not ready makes the web/portal verify red too (design red rule "ready != 200").
- Deploy logs print task definitions as `family:revision` (V2 did this for the api; the full ARN names the account).
- `ui-smoke-portal.yml` concurrency group now includes `github.workflow` (the caller's name in a call): a
  hand-dispatched smoke on `https://portal.lumiguides.it.com` can no longer cancel a Deploy Portal Dev smoke.
- One small app change (the `/api/healthz` route + `lib/health.ts`), which the brief did not anticipate (above).

## Tradeoffs

- One parameterized verify workflow vs. three copies: one place for the OIDC/ECR/expected-commit logic; the price is
  a resolve step and longer `if:`/group expressions.
- A second script (`edge_verify.sh`) instead of extending the shared one: keeps the Booking byte copy intact.
- `/tenant-login` 200 is still a check (as before): it holds while `PORTAL_API_KEY_SIGNIN` is on. The §4.5 cleanup
  (from 03/11/2026, flag off → 307 to the web sign-in) must change `edge_verify.sh` (e.g. read the asset from `/terms`)
  in the same PR.
- The smoke `needs: [deploy, verify]`: a red verify skips the smoke (and `result` is red); a full Playwright run
  against a service known to be wrong would add nothing.

## Should know

- Required PR check names are unchanged (no `ci.yml` change). New deploy check names: **Deploy Web Dev result**,
  **Deploy Portal Dev result**, `verify / Post-deploy verify`, `smoke / UI smoke portal (Playwright)`.
- Tests: `api/tests/unit/test_post_deploy_verify_web_portal.py` (new; rows with the real rows files, `edge_verify.sh`
  with a stub curl that answers `%{redirect_url}`, the resolve step per app, config/result scripts of both deploys,
  the smoke step's key check with a stub `npx`); `test_post_deploy_verify.py` and `test_portal_guards.py` adjusted
  (group expression, the script argument, `--connect-to` replaced by the verify/smoke wiring); `portal/lib/health.test.ts`.
- Local checks (27/10/2026): pytest 213 passed (the four verify/guard/preflight files); ruff check + format clean;
  `node --test lib/health.test.ts` 2/2; actionlint 1.7.12 (with shellcheck 0.11.0) clean on the six workflow files
  touched or calling them; shellcheck `-S warning` clean on `edge_verify.sh` (SC2329 info only: functions called
  through `retry`); `check_resource_ids.py` 0 findings. No build, no Playwright run locally.
- Pushes that change only `post-deploy-verify.yml`, the rows, the scripts or `ui-smoke-portal.yml` deploy nothing;
  this PR changes both deploy workflows and `portal/`, so its merge runs Deploy Web Dev and Deploy Portal Dev with the
  new verify (and the portal smoke).
- Live proof (orchestrator): see the PR body / the lane report (green deploy runs, wrong-sha dispatches red, the

## Slice G5: the deploy gate blocks only on a running `crm_dispatch` — 28/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft D1.3-D1.4, Phase C → G5)
and critic point 8. G4 part 1 (uvicorn `--timeout-graceful-shutdown 5`, #98) is merged.

### Decisions

- **`DEPLOY_BLOCKING_KINDS = {crm_dispatch}`** (`app/jobs/kinds.py`): the provider send runs inside the row-lock
  transaction (`app/dispatch/worker.py`), and the providers take no idempotency key, so a release after the send
  re-sends on the re-claim. It stays blocking until G4b ships the committed `crm.dispatch_attempt` marker (critic 8);
  removing it from the set is part of G4b.
- **Gate** (`app/routers/ci.py`): `safe_to_deploy = no RUNNING row and no due QUEUED row of DEPLOY_BLOCKING_KINDS`
  (`queue.blocking_count`). New fields `blocking_kinds`, `blocking_running`, `blocking_due`, `blocked_by`; `active` / `by_status` / `by_kind` / `exempt_kinds` unchanged.
  The CRM does not read CIS rerun waves (design Q4).
- **Preflight script**: same message change as Booking (safe → re-claimed count; blocked → `blocked_by` + by-kind).
- **Due queued dispatches block too** (review follow-up; the first commit let a queued dispatch through, as the
  design words it). The preflight runs before the image build + push, and the old task keeps claiming until its
  SIGTERM minutes later: a dispatch queued inside its 10 s undo delay would be claimed by the old task and could be cut
  mid-send. So a queued `crm_dispatch` due within `kinds.DEPLOY_BLOCKING_HORIZON_SECONDS` = 900 s counts as
  `blocking_due`; one due later (a retry backoff, ≤ 900 s) waits for whichever task is live. Same rule as CIS and
  Booking. Cost: a deploy waits a few seconds to minutes while messages are being sent.
- **Workflow text** (`deploy-dev.yml`): header comment, `override_running_jobs` description and the preflight step
  name now say the guard blocks only on a running or due `crm_dispatch` (review follow-up).

### Changed (vs. the design)

- `DEPLOY_BLOCKING_KINDS` was planned in G4; it ships here with the gate that reads it.
- **Order / no Partner drain proof.** The design ships the relaxation "only after G1–G4 are live". For the CRM, G4
  part 1 (uvicorn graceful shutdown) is merged, but no live drain proof is planned: every kind except `crm_dispatch`
  now relies on the worker's release-on-shutdown path, proven by unit and integration tests only. A short live proof
  for the orchestrator, before relying on the new gate: queue an ordinary job that runs for a while (for example a
  `crm_job_retention` dry run, or the next `crm_booking_sync` slot), dispatch Deploy Dev while it runs, then read the
  row with AA-CIS-Infra `db/scripts/aa993_g4_bk_noop_report.py`-style SQL (`crm.job`: `progress.releases` ≥ 1, ended
  `succeeded` on the new task). If that is skipped, the relaxation ships without a live drain proof (recorded here).

### Tradeoffs

- Due-queued horizon 15 min, not "until the old task is gone": a dispatch due later than that but before a slow roll
  finishes could still be claimed by the old task. Accepted: dispatches are due at once or after 10 s, and the retry
  backoff is capped at 900 s.
- Every other CRM kind is treated as re-run safe (the worker contract: "every handler is idempotent"). `crm_offboard`
  erase runs in one transaction (a release rolls it back; the re-run starts over); `crm_audit_export` writes
  per-hour objects under Object Lock with a manifest chain and re-runs an hour it did not finish.

### Should know

- Tests: `tests/unit/test_deploy_gate.py` (`blocking_count`; queued/running ordinary jobs → safe; running
  `crm_dispatch` → unsafe; due queued dispatch → unsafe; dispatch queued past the horizon → safe; the blocking set),
  `tests/unit/test_deploy_preflight_script.py` (new messages, older API without `blocked_by`),
  `tests/integration/test_job_runner.py::test_deploy_gate_blockers_are_running_or_due_dispatch_rows` (real `crm.job`
  SQL: queued past the horizon, succeeded and a running other kind → `{}`; one running + one due dispatch → counted;
  CI only — locally the same query was checked against a Postgres scratch copy of the job template table, rolled
  back). Review follow-up: 89 gate/preflight unit tests passed, `ruff check` + `ruff format --check` clean. Local: unit suite 1945 passed; `ruff check` + `ruff format --check`
  clean.
- The CRM API service must run ≥ 1 task (`runningCount`) when the proof Deploy Dev is dispatched; with 0 tasks the
  preflight skips the gate ("no task running, pending or desired — gate skipped") and goes green falsely. The
  preflight log must show the `GET .../crm/ci/deploy-gate -> 200` line and `blocked_by`.
- Live proof (orchestrator): with a `crm_dispatch` row running (seed one through the CRM test agency, or set a queued
  row `running` with a future lease via DB Migrate run-script, then restore it), `GET /crm/ci/deploy-gate` answers
  `safe_to_deploy: false`, `blocked_by: ["1 crm_dispatch job(s) running (deploy-blocking kind)"]`, and a dispatched
  Deploy Dev preflight is red; with only the heartbeat / pulls / any other kind queued or running it passes.

## Slice G4b: the `crm_dispatch` send marker (`crm.dispatch_attempt`, crm-023) — 28/10/2026 (S255)

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` §2 "G4b" and Q9 ("the marker, not an
idempotency key"); critic point 8. Root companion: the DM-7 retention row for `crm.dispatch_attempt` and the
`schema-ownership.md` note (root branch `docs/aa-993-g4b-dispatch-attempt-retention`), merged before the Infra copy
(`db/check_retention_rows.py` fails the copy without it).

### Decisions

- **Two transactions in `app/dispatch/worker.py`.** tx1: lock the row, gate it, insert one `crm.dispatch_attempt`
  (`job_attempt`), commit. tx2: lock the row again, call the sender, then decide the row **and** close the attempt with
  the sender's code in the same transaction. The sender's own writes (message `sent`, rotated credential) stay atomic
  with the decision, exactly as before; only the marker moved ahead of the provider call.
- **Open attempt found → `held` / `send_uncertain`**, message `failed` / `send_uncertain`, attempt closed
  `send_uncertain`, one audit event (`allowed`, reason `send_uncertain`). This check runs **before** the gate: an
  uncertain send stays reported as uncertain even if the client was archived since.
- **Cancel before the sender was called → attempt closed `not_sent`** in a shielded transaction of its own
  (`_close_alone`, best effort), so the re-claimed job sends. "Called" means the worker entered `sender.send()`; a
  cancel during the sender's own reads (before the provider) is treated as "maybe sent" — conservative.
- **Sender raised (not cancelled) → attempt closed `retry`** in tx2 (committed), then the exception is re-raised for
  the job's backoff, so retries keep working as before. On the last attempt the row drops `send_failed` as before and
  the attempt closes `send_failed`.
- **Row changed between tx1 and tx2** (Undo, archived, trashed, consent withdrawn): attempt closed `not_sent`, row
  skipped or dropped by the gate as before.
- **`DEPLOY_BLOCKING_KINDS = frozenset()`** (`app/jobs/kinds.py`). The gate mechanism, `blocking_count` and the preflight
  stay for a future kind; the tests keep exercising them with an explicit `{crm_dispatch}` set.
- **Readiness** requires `crm-023` (`app/db.py`): the code reads and writes the table.
- **Table shape:** base template (trash columns, `set_updated_at`, FORCE RLS, tenant policy); outcome column named
  `outcome` (not `status`, which would need the status-transition trigger); partial unique index
  `dispatch_attempt_open_uq` (one open attempt per row); `crm.guard_dispatch_attempt()` seals a closed attempt (CRM38);
  `crm_app` gets SELECT, INSERT and column UPDATE (`decided_at`, `outcome`) only; FK to `crm.dispatch_queue
  (dispatch_id)` with no ON DELETE action (crm-019 rule), so `crm.erase_subject` deletes attempts before dispatch rows
  in the trip, traveller and agency scopes.

### Changed (vs. the design)

- **Contract, not expand.** The design calls crm-023 an expand migration. Two parts change pre-existing objects:
  `dispatch_queue_gate_chk` gets `send_uncertain` (the design's own decision code), and `crm.erase_subject` must name
  the new tenant table (the catalogue test `test_the_agency_erase_knows_every_tenant_table` and the CRM16 runtime guard
  refuse an unknown tenant table). Under ADR 0017 §3 both are contract, and the runner on Infra `main` does not know
  `-- migrate: expand` yet (M2a), so the file has no header and ships MIG-4 style: migration PR → Infra copy → manual
  DB Migrate apply → code PR. The design placed G4b "after M4"; this does it before M4 through the old flow.
- **Message state for an uncertain send:** `failed` with `failure_code = send_uncertain` (no new message status;
  the crm-015 check already allows any `[a-z_]` code with `failed`). The agent sees the failed chip; the code tells
  "check your Sent folder before sending again". A dedicated UI label is a follow-up, not built.

### Tradeoffs

- A send that raised (timeout after the provider accepted) is still retried, as before G4b: the marker targets the
  cancel / crash window, not ambiguous provider errors.
- A hard crash between tx1's commit and the sender call leaves an open attempt, so the re-run holds the row
  `send_uncertain` although nothing went out. Rare (no await of note in between) and safe-side.
- The shutdown path normally never cuts a send: the lifespan waits `WORKER_STOP_TIMEOUT_S` (20 s) for the running job
  and a dispatch takes seconds. `send_uncertain` is the backstop for a stop that times out or a crash.
- Test fragility found: `test_crm_migrations::test_reapply_is_a_no_op` re-applies every file, and crm-015's
  DROP + ADD of `dispatch_queue_gate_chk` (without `send_uncertain`) fails on any `send_uncertain` row. The crm-023
  tests therefore roll back or erase their `send_uncertain` rows. Production never re-applies a registered key.

### Should know

- Commits: (1) the migration + `tests/integration/test_crm023_schema.py` + the CONTEXT row (the migration-only PR);
  (2) the worker, the blocking set, readiness, docs and the worker tests. The code PR merges only after crm-023 is
  applied on Dev (readiness would report it missing otherwise).
- Infra checks run locally on the file: `run_migration.py --inspect` (no errors, no warnings),
  `check_migration_files.py` (0 problems), `check_retention_rows.py` (0 without a row once the root row is in).
- Tests: `tests/unit/test_dispatch_marker.py` (stateful fake: order of writes, cancel after send → one send +
  `send_uncertain`, cancel before send → resend, retry, last attempt, row changed in between, open attempt wins over
  the gate, best-effort close, the blocking set), `tests/integration/test_crm023_schema.py` (registration + re-run,
  privileges, open-unique, CRM38, RLS, gate code, trip and agency erase), `tests/integration/test_dispatch_marker_db.py`
  (real two transactions, real `MailSender`, fake provider: both design cases), `test_deploy_gate.py` /
  `test_job_runner.py` adjusted to the empty set. Local (28/10/2026, PostgreSQL 16 scratch cluster): unit 1975+ passed,
  integration 530 passed (full suite), ruff check + format clean.

  E2E mail target and dispatch Deploy Dev while it is due; exactly one message arrives, and
  `GET /crm/ci/deploy-gate` answers `blocking_kinds: []`.
