# AA-1025 slice H1c (S265 lane l1-h1bc): the CRM app profile

Plan: root `docs/audits/2026-11-01-S263-gateway-gap-audit/plan.md` row H1 (H1a = CIS table + admin, CIS 345; H1b =
TripPlanner; this slice = the CRM, "the same shape"). Root ADR 0009 §4, root ADR 0008a §6. $0: no provider call.

## Decisions

- **The profile lives in `crm`, written over crm.ops.v1.** ADR 0008a §6: the CRM reads no `shared.llm_*` table and
  holds no grant outside `crm`, so it cannot read CIS's `shared.llm_app_profile` row. `crm.llm_app_profile` (crm-041)
  holds the same fields; the CIS admin relays its edit of the `crm` row to `PUT /crm/ops/v1/llm/app-profile` with the
  staff member's own WORKFORCE token (the L1 console pattern of AA-941, no new secret or M2M client). CIS writes the
  CRM first and its own row only when the CRM said 200, so a refused relay changes nothing.
- **The whole profile per PUT**, not a patch: CIS sends its row after the edit, the CRM replaces its row. Simple to
  reason about; two admins editing at once is last-write-wins on both sides, like the CIS PATCH.
- **No seed row; no row = AI on, no daily budget** (the CIS rule). The first PUT inserts it.
- **crm-041 is contract**: the schema's default privileges (crm-001) give `crm_app` DELETE on every new table, and a
  deleted row would switch AI back on (the CIS 345 review point), so the file REVOKEs ALL first; REVOKE is refused by
  the expand lint. MIG-4: migration-only PR, Infra copy, Migration Apply, then this code PR (raises readiness to
  crm-041).
- **Where the gateway checks it**: right after the stage profile read (so the refused row names the route's first
  model) and before the stage profile's own refusals, the rate cap, the budget lock and the scrub. AI off wins over
  every other refusal; nothing is scrubbed or sent.
- **Refusal codes** `app_disabled` (error class `disabled`) and `app_budget_exhausted` (class `budget`); an unreadable
  day spend is `spend_unreadable` (fail closed, like the agency budget). The ledger's refusal CHECK allows any
  `^[a-z][a-z0-9_]{0,39}$` code, so no ledger migration. The web maps them to the existing "AI paused" / "budget"
  fallback lines.
- **The daily budget is every agency together**, from the platform rollup `crm.llm_usage_daily` (guardrail rows
  included), today UTC. It is on top of each agency's monthly budget, not instead of it.
- **The profile read fails open** (missing table, read error, no row = defaults), in a savepoint so the call's
  transaction stays usable. A database that cannot be read also fails the stage profile read, which fails closed.
- **No agency audit event for the PUT**: it is a platform setting, not an agency's data (like `/data-coverage`). The
  CIS audit row (`llm_app_ai_switched_off` / `_on` / `llm_app_profile_updated`) and the row's `updated_by`
  (`platform:<staff sub>`) are the record. `updated_by` is not returned (a staff id).
- **The CRM's daily budget signal is a CRM-side ops e-mail** (fix pass after review: the plan's H1 row wants the CRM
  signal heard, and a refusal that only logs `crm_llm_app_budget_refused` reaches nobody). The job sampler (every 5
  minutes, `app/jobs/metrics.py`) reads the profile's budget and today's `crm.llm_usage_daily` total in one statement
  (`app_profile.read_day_spend`) and `ops_alerts.spend_findings` raises `llm_app_spend_near` at 80 % and
  `llm_app_spend_cap` at 100 % (the shared core's `budget.threshold`, the thresholds `budget.decide` uses). Two checks
  so a cap reached after the near e-mail still mails; one e-mail per check and UTC day (the existing `crm.job` ledger
  dedupe), on the platform alerts SNS topic, which is the topic of the CIS ops e-mail: the same people hear it.
  A budget of 0 counts as reached at once, as in the CIS TripPlanner check.
- **Not on the CIS bell.** CIS's ops checks run without a staff token and the CRM's ops API takes only staff tokens
  (ADR 0008a: CIS does not read `crm.*`); a bell would need an M2M client for crm.ops.v1 (Cognito + Terraform), a
  separate decision. E-mail alone is the CRM's existing alert channel for every other ops check, so the
  CRM signal follows it. Recorded in the plan's H1 row (root PR).

## Tradeoffs

- One extra SELECT per AI call (a one-row table), plus one rollup sum when a daily budget is set. CRM AI volumes are
  small; no cache, so a switch takes effect on the next call.
- The daily budget is checked before the call with today's spend, not the call's estimate: a burst can pass it by
  the cost of the calls in flight (calls of one agency are serialised by its budget lock, calls of different agencies
  are not). Loose by design: it is an app ceiling, the agency budget is the tenant's own stop.
