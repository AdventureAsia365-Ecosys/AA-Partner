# AA-964 — CRM-33a AI gateway + drafts + guardrails (slice B3 of the S262 gateway plan)

Two PRs in this repo, in MIG-4 order (crm-032 is a contract file):

1. `feat/s262-aa964-crm-032-llm-call-v2`: migration only (`api/migrations/032_crm_llm_call_v2.sql`, its integration
   test, the CONTEXT.md table row). Merge, let the Migration Sync bot copy it to AA-CIS-Infra, run DB Migrate `apply`,
   merge the `bot/db-schema-reference` PR.
2. `feat/s262-aa964-crm-ai-gateway`: the code (adds `crm-032` to `REQUIRED_SCHEMA_VERSIONS`), merged only after (1) is
   applied on Dev.

## Decisions

- **crm-032 is contract, not expand.** It replaces `llm_call_role_chk`, adds CHECKs on existing tables and adds
  columns to a ledger (a hot table in Infra `owners.yaml`). ADR 0017 d3 makes each of those contract, so no
  `-- migrate: expand` header and the code ships in a second PR.
- **Column names follow CIS 319** (`attempt_no`, `request_id`, `connection_key`, `deployment_wire_id`,
  `cache_read_tokens`, `cache_write_tokens`, `units`, `unit_kind`, `pricing_mode` with the same regex,
  `prompt_hash`, `prompt_version`, `is_shadow`, `is_experiment`), so the CIS Calls tab maps both ledgers with one
  column list. `outcome` stays the CRM's name for the CIS `status` (ok / refused / error); `crm.ops.v1 /llm/calls`
  serves it as `status`.
- **`app` is NOT NULL DEFAULT 'crm' with CHECK = 'crm'.** The CRM only writes its own rows; the default keeps every
  existing row and the pre-AA-964 INSERT valid.
- **`is_shadow` / `is_experiment` are NOT NULL DEFAULT false** (CIS has them nullable because it has years of rows
  without them; the CRM table holds a few rows and nothing ever wrote a shadow call).
- **`units` + `unit_kind` added** (not in the plan's column list, but the plan says the guard row records "units"):
  the guardrail bills text units (1 unit = up to 1000 characters), not tokens. Both or neither.
- **Budget alert state in `crm.tenant_settings`** (`ai_alert_month`, `ai_alert_pct`): the 75 / 90 / 100 % alert of R5
  must fire once per month and level, so the gateway needs to remember the highest level raised this month. A
  `crm.metric_event` (the bell) cannot hold it: that table needs a `trip_id`.
- No new index: `/llm/calls` reads per agency through `llm_call_tenant_at_idx (tenant_id, at DESC)`.

- **Gateway order** keeps root ADR 0008a §5 for everything that reaches the model (the PII filter always runs before
  the call), with checks moved in front of the paid scrub: rate cap -> stub-scrubber/real-provider check -> budget +
  `ai_enabled` under the per-agency lock -> scrub (guard rows) -> budget again if guard rows were written -> seal map ->
  call -> row. Review fix (S262): the budget used to be checked only after the scrub, so at 100 % every refused draft
  still paid `ApplyGuardrail` units (up to about 9 per draft) and spend kept growing past the budget; and any caller
  other than the draft endpoint paid a scrub before its `ai_disabled` refusal. Now a used-up month or AI switched off
  makes no guardrail call and writes no guard row. The draft endpoint still checks `ai_enabled` itself first (409).
- **Guardrail rows** come from a `ContextVar` collector (`app.privacy.guardrails.collect_guard_calls`) that the
  detector appends to: the detector has no DB context and is shared by the process. An attempt that fails or times out
  keeps an estimated unit count (`pricing_mode estimate`); AWS may bill it. Outside a collector (the corpus workflow)
  nothing is recorded. Price: USD 0.10 per 1000 text units (PII filter, AWS pricing page; re-check before Guardrails is
  switched on). The guard row's `connection_key` is `bedrock_guardrails`, its `model` / wire id `apply_guardrail`.
- **Guardrail down on acc2** (open item of the S261 capacity plan): fail closed, "reply by hand", log line
  `crm_scrub_unavailable` (an alarm can count it). No second guardrail in another account: that path would need its
  own corpus run before traveller text may reach it.
- **Prompt injection**: the client text goes inside `<client_message>` tags (a closing tag inside the text is broken
  up) under a fixed system instruction; the model gets no tools; the answer is a suggestion with
  `approval_required: true` and nothing is sent from the draft endpoint.
- **Budget**: owner may set 0 .. `AI_BUDGET_MAX_USD` (default 2 USD, the design's test cap); AA pays the calls, so an
  owner cannot raise it above the plan. The `ai_assist` entitlement (L1 "allow features") is **not** enforced yet: no
  other feature enforces `allowed_features` today and gating would need a crm-platform-admin write for every Dev
  check; follow-up when plans exist.
- **Provider prices come from the environment** (`CRM_LLM_USD_PER_MTOK_IN` / `_OUT`), and `app.settings` refuses
  `CRM_LLM_PROVIDER=bedrock` without them: a real model without a price would spend money the budget never sees.
- **Connection keys**: `stub`, `bedrock` (task role), `bedrock_role` (assumed CRM-only invoker role), never an account
  label or id.
- **Permissions**: new actions `ai_use` (every role: read the meter, ask for a draft) and `ai_settings` (owner).
- **`crm.ops.v1` 1.6 `GET /llm/calls`**: row-level, scrubbed fields only (ids, codes, numbers, the hash of the
  scrubbed prompt, the receipt's entity total; never the per-kind counts, the member, a prompt or an output), newest
  first across agencies through one `platform_tx` per agency, keyset cursor `<at>~<call id>`, at most 31 days / 500
  rows, one `ops_read` event (reason `llm_calls`) per agency whose rows were returned. `outcome` is served as
  `status`, the provider request id as `provider_request_id` (`request_id` already means a data request in this
  contract).

## Changed (vs. the plan text)

- Added `units` / `unit_kind` and the two `tenant_settings` columns (see Decisions).
- `reasoning_tokens` and `effort` (CIS 319) are left out: Bedrock Haiku drafts report neither today; a later key
  adds them if a model needs them.

- No draft UI in the trip workspace yet and no `ai_draft` table (R39 validation / feedback codes): the plan's B3 slice
  asks for the gateway, settings page and the draft endpoint; the BFF allow-list already has the draft route.
- The ops read is `GET /crm/ops/v1/llm/calls` (plan: "`crm.ops.v1` `GET /llm/calls`"); the root contract file
  `docs/contracts/crm.ops.v1.openapi.yaml` gets 1.6 in a root PR.

## Tradeoffs

- The per-agency budget lock is now taken before the scrub, so the scrub (at most the detector timeout, 3 s) runs
  inside it: calls of one agency wait for each other a little longer. Accepted: a second call at 99 % then sees the
  first call's guard rows and refuses before paying its own scrub. Without the lock the pre-check would race.
- The budget is read twice when the scrub wrote guard rows (before and after); the second read is what stops a call
  whose own guardrail cost took the month to 100 %. That last scrub is the only guardrail spend past the budget.

- Re-adding the CHECKs with `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT` (validated at once) keeps the file
  re-runnable without DO blocks; fine because `crm.llm_call` is tiny (180-day retention, a handful of rows on Dev).

- The cross-agency `/llm/calls` read opens one `platform_tx` per registered agency (like `/tenants` and
  `/data-coverage`): fine for tens of agencies; a platform rollup view would be the next step at hundreds.
- Two rows written in one transaction share `at = now()`; the keyset uses `(at, llm_call_id)` so paging stays stable.
