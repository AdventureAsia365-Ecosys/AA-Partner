## Decisions

- **Migration key crm-017, Guard 0 needs crm-016** (the brief assigns 017; `crm.erase_subject` / `crm.erase_held` are
  the crm-016 text plus this card's tables). SQLSTATEs from CRM33 (crm-016 ends at CRM32): CRM33
  `aa_request_invalid`, CRM34 `aa_tour_not_served`.
- **The M2M client reuses AA-978's `TokenProvider`** (one instance for the whole process, one cached token per scope):
  each Booking call asks for exactly its scope (`booking.b2b/read`, `/quote`, `/hold`, `/book`), the catalog for
  `cis.catalog/read`. The Cognito client already holds every scope (Infra `identity_m2m.tf`, AA-972 / AA-976 / AA-978),
  so **no Cognito, IAM or secret change**: the same `M2M_CLIENT` secret. The only Infra change is one environment
  variable, `BOOKING_API_URL` (the Booking API origin, `https://api-booking.<zone>`; paths `/booking/b2b/v1/...`), on
  the task definition. Monthly cost: none (no new resource; a few hundred extra token requests a month are within the
  M2M pool's free tier).
- **Lines from quote / hold / feed only.** An AA line is never typed by the agency:
  - the agent picks a served AA tour (catalog cache), a Booking component of it, a date, pax counts (adults, children,
    infants; rooms by occupancy; nights) and the quote currency, optionally the sell amount;
  - `crm.aa_line_request()` (SECURITY DEFINER, EXECUTE crm_app) creates the line as `planning` / `aa_sub_status
    pending`, its title taken **in SQL** from `crm.aa_catalog_tour` (never from the body), and the quote request in
    `crm.aa_request` in one statement; the guard (crm-014 3a) still refuses every crm_app write of an AA line, so the
    definer is the only member path, and it can only create a pending placeholder;
  - the job `crm_booking_sync` (actor `job:crm_booking_sync`) fills it from the quote (b2b price as cost, FX lock,
    validity, price hash, availability), the hold (hold id, expiry), the confirm (booking id, bk- trip case code as
    the confirmation number) and the feed (confirmed / declined / expired / cancelled);
  - edits stay 403 `aa_line_read_only` (route, crm-014 guard and money functions). Actions on an AA line are requests:
    Hold, Confirm with AA (trip booked or later: after the deposit, design F6), Release, Re-quote.
- **Outage queue = `crm.aa_request`.** One row per request (quote, requote, hold, confirm, release, refresh), status
  `pending -> done | failed | cancelled`, attempts, `next_attempt_at` (backoff 30 s doubling to 15 min, at most
  :data:`MAX_ATTEMPTS` = 96, about a day), `lease_until` (a claim lease, so the minute run and a nudge never send one
  request twice), `last_error_class` (a code). While it is pending the line shows **"AA pending"** (with the retry
  time when Booking failed). **No duplicates:** one live request per (line, kind) (partial UNIQUE); the quote request
  owns its line (`booking_line.aa_request_id` UNIQUE); holds and confirms send `Idempotency-Key = crm-<kind>:<request
  id>`, stable across retries, so Booking answers a retry with the same hold / booking; a release is idempotent in
  Booking (204); quotes are not idempotent in Booking, but a repeated quote only replaces the line's quote (same line,
  a new money head only when the amount or rate changed).
- **Transient vs. final Booking answers.** Retried (stay pending): transport errors, timeouts, 5xx / 503, 401 (token
  dropped and asked again), 429 without `rehold_limit`. Final (done or failed with a code on the line): 409
  `price_changed` (the job re-quotes once and retries the hold), 410 `hold_expired`, 422 `sold_out` / `invalid`, 429
  `rehold_limit`, 409 `extend_limit`, 409 `tour_not_served`, 403 `unknown_partner` / `forbidden` (AA has not
  activated the agency as a B2B partner: failed `unknown_partner`, the agent asks AA).
- **Hold sets before CRM-21.** Booking holds one set per `(tenant, proposal_ref, version)`. Until the proposal builder
  (CRM-21a/b) ties holds to a proposal version, each AA line is its own hold set: `proposal_ref = crm-line:<line
  id>`, `proposal_version` = the line's quote count (a re-quote after an expiry starts a new version). Booking's
  re-hold limit (3 a day per proposal_ref) then applies per line. CRM-21b replaces the ref with the proposal id.
- **Feed (`GET /events`) per agency**, every minute, in the same Recurring kind: the cursor in
  `crm.booking_feed_state` (one row per agency, created with its first AA request, so agencies without AA lines are
  never polled); each event in its own transaction, deduplicated by `crm.inbox_events` (the design's table name; its
  DM-7 row exists: unique on `(tenant_id, source, contract, idempotency_key)` = the event id). Tolerant reader of
  1.1: unknown fields ignored, unknown types recorded `ignored / unknown_type` (a later minor never stops the feed).
  `departure.*` events are recorded `ignored / informational` (the incident banner is M17, a later card).
- **Catalog cache (`crm.aa_catalog_tour`, platform table, no tenant, no PII).** Published AA tour content from
  `catalog.http.v1`: the hourly `crm_catalog_sync` lists every tour (pages of 50), re-fetches a tour whose
  `content_hash` changed (`If-None-Match` with the stored ETag), and re-checks a tour that left the list: 410 ->
  `retired` (reason kept), 404 with a reason -> `paused`. A run is bounded (:data:`MAX_DETAILS` fetches), the next run
  continues. Lines show "no longer offered" by joining the cache (`retired`), never by a write per agency.
- **"From"-price warning (warn, never block, ADR 0005a decision 1).** For a `trip_plan` line the job asks
  `GET /price-parity` in the quote currency and stores `from_price`; `below_from_price` = the agency's sell per person
  (adults + children) is below it. The add form shows the same warning before submitting
  (`GET /crm/v1/aa/products/{source_id}?currency=` returns the from price). No sell, or no parity, = no flag.
- **AA-aware Lost reasons.** The trip's lines answer a `lost_reason_hint`: a declined AA line -> `aa_sold_out` when
  Booking's `decline_code` is `sold_out`, else `aa_on_request_declined`; a quote or hold answered sold out ->
  `aa_sold_out`. The Lost dialog pre-selects it (the agent may change it). Moving a trip to Lost (or cancelling it)
  queues a release of every live AA hold and cancels the pending quote / hold requests; the release waits the stage
  Undo window, and Undo cancels it.
- **Money of AA lines** (`crm.booking_line_aa_money`, definer, job actor only): cost = the quote line's `b2b_price`,
  sell = the agency's sell from the request, both in the quote currency with the frozen FX block `fx_source
  aa_quote_lock`, `fx_basis quote_lock` (design §3.5 "AA lines take the Booking quote's FX lock"): rate = 1 / the
  quote's `rate_per_usd` into USD, crossed to a non-USD base currency through `crm.fx_resolve('USD', base, rate
  date)` (its `stale_days`). A repeated identical quote writes nothing.
- **The restore re-check** (AA-942 seam `app.state.booking_checker`) is `app.booking.checker.BookingChecker`:
  `GET /holds/{id}` per open AA commitment (active -> held, confirmed, expired, released).

- **One Recurring kind, two jobs of work** (`crm_booking_sync`): the request queue and the feed run in the same minute
  pass per agency, so one kind is exempt (deploy gate + Infra `owners.yaml` `idle_exempt_kinds`), like
  `crm_membership_pull`. A member's ask also queues a one-agency nudge (same kind, payload `tenant_id`), so a healthy
  Booking answers in seconds; the nudge sends requests only (no feed). The catalog sync is a separate hourly due-now
  kind (not exempt: its row exists only while due).
- **Lost / cancel and AA** (design §2.7 side flows, C12): Lost cancels the waiting quote / hold / refresh requests and
  queues one release per line Booking has not booked, `next_attempt_at = now + 15 s` (the stage Undo window is 10 s);
  `stages.undo` cancels those releases. Cancel (C12) releases holds the same way; lines AA already booked are only
  listed in the dry run (`aa_bookings_kept`): Booking's cancel with its fee is the cancellation card (CRM-27).
- **Declined line** -> the line is `cancelled` / `declined` with Booking's `decline_code`, the trip gets one urgent
  `aa_line_declined` task for its owner (design F7 "An AA decline creates a task offering [Swap product] or [Refund that
  part]"; the swap / refund actions themselves are CRM-21b / CRM-27).
- **On request**: Booking's confirm answers `on_request` for a line without a fixed departure (AA-973). The line stays
  `planning`, sub-status `on_request`, `confirm_class aa_on_request`, the bk- code as its confirmation number, and the
  commitment `requested` (the trip waits on `aa`); `line.confirmed` from the feed confirms it.
- **The "AA pending" placeholder line** is created at request time by the definer, so the UI shows the row at once
  and the outage queue has a line to retry for; its title and dates are the catalog's, its money arrives only with the
  quote. A first quote Booking refuses for good leaves the line `failed` (shown "Ask AA") with the code; the agent
  re-quotes or releases it (a release of a line without a hold is done in the CRM, no Booking call).
- **Assistant**: may ask for AA lines and holds / releases (trip edit), never with a sell amount (owner / agent:
  `MONEY_FIELDS_EDIT`; the definer refuses it too, 42501). The line view has no money block for her (unchanged).

## Tradeoffs

- **Each line its own hold set until CRM-21b** (`proposal_ref = crm-line:<id>`): simple and correct for the thin
  lifecycle, but Booking's re-hold limit counts per line, and a multi-line proposal is not held atomically. CRM-21b
  moves the ref to the proposal version; nothing in crm-017 stores the ref, so the change is code only.
- **A per-minute pass over every active agency** (two short transactions each when it has nothing to do). Fine for
  Dev and the first agencies; at scale a platform list of "agencies with AA activity" (a definer function or a
  platform table) would replace `registry.agencies`.
- **The product look-up is live** (cached 5 minutes per agency in process), not stored: Booking's offer is small and
  changes rarely; storing it would need another platform table and sync. When Booking is down the form says so and
  nothing is asked (a line already asked for keeps retrying).
- **`below_from_price` is visible to the assistant** (a yes / no without amounts); the sell and the cost stay hidden.
- **The restore re-check calls Booking inside the restore's transaction** (the AA-942 seam's shape): a slow Booking
  holds one pool connection up to the 10 s timeout per hold.
- **Catalog: full passes only** (the contract's `updated_since` is not a full change cursor, AA-976 notes), bounded per
  run (10 pages, 100 tour fetches, 50 re-checks): about 1 + changed tours requests an hour.
