## Decisions

- **One matrix, one source** (`app/permissions.py`): 46 actions x 3 roles, every action of design §4.6 including the
  ones whose routes come later (export, client delete, refund, proposals, campaigns, workflows, terms, support
  settings). Rules: ALLOW, DENY, OWN (agent deletes own trips), ASSIGNED (assistant sends on assigned trips),
  THRESHOLD (agent refunds up to `tenant_settings.refund_owner_threshold_base`). A missing fact refuses. The test
  (`tests/unit/test_permissions.py`) writes the design table out again and compares every cell, so a change on
  either side fails.
- **Enforced at the door**: `tenant_tx(..., action=Action.X)` refuses a DENY role right after the membership check
  (403 `role_forbidden`) and commits a `denied` audit event (action = the matrix code, object_kind `permission`).
  Every `tenant_tx(` in `app/routers/` must pass `action=` (`test_every_router_tenant_tx_names_its_permission_action`).
  Attribute rules are checked by the service with `permissions.require(ctx, action, own=/assigned=/amount=)`.
  Existing ad-hoc checks moved onto the matrix: intake-form writes (`settings_forms_manage`), trip reassign
  (`reassign`; taking an unassigned trip stays open to all), document delete (`document_delete`), cancelling a trip
  (`trip_cancel`, owner / agent). The old 403 codes `owner_only` / `not_allowed_for_role` become `role_forbidden`.
- **Margin serializer by key name, not a field list** (`app/margin.py`): every AGENCY router is built with
  `MarginFilteredRoute` (`class_router(AGENCY)` sets it), which strips keys matching
  `(^|_)(net|b2b|cost|costs|margin|margins|commission|commissions)(_|$)` at any depth unless the request's role holds
  `view_margin`. The role comes from a context variable `tenant_tx()` sets; no `tenant_tx()` (e.g. `/memberships`)
  means "unknown" = filtered (fail closed). A stripped key is logged (`crm_margin_key_stripped`): a route should not
  build it. The "allow-list" of the design is therefore "every key except the margin family" for the assistant;
  a literal per-role field allow-list would have to change with every card. No money table exists yet, so the
  database-side margin RLS (enforcement item 1) arrives with the first money table (CRM-19/20).
- **Contract test over every `/crm/v1` route** (`tests/unit/test_margin_filter.py`): (1) every live `/crm/v1` route is
  a `MarginFilteredRoute` (walked through FastAPI 0.142's included-router wrapper and cross-checked against the
  OpenAPI view); (2) for every (path, method), a twin route with the same path, guard and route class answers a payload
  full of margin keys: the assistant and an unknown role get none, owner / agent get all; (3) a real route (the board)
  end to end. Card R: "any assistant response containing a margin, net or commission key fails the test".
- **Membership writes guarded by the database too** (crm-008 `crm.guard_member_write`): inside a member request only
  an owner writes `crm.member` (SQLSTATE CRM02); an accepting invitation (`app.actor = invitation:<id>`) writes only
  the member it names; platform contexts (`platform:*`, `seed:*`) may write; any other actor kind (a job) may not. The
  last active owner cannot stop being one except by a platform context (CRM01), serialised per agency with an
  advisory lock (each query in a VOLATILE plpgsql function takes a fresh snapshot, so the second of two concurrent
  demotions sees the first). A context without `app.actor` (migrations, admin sessions, older tests) is not limited by
  the owner rule.
- **Invitation = claim, then accept** (root ADR 0006b decision 5). With MessageAction=SUPPRESS and admin-only
  recovery, a person created without a password could never sign in (an e-mail code is not allowed while MFA is
  required, a passkey needs a first sign-in). So the **claim** step (public, token-only, rate limited) creates the
  account with a random temporary password that the join page shows once (`AdminCreateUser`, SUPPRESS), or finds the
  existing account (`ListUsers` by exact e-mail: the pool's usernames are case-insensitive e-mails, so one address is
  one account) and shows no password. The invitation keeps that account's `(iss, sub)`. **Accept** (partner-pool
  bearer) requires the caller's token to carry exactly that `(iss, sub)` — the binding is the verified token, never an
  e-mail lookup at accept time (the ADR's "verified email equals invited email" is met because the claimed account is
  the one the pool holds for that address; Cognito access tokens carry no e-mail). No new IAM call: the allow-list stays
  AdminCreateUser / ListUsers / AdminDisableUser / AdminUserGlobalSignOut.
- **MFA before active**: the pool requires MFA (`mfa_configuration = ON`), so no sign-in — and therefore no accept —
  happens without an enrolled authenticator. The API does not inspect `amr` (Cognito access tokens do not carry it).
- **Account that never finished setup** (`FORCE_CHANGE_PASSWORD`, e.g. claimed then the invitation expired): ~~claim
  answers 409 `account_setup_pending`~~ — superseded S263 (`AA-939-join-fix.md`): the claim gives that account a new
  temporary password with `AdminCreateUser` `MessageAction=RESEND` (the allow-listed action) when a new invitation to
  its address is claimed (never for the same claimed link: that answers `already_claimed`).
- **Removal = membership disabled + global sign-out**, not `AdminDisableUser`: a person may belong to several agencies.
  Access ends at once anyway (`tenant_tx()` checks `crm.member` per request); the refresh token is revoked best-effort.
- **Reassign queue = a query, not a flag**: open trips (and clients) whose owner is no longer an active member. The
  owner moves them (with the open tasks; clients too when no trip list is given). Card E: "a deactivated agent's trips
  land in the reassign queue".
- **Owner recovery** (Q1 6.3): `crm.owner_recovery_request`, opened and completed by a platform context only
  (`/crm/ops/v1`, group `crm-platform-admin`; the L1 console UI is CRM-13a / AA-941), `eligible_at >= created_at + 14
  days` (CHECK), completion not before it (CRM03), any active member cancels while pending (banner on every page with
  [Cancel]); the agency's active owners get an AA system mail when it opens (best effort). The platform's
  `deactivate` of a member is the way an agency can end up without an owner; then nothing inside the agency can make
  an owner (matrix + database), only the recovery: card E "last owner deactivated -> recovery only".
- **Entitlements** (R11): `crm.tenant_entitlement` (plan free/core/pro, member_limit default 10, allowed_features from
  a fixed list), written only by platform contexts (CRM04). No backfill: FORCE RLS hides `crm.tenant` from the
  migration, so "no row = the defaults" (`plan: free`). The member limit counts active + invited members + live
  invitations; the invite refuses at the limit (409 `member_limit_reached`).
- **Team page shows the invited address**: `crm.member` holds `(iss, sub)` only (ADR 0006b); the owner sees each
  member's address from the accepted invitation (vault-decrypted, one `list_view` event with the ids); seeded members
  show a short id. Pending invitations show a masked address.
- **AA system mail** for invitations and recovery notices (ADR 0006b decision 3 pointer): SES v2 `SendEmail` as
  `SES_FROM_ADDRESS` through `SES_CONFIGURATION_SET` (transactional stream), EN + VI in one mail. The invitation
  is sent inside the transaction: a mail failure rolls the invitation back. The join link is
  `PARTNER_WEB_ORIGIN/join?t=<token>`; only the token's SHA-256 is stored.
- **Join pages without the token in URLs**: `/join?t=` moves the token into a sealed cookie (purpose `invite`, path
  `/join`, 2 h) and redirects; the claim answer (with the one-time password) is kept only in a second sealed cookie
  (15 min, path `/join`). `/join`, `/join/invite`, `/join/claim` are public; `/join/accept` and `/join/confirm` need a
  session. New write routes call `refuseForeignWrite` (`web/lib/writeGuard.ts`, byte-identical to `main`'s).
- **Passkeys deferred, TOTP now**: AA-930 showed a passkey satisfies required MFA only with WebAuthn
  `FactorConfiguration = MULTI_FACTOR_WITH_USER_VERIFICATION`; the pinned AWS provider (6.69.1, schema checked) has no
  argument for it, and a SINGLE_FACTOR passkey is not a valid first factor while MFA is required. The pool runs password
  + TOTP (the ADR's fallback); the custom domain `partner-auth.` exists from day one so the relying-party id will not
  move when passkeys are added.
- **Safe rollout of the sign-in switch**: Infra `crm_partner_signin_enabled` (default false) chooses the CRM web's
  `COGNITO_DOMAIN` / `COGNITO_CLIENT_ID`; the API accepts both the partner pair and (Dev only) the cis-portal bridge
  meanwhile. The web code needs no change: it reads the client from the environment.
- **Migration key crm-008** (fixed in S249: crm-007 = AA-940, crm-009 = AA-938). Guard 0 checks crm-006 only, so it
  applies with or without crm-007. `REQUIRED_SCHEMA_VERSIONS` adds `crm-008` (readiness 503 until applied).

## Tradeoffs

- Pattern-based margin filtering can strip a harmless key whose name contains a margin word (`cost_center`); that is
  the safe side, and the log line shows it.
- The temporary password is shown on a web page instead of mailed: the link in the mail is the factor either way;
  this keeps the password out of mailboxes and needs no extra Cognito call.
- The membership write guard leaves actor-less sessions unrestricted so migrations and the existing test seeds keep
  working; request code always sets an actor.
- The recovery banner is one extra API call per agency page (`GET /crm/v1/recovery`, a single indexed row read).

## Review round 1 (independent agent review, S249)

The review reproduced three DB-level bypasses of the first crm-008 draft on a throwaway PG 16 (RDS role shape). All
three are fixed in crm-008 itself (not yet applied anywhere, so no forward file is needed); its probe now answers CRM02
for each.

### Decisions

- **DELETE on `crm.member` is refused by the trigger, not by REVOKE.** crm-002's Guard 1 asserts crm_app holds DELETE
  on crm.member, and `test_reapply_is_a_no_op` re-runs every file: a REVOKE in crm-008 makes a crm-002 re-run fail. So
  `member_guard_write` now fires `BEFORE INSERT OR UPDATE OR DELETE` and refuses any DELETE from a crm_app session
  (whatever the actor, platform included); only an unscoped admin / migration session or a platform actor in a non-API
  session deletes. TRUNCATE stays revoked (Guard 1 asserts it; a trigger cannot refuse it).
- **Both guards fire on every write (no column list).** crm.member has no column a non-owner may update, so the simplest
  safe rule is "a non-owner member writes nothing", and a column added later is guarded without touching the trigger.
  Guard 1 asserts `tgattr` is empty for both triggers and that the member guard covers DELETE.
- **Member identity is fixed outside platform contexts**: member_id, tenant_id, cognito_iss, cognito_sub, created_at,
  created_by. Even the owner cannot rebind a row to another subject; the L1 console (platform:) can correct one.
- **The invitation guard names the columns each writer may change** (compared as `to_jsonb(NEW) - allowed` vs OLD,
  so every other column, present or future, is fixed): owner = insert a pending unbound row, then only status
  revoked / expired and the trash columns; `invitation:<same id>` = pending -> claimed (cognito_*, claimed_at),
  claimed -> accepted (accepted_at, member_id; the member must carry the claimed subject and role), pending / claimed
  -> expired only after expires_at; everyone else nothing.
- **A crm_app session without `app.actor` is no longer exempt** (non-blocking item, done because it is cheap now): the
  exemption is `actor = '' AND current_user <> 'crm_app'` ("unscoped": migrations, admin sessions). Every API context
  already names its actor; five integration-test helpers that wrote members as bare crm_app now set `seed:test`.
- **`platform_tx()`** (non-blocking item): `system_tx` takes `job:` / `seed:` only; AA staff actions use the new
  `platform_tx` (actor `platform:` only). Code rules: only `app/members/recovery.py` opens it, and only
  `app/routers/ops.py` calls `open_request` / `complete_request` / `deactivate_member` (with a non-empty-walk check).
- **The invitation row is locked** (`SELECT … FOR UPDATE` by id once the agency is set; the lookup policy is SELECT-only,
  so the lock goes through tenant_isolation). Two claims run one after the other: one account; the second
  answers `already_claimed` (S263: never a second password for one invitation; audited as a denied claim). Two accepts: one wins, the other gets 410 `invitation_used` (was a 500 on
  member_identity_uq). An integration test with a slowed directory proves the overlap (it fails without the lock).
- **Accept never changes an active member's role**: an existing active member (e.g. a seeded owner with no accepted
  invitation, invited as agent) gets 409 `already_member` and nothing is written; a disabled member still comes back
  with the invited role. Remaining DB refusals while accepting map to 409 (`invitation_race`, `last_owner`,
  `role_write_forbidden`); anything else stays a 500. The join page words `already_member` and `invitation_race`
  (EN/VI).
- **Seat limit serialised**: `team.invite` takes `pg_advisory_xact_lock('crm.member.seats:<tenant>')` before counting.
- **Partner pool alerts** also match events without a role session (`exists: false` next to `anything-but`), so a
  static IAM user key or root changing the pool alerts too (Infra).
- **Lost one-time password**: no self-service re-issue (it would need AdminSetUserPassword / AdminDeleteUser in the task
  role, outside the ADR 0006b allow-list). The AA support runbook is in AA-CIS-Infra `tools/identity/README.md`
  ("an invitee lost the one-time password"); the join page already tells the person to ask the owner or AA support.

## E2E fix after the first Dev invite run (S249)

The first `e2e-dev.yml` dispatch with `invite=true` failed twice: `invite.spec.ts` did not find the authenticator
secret, and `slice1.spec.ts` stayed on the managed login TOTP page.

### Decisions

- **TOTP replay**: Cognito refuses a code it already accepted for the same user in the same 30 s step; the owner signed
  in in `invite.spec.ts` and again in `slice1.spec.ts` seconds later. `freshTotp()` now records the last step it handed
  out per secret and waits for the next step when the current one is used (the 5 s margin rule is unchanged). The
  record is kept in module state and in a file under the OS temp dir named by a hash of the secret (never the secret):
  Playwright starts a new worker process after a failed test, so module state alone would not have covered that run.
  `freshTotp()` takes an optional clock (now / sleep) so the rule is unit-checkable without real waits.
- **Authenticator setup page (managed login v2)**, looked at on a throwaway partner-pool user on Dev (created and
  deleted the same run): the page replaces "Change password" client-side (URL `/login/complete` then `/mfa/totp`),
  heading "Set up authenticator app MFA", a QR image, a "Show secret key" inline-link button that reveals
  `<p class="qr-secret-key">Secret key: <52 base32 chars></p>`, a "3. Enter code" text field and a "Sign in" submit.
  The old spec read the body while still on the password page (`isVisible({ timeout })` does not wait), and its submit
  pattern had no "sign in". The spec now waits for the heading, clicks "Show secret key", reads the key line
  (`p.qr-secret-key`, or the "Secret key:" text) and parses it with `parseSetupSecret()` (tolerates groups, lower case,
  padding).

### Should know

- Checked locally (not in CI): the new extraction + `freshTotp()` completed MFA setup on the throwaway user, and managed
  login redirected to the partner host (`/select-agency`, the user is in no agency). No passkey offer was shown.
- No unit-test runner in `e2e/` (Playwright only); the helper was checked once with a `node --test` script (RFC 6238
  vectors, same-step wait, cross-process record, margin, secret parsing), not committed.

## Card R on real money, every GET route (S258, milestone C-M2)

Branch `test/crm-milestone-proofs`. Agent Claude Code. Adds `api/tests/integration/test_margin_routes_api.py`; no app
code changes.

### Decisions

- **Value-based, over real data, over HTTP.** The unit contract test (`tests/unit/test_margin_filter.py`) proves the
  serializer is on every `/crm/v1` route with synthetic bodies; since AA-939 the money cards (AA-944 ledger, AA-947 AA
  lines, AA-949 builder) re-asserted it on their own services. The new test seeds ONE agency on PostgreSQL with every
  margin-bearing value the CRM stores today (supplier default commission, a confirmed agency line with cost / sell /
  commission and its derived margin, an AA line costed by Booking's quote through the sync job, a day-by-day version
  with an agency option net and an AA option net from a live quote), each value unique, then calls EVERY
  `GET /crm/v1` route of the live app (real verifier with local pools, real `tenant_tx()`, real serializers and route
  class) as the owner and as the assistant. The assistant's bodies must carry no margin-family key and none of the
  cost-side values (so a `{"kind": "cost", "amount": ...}` row the key filter cannot see still fails); the owner's
  bodies must carry every value somewhere (positive control).
- **Unclassified routes fail.** A `GET /crm/v1` route whose path parameter this seed cannot fill fails the test until it
  is seeded or listed in `UNSEEDED` with the reason it cannot carry money (today: conversation messages, a mail import,
  the owner-only agency export).
- **GET only.** Write routes answer with the same serializers (the unit contract test covers their wiring); reads are
  what an assistant browses. The milestone says "every route": writes are covered by `tests/unit/test_margin_filter.py`,
  not by this test.
- **Assistant-side control (review fix).** The assistant's check fails only on a margin key or value, so a wrong token,
  a wrong tenant header or a blanket 403 would leave it green with nothing tested. `ASSISTANT_READS` (the builder,
  `/bookings`, `/trips/{id}/lines`, `/suppliers`, `/suppliers/{id}`, the routes the owner control finds the values on)
  must answer the assistant 200. Mutation check: an assistant with a random tenant header fails on it (403s).
- **No false leak from timestamps (review fix).** The first version planted a 7.25 % commission and matched values as
  plain substrings: a `created_at` like `...:47.251903` contains `7.25`, about once per thousand timestamps, so the
  test could fail with no leak. The commission is now 73.25 (no seconds field reads 73) and values match on number
  boundaries (`(?<![\d.])value(?!\d)`), for the leak check and the owner control alike.
- **Own catalog row.** The AA line uses the builder tests' `T-949` row (inserted as `served`), not a catalog sync:
  `test_aa_lines_api.py` retires `T-100` and leaves the shared catalog sync in backoff, so a sync here would depend on
  test order.

### Should know

- Mutation check (local, not committed): with `app.margin.sees_margin` forced to `True`, the test fails on
  `/crm/v1/bookings` (keys `cost`, `commission_expected`, `confirmed_cost_base`, `confirmed_margin_base`, ...): both
  layers (service-level omission, HTTP key filter) are needed for it to pass, and it catches either one missing.
