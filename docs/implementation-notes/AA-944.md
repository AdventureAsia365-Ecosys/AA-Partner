## Decisions

- **Key crm-014, Guard 0 needs crm-012 and crm-013** (schedule §1). `crm.erase_subject` is the crm-013 text (it keeps
  the `membership_inbox` step) plus the ledger steps; crm-015 (AA-945) starts from the crm-014 text.
- **SQLSTATEs CRM22–CRM27 belong to crm-014**: CRM22 `aa_supplier_builtin`, CRM23 `line_incomplete:<codes>`, CRM24
  `aa_line_read_only`, CRM25 `fx_rate_missing:<currency>`, CRM26 `line_not_editable`, CRM27 `supplier_in_use`. crm-015
  starts at CRM28.
- **Margins: a RESTRICTIVE policy, not a replaced tenant policy.** `booking_line_money` keeps the template's
  `tenant_isolation` TO the six roles, plus `booking_line_money_margin_roles` AS RESTRICTIVE FOR SELECT TO crm_app
  (`app.member_role` owner / agent, or no member role and a `job:` / `seed:` / `platform:` actor). Restrictive policies
  are ANDed, so this only narrows; the base-template test stays unchanged in spirit and checks the policy is
  restrictive (`RESTRICTIVE_POLICIES`). crm_owner (the definer functions, the erase) is not affected.
- **Money is written only through definer functions.** crm_app has SELECT only on `booking_line_money`. The assistant
  must be able to confirm a line (R18: never blocked) although it may not read money, so the freeze cannot run as
  crm_app. `crm.booking_line_confirm(line)` (definer) re-checks the level, freezes the unfrozen heads and moves the
  status; `crm.booking_line_money_put(line, kind, amount, currency)` (definer) checks the role itself (owner / agent /
  job) and writes a new head. Both use the internal `crm.booking_line_money_write` (nobody else may execute it). The
  database therefore holds the invariant "a confirmed agency line's money is frozen": the guard trigger refuses any
  crm_app statement that confirms an agency line (CRM26), so the only way in is the function.
- **FX resolution lives in the database** (`crm.fx_resolve`), not in Python: the confirm (definer) needs it, and one
  implementation keeps the API's displayed rate and the frozen rate identical. Order (R17 §3.1): override of the day
  -> platform of the day -> the latest earlier day within 30 days (`stale_days`); an override wins a tie; platform
  rates direct, inverse or crossed through USD / EUR on one day and one source; source priority `booking_b2b`,
  `manual_aa`, `ecb`, `exchangerate_api`, `sbv`, `synthetic`; `fawazahmed0` rows are never used (cross-check only).
  `fx_mode = manual` reads the agency's overrides only. The basis date is the confirmation date in the agency
  timezone (`tenant_settings.timezone`, crm-012).
- **No drift on corrections**: a correction in the same currency re-uses the head's frozen rate; another currency
  resolves the rate of the confirmation date (not today's).
- **Strict duplicate key** (plan gap a): trigger-kept `conf_unique_key` + `UNIQUE (tenant_id, agency_supplier_id,
  conf_unique_key)`, race-free. Set only for a **confirmed** agency line (planning duplicates are fine; the check bites
  at confirm), when the agency is strict or the supplier is `confirmation_unique`. The number is normalised to upper
  case letters and digits ("hp 1001" = "HP-1001"). A line confirmed before the agency went strict has no key, so the
  trigger also looks for a confirmed un-keyed line of the supplier with the same normalised number and raises the same
  `unique_violation` / `booking_line_conf_uq` (found by the API integration test: switching Basic -> Strict must still
  catch the older line). That read sees only committed rows, which is enough: the older line was committed earlier,
  and two new confirms racing each other meet in the UNIQUE index.
- **The AA supplier row comes from `crm.ensure_aa_supplier()`** (definer, EXECUTE crm_app), called by provisioning and
  lazily by the supplier list, plus a backfill in the migration for existing active / locked agencies (ids from the
  crm-007 export registry, which every agency has and the owner reads without FORCE RLS). Not an AFTER INSERT trigger on
  `crm.tenant`: earlier test files re-apply crm-012 / crm-013 (their own `erase_subject` text, which does not know
  `agency_supplier`), and an automatic row in every new agency would make their agency erases fail with CRM16.
- **Money rows carry no trip column**: the erase reaches them through the line, and the hold rule through the line's
  trip (`crm.erase_held` scope `booking_line`). They are append-only, so the hold guard trigger is not needed on them.
- **Only a planning line goes to the trash** (plan: "DELETE of planning lines only"); a confirmed line is cancelled
  first. A supplier goes to the trash only when no live line names it; its purge (scope `agency_supplier`) refuses the
  AA row (CRM22) and any supplier a line (even a trashed one) still names (CRM27).
- **`visible_to_travelers` defaults to false** (privacy-safe; the agent shows a line on purpose). A cancelled line is
  forced to false (R22).
- **`fx_rate_platform.source`, not `provider`**: the column follows the root ERD design (`docs/architecture/erd/design/
  crm.md` group F), so the design page needs no change. Its CHECK adds `exchangerate_api`, `fawazahmed0`, `synthetic`
  to the design's `ecb | sbv | booking_b2b | manual_aa`.
- `base_currency` default **USD** is an assumption (the design names none); owner-editable in Settings > Payments.

## Changed (vs the plan)

- `crm.booking_line_confirm` and `crm.booking_line_money_put` (definer) were added next to the planned
  `crm.booking_line_confirm_check`; crm_app has no INSERT on `booking_line_money` (the plan had API inserts).
- `crm.fx_resolve` in SQL instead of `app/ledger/fx.py` doing the resolution (the Python module only calls it).
- No tenant insert trigger for the AA row (see Decisions); `app/agencies.py` and the supplier list call
  `crm.ensure_aa_supplier()`.
- A helper view `crm.v_booking_line_money_current` (security_invoker, plan gap d) for the heads.

## Tradeoffs

- Definer functions concentrate the money rules in the database (defence in depth behind the API's 403 / 409) at the
  cost of plpgsql the API cannot unit-test without Postgres; the integration file `test_crm014_schema.py` covers them.
- The restrictive policy lets a `job:` / `seed:` / `platform:` actor read money without a member role. The same threat
  model as crm-006 §4.3 / crm-012: it protects against code bugs and the assistant role, not against a compromised
  crm_app (which can set its own GUCs).
- 30-day look-back for a stale rate: a rate older than that is refused (CRM25) rather than silently used.
