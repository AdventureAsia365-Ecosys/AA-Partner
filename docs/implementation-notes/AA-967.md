## Decisions

- **Two new tables, both receipts.** `crm.export_job` (name from the design ERD / retention register, group J) and
  `crm.data_request` (the errata's log). Neither holds personal data (ids, codes, counts, hashes, dates; no free text),
  so both join the agency erase **keep list** like `erasure_request` instead of being deleted at offboarding. This is the
  smallest change to `crm.erase_subject` (two names in `c_keep`), so crm-026 is the crm-025 text plus two words.
- **No foreign key to the traveller** on either table: the log entry and the export record outlive the client's erasure
  they document (same rule as crm-025's signed evidence).
- **crm-026 builds on crm-025** (Guard 0 needs it registered, and checks the live text has `signature_event_kept`):
  the branch sits on #135's commit; after #135 squash-merges, `git rebase --onto origin/main <#135 commit>`.
- **Cool-off on `crm.erasure_request.erase_not_before`** (a column, not a new status): the owner's typed confirmation
  sets `confirmed_by` + `erase_not_before` and queues the erase job for that time; the request stays `requested` /
  `export_ready`, so the existing cancel path and the crm-011 guard need no change, and the agency keeps working (and
  the owner can cancel) during the cool-off.
- **`verified_at`** on `erasure_request`: set by the erase job only after the verification step passed.
- **Data-request due date** at most received + 92 days (one month + a two-month extension, GDPR art. 12(3)); the API
  defaults it to + 30 days.

## Changed (vs. the card)

- The card names `crm.erase_subject()` + `crm_eraser` and the signed-agreement exception: both exist (AA-942, crm-025);
  this card uses them unchanged except the keep list.

## Tradeoffs

- A separate `export_job` table instead of reusing `erasure_request` (purpose `export_only`, crm-011): that table's
  one-open-agency-request index would make a routine owner export block offboarding (and vice versa), its export key
  CHECK names `.jsonl.enc`, and a client export does not fit its tenant-only `export_only` rule. Widening those is a
  bigger contract change than a new table.
