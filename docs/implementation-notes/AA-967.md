## Decisions

- **Two new tables, both receipts.** `crm.export_job` (name from the design ERD / retention register, group J) and
  `crm.data_request` (the errata's log). Neither holds personal data (ids, codes, counts, hashes, dates; no free text),
  so both join the agency erase **keep list** like `erasure_request` instead of being deleted at offboarding. This is the
  smallest change to `crm.erase_subject` (two names in `c_keep`), so crm-026 is the crm-025 text plus two words.
- **No foreign key to the traveller** on either table: the log entry and the export record outlive the client's erasure
  they document (same rule as crm-025's signed evidence).
- **crm-026 builds on crm-025** (Guard 0 needs it registered, and checks the live text has `signature_event_kept`):
  the branch sits on #135's commit; after #135 squash-merges, `git rebase --onto origin/main <#135 commit>`.
- **Cool-off on `crm.erasure_request.erase_not_before`** (a column, not a new status): the owner's typed confirmation
  sets `confirmed_by` + `erase_not_before` and queues the erase job for that time; the request stays `requested` /
  `export_ready`, so the existing cancel path and the crm-011 guard need no change, and the agency keeps working (and
  the owner can cancel) during the cool-off.
- **`verified_at`** on `erasure_request`: set by the erase job only after the verification step passed.
- **Data-request due date** at most received + 92 days (one month + a two-month extension, GDPR art. 12(3)); the API
  defaults it to + 30 days.

Code PR (`feat/aa-967-portability-deletion`):

- **Tables from the catalog, not a list.** `app/portability/tables.py` exports every tenant table the login role can
  read (pg_catalog at build time) minus `NEVER_EXPORT_TABLES` (keys, vendor secrets, F3 maps, portal codes, the audit
  with its own download) and the index / token columns. A table a later card adds is exported without a code change.
  The AA-942 offboarding export (JSON lines) now uses the same table set (format 2; AA-942 listed 24 tables by hand and
  missed mail, proposals, invoices, signatures). The DEK purpose per `*_enc` column is explicit (`mail` for the mail
  tables, `docs` for the crm-025 sealed envelope, `vault` otherwise); no "try another key" fallback, since a wrong-key
  attempt writes a `decrypt denied` audit event.
- **ZIP layout** (`app/portability/builder.py`, schema_version 1): `manifest.json`, `json/<table>.json`,
  `csv/<table>.csv` (BOM, formula guard as the access-log CSV), `documents/manifest.csv` + `documents/files/<id>/<name>`
  (up to 100 MiB of documents, the rest listed `skipped_size_cap`; a stored copy that fails its digest is listed
  `skipped_integrity`), `SHA256SUMS` (`sha256sum -c` format). Fixed entry timestamps. The ZIP's SHA-256 is shown on
  the page and sent as `X-Content-SHA256`.
- **"Short-lived link"** = a random token (`secrets.token_urlsafe(32)`), only its SHA-256 on the row, 5 minutes, single
  use, and still owner-only behind the normal `/crm/v1` session (a leaked link alone is useless). The browser fetches
  it through the BFF and saves the blob (the BFF passes content-type only).
- **Progress**: one short `lifecycle_tx` per step (tables, then every 10 documents) while the build transaction reads,
  so the page sees it; the build runs as actor `job:crm_data_export` (added to `LIFECYCLE_ACTORS`; the module joins
  the `lifecycle_tx` allow-list in `test_code_rules.py`).
- **Withdrawal**: a client erasure cancels (and deletes the objects of) every open or ready agency export and that
  client's exports; an agency erase all of them. A build running meanwhile finds its row cancelled and deletes its
  object instead of marking it ready.
- **Client erasure** moved from the router into `app/portability/subject.py`: dry run = counts + kept + exceptions +
  exports to withdraw; run = withdraw, erase, verify (a second dry run must answer `subject_not_found`), receipt format 2
  with `verified_at`, close the logged request.
- **Offboarding verify**: a canary sealed under the vault DEK just before `KeyProvider.destroy` must fail to open after
  it (`KeyDestroyed`); otherwise 503 `verify_failed` rolls everything back and the request is `failed`. The receipt's
  `verify` block also states `other_tasks_caches_expire_by` (the AA-934 comment: other tasks' DEK caches).
- **Cool-off** `OFFBOARDING_COOL_OFF_HOURS` (default 72, code default: no Infra change needed). The erase job's first
  step (`_start`) moves the request to `erasing` and the agency to `offboarding` only once `erase_not_before` passed;
  run early it raises `cool_off_running` (retried); a request cancelled meanwhile is `skipped`.
- Rules: `signed_agreements` (36 months after the trip, crm-025) and `accounting_records` (with the trip) are listed on
  Settings > Data and privacy. A `data_requests` rule was dropped again: the "until you delete it or leave" window would
  be wrong for a receipt that outlives offboarding.

## Changed (vs. the card)

- The card names `crm.erase_subject()` + `crm_eraser` and the signed-agreement exception: both exist (AA-942, crm-025);
  this card uses them unchanged except the keep list.
- **Not built: re-import.** The lane plan's Done-when says "export of a synthetic agency re-imports into a fresh
  synthetic agency with equal counts". There is no import path; the integration test checks the half that exists: every
  table's row count in the ZIP (JSON and CSV) equals the database's, and the document comes back byte for byte. An
  importer (fresh ids, re-encryption under the new agency's keys, FK order) is its own slice.
- **Not built: deferred erasure.** The card's E "a traveller on a trip currently Travelling is deferred to trip
  completion unless the owner confirms": the erasure answers 409 `traveler_on_trip` (crm-010 CRM12) as before, and the
  logged data request stays open with its due date; the owner cancels / deletes the trip or waits. No scheduler for a
  deferred erase.
- **Not built: AA-forwarded requests from the L1 console.** The channel `aa_forwarded` exists; the CIS admin still only
  raises agency export / deletion requests (AA-941). Logging a forwarded client request from CIS would add a
  `crm.ops.v1` write and its allow-list.

## Tradeoffs

- A separate `export_job` table instead of reusing `erasure_request` (purpose `export_only`, crm-011): that table's
  one-open-agency-request index would make a routine owner export block offboarding (and vice versa), its export key
  CHECK names `.jsonl.enc`, and a client export does not fit its tenant-only `export_only` rule. Widening those is a
  bigger contract change than a new table.
