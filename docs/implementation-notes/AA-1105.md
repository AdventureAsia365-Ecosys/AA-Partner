# AA-1105 — AA Academy part 2, slice S5: the academy web on the academy host (AA-Partner web)

Root notes: AA-Ecosys `docs/implementation-notes/AA-1105.md`. CIS learning API: AA-CIS-App
`docs/implementation-notes/AA-1105.md` (slice S4). Design: root ADR 0022, `docs/research/lms/README.md`, contract
`docs/contracts/learn.http.v1.openapi.yaml`.

## Decisions

- **One host, its own gate, decided first.** `WEB_ACADEMY_HOSTS` (AA-CIS-Infra `crm_web.tf`) makes a host kind
  `academy` (`lib/hosts.ts`), checked before the partner and client lists, and an academy host is removed from those
  lists in `lib/config.ts`. On it the proxy (`proxy.ts academyGate`) serves only `/academy/*`, `/verify/<code>`,
  `/prefs/locale` and static files; `/` goes to `/academy`; everything else (agency, studio `/portal` and `/api`,
  staff console, client pages, `/crm/*`, `/bff/*`, `/auth/*`) is 404. On the partner and client hosts `/academy*` and
  `/verify/*` are 404 (localhost serves them in local and test). The academy route handlers repeat the host check
  (`academyHostAllowed`).
- **Own session, same shape as the staff console (AA-1019).** `lib/academySession.ts`: cookies
  `__Secure-aa_academy_{s,r,tx}` on paths `/academy` and `/academy/auth`, sealed with `ACADEMY_SESSION_SECRET` under
  new seal purposes `academy-*`; the config refuses a client id equal to the agency or staff client and a key equal
  to the agency or staff key. The callback accepts only an access token of the academy-web client and asks for no
  group: CIS decides who is a learner (403 `not_a_learner`), and the learner layout shows why with a sign-out.
  Callback `/academy/auth/callback` and sign-out page `/academy/signed-out` match the academy-web client's URLs in
  AA-CIS-Infra `identity_variables.tf`.
- **Server reads + one BFF.** Server components read `/learn/v1/*` with the session token (`lib/academyApi.ts`); the
  browser calls `/academy/bff/<path>` (`lib/academyBff.ts`: the 15 learner routes of learn.http.v1, `lang` the only
  query), which needs the page's own call header `x-aa-academy` on every method (lumiguides.it.com hosts are one
  site) and forwards the learning API's status and Problem body. A 401 on a page goes once through
  `/academy/auth/refresh` with the one-shot refresh marker, then shows an error (no loop).
- **Captions from the academy origin** (API lane constraint, no bucket CORS change): `/academy/captions/<lesson>/<lang>`
  asks CIS for fresh presigned URLs, fetches the `.vtt` server side (https on an S3 host only, size cap, WebVTT
  signature) and serves `text/vtt` with `nosniff`. The video itself plays from S3 (`<video src>` needs no CORS).
- **Public verify page `/verify/<code>`** (the API's `verify_path`): no sign-in, `Referrer-Policy: no-referrer`, not
  indexed. The web limits its own visitors (`lib/academyVerify.ts`): behind the web every visitor reaches CIS from one
  NAT address. The per-visitor, per-minute limit is the CIS setting `cis.learn.verify_visitor_requests_per_minute`
  read from the `X-Learn-Visitor-Limit` header CIS sends on every verify answer (contract `learn.http.v1` 1.1; no
  literal, no env var; CIS clamps it to its per-address limit minus one); until CIS has sent it, one call per visitor
  per minute and none while one is in flight; a CIS 429 is passed on with its Retry-After. Visitor = `CloudFront-Viewer-Address` (IPv6 /64),
  the key the CRM's intake form already uses.
- **Quizzes start on click**, never on render (a reload must not open an attempt). The UI shows the API's pass mark,
  items per attempt, best score and `retake_at`; it computes none of them.
- **Spaced review with ts-fsrs 5.4.2** (research §6.4 names ts-fsrs; MIT, no dependencies; 5.x because 6.0 is a new
  major two weeks old). Added to the lockfile by hand (one entry) so the local npm does not rewrite unrelated `libc`
  fields. The target retention comes from the API's `target_retention` (setting `cis.learn.review_target_retention`).
- **Lesson Markdown** (`lib/academyMarkdown.ts`): blocks and inline tokens rendered as React elements, never HTML;
  only absolute https links open (relative repo paths show as text); tables show as monospaced text (the kit has no
  raw `<table>` outside DataTable).
- **Strings**: `lib/i18nAcademy.ts` (EN + VI, spread into `lib/i18n.ts`); client components get only the academy
  strings (`academyDict`), not the whole dictionary.

## Tradeoffs

- **Review rating before the answer.** learn.http.v1 takes the browser's next card together with the chosen answer,
  so the FSRS rating must be chosen before the server says whether the answer was right. The page asks the learner to
  rate how well they knew it (Forgot / Hard / Good / Easy) before checking. A wrong answer rated Good keeps a too
  optimistic schedule. Follow-up for CIS: grade first, then accept the card (or derive the rating on the server).
- **Verify limit (S281 review fix).** The first cut learned the limit from `X-RateLimit-Limit`, which the CIS verify
  route never sent (only the `/v1/*` tenant middleware sets it), so the per-minute limit never turned on and only the
  one-in-flight rule held: a visitor reloading one call after another could use up CIS's per-address cap for every
  visitor. Even with that header, the web would have given one visitor the whole host budget. Fixed across three
  repos: CIS setting `cis.learn.verify_visitor_requests_per_minute` (CIS 429, default 6, 1..300), sent on every verify
  answer as `X-Learn-Visitor-Limit` clamped to the per-address limit minus one (root contract `learn.http.v1` 1.1), and
  the web reads that header. Before the first answer of a process the web holds each visitor to one call per minute
  (a structural "one until told", not a tunable value).
- **Per-process limiter**: one web task on Dev; with several tasks each counts its own visitors (like the CRM API's
  in-process limits).
- **Technical constants** (not policy): upstream timeouts, the BFF body cap (64 KiB, a quiz submission), the caption
  size cap (512 KiB) and the limiter's memory bound; each is marked in the code.
