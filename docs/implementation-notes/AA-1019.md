## Decisions

- **The console lives in the CRM web under `/staff`**, on the agency host (`portal.`), not in the CIS admin. ADR 0006b
  decision 6 gives the staff routes their own WORKFORCE client (`crm-staff`), and the CRM web already holds the BFF,
  the sealed-cookie session and the kit. The CIS admin stays a client of `/crm/ops/v1` only.
- **A second session, not a second role in the agency session.** `lib/staffSession.ts`: cookie names
  `__Secure-aa_crm_staff_{s,r,tx}`, paths `/staff` (session) and `/staff/auth` (refresh, sign-in attempt), its own key
  `STAFF_SESSION_SECRET` and seal purposes `staff-*`. The browser never sends a staff cookie to an agency page, `/bff` or
  `/auth`, and the agency cookie (Path `/`) that the browser does send to `/staff` is never read there. `__Host-` is not
  possible with a non-root path; `__Secure-` still forbids a non-Secure write. SameSite stays Lax (the OAuth callback is
  a cross-site top-level GET, same reason as the agency session).
- **Own key, not only own purpose.** The agency key `WEB_SESSION_SECRET` is also held by the Content studio (it reads the
  agency session, AA-979 P2b). A staff cookie sealed with a separate secret cannot be opened by the studio. The config
  refuses a staff key equal to the agency key, and a staff client id equal to the agency client id.
- **Group check in the web too.** Each staff BFF line names its groups; the handler answers 403 `missing_group` before
  any upstream call when the session's groups (from the token's `cognito:groups`, kept in the sealed session) lack one.
  The API checks again (class guard + `require_group`), so the web check is defence in depth and a UI hint, never the
  authority. A WORKFORCE user with no staff group is signed out at the callback (`?reason=no_group`, the refresh token
  revoked at once).
- **BFF onto `/crm/staff/v1` only**, query parameters allow-listed per path (`days`, `fields`, `stage`/`cursor`/`limit`),
  8 KiB body cap (session starts are a few ids). No `X-AA-Tenant-Id`: the path names the agency.
- **New API read `GET /crm/staff/v1/breakglass/agencies`** (crm-ops): the break-glass picker by name (lessons: never make
  a person type a UUID). Ids, names, status and the caller's own live break-glass session; no audit event (nothing of
  the agency is read but its name, same as the AA-971 `support/agencies` list).
- **S-02 view count.** The release page is a server component; every render calls the API read (view_count + 1, one
  `ops_release_view` event). Links to it use `prefetch={false}` so a hover or viewport prefetch never counts a view.
- **Manifest download** goes through the staff BFF as JSON (`{filename, watermark, row_count, csv}`) and the browser
  saves a Blob; the file is never stored on the web server. The file name is sanitised.
- **Times** on the console are shown in UTC (`formatInstant(..., "UTC")`), like the agency banner: server and client
  render the same text and staff in different places read one clock.
- **The Dev E2E staff identity** (A10c): `e2e-crm-staff@e2e-mail.lumiguides.it.com`, groups exactly `crm-ops` +
  `crm-support`, Dev only (trigger flag + API guard). "Read-limited like other E2E users" is implemented as
  **synthetic agencies only**: `Caller.e2e_synthetic_only`; `ops_tx`, `staff_tx` and `support_tx` refuse an agency whose
  `crm.tenant.is_synthetic` is not true (403 `e2e_synthetic_only`), and the board and both agency lists skip it. It may
  still start support / break-glass on a synthetic agency, because the AA-1019 live checks need exactly that (support
  read 403 after revoke; break-glass mail and alarm). On Dev every agency is synthetic (crm-002), so the rule matters
  mostly as the second lock behind the Dev-only trigger flag.

- **Staff GETs that act are console-only (review finding B1).** Opening one release (view_count + audit), the
  manifest export (audited, shown to the agency) and every S-04 read (an access-log line) are GETs, and the staff
  cookie is SameSite=Lax, so a cross-site top-level navigation, or an `<img>` on a sibling `*.lumiguides.it.com` host
  (`it.com` is a public suffix: same site), would carry it; the write guard only checks POST. Every staff BFF call,
  every method, now needs the header `x-aa-staff-console: 1` that only the console's fetch sends (a custom header makes
  a cross-origin fetch preflight, which this server never answers) and, when the browser sends it, `Sec-Fetch-Site:
  same-origin`; else 403 `console_call_required` / `cross_site_refused` before any cookie is read. Applied to all routes,
  not a per-route flag, because every allow-listed route is called only by `staffSend`. The three pages that count or
  audit on render (one release, one agency, one trip) read `Sec-Fetch-Site`; `cross-site` / `same-site` gets an
  "Open the page" step (a same-origin link, prefetch off) instead of the read. A typed URL / bookmark (`none`) and a
  console link (`same-origin`) read at once.
- **The top bar's environment badge** names the deployment's environment (`staff.env.dev|stg|test|local`, EN + VI) and
  is absent on prod (finding B3; the prop is `environment`, not `syntheticBadge`).

## Changed (against the issue text)

- "A second key in the CRM web secret" became two keys: `staff_cognito_client_secret` and `staff_session_secret`
  (reason above). Both are written by the Infra tool `staff-web-secret`, which keeps the agency keys as they are; the
  agency `web-secret` command now keeps the staff keys too (it used to rewrite the whole JSON).
- The crm-staff URLs moved from `partner-dev.` (which answers 301 to `portal.` since AA-979) to `portal.`.
- `/healthz` reports `staff_auth_configured`, and the web post-deploy verify row requires it (a deploy without the
  staff secret keys is red, not silently without a console).

## Tradeoffs

- One web app for agencies and AA staff keeps one deploy and one kit, at the cost of two sessions on one host. The
  separation is by cookie path + key + client + API class; tests cover each direction (staff cookie on agency BFF / agency
  page, agency cookie on staff BFF / staff page).
- The E2E identity can open break-glass on synthetic agencies; that mails the synthetic owner (an E2E mailbox address)
  and raises the AA ops alarm, which is the point of the live check. It cannot touch a real agency.

## Live checks: the expected codes of the staff BFF (S262 live finding D2)

The first live-step text expected `GET /staff/bff/ops-releases` with no cookie to answer 401 `session_expired`. The
B1 guard runs before the session is read, so the codes are:

| Call to `/staff/bff/*` | Answer |
|---|---|
| no `x-aa-staff-console: 1` header, no `Sec-Fetch-Site` (curl), with or without a cookie | 403 `console_call_required` |
| a browser navigation or call with `Sec-Fetch-Site` other than `same-origin` (`cross-site`, `same-site`, `none`), header or not | 403 `cross_site_refused` |
| header `x-aa-staff-console: 1` (and `Sec-Fetch-Site: same-origin` or none sent), no staff cookie | 401 `session_expired` |
| header + a staff session whose groups lack the route's group | 403 `missing_group` |
| header + a valid staff session | the API's answer (200, or its own 4xx such as 404 `release_not_found`) |

So the no-cookie curl check is `curl -H 'x-aa-staff-console: 1' https://portal.<domain>/staff/bff/ops-releases`
-> 401 `session_expired`; without the header the same curl answers 403 `console_call_required`.

## S262 live follow-ups (lane w13)

### Decisions

- **D1, the staff member's sessions in one agency include the ended ones.** `GET
  /crm/staff/v1/agencies/{id}/session` (`app/support/sessions.py` `my_sessions`) used to return only sessions still
  marked active, so after the owner ended AA support the page found nothing and said "You have no open session in this
  agency.", and "Your sessions in this agency" was empty. It now returns the caller's own sessions in that agency, the
  live one first then the newest, at most `MY_SESSIONS_LIMIT` (10), each with `ended_at` and `end_reason`:
  `staff_ended` (status `ended`), `owner_ended` (status `revoked`, the owner ended AA support), `session_expired` (its
  own window passed) or `grant_expired` (the owner's grant window passed first). A support session counts as live only
  while its grant is active and unexpired too (same rule as `support_tx` and the owner's view), so a session whose grant
  lapsed is shown as `expired` here as well. Ids, codes and times only; still no audit event (nothing of the agency is
  read).
- **The page calls nothing else when no session is live.** `endedNoticeKey()` (`lib/staffConsole.ts`) words the reason
  of the caller's latest session when it ended within 24 hours (`ENDED_NOTICE_MS`); older than that, or no session,
  the page keeps "You have no open session in this agency." The overview is still read only with a live session, so a
  refused page writes no extra `support_read` denial.
- **Owner-ended wording is definite.** With `end_reason` known the page says "This session has ended. The agency owner
  ended AA support." rather than the refusal text's "may have ended" (that text stays for a 403 `support_session_ended`
  on a later read inside a page).
- **O2, the settings card.** `app/support/reads.py` `SETTINGS_KEYS` is the one list of the overview's settings (the
  response model, the SQL and the dict are checked against it in `tests/unit/test_support_routes.py`).
  `web/lib/staffSettings.ts` gives each key an EN and VI label and formats its value (On / Off, "2.00 USD a month",
  "36 months without trips", "30 days", Basic / Strict, Automatic / Manual, the setup steps by their onboarding names,
  "None" for an empty list). `web/tests/staffSettings.test.ts` reads `SETTINGS_KEYS` and `END_REASONS` from the API
  source, so a key added there without a label fails the web tests. A key this web does not know yet is still shown,
  in plain words, after the known ones.

### Changed

- `SessionOut` (staff router) gains `ended_at` and `end_reason` (both optional, None on start responses).
- The history line shows the end time of an ended session (not the planned expiry) and the reason label ("Ended by
  you", "Ended by the owner", "Expired", "Owner's permission expired").

### Should know

- No migration: the query uses `crm.support_session` / `crm.support_grant` columns that exist since crm-033, and the
  `support_session_recent_idx` index covers the per-agency order.
- The trip page (`/staff/support/<agency>/trips/<trip>`) still shows the API refusal of the trip read; only the agency
  page words the end reason.
