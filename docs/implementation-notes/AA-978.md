# AA-978 — CRM side of the CIS membership feed (tenant.membership.v1)

AA-Partner part of AA-978 (CRM-P1): migration crm-013 (this file's first section) and the consumer
`crm_membership_pull` (second PR). The CIS producer (CIS migration 276, `/tenant/membership/v1`) and the Infra wiring
(`cis.tenant/read` scope, `CIS_API_URL`, `M2M_CLIENT`, the idle exemption) are separate PRs in AA-CIS-App and
AA-CIS-Infra. Session S250, agent Claude Code.

## Decisions

- **Key crm-013, not crm-012.** The S250 schedule §1 gave crm-012 to AA-943; this file stacks on it (Guard 0 needs
  crm-012 registered) and its `crm.erase_subject` is the crm-012 text plus one step. crm-014 (AA-944) and crm-015
  (AA-945) must start from the crm-013 text.
- **Erasure gap (schedule §5) closed by keeping `tenant_id` and erasing with the agency.** `crm.membership_inbox`
  carries the agency id, so it is an append-only tenant table (the crm-003 template: tenant_id / created_at /
  created_by, ENABLE + FORCE RLS, one `tenant_isolation` policy TO the six CRM roles, crm_app INSERT + SELECT only),
  and the agency scope of `crm.erase_subject` deletes its rows. Dropping the column was the other option; the agency
  id is what an L1 / support question about an event starts from, and the root DM-7 row (S250 R2) already says "while
  it carries tenant_id, an agency's rows are also deleted at offboarding". A plain platform table with a `tenant_id`
  column would also have failed AA-CIS-Infra catalogue rule `a` (tenant_id table without an `app.tenant_id` policy).
- **No foreign key from the inbox to `crm.tenant`, and no row without a live agency** (review round 1). CIS reports
  every CIS tenant; most have no CRM agency. The consumer writes an inbox row only for an agency the CRM holds, active
  or locked: an event of an unknown or offboarding agency is ignored without a row, so no row outlives its agency's
  erase (no erase or purge would ever reach it). The table comments say so; the DDL is unchanged.
- **Its own append-only trigger function** `crm.membership_inbox_append_only()` (same body as crm-010's
  `crm.erasable_append_only()`): crm-010's Guard 1 refuses `erasable_append_only` on any table but consent /
  trip_stage_history / llm_call, so reusing it made a re-run of crm-010 fail (caught by `test_reapply_is_a_no_op`).
- **`crm.membership_feed_state` is a platform singleton** (no tenant column, no RLS, on the template exemption list):
  cursor, last success, last error class + time, consecutive failures (the job's backoff). crm_app SELECT + UPDATE.
- **`crm.tenant.lock_source` kept in step by a trigger**, not by every writer: leaving `locked` clears it; a lock
  that names no source is `aa_ops`. So the L1 console's lock / unlock (`app/ops/console.py`) needs no change and
  agencies locked before crm-013 (NULL) read as AA locks, which the feed never lifts.
- **Who may name a source (SQLSTATE CRM21 `lock_source_forbidden`)**: `cis_tenant` / `cis_membership` only the feed
  actor `platform:feed-tenant-membership`; any explicit source only a `platform:` actor; an unscoped session (no
  `app.actor`, not crm_app) is not restricted, as in the crm-008 guards. CRM21 is the next free code after crm-012's
  CRM20; AA-944 / AA-945 start at CRM22.
- **Consumer reason codes** (inbox `reason_code`): the contract's (`crm_role_present`, `unknown_field`,
  `missing_field`, `invalid_type`, `invalid_role`, `invalid_field`, `identity_missing`, `tenant_mismatch`,
  `membership_missing`, `status_mismatch`) and the feed's (`member_disabled`, `agency_locked_no_owner`,
  `agency_locked`, `agency_unlocked`, `already_disabled`, `already_locked`, `not_locked`, `lock_not_from_cis_tenant`,
  `no_crm_member`, `no_identity`, `unknown_agency`, `agency_offboarding`, `informational`).
- **Lock precedence** when CIS removes the last owner: an active agency or a `cis_tenant` lock becomes
  `cis_membership`; an `aa_ops` lock stays AA's (AA decides when to unlock; a recovery is still needed for an owner).

- **Review round 1 (S250):**
  - *L1 lock over a CIS lock.* `console.lock_agency` on an agency the feed locked (`cis_tenant` / `cis_membership`)
    sets `lock_source = aa_ops` and audits `tenant_lock` (field `lock_source`); before, it was a no-op and the next
    CIS `tenant.unlocked` reopened an agency AA meant to keep locked. A lock that is AA's already stays a silent no-op.
  - *Withdrawn invitations.* CIS 276 emits `membership.removed` with a null identity for an invitation removed before
    activation. The contract text (root R1, new sample `event-invitation-withdrawn-valid.json`) and
    `app/cis/contract.py` now refuse a null identity only while `active`; the feed records it ignored / `no_identity`.
  - *Malformed values.* Every enum test checks `isinstance(value, str)` first (a list is unhashable: TypeError would
    have escaped the job and blocked the feed). `_pull` turns any non-database exception into `apply_error` too.
  - *Last-owner race.* The feed takes the crm-008 key `crm.member.owner:<tenant>` before it reads the member, the
    same advisory lock a member request's guard takes when it demotes or disables an owner. Each later statement takes
    a fresh READ COMMITTED snapshot, so the owner count sees the other side's commit (integration test holds a member
    request open and checks the feed waits, then locks).
  - *One event never blocks the feed.* A refusal of SQLSTATE class `CR` (CRM guards) or `23` (integrity) is recorded
    as rejected / `apply_refused` (ERROR log) and the run goes on. Data errors (`22`) are systemic on purpose: asyncpg
    raises 22000 itself for a wrong argument type, which is a bug here, and recording it as a refusal would skip every
    removal silently. Privilege / schema / transient errors stay `apply_error` (cursor kept, backoff).
  - *Monitoring.* `/crm/health/ready` carries `membership_feed` (one word; never fails readiness, so a CIS outage
    cannot roll a deploy back) and `crm_membership_feed_stuck` is logged at ERROR from 10 consecutive failures. The
    CloudWatch metric filter + alarm on that line is an AA-CIS-Infra follow-up (lane C).
  - *Inbox rows only for agencies the CRM holds.* Unknown and offboarding agencies get no inbox row (crm-013 comments
    updated, DDL unchanged): those rows could never be erased or purged. They are ignored anyway, so losing replay
    protection for them changes nothing.
  - *Truncated bodies.* `app/cis/http.py` refuses a body shorter than its Content-Length (`incomplete_body`;
    urllib's `read(n)` returns it silently) and maps `http.client.HTTPException` to `unreachable`.
  - *Test fakes.* The console reads `status, lock_source` from the row lock now, so the scripted tenant row of
    `tests/unit/test_ops_contract.py` is a record, not a bare status (it failed with a TypeError after round 1).

## Changed (vs. the plan)

- File `013_crm_membership_feed.sql` (plan: 012) per the schedule.
- The inbox is an append-only **tenant** table, not a platform-exempt one (plan S5 put both new tables on the
  exemption list); only `membership_feed_state` is on it.
- Inbox columns: no `occurred_at` and no `received_at`: `created_at` is the receive time (append-only template
  column). The root DM-7 row (R2) says "90 days after `received_at`"; it means `created_at` (reported to the
  orchestrator for the R2 text).
- **Consumer: CIS is a deny-list, not a gate** (plan note b). Only `membership.removed` and the tenant lifecycle
  events change anything; `created` / `invited` / `activated` / `role_changed` are recorded as ignored. CRM-only
  members (no CIS row) are never touched.
- **Consumer: its own context `membership_feed_tx`** in `app/tenancy.py`, not `platform_tx` (the plan's wording).
  `platform_tx` answers 404 for an agency it does not know and refuses statuses, but the feed must record events of
  CIS tenants that have no CRM agency (most of them) and meet locked agencies. It is a `platform:` actor like
  `platform_tx` (the crm-008 guards accept it), allowed only in `app/cis/membership_feed.py` (code-rules test).
- **Consumer: HTTP on the standard library** (`app/cis/http.py`: urllib in a worker thread, no redirects, 2 MiB cap)
  instead of adding `httpx` to the runtime pins: a few calls a minute, and AA-945 plans the `httpx` runtime pin with its
  pinning test; whoever lands it first can switch this client over.
- **Consumer: a CIS failure does not fail the job.** 401 / 403 / 404 / 429 / 5xx, a transport error, a malformed page
  or a token error are recorded in `crm.membership_feed_state` (`last_error_class`, `failures`) and the run ends
  `status = error`; the next runs back off 20 s doubling to 5 min. Failed `crm.job` rows are kept forever (no archive
  bucket yet), so a CIS outage must not write one every 20 s. A database error while applying one event stops the run
  the same way (`apply_error`), keeping the cursor before that event.
- **Consumer: the owner recovery accepts the feed's lock.** `recovery.open_request` / `complete_request` now meet an
  agency locked with `lock_source = cis_membership` (any other lock is 409 `tenant_locked`, as before), and the
  completion unlocks it (audit `tenant_unlock` / `owner_recovered`). Without this the E case had no way back.
- **Not done: feed lag and `lock_source` on the L1 console read.** `crm.ops.v1` responses pass a key allow-list and
  the contract is a root file; adding keys is a contract change (a follow-up card). The feed state shows on
  `/crm/health/ready` (`membership_feed`) since review round 1; staff see a CIS lock as `locked` only.

## Tradeoffs

- **Trigger vs. explicit writes for `lock_source`.** The trigger keeps the old console code correct and makes the
  source impossible to leave stale; the price is one more trigger on `crm.tenant` and a SQLSTATE.
- **Type CHECK allows NULL only for `rejected`.** A rejected event whose `type` is not one of the eight still gets an
  inbox row (so a replay is a no-op and the reason is on record) without widening the CHECK to any string.
- **Consumer: Recurring 20 s kind vs. a due-now hook.** A Recurring kind keeps a queued-ahead row, so it must be
  exempt from the deploy gate and the DB Migrate idle check (Infra `owners.yaml`, lane C branch
  `chore/aa-978-membership-pull-exempt`). The worker schedules the next slot at its maintenance pass (every 15 ticks,
  about 30 s when idle), so the effective period is 20-35 s: inside the issue's one minute.
- **Consumer: contract checked by hand, not by a JSON Schema library.** No YAML / JSON Schema package is pinned at
  runtime; `app/cis/contract.py` encodes the closed shapes and `tests/unit/test_cis_contract.py` compares its enums and
  field lists with the vendored file and runs the root samples, so a contract change fails CI here.
- **Consumer: the vendored contract is pinned by hash** (the root repo is private, the "Vendored CIS copies" job cannot
  fetch it). The copy is the S250 R1 text (root `docs/s250-contracts`); if R1 changes before it merges, copy it again
  and update `ROOT_CONTRACT_SHA256`.

### Decisions

- **90-day inbox purge = crm-018**, a new step in `crm.lifecycle_purge_expired` (the crm-010 text + one
  `crm.erase_rows('membership_inbox', 'created_at < now() - 90 days')`), so it runs inside the existing daily
  `crm_lifecycle` run, per agency (FORCE RLS), under `app.erasing` (the inbox trigger already lets crm_owner delete
  then), dry run included, skipped under an agency legal hold like the LLM-call step (hold rule 4c / 4f). No new job
  kind, grant or table. The job records `membership_inbox_purged`; the Settings > Data and privacy rules list gains
  `membership_events` (90 days, purge, crm_lifecycle; EN + VI words in `web/lib/i18n.ts`).
- **Order (crm-016 / crm-017 from other lanes).** Guard 0 checks only what crm-018 needs (crm-013 registered, the
  inbox, its trigger function, the crm-010 functions), not crm-016 / crm-017, which touch neither. Guard 0 also
  refuses to run when the live purge function already erases a table this text does not know (a later key replaced
  it), so a lane that extends the purge before crm-018 applies is caught, not overwritten. crm-016 (on its branch)
  does not touch the purge; crm-017 did not exist when this was written.
- **crm.ops.v1 1.2** (additive minor, root branch): `TenantSummary.lock_source` (null unless locked; a locked agency
  with NULL from before crm-013 reads `aa_ops`, the trigger's reading), `membership_feed_state` (`ok` / `pending` /
  `stale` / `failing` / `unknown`, `feed_state.health_word` without the `not_configured` setting) and
  `membership_feed_lag_s` (seconds since `last_ok_at`). The feed values are platform-wide (the same on every agency):
  the S-01 page shows them where staff look at a locked agency. Read in `SUMMARY_SQL` with a `LEFT JOIN` on the
  singleton (crm_app SELECT), so no extra round trip; `test_code_rules` now allows `app/ops/console.py` to use
  `feed_state` (it calls only the pure `health_word`).
- **Members tab (portal)**: `/portal/account/members`, read only, from CIS `GET /v1/account/members` (new; no tenant read
