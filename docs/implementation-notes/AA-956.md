# AA-956 — CRM-26 Module 8 ops release

Design: root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` M8, F8.3 "Ops release" (Fix B2), F10.3, C12
step 6, S-02 (Fix B3), R33, R44 data, §3.6 retention ("trip end + 90 days, with a receipt"), §4.3 (no reader role
sees `ops_release`), §4.9 "AA ops reads". Data standards Part B §7 rows `ops_release` / `supplier_manifest_export`.

## Decisions

- **One live release per trip** (`crm.ops_release`, crm-034, partial unique on `purged_at IS NULL`). A purged row
  stays as its receipt (`deletion_receipt`, counts only), so the agency's Activity and the S-02 board can show "purged
  on X" without keeping any personal data.
- **Only a job creates a release** (`job:crm_ops_release_sync`, guard CRM45). The job runs hourly for every agency
  (due-now hook, like the stage date rule) and once per trip when nudged: Booking confirms / declines / cancels an AA
  line (`app.booking.sync` `apply` and `apply_event`), a member withdraws, the trip is cancelled (C12). A nudge row is
  ids only.
- **The document** (`app/ops_release/build.py`) is the minimal Q1 3.10 set: name (given + family when on file, else
  the display name), age band on the departure date (never the date of birth), dietary / mobility codes (only while
  the traveller's latest `health_data` consent is yes), arrival / departure flight (number, airport, local time and
  its IANA zone, R33), insurance choice of the signed waiver; per trip the dates, party size, agency name and time
  zone, and the confirmed AA lines (title, tour, Booking departure / booking ids, service dates). Never: phone,
  e-mail, emergency contact (X6 default), passport, nationality, date of birth, notes, messages, documents, money, the
  trip title (agencies write client names into it).
- **Sealed under the agency's `ops_release` DEK** (AAD = tenant, `ops_release`, `payload_enc`, row id). A refresh
  rebuilds the canonical JSON and seals again only when the text changed; `payload_version` then moves up.
- **Completeness** (the S-02 indicator): per traveller Stage 3 details on file (`app.portal.progress`), waiver signed
  (when the agency has one), both flights given. Stored as counts only.
- **T-21 alert, once per release**: incomplete and the departure within 21 days -> one urgent task
  `ops_release_incomplete` for the trip owner (anchor `ops_handoff`), `t21_alerted_at`, the audit event, and the
  structured log line `crm_ops_release_incomplete_t21` (ids and counts) that AA ops alerting reads (the API task has
  no SNS permission; same pattern as the AA-971 break-glass alarm).
- **Purge date** = trip `end_date` + 90 days, recomputed on every pass (card E: dates moved -> purge date moved).
  NULL while the return date is unknown (the trip then stays Travelling with a task, F10.1).
- **Withdraw** (C12 step 6 and the agency's own button): a member marks the live release withdrawn (AA ops lose the
  document at once: the staff read answers 404) and nudges the job, which purges a release withdrawn before departure
  at once. The trip cancel (`app.stages.cancel`) does the same, listed as a dry-run effect `ops_release_withdrawn`.
  A withdrawal because no confirmed AA line is left (`aa_lines_cancelled`) is lifted by the job when a new AA line is
  confirmed; a cancel or a member's withdrawal stays.
- **AA ops access** (`/crm/staff/v1`, WORKFORCE `crm-staff` client, group `crm-ops` only; `crm-support` -> 403):
  - `GET /ops-releases` — the S-02 board over every active or locked agency: no personal data (agency name, trip
    reference, dates, party size, completeness counts, Booking departure ids, purge countdown, view count, the
    Booking incident admin link). One `ops_release_list` event per agency listed (object ids = the trips).
  - `GET /agencies/{tenant}/trips/{trip}/ops-release` — one release document. 404 `release_not_found` unless the
    release is live (not withdrawn, not purged) **and** the trip still has a confirmed AA line now (card R: "a
    release for an unconfirmed line -> 404", even in the hour before the job withdraws it). Each view: `view_count`
    + 1 and one `ops_release_view` event in the agency's audit ("AA ops viewed trip X", actor kind `aa_ops`, actor
    `ops:<staff sub>`, the released field codes).
  - `POST /agencies/{tenant}/trips/{trip}/ops-release/manifest` — the minimal supplier manifest as CSV, the fields
    the caller picks from `name, age_band, dietary, mobility, arrival_flight, departure_flight` (default the first
    four), a watermark code printed on every row and in the header, one `crm.supplier_manifest_export` record (no
    personal data, the file itself is never stored) and one `ops_manifest_export` event. Cells that start with
    `= + - @` are prefixed with `'` (CSV formula injection).
- **New request context `ops_tx()`** (`app/tenancy.py`): `app.tenant_id`, agency active or locked (offboarding ->
  404), `app.actor` = `ops:<sub>`, audit actor kind `aa_ops`. No membership, no reader role: the crm-034 guards limit
  what this actor writes (a view count, a manifest record). Only `app/ops_release/staff.py` opens it (code rule test).
- **Fix B3**: S-02 never flags an incident. It links to the Booking staff admin `<BOOKING_ADMIN_URL>/b2b-desk`
  (tab "Departures & incidents", the "Flag incident on departure" button) with the departure ids to look for.
  `BOOKING_ADMIN_URL` is a new optional setting (https origin, no path); empty = no link, the ids still show.

## Tradeoffs

- Hourly pass + nudges instead of a trigger on `crm.booking_line`: the release needs the vault (KMS) to seal, which a
  trigger cannot do; a nudge makes a confirm reach AA ops within about a minute, the hourly pass catches anything a
  nudge missed (a Stage 3 form filled in, a flight added, dates moved).
- The job uses `system_tx` (active agencies only): a locked agency's releases keep their last version and are not
  purged while locked. The lock is short (billing / support); the purge runs on the first pass after the unlock. An
  offboarding agency's releases are erased with the agency (cascade).
- Board audit: one event per agency per board read (not per release) keeps the audit readable; the board carries no
  personal data. Each document view is its own event.
